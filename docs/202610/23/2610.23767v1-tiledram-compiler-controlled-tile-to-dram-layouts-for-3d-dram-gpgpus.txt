## Abstract 

Modern GPU compilers expose rich layout abstractions for mapping tensors to threads and on-chip resources, but compute-unit-local (CU-local) 3D DRAM architectures lack a corresponding abstraction for specifying how operand-tile data are arranged within the DRAM address space. Without such an abstraction, conventional placement under the ex-isting DRAM address mapping can subject structured tile accesses to severe row-buffer conflicts. We present TileDRAM , a compiler–runtime toolchain that introduces tile-to-DRAM layouts as a compiler-visible abstraction for DRAM placement. TileDRAM extends the GPU Linear Layout abstraction from compute-side mapping targets to DRAM placement coordinates and selects layouts per tile access signature, using recurring tile-local access behavior as the specialization unit. Since row-buffer locality depends on ordered request history, TileDRAM evaluates candidate layouts through their row-buffer behavior under fixed DRAM address mappings. Accesses under the selected layouts are realized through ordinary address arithmetic, without new address-remapping hardware or ISA support. In full-trace replay on Accel-Sim/Ramulator2 across 108 MoE FFN cases, TileDRAM reduces the request-weighted row-conflict rate from 75.7% to 15.2% and achieves a 1.77 ×

geomean speedup. Retargeting six traces to six 3D DRAM organizations yields a 2.20 × geomean speedup under the same compiler abstraction. On an RTX 3090, address trans-formation adds 0.17% geomean overhead over identity.

its nearby 3D DRAM stack through a software-managed address-space aperture served by a local memory controller. However, this high-bandwidth local path also subjects operand request streams directly to the DRAM controller. Without warp-level request coalescing and traffic attenua-tion through the on-chip caches, numerous fine-grained and potentially redundant memory requests can propagate to the DRAM subsystem, substantially amplifying contention among concurrent memory requests, and ultimately reduc-ing the effective memory bandwidth available to the appli-cation. DRAM service efficiency therefore depends on the row-buffer locality of the resulting row-access sequence. This dependence on DRAM placement reveals a miss-ing abstraction between compiler-visible tile semantics and DRAM placement: a tile-to-DRAM layout that defines how operand-tile data are arranged within the DRAM address space. Under a fixed DRAM address mapping, the tile-to-DRAM layout determines the physical address stream pre-sented to the memory controller and thereby governs the row-buffer locality of DRAM accesses (Figure 1). Across our 108 full-trace MoE FFN cases, conventional placement under the fixed DRAM address mapping yields a 75.7% request-weighted row-conflict rate: successive accesses to the same row buffer target different rows, each paying a precharge and an activation. Modern GPU software stacks offer rich tile-level abstrac-tions for compute-side layout and data movement, but pro-vide no corresponding abstraction for DRAM placement. Triton, CUTLASS, and CuTe provide tiled programming and layout abstractions [2, 31, 48], while cuTile, CuTe DSL, Tile-Lang, and Gluon expose tiles directly in their programming abstractions [5, 29, 30, 35, 50]. Linear Layouts provide a for-mal representation of distributed tensor layouts as linear maps between labeled vector spaces over F2 [55]. Across these systems, the operand tile is already an established compiler-visible unit for specifying layout and data move-ment. However, these abstractions stop at the compute side: they determine how tile data map to threads, registers, and shared memory, but not how operand-tile data are arranged within the DRAM address space. DRAM placement therefore remains outside the compiler’s tile-level layout abstraction. Prior work improves row-buffer locality by modifying the DRAM address mapping in the memory controller [19, 43, 52]. Application-specific synthesis can optimize one global mapping for a representative workload trace [43], but that mapping must therefore accommodate the heterogeneous access patterns within the trace (Section 2.3). Independently specializing these patterns at the controller side would re-quire maintaining multiple mapping contexts and selecting the appropriate context for each request [52]. Taken together, these observations yield two key insights. First, CU-local integration provides high local bandwidth, but compiler-awareness of DRAM placement is necessary to fully utilize the bandwidth. Placement should therefore become an explicit compiler-controlled decision. Second, we identify recurring tile-local access behavior as a stable unit for specializing placement. This granularity also aligns naturally with existing GPU software abstractions, where operand tiles are already compiler-visible units for layout and data movement. Guided by these insights, we propose TileDRAM , a compiler–runtime toolchain that introduces tile-to-DRAM layouts as a compiler-visible abstraction for compiler-controlled DRAM placement. TileDRAM represents this abstraction as tile-to-DRAM Linear Layouts : reusable F2-linear maps that extend the Linear Layout abstraction from compute-side resources to DRAM placement coordinates. Each layout maps logical operand-tile coordinates to DRAM placement coordinates. Although access behavior varies with operand properties and tile configurations, the same ordered tile-local access be-havior recurs across many tile instances. TileDRAM captures this with a tile access signature that combines tile configu-ration, operand properties, and the ordered tile-local access sequence. The tile-to-DRAM mapping itself is stateless, with each tile coordinate mapped without reference to access his-tory. However, the induced row-buffer behavior is stateful, because whether a request hits an open row depends on preceding requests in the ordered tile-local access sequence. TileDRAM therefore evaluates candidate layouts by simu-lating row-buffer state transitions under each signature’s ordered access, selecting the layout with the fewest row conflicts. An offline solver selects reusable layouts for each tile ac-cess signature; the compiler applies them during address generation, and the runtime supplies each tile’s placement without new address-remapping hardware or ISA support. Retargeting to different 3D DRAM organizations reselects layouts while reusing the same abstraction and compilation path. Using NVBit traces of Triton/Gluon kernels [35, 48, 49] replayed with Accel-Sim/Ramulator2 [14, 21], TileDRAM re-duces the request-weighted row-conflict rate from 75.7% to 15.2% and achieves a 1.77 × geomean kernel speedup across 108 MoE FFN cases. Across six full-trace streams retargeted to six 3D DRAM organizations, TileDRAM reduces row con-flicts by 79.2% and achieves a 2.20 × geomean speedup. On an NVIDIA GeForce RTX 3090, address transformation adds 0.17% geomean overhead over identity across the 108 mea-sured kernel configurations. Together, these results establish compiler-controlled DRAM placement as a new optimization dimension: with the DRAM address mapping left unchanged, the compiler-selected layout alone accounts for the gain. ## 2 Background and Motivation 

2.1 3D DRAM and the CU-local Architecture 

Recent 3D DRAM architectures place multi-tier DRAM struc-tures close to logic through dense vertical integration. In the CU-local organization modeled here, the vertically integrated DRAM structure is connected to a separate logic die through face-to-face Cu–Cu hybrid bonding [16, 25, 38]. The logic die can host memory controllers and near-memory compute in recent designs [16, 24, 38]. This stacked integration provides a high-bandwidth local DRAM–logic path, while a distinct package-level endpoint connects the GPU or xPU to the stack [16, 24, 38]. This separation makes the package-level endpoint the bandwidth boundary for chip-wide access. Stratum reports 19.01–30.34 TB/s of internal bandwidth across its memory tiers [38]. Exporting a stack through an HBM-style package interface instead offers roughly 0.8–1.2 TB/s per stack in HBM3/HBM3E [11, 46], making the package-level endpoint 16–38 × narrower than the modeled internal path. This gap motivates placing compute near the stack rather than ex-porting its bandwidth [16, 38]. Recent industrial inference hardware provides a concrete instance of this CU-local princi-ple. OpenAI’s Jalapeño adopts a memory-sliced architecture in which each compute core slice has a local view of its own HBM4 slice and the chip omits a global last-level cache, avoiding contention on a unified global memory subsys-tem [7]. Remote and global memory accesses use a separate general-purpose interconnect. A transparent GPU-wide LLC offers a contrasting global abstraction: it makes the stack a shared last-level cache reach-able from every CU. Requests and responses therefore tra-verse a chip-wide NoC and arbitration path. The associated routers, buffers, and links consume area and power even when the target cache line resides in that stack [12, 54]. More generally, GPU-global-memory and GPU-wide-LLC or-ganizations place package-level or chip-wide interconnects on the common path to stack-resident data. A CU-local or-ganization instead keeps common accesses within a local compute–memory domain, while retaining a separate path for remote or global communication. Motivated by this locality-oriented organization, we model the CU-local design shown in Figure 1(b), where each CU accesses its nearby 3D DRAM stack through a local memory controller, and analyze one CU–stack pair at a time. Tile-DRAM’s architectural boundary is a software-managed CU-local aperture in a dedicated device-physical address space. Requests to this aperture reach the local controller without virtual-address translation, warp-level request coalescing, or caching; all other addresses traverse the conventional memory hierarchy. The local stack remains a conventional banked, row-buffered DRAM system [23, 42].

## 4 Tile-to-DRAM Linear Layouts 

This section develops tile-to-DRAM Linear Layouts as an 

F2-linear representation of compiler-controlled DRAM place-ment. For each tile access signature, we formalize how a candidate layout and the signature’s ordered tile-local access sequence jointly determine row-buffer behavior. TileDRAM formulates layout selection as a row-locality optimization subject to the target DRAM address mapping and placement constraints. Each admitted signature yields a reusable tile-to-DRAM layout template for the target contract, used to bind logical tiles to concrete DRAM regions. 

4.1 Tile-to-DRAM Linear Layout Object 

A tile-to-DRAM Linear Layout maps each layout unit to a row-buffer domain, a row within that domain, and a within-row position. We call the hardware unit that independently holds one open row a row-buffer domain , or simply a domain; in the evaluated 3D organization, a domain is one (tier, bank) pair, but the construction needs only whatever unit the target tracks independently. Triton distributed layouts map hardware-resource co-ordinates to logical tensor coordinates; TileDRAM maps normalized tile coordinates to DRAM placement coordi-nates. ## 5 Compiler and Runtime Realization 

The target-specific tile-to-DRAM layout template developed in Section 4 is realized through the three-stage PLAN– BIND–APPLY lifecycle. PLAN selects and realizes the tem-plate. BIND spans compilation and runtime: compiler-side BIND performs template lookup, emits binding metadata, and marks the corresponding accesses for APPLY; runtime BIND uses that metadata to construct a tile descriptor for a resident tile (a concrete tile instance placed in a DRAM region). During execution, APPLY consumes that descriptor to transform each active lane’s source address; GPU exe-cution and replay use the same address transformation. In the evaluated Ampere-class realization, operand-tile loads use cp.async lowered to LDGSTS.128. Figure 6 isolates this compiler/replay address equivalence, and Appendix C shows the programmer-facing kernel entry. 

5.1 Semantic Extraction and Offline Template Construction 

Programming interface. TileDRAM does not require programmers to name DRAM banks, rows, or address-map bits. The programmer-facing annotation supplies problem, tile, execution, and operand properties, while the kernel body remains ordinary Triton/Gluon code (Appendix C); DRAM placement remains TileDRAM-managed rather than part of the kernel’s logical tile specification. 

Semantic extraction. From the tiled-kernel representa-tion, the compiler derives the tile configuration and operand properties. A recorded representative active-lane sequence supplies the ordered tile-local access sequence; together, these fields form the tile access signature. Normalization relative to the source interval (Section 4) yields the represen-tative normalized source sequence used by PLAN. For each admitted signature and target contract, PLAN synthesizes the layout and its target-specific layout realization, publish-ing one reusable template keyed by the signature.

Address lowering (APPLY). At compilation, the compiler places APPLY after the source pointer tensor is formed by address arithmetic for each admitted tile access. At execu-tion, the path uses the tile descriptor for the current resident tile to transform each active lane’s source address for its 16-byte LDGSTS.128 transfer. The transformation follows three ordered stages: Extract each source address relative to the source interval, yielding the layout-unit index and within-unit byte offset; Transform the layout unit through the de-scriptor’s target-specific layout realization; and Reconstruct 

the backend address from the transformed unit, unchanged byte offset, and region base before the copy. Per-lane in-teger and pointer operations realize this software-selected placement through ordinary address generation, requiring no new address-remapping hardware or ISA support. The formal address contract is given in Appendix A.1, and the binding metadata and address-lowering sequence appear in Appendix C. Only operand accesses with a tile descriptor are redirected to their assigned DRAM regions, while ordinary loads and stores retain the conventional memory path. 

5.3 Runtime Replay and Simulator Execution 

Simulator replay represents each dynamic tile access as an or-dered tile-local access sequence of active-lane asynchronous-copy events (LDGSTS.128) carrying source address 𝑠 𝑖 and event metadata 𝜂 𝑖 . Here, 𝜂 𝑖 denotes the event’s identity, desti-nation, dependency, and request attributes. Runtime schedul-ing may interleave ordered tile-local access sequences from resident tiles while preserving the event order within each se-quence. Each sequence carries the descriptor for its resident tile as input to the APPLY path. For each asynchronous-copy event, the simulator evalu-ates the same address transformation specified by APPLY using the descriptor for the sequence’s resident tile. It carries the resulting backend address together with the event meta-data into replay. Replay uses the descriptor’s template and placement while preserving event metadata and dependency. The production compiler lowering and simulator-side trans-former implement one common address function, checked against an independent reference evaluator. Appendix D re-ports the covered configurations, address-function families, and byte addresses. Each transformed asynchronous-copy event forms one CU-local DRAM request in the Ramulator2 replay. Ramulator2’s fixed address mapper and controller ad-vance row-buffer state and return service latency to GPGPU-Sim, which applies it to the originating asynchronous-copy dependency.

## 6 Evaluation 

6.1 Experimental Setup 

Simulation and replay protocol. We evaluate Tile-DRAM with traces collected from Triton/Gluon tiled GEMM kernels using NVBit [35, 48, 49] and replayed through Accel-Sim/Ramulator2 [14, 21] on one CU and its paired 3D DRAM stack. Each baseline–TileDRAM pair holds the logical event trace, target organization, the initial closed-row state, and refresh/precharge policy fixed while varying DRAM place-ment. Layout selection uses the ordered tile-local access sequence, whereas replay counters follow FR-FCFS service order. Before replay, we verify that the compiler lowering and simulator transformer produce the same addresses as the canonical byte-address function in Appendix A.1. The evaluation covers 108 full-trace MoE FFN cases span-ning Qwen3 [40], DeepSeek-V3 [3], Qwen3.5-35B-A3B [41], Kimi K3 [15], Hunyuan-A13B [47], and Llama 4 [22], across up/gate and down projections and eight tile shapes. The same 108 kernel configurations provide hardware-cost calibration; a separate sweep covers 36 full-trace stream–organization pairs. All reported TileDRAM layouts use the same greedy selection route (Appendix A.5). We report row-conflict rates from pooled row events and speedup as the geometric mean of per-case baseline-to-TileDRAM cycle ratios. Per-case syn-thesis time and peak resident memory measure offline layout-selection cost; address-transformation cost is measured sep-arately on RTX 3090 hardware. The primary 3D DRAM con-figuration uses 8 tiers, 16 banks, 13 row bits, and 3 column bits with RoBaTiCoCh address mapping, OpenRowPolicy, and FR-FCFS scheduling.

TileDRAM preserves row locality when retargeted across the evaluated 3D DRAM organizations. ## 7 Related Work 

3D DRAM Architectures and Accelerators. Vertical in-tegration and hybrid bonding place high-bandwidth memory close to compute, motivating architectures that exploit lo-cal memory–logic bandwidth for LLM and MoE inference. H2-LLM co-designs heterogeneous hardware and dataflow around hybrid-bonded memory [16], HybridSpec combines such memory with heterogeneous execution and speculative decoding [9], Stratum uses tiered monolithic 3D DRAM and expert placement for MoE serving [38], and Raptor demon-strates an early-silicon 3D-DRAM accelerator [24]. At indus-trial scale, OpenAI’s Jalapeño pairs compute core slices with local HBM4 slices in a memory-sliced organization [7]. Other designs explore hybrid NVM–DRAM, processing-in-memory, and near-memory parallelism [6, 8, 17]. These systems es-tablish the architectural substrate for TileDRAM; TileDRAM instead exposes how operand tiles are placed within local DRAM as a compiler-visible layout decision. 

Compute-Side Tile Layouts and Algebraic Layout Ab-stractions. Modern GPU programming systems make tiled tensor organization and layout first-class abstractions: CUT-LASS and Triton support tiled computation, while CuTe pro-vides composable tensor layouts and layout algebra [2, 31, 48]. Graphene represents multidimensional data and threads as hierarchically tiled first-class tensors, expressing opti-mized GPU computations as mappings between data and thread tiles [5]. Gluon exposes explicit tensor layouts for low-level control, and Jalapeño uses Gluon to program its spatial architecture [7, 35]. Linear Layouts provide an alge-braic representation for such compute-side layouts, mapping hardware-resource coordinates to logical tensor coordinates over F2 [55]. TileDRAM extends this abstraction to DRAM placement coordinates, making tile-to-DRAM placement a compiler-visible layout decision. 

Controller Mapping and Software-Directed DRAM Placement. Permutation-based interleaving distributes pages across DRAM structures [53]; Liu et al. [19] propose PAE, an XOR-based mapping that improves bank/channel parallelism while preserving row-buffer locality; SDAM exposes software-configurable mappings for a 3D memory controller [52]; Rotaru et al. synthesize an application-specific mapping over F2 from a representative application trace [43]; and FACIL selects a mapping for each huge page [44]. These approaches treat the controller mapping as the decision variable. A single workload-specific mapping must serve heterogeneous accesses, while specializing dif-ferent access patterns requires multiple mapping contexts and controller-side selection support. Software-directed placement instead chooses where data reside, at page [1], DNN-layer [39], region [13], or stream [18] granularity; the stream-based design also controls element order and cache placement in a distributed DRAM cache. TileDRAM keeps the controller mapping fixed and instead specializes data placement using recurring ordered tile-local access behavior. Many tile access signatures can therefore coexist under one mapping, with each placement realized through ordinary address arithmetic and without controller or ISA changes.

## 8 Conclusion and Future Work 

TileDRAM shows that DRAM placement can be an explicit compiler-controlled tile layout decision while the memory-controller address mapping remains fixed. Building on re-curring tile-local access behavior as a stable specialization unit, it extends GPU Linear Layouts to represent reusable tile-to-DRAM placements selected per tile access signature. The resulting compiler–runtime toolchain realizes these lay-outs through ordinary address arithmetic, without new ISA support or remapping hardware. Across 108 full-trace MoE FFN cases, TileDRAM reduces the request-weighted row-conflict rate from 75.7% to 15.2% and achieves a 1.77 × ge-omean speedup; retargeting across six 3D DRAM organiza-tions yields a 2.20 × geomean speedup, while address trans-formation adds 0.17% overhead on an RTX 3090. Our evaluation focuses on tiled GEMM within one CU– stack pair, with the 3D DRAM memory system evaluated through trace-driven Accel-Sim/Ramulator2 replay. Future work includes extending TileDRAM to other kernels, such as attention and convolution, coordinating layouts across multiple CU–stack pairs, and validating compiler-controlled placement on physical 3D DRAM systems.

B.2 Cost of Rotaru-Style Exhaustive Full-Trace Synthesis 

The multi-bank mapping synthesis of Rotaru et al. [43] uses a complete workload trace as its specialization unit and treats the domain mapping as an outer search variable. After fixing an outer mapping, the trace is compressed into weighted same-domain predecessor differences for the fixed-domain Problem 3 solver. Changing the outer mapping changes request-domain membership, same-domain prede-cessors, and therefore the resulting difference histogram. Trace construction is thus candidate-dependent: a separate fixed-domain Problem 3 instance must be reconstructed for every outer candidate before its inner subspace solve. For the evaluated organization, the source coordinate spans 𝑛 = 23 bits and the target requires 𝑏 = 7 tier-and-bank dimensions, corresponding to 128 row-buffer domains for a full-rank 𝑊 𝐷 . The bit-selecting family then contains 245,157 candidates for 𝑊 𝐷 , while the structured-XOR fam-ily contributes 105,417,617 raw candidates. Together they yield 105,662,774 outer candidates before rank filtering and row-space deduplication. Applying this search directly to the Llama 4 full trace with 7,864,320 active-lane copy events would perform approximately 8 .31 × 10 14 evaluations of can-didate copy events before any fixed-domain Problem 3 solve, full-map completion, or physical address-mapping evalua-tion. At a sustained aggregate rate of 10 billion evaluations of candidate copy events per second on a large multicore CPU, this construction requires approximately 23.1 hours; at 1 billion evaluations per second, it requires approximately 9.6 days. These throughput-based estimates quantify raw outer construction before Problem 3 solves, map completion, or physical address-mapping evaluation. The outer construc-tion alone therefore makes Rotaru-style exhaustive full-trace controller-map synthesis computationally prohibitive as a routine per-configuration path at the MoE FFN scale. Each new phase, problem shape, or autotuned tile configuration supplies a new workload-wide specialization target. These experiments separate synthesis tractability from mapping effectiveness. Fixed global hashes are inexpensive but produce negligible changes in the evaluated replay. Rotaru-style exhaustive full-trace synthesis explores a much larger mapping space, but its candidate-dependent outer construction is computationally prohibitive at this scale. TileDRAM instead changes the specialization granularity: it keeps the controller mapping fixed and reuses placement selected per recurring tile access signature.

Tile-access and binding metadata. For each tile access signature, the compiler records the operand-property tu-ple, comprising operand position ( lhs or rhs ), data type (dtype ), source-stride pattern ( stride ), and source layout (row-major or column-major), together with the access shape and address space needed by the lowered path, and routes the resulting source pointer tensor through APPLY. Compiler-side BIND performs template lookup and records the se-lected target-specific layout template together with the rule for deriving the tile ID from the current execution context. When that tile is placed in a DRAM region, runtime BIND obtains the referenced template from this binding metadata and combines it with the concrete tile ID, source interval, and concrete DRAM region to construct its tile descriptor for that region. Runtime BIND passes the descriptor for the active resident tile as a runtime input to APPLY. 

Address-lowering sequence. For each admitted operand access, lowering places the APPLY path after the source pointer tensor is formed by address arithmetic. At execution, the path extracts the source-relative coordinates, separates the layout-unit index from the within-unit byte offset, applies the F2-linear map, affine XOR translation, and byte place-ment, then reconstructs the backend address while retaining that offset. Shifts, masks, XOR, parity, and address arithmetic implement this sequence before the original asynchronous copy. The compiler records the canonical address-function as-sociated with each transformed tile access signature. The compiler-side template reference and runtime BIND connect the programmer-facing kernel intent, the lowered compiler realization, and the simulator descriptor recorded by the cross-path equivalence artifact.
