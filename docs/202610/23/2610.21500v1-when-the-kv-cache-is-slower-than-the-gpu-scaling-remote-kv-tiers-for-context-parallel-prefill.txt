# Abstract 

Reusing the attention KV cache across requests is a standard way to cut prefill cost in long-context LLM serving, and production systems increasingly back the per-engine cache with a remote tier shared by every engine. We study such a tier in a disaggregated deployment of GLM-5.3, an FP8 mixture-of-experts model with multi-head latent attention (MLA), on 8 ×B300 nodes running prefill context parallelism (PCP8). Enabling the remote tier (LMCache with a Valkey store) left median time-to-first-token unchanged but raised the 16k-token p99 from 3.96 s to 17.3 s. Replaying a production request stream on an isolated engine, we find that a remote hit took 0.88 s against 0.31 s to recompute the prompt, and that synchronous loading turned a hit-heavy stream into an unstable queue: p99 83.32 s with the GPUs 7% busy. Atwo-term cost model explains both: a hit pays off only if the tier delivers more than 𝐵 ∗ = 𝑠𝑅 (2.53 GB/s for this model and GPU), and a fixed per-hit engine cost ( 𝑇 0 ≈ 0.33 s) means that hits on prompts shorter than about 17k tokens cannot beat recompute at any bandwidth. Guided by the model, we (i) shard the MLA KV store across PCP ranks, with a proof that the existing minimum-over-ranks lookup returns the longest cached prefix and a load protocol that can never desynchronize collectives; (ii) partition the remote tier by rank, one server instance per rank with no coordination, which raises GET bandwidth 6 .3× to 10.76 GB/s; (iii) add asynchronous loading to the sharded store; and (iv) fix three client bugs that caused unbounded stalls. On the hit-heavy stream, with 98.5% of prompt tokens served from the remote tier, p99 falls from 83.32 s to 0.67 s. The sharded store raises prefill throughput by 14%, and by 34% together with an upstream kernel fix. All changes are submitted upstream to LMCache. 

# 1 Introduction 

For long prompts, prefill dominates time-to-first-token (TTFT): reading a 200k-token prompt takes seconds even on the newest accelerators. Serving systems therefore keep the attention key/value (KV) cache of earlier prompts and reuse it when a new prompt shares a prefix [4, 16, 19, 22, 26]. A common layout has two tiers: a fast tier in each engine’s host memory, and a larger remote tier that every engine can read and that survives restarts. The remote tier is attractive because it decouples cache capacity from engine count and lets one engine reuse what another computed. The implicit assumption behind a remote tier is that loading 

KV is cheaper than recomputing it. This paper reports a production setting in which the assumption failed, explains why with a simple model, and shows how to restore it. 

Setting. We serve GLM-5.3, a large mixture-of-experts (MoE) model with DeepSeek-style multi-head latent attention (MLA) [1, 2], in FP8 on nodes with eight NVIDIA B300 GPUs. Prefill and decode run on separate nodes [21, 27]. Each prefill node runs one vLLM [16] engine with prefill context parallelism across its eight GPUs (PCP8): the prompt is split along the sequence, the ranks exchange KV with collectives, and all eight ranks advance in lockstep. LMCache [19] stores KV in 256-token chunks in host memory (L1) and in a Valkey [24] remote store (L2). 

Problem. Turning on L2 for an enterprise SLA workload of 9k–200k-token prompts left median TTFT unchanged but inflated the tail: p99 rose from 3.96 s to 17.3 s at 16k tokens and from 6.06 s to 25.0 s at 32k. The deployment was rolled back to L1 only. 

Findings. We rebuilt one production engine’s request stream from logs, replayed it against an isolated engine with the identical image and configuration, and profiled it (§3). Three effects explain the regression: 1. A hit was slower than a miss. A 16k-token prompt took 0.31 s to recompute but 0.88 s to load from L2 (§6.1). On a B300 node the GPU prefills about 52.2k tokens/s; the L2 path delivered well under the bandwidth needed to keep up with that. 2. Synchronous loading is unstable under hit-heavy load. 

A load inside the engine step stalls all eight PCP ranks. When the arrival rate times the per-hit service time exceeds one, the engine becomes an overloaded queue: median latency grew from 3.52 s to 52.30 s within six minutes while the GPUs were 7% busy (§6.3). 3. Rare client bugs caused unbounded stalls. A lost-completion race and a missing-key read that never returns each froze an engine for 3–10 s per request, or permanently (§5.4).

# 2 Background 

MLA and its KV cache. MLA [1] projects each token’s keys and values into one low-rank latent vector shared by all attention heads. The per-token KV state is therefore small and independent of the head count. For GLM-5.3 in FP8, one 256-token LMCache chunk covering all layers is 12.4 MB, so 

𝑠 ≈ 48 .4 KB per token. Splitting attention heads across GPUs (tensor parallelism) does not shrink this state, because every head needs the full latent. 

Prefill context parallelism. PCP [13, 17, 25] splits the prompt along the sequence, so each of the 𝑊 ranks processes about 1 /𝑊 of the tokens. Ranks exchange KV with an All-Gather so that causal attention sees every earlier token; after the exchange every rank holds the whole prompt’s latent KV. In our deployment the MoE layers additionally use expert parallelism (EP8). Every forward step contains NCCL collec-tives, so the ranks run in lockstep : anything that delays one rank delays all of them. 

Prefill/decode disaggregation. Prefill is compute-bound and decode is memory-bandwidth-bound, so separating them lets each use its own parallelism and batch limits [21, 27]. A router sends each request to a prefill engine, which computes (or loads) the prompt’s KV and ships it to a decode engine over NIXL [20]; the decode engine streams the answer. 

LMCache. LMCache [19] splits KV into fixed-size chunks keyed by a hash of the token prefix, so a chunk’s key identifies everything before it. A lookup returns the longest prompt prefix whose chunks are all present; a gap means everything after it is recomputed. For MLA, LMCache stores and loads only on worker 0 ( save_only_first_rank ), since every tensor-parallel rank holds the same latent KV. The remote backend speaks the RESP protocol to a Redis-compatible server, through a native client that keeps a pool of connections per engine worker. 

Valkey. Valkey [24], like Redis, executes every command on a single main thread; I/O threads only parallelize socket reads and writes. A single instance’s command throughput is therefore bounded by one core, whatever the client count. 

# 3 Methodology 

We wanted measurements that match production without touching it. 

Trace replay. From router logs and the benchmark client’s database we rebuilt the exact request stream that one pro-duction prefill engine received in the 16k-token cell of the SLA workload: 683 requests with their original prompts and send times. A replayer sends each request at its original offset and records completion time, prompt tokens and cached tokens. Unless stated otherwise, latency is the prefill leg’s completion time, which the router logs as “prefill completed” in production. 

Isolated engine. Replays ran on a free 8 ×B300 node with the production container image, command line and environ-ment (vLLM 0.31.0, LMCache 0.5.5 with the sharded-store patch, FlashInfer 0.7.0, NCCL 2.30, CUDA 13.0). The differ-ences from production were: prefill only (no decode handoff), the LMCache controller off (so no production router could select the engine), and a private Valkey 8.1 (400 GB, LRU, 16 I/O threads) instead of the shared 1.28 TB instance. Asampler recorded engine metrics every 5 s and Valkey INFO commandstats for server-side GET counts and time. 

Hit-heavy subset. The full stream’s chunks ( ≈495 GB) ex-ceed the private Valkey, and replaying it in order under LRU evicts each prompt just before it is needed again, so hit rates stay at 10–20%. To measure the hit path we use the first 450 requests (7.35M prompt tokens, median 16,390 tokens, range 14,715–17,889), which fit. Before each arm, Valkey is flushed, primed by one replay, and the engine restarted so that L1 is empty; 98.5% of prompt tokens are then served from L2. The same 450 requests in the cold run give the recompute baseline. 

Profiling. Nsight Systems captured all eight GPU workers with CUDA and NVTX tracing, started and stopped through vLLM’s profiler hook; py-spy took stack dumps of engine processes during stalls with no GPU activity. # 5 Design 

The model points to two levers: deliver more bandwidth per prompt, and keep the engine running while loads are slow. 3Both start from where the KV lives under PCP. 

## 5.1 Sharding the MLA KV Store Across PCP Ranks 

The rank-0 bottleneck. Under tensor parallelism, storing MLA KV only from rank 0 is sound: every rank holds the same latent. Under PCP the latent is also replicated after the AllGather, but now rank 0 copies the entire prompt’s KV to host memory inside the step, while the other seven ranks wait for it at the next collective. In an Nsight trace of two concurrent ∼200k-token prompts, rank 0 wrote 19.1 GB to host memory and was 82% busy against 98% on the other ranks, which accumulated ∼1.55 s of AllGather wait each in a 9.5 s window. 

Ownership. Since every rank holds the whole prompt’s KV after the AllGather, any rank can store any chunk. Chunk 

𝑐 , the chunk that starts at token 256 𝑐 , is owned by rank 

𝑜 (𝑐 ) = 𝑐 mod 𝑊 . Each rank stores, looks up and loads only its own chunks, and its L1 is a 1 /𝑊 slice of the engine’s host-memory budget, so total memory is unchanged.

The minimum the scheduler already computes is therefore exactly the longest prefix whose chunks are all present: sharded lookup needs no new messages. We also checked the claim exhaustively for up to 10 chunks and 𝑊 ∈ { 2, 3, 4, 8}, and on random prompts of up to 800 chunks. 

Load. Loading must never let one rank skip a collective that the others enter, or the step hangs. Every rank therefore runs the same sequence regardless of what it found locally (Algo-rithm 1): fetch and stage its owned chunks, then exchange one small message per rank containing a fingerprint of the chunk list, its first failure and its chunk metadata; compute the agreed prefix from the 𝑊 messages, which are identical on every rank; and broadcast each chunk of the prefix from its owner. Local failures (eviction, a failed GET, an unhealthy engine, a staging error) are reported only through the exchange and become an agreed, shorter prefix; mismatched inputs produce different fingerprints and an agreed prefix of zero. Multi-process tests with real cache engines check these invariants under random failures and after repeated failed loads.

Remote keys. For MLA, LMCache names every remote key after worker 0 so that ranks share one copy. In shard mode every rank writes its own chunks under that worker-0 name, which keeps a chunk’s remote key independent of the rank that wrote it and preserves reuse across engines. 

## 5.2 A Rank-Partitioned Remote Tier 

Raising 𝐵 needs more server threads, hence more Valkey instances. Spreading keys over instances usually requires a cluster protocol or client-side consistent hashing. The sharded store already provides a static partition: rank 𝑟 only ever touches chunks with 𝑐 mod 𝑊 = 𝑟 , and rank 𝑟 of every engine owns the same chunk indexes. Instance 𝑟 can therefore hold ex-actly rank 𝑟 ’s chunks, with no routing logic, no traffic between instances, and no loss of cross-engine reuse. The client change is one substitution: {rank} in the remote URL becomes the worker’s rank, e.g. resp://valkey-{rank}:6379 . Each rank’s share of a 16k-token prompt ( ∼100 MB) is then fetched from its own instance in parallel with the other seven. 

## 5.3 Asynchronous Loading for the Sharded Store 

With enough bandwidth, 𝜌 ≪ 1 and synchronous loads keep up (§4). Asynchronous loading is still valuable because it removes the failure mode: a slow load delays only its own request while the engine keeps running others. LMCache’s asynchronous path assumed rank 0 performs all lookups; we extend it to shard mode without new protocol messages. Each rank prefetches only its owned chunks and passes the storage layer a custom cumulative-length vector whose 𝑘 -th entry is the start token of its 𝑘 -th owned chunk. The storage layer’s “contiguous hits” answer is then exactly 𝑎 𝑟 from the proposition, in tokens, and the scheduler’s minimum is the same prefix as in the synchronous path. A property test over 3,000 random presence patterns checks this equivalence. One edge case changed: a rank with no hits used to report 0 tokens, which is wrong under sharding (if rank 1’s first owned chunk is missing, the correct answer is 256 tokens, since chunk 0 belongs to rank 0). It now reports the first entry of the vector, which is 0 outside shard mode. 45.4 Three Client Bugs 

Bandwidth explained the steady cost; three bugs explained the worst outliers, all of which left an empty GPU timeline. 

Lost completions. The native client’s synchronous methods submitted a request and only then registered the future that would receive the result, while completions were drained on an event-loop thread. A completion drained between the two steps was dropped, and the caller blocked forever. Sharding multiplies the exposure by 𝑊 , since every lookup now goes to every rank, and one loss is permanent: afterwards every scheduler lookup waits its full 3 s timeout. One production engine logged exactly this, one timeout per routed request (16 of 16 in one minute) from one moment on, and py-spy showed every lookup thread blocked in fut.result() with nothing outstanding. The fix holds one lock across submit-and-register and across the drain. A test with a fake client that drains before submit returns fails without the fix; replays showed no measurable latency cost. 

A GET of a missing key never returns. RESP encodes a missing value as the 5-byte null bulk string $-1\r\n . The native connector read a fixed 11-byte header sized for a chunk, so on a missing key the read never completed and the connection was lost for good. Under LRU eviction a chunk can disappear between the lookup ( EXISTS ) and the load ( GET ); a synchronous load then stalls all ranks for the 10 s blocking timeout. The fix parses the header up to CRLF, treats $-1 as a per-key miss with the reply fully consumed, and makes the Python layer free unfilled buffers instead of returning them as KV. Against a real Valkey, a 4-chunk GET with one key deleted now returns [T,T,F,T] in 69 ms and the connection serves the next GET in 40 ms; before, it produced no completion within 12 s. 

Async GETs used the wrong key. The asynchronous GET did not rewrite keys to the worker-0 name used by the asyn-chronous lookup, so ranks other than 0 found their chunks and then requested keys that do not exist (which is how we found the previous bug). Upstream never exercised this, because only rank 0 performed asynchronous lookups for MLA.

# 7 Discussion 

Judge a cache tier against the prefill rate. 𝐵 ∗ = 𝑠𝑅 grows with accelerator speed: every faster GPU generation raises the bandwidth a cache tier must deliver to be worth reading. At 2.53 GB/s per prompt for one B300 node, a cache tier built from general-purpose key-value servers needs to scale out with the engine’s parallelism, as the rank partitioning does here, or move to RDMA transports [22]. Compression [18] lowers 

𝑠 , and loading and computing different parts of a prompt concurrently [14] avoids treating the choice as all-or-nothing. 7Shrink the fixed cost. Our 𝑇 0 ≈ 0.33 s means that, on this implementation, remote hits on prompts below ∼17k tokens are slower than recompute at any bandwidth. The load path broadcasts each chunk from its owner, one collective per chunk; for a 16k prompt that is 64 broadcasts plus 𝑊 

metadata exchanges. Batching chunks per owner into a single AllGather-style collective, and overlapping the exchange with the fetch, are natural next steps. A load-or-recompute policy that compares the model’s predicted load time with 𝑛 /𝑅 per request would also stop short prompts from paying 𝑇 0.

Static partitions make scale-out free. The rank partitioning works because the sharded store fixes ownership by chunk index, a property any deterministic, rank-local placement shares. Scaling to more instances than ranks (for capacity rather than bandwidth) needs a second-level hash within each rank’s partition; scaling the instance count with 𝑊 keeps the property that one rank talks to one server. 

Lockstep amplifies everything. Under PCP, any per-rank stall (a rank doing all the stores, a slow GET, a lost completion) stalls all ranks. Designs for context-parallel engines should keep per-rank work symmetric and keep any operation that can block for an unbounded time out of the step. 

# 8 Limitations 

• Single runs. Each condition was run once. The large effects (124 × at p99, 6 .3× bandwidth, the unstable queue) are far outside run-to-run variation, but differences under about 10% (for example H3 against H4) are not established. 

• Prefill only, one engine. The replays omit the KV handoff to decode and use one engine as the only Valkey client; contention from several engines on shared instances is estimated, not measured. At the workload’s ∼0.45 requests/s per engine and 0.79 GB per prompt, six engines would draw about 2 GB/s, well below 10.76 GB/s. 

• One prompt-length bucket. Latency results are for 14.7k– 17.9k-token prompts. 𝑇 0 is fitted on one point, and the prompt-length threshold it implies is a prediction that we have not yet measured directly. 

• Cache state. The hit-heavy subset was chosen to fit in the private instance; production’s full, evicting instance would produce more misses and more EXISTS -to-GET races. 

• End-to-end comparison. §6.6 compares deployments that differ in more than the cache tier. 

# 9 Related Work 

KV-cache reuse and tiering. vLLM’s PagedAttention [16] and SGLang’s RadixAttention [26] reuse prefixes within an engine. CachedAttention [4] keeps conversation KV in host memory and disk and overlaps loading with computation; Mooncake [22] builds a disaggregated KV store over RDMA for a production chatbot; MemServe [6] adds an elastic mem-ory pool for disaggregated serving; LMCache [19] provides the multi-tier cache layer we build on. These systems motivate remote tiers; we characterize when such a tier is slower than recompute on fast GPUs and show how context parallelism enables a coordination-free scale-out of the tier. 

Load versus recompute. CacheGen [18] compresses KV to cut transfer time over networks. Cake [14] computes and loads different parts of the prompt concurrently, and HCache [5] restores state from cached hidden states, trading transfer for partial recomputation. Our cost model makes the underlying trade-off explicit for a remote tier, including a fixed cost that bandwidth cannot remove; these techniques act on its 𝑠 and 𝐵 

terms. 

Disaggregation and context parallelism. DistServe [27] and Splitwise [21] separate prefill from decode; DéjàVu [23] streams KV between stages. Ring Attention [17], DeepSpeed-Ulysses [13] and context-parallel inference [25] split long sequences across devices. We show that combining MLA, context parallelism and a KV cache layer designed for tensor parallelism concentrates cache I/O on one rank, and give a sharded store whose correctness follows from the existing lookup protocol. 

# 10 Conclusion 

A remote KV tier is only useful if it beats recomputation, and on current GPUs that is a high bar: for GLM-5.3 on a B300 node, a cache hit must arrive at more than 2.53 GB/s, and a fixed engine cost puts short prompts out of reach altogether. A single key-value server could not meet the bar, and synchronous loading turned the shortfall into an unstable queue. Sharding the MLA KV store across context-parallel ranks spreads cache I/O evenly, and its static ownership lets the remote tier scale out by rank with no coordination. Together with asynchronous loading and three client fixes, this brings hit-heavy p99 from 83.32 s to 0.67 s.
