## 摘要
在无服务器大语言模型（LLM）推理场景中，云服务提供商通常在单个GPU上部署多个实例以提升资源利用率。然而，每个实例均独立维护其模型权重和运行时状态，导致重复的GPU内存占用成为主要瓶颈。内存去重是一种在CPU系统中广泛使用的消除冗余数据的技术，但将其扩展至GPU内存面临根本性挑战：有效的GPU内存去重必须避免CPU与GPU之间冗余的数据搬移，同时在缺乏原生写时复制（Copy-on-Write, COW）支持的情况下，保障共享页的写隔离性。本文提出gKSM——一种面向无服务器LLM推理的透明式GPU内存去重框架。gKSM通过三项关键技术应对上述挑战：（1）CPU-GPU协同哈希管理，将哈希计算卸载至GPU内核；（2）零拷贝模型权重去重，在模型权重传输前即消除冗余；（3）跨特权级页错误处理机制，结合轻量级内核钩子与用户空间中的CUDA虚拟内存管理（VMM）重映射。此外，gKSM还设计了稳定的页面扫描算法与复用感知的集群级放置策略。实验表明，相较于ServerlessLLM，gKSM在保持高吞吐量的同时，GPU内存使用量降低59.8%；在内存受限的工作负载下，整体吞吐量提升2.15倍，并支持五个实例并发执行；在集群级仿真中，gKSM的服务率达99.97%，显著优于SLInfer（78.2%）和ServerlessLLM（26.9%）。

## Abstract
In serverless LLM inference, cloud providers commonly locate multiple instances on a single GPU to improve utilization. However, each instance independently maintains its model weights and runtime state, making duplicate GPU memory the primary bottleneck. Memory deduplication is a widely-used technique for eliminating duplicate data in CPU systems, but extending it to GPU memory faces fundamental challenges. Effective GPU memory deduplication must avoid redundant data movement between CPU and GPU while preserving write isolation for shared pages without native copy-on-write (COW) support.   This paper presents gKSM, a transparent GPU memory deduplication framework for serverless LLM inference. gKSM addresses these challenges through CPU-GPU collaborative hash management that offloads hash computation to GPU kernels, zero-copy model weight deduplication that eliminates duplication before model weight transfer, and a cross-privilege page fault handler that combines a lightweight kernel hook and CUDA Virtual Memory Management (VMM) remapping in the user space. gKSM also designs a stable page scanning algorithm and a reuse-aware placement policy in cluster scale. Experiments show that gKSM reduces GPU memory usage by 59.8% while maintaining high throughput compared to ServerlessLLM. Under memory constrained workloads, gKSM improves aggregate throughput by 2.15X and supports five instances concurrently. In cluster level simulation, gKSM achieves a service rate of 99.97%, compared to 78.2% for SLInfer and 26.9% for ServerlessLLM.

- **CPU去重不可直接迁移**：GPU内存去重面临三大架构鸿沟：

  - **PCIe带宽浪费**：传统“先拷贝后去重”流程在权重加载阶段即产生冗余PCIe传输与瞬时OOM风险；
  - **无原生COW支持**：GPU驱动（尤其闭源用户态组件）不提供写时复制语义，无法像Linux KSM那样透明保障写隔离。

## 2. 方法论：核心思想与关键技术细节

- **核心思想**：以**驱动层拦截+CPU-GPU协同+跨特权COW**三位一体，在保持应用完全透明前提下，实现GPU页级去重与强隔离。

- **关键技术细节**：

  - **CPU–GPU协同哈希管理**（Section 3.2）  
    - GPU端：用CUDA kernel执行`xxHash3`批量哈希（吞吐167.7 GB/s，比CPU快16.9×）；  
    - CPU端：维护每GPU元数据表（虚拟地址/权限/哈希值） + 全局哈希桶表（indexed array）；  
    - 流程：GPU计算哈希 → CPU查桶得候选页 → **精确内容比对**（防哈希碰撞）→ 仅全等才合并；  
    - *设计哲学*：哈希加速靠GPU，逻辑控制靠CPU，零数据搬移。

  - **零拷贝模型权重去重**（Section 3.3）  
    - 在`cudaMemcpyHtoD()`路径插入hook；  
    - 权重仍在CPU内存时即完成：哈希 → 查全局表 → 精确比对（用pinned buffer）→ 若命中，**直接将当前虚拟地址映射至已有共享物理页句柄，跳过GPU拷贝**；  
    - 未命中则正常拷贝，并注册为新共享页；  
    - *效果*：彻底消除PCIe冗余传输与瞬时内存峰值。

  - **跨特权页错误处理（COW实现）**（Section 3.4）  
    - 共享页设为只读 → 写触发GPU页错误；  
    - **内核侧**：轻量hook UVM replayable fault path → 仅捕获故障地址/类型/PID/GPU ID → 写入字符设备队列（无拷贝、无VMM调用）；  
    - **用户侧**：专用COW handler线程批量消费队列 → 验证元数据 → 若非Owner，则用`cuMemCreate`+`cuMemcpy`创建私有副本 → `cuMemMap`重映射虚拟地址 → `cuMemSetAccess`设为可写；  
    - *所有权转移机制*：若写者本是Owner，则选同GPU另一共享者为新Owner，自身转为私有；引用计数归零时恢复写权限并清理表项。

  - **稳定页扫描算法**（Section 3.5.2）  
    - 背景线程周期扫描动态页（KV cache/激活）；  
    - “稳定性”定义：连续N次扫描哈希值不变 → 才进入候选；  
    - 扫描间隔指数退避（1s→16s），平衡响应性与开销；  
    - *目的*：避免对高频修改页过早共享，引发昂贵跨特权COW。

  - **复用感知放置策略**（Section 3.5.3）  
    - 将实例内存需求分解为`M_i = S_i（可共享） + P_i（私有）`；  
    - 对候选GPU `g`，估算复用内存 `R̂(i,g)`（基于已驻留实例的共享页重叠）；  
    - 选择增量成本最小GPU：`g* = argmin_g [S_i + P_i − R̂(i,g)]`；  
    - *关键约束*：**仅限单GPU内共享**（NVLink/网络远程访问延迟过高，公式(1)-(3)量化证明）。

## 7. 优点

- **首创性与深度**：首个在**CUDA驱动层**实现GPU内存去重的系统，直击硬件栈最深层瓶颈；
- **架构精巧**：
  - 协同哈希规避了CPU-GPU数据搬移，发挥各自优势；
  - 零拷贝设计从源头杜绝PCIe浪费与OOM风险；
  - 跨特权COW以极小内核改动（仅fault hook）+ 稳定CUDA VMM API实现强隔离，兼顾安全性与可维护性；
- **实用性强**：
  - 复用感知放置策略将系统能力转化为实际集群收益；
  - 稳定页扫描机制使动态内存（KV cache）去重变得可行且高效；
- **评估严谨**：实验设计覆盖从单卡到集群、从稳态到压力、从宏观指标到微观API开销，证据链完整。

## 8. 不足与局限

- **硬件依赖性强**：深度绑定NVIDIA CUDA VMM API（`cuMemCreate`/`cuMemMap`等），**不适用于AMD ROCm或Intel XeHPG平台**；未讨论对旧版CUDA（<12.4）兼容性。
- **安全侧信道风险**（Section 5）：
  - 虽指出2MB粒度增加探测难度，但未提供量化防护（如hash加盐、定时刷新共享页）；
  - 对KV cache去重未强制租户域隔离（仅建议operator-defined trust domain），生产环境需额外策略。
- **部署复杂度**：
  - 需修改CUDA Driver API行为（symbol interposition），可能与未来驱动更新冲突；
  - COW handler为用户态长期运行进程，引入新的故障点（如handler crash导致写挂起）。
- **适用场景限制**：
  - 严格限定**单GPU内共享**，放弃NVLink/网络共享虽合理（延迟论证充分），但也放弃了超大规模模型分片共享的可能性；
  - 对**频繁权重更新场景**（如在线微调、RLHF）未验证，稳定页扫描假设可能失效。
- **实验局限**：未在真实生产集群（而非trace仿真）中验证长周期稳定性、故障恢复能力及与K8s等编排系统的集成效果。
