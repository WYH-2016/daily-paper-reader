## 摘要
大语言模型（LLM）智能体已能在主流GPU栈上胜任内核工程师角色，但在昇腾（Ascend）NPU等新兴加速器上表现欠佳——这类加速器的编程模型在预训练数据中几乎未被覆盖。近期的NPU智能体主要通过经验弥补这一差距：它们积累自身生成与优化尝试过程中的记忆，并在后续任务中复用这些记忆。我们认为，仅依赖经验不足以支撑内核生成。智能体只能记住其曾尝试过的内容，而极少尝试其未知的机制。因此，当新算子需要不同机制时，此类记忆几乎无法提供帮助；即便对熟悉算子，随着优化推进亦会不断出现未曾见过的新场景。本文提出ASCENDEVOLVE，它将进化式内核搜索的每一步均锚定于一个大型外部知识库，该知识库构建自平台文档、工具包头文件及算子仓库。由于该语料规模远超任何上下文窗口容量，ASCENDEVOLVE对其建立索引，并为每个智能体路由至一小片任务相关的证据片段，而非整个语料库本身。所检索的知识可激发多样化的实现策略，在候选方案失败时指导修复，并约束优质候选方案的重组方式。在涵盖四个难度等级的CANN-Bench中53个Ascend C算子上的实验表明，ASCENDEVOLVE整体得分为71.39，相较Reflexion和OpenEvolve分别提升11.6%和17.2%。

## Abstract
LLM agents have become capable kernel engineers on mainstream GPU stacks, but they struggle on emerging accelerators such as Ascend NPUs, whose programming model is barely represented in pretraining data. Recent NPU agents address this gap largely through experience: they accumulate memory from their own generation and optimization trials and reuse it on later tasks. We argue that experience alone is not enough for kernel generation. An agent can only remember what it has tried, and it rarely tries a mechanism it does not know. As a result, such memory offers little help when a new operator calls for a different mechanism, and even familiar operators raise unseen situations as optimization proceeds. We present ASCENDEVOLVE, which grounds every step of an evolutionary kernel search in a large external knowledge base built from platform documentation, toolkit headers, and operator repositories. Because this corpus far exceeds any context window, ASCENDEVOLVE indexes it and routes each agent to a small, task-specific slice of evidence instead of the corpus itself. The retrieved knowledge seeds diverse implementation strategies, guides repair when a candidate fails, and constrains how strong candidates are recombined. On 53 Ascend C operators from CANN-Bench spanning four difficulty levels, ASCENDEVOLVE achieves an overall score of 71.39, improving over Reflexion and OpenEvolve by 11.6% and 17.2%.

## 1. 核心问题与整体含义（研究动机和背景）

- **根本挑战**：大语言模型（LLM）在主流GPU（如CUDA/Triton）上已展现出较强的内核生成能力，但在华为昇腾（Ascend）NPU等新兴AI加速器上性能严重受限——因其编程模型（Ascend C、CANN栈）在通用预训练语料中几乎缺失，导致LLM“零先验知识”。
- **现有方案瓶颈**：近期NPU智能体（如Reflexion、OpenEvolve）主要依赖**自我生成经验（self-generated experience）**——即通过反复试错积累历史轨迹（如成功/失败的代码、编译日志、性能数据），并在后续任务中复用。但作者指出该范式存在**经验闭包（experience closure）** 本质局限：
  - **覆盖缺口（Coverage Gap）**：无法自发探索未曾在过往轨迹中出现的新机制族（如动态索引对齐、gather类操作）；
  - **修复缺口（Repair Gap）**：优化中途首次遭遇新约束（如编译器拒绝某API签名），经验库无对应修复先例；
  - **有效性缺口（Validity Gap）**：旧版本工具链下有效的代码模式，在新CANN版本中可能失效，经验不具备跨版本泛化性。
- **核心主张**：必须将**平台原生知识（primary platform knowledge）** ——即官方文档、头文件、示例代码、厂商算子实现等——作为与经验并行、互补且不可替代的决策依据，而非仅靠“试出来”。

## 2. 方法论：核心思想与关键技术细节

- **核心思想**：提出 **ASCEND EVOLVE**，一种**知识引导的进化式内核搜索框架**，其核心是将LLM的每一步决策（生成、修复、重组）都锚定于从外部知识库中**按需检索（demand-driven retrieval）** 的、**任务专属（task-specific）** 证据切片，实现“知识塑造经验，经验反哺知识”的双向闭环。

- **关键技术细节**：
  - **分层知识库构建**：
    - **共享知识库（KG）**：静态、不可变，包含昇腾平台全量权威源——CANN官方文档、`<acl/acl.h>`等头文件、`cann-op`开源算子库、目标机器实测事实（如编译器版本、硬件规格）。每条源附带**版本元数据**与**可信度排序（authority order）**。
    - **算子专属知识库（Ko）**：动态生成，含两部分：① **任务契约（contract）**：定义算子语义、输入/输出形状/类型、参考实现、验收标准；② **检索简报（retrieval brief）**：自动链接至KG中相关API、兄弟算子、潜在冲突点（如某厂商算子与参考实现数值稳定性常数位置不一致）。
  - **三级检索机制（R）**（规避上下文窗口限制）：
    1. **路由（Route）**：基于当前具体问题（如“`DataCopy`如何处理尾部元素？”）和Ko中的简报，利用全局索引定位少量候选源文件；
    2. **过滤（Filter）**：依据目标环境元数据（如CANN v9.1）剔除版本不匹配源；对冲突信息按权威序裁决（实测 > 匹配版文档 > 其他版本）；
    3. **读取（Read）**：LLM直接阅读筛选后的源码片段及其上下文（如循环体+所需变量声明），确保可执行性。
  - **双阶段进化搜索算法**：
    - **阶段I：树状机制探索（Tree-based Exploration）**：  
      启动M条**机制正交**的实现路径（如分别以tiling、vectorization、memory movement为起点），每条路径独立进行K轮迭代：  
      `选择父节点 → 提出可证伪假设（如“改用向量化load”）→ 生成子候选 → 调试修复 → 执行评估（正确性C(x) + 延迟L(x)）→ 若F(x)提升则接受，否则回溯`。  
      *关键设计*：保留所有被拒分支作为**负向经验（negative experience）**，防止重复错误。
    - **阶段II：机制级交叉（Mechanism-level Crossover）**：  
      从阶段I各路径最优候选中选出**基线（base）** 和**供体（donor）**（其机制需针对性解决base的弱点，如慢尾部处理）；  
      利用KG验证二者**机制兼容性**（如tiling结构、dtype行为是否冲突）；  
      若兼容，则将donor的**特定机制模块**（非整段代码）移植到base中，生成后代并评估；失败组合被记录以防重试。

## 8. 不足与局限

- **性能与语义正确性分离**：在最难算子（L4）上，KB主要提升**可执行性（executability）**，但对**数值精度/语义正确性**保障有限（Conclusion中明确指出：“retrieved knowledge improves executability more than numerical correctness, but cannot guarantee semantic correctness”）。  
- **依赖高质量知识源**：方法效果高度依赖KG中文档/代码的完整性、准确性与时效性；若厂商文档存在错误或缺失，可能引入系统性偏差。  
- **计算开销未量化**：虽强调“demand-driven”降低LLM负担，但未报告实际LLM调用次数、检索延迟等关键效率指标，难以评估工业部署可行性。  
- **泛化性待验证**：实验仅限昇腾NPU，未在其他新兴加速器（如Graphcore IPU、Cerebras WSE）上验证，其知识库构建与检索策略的迁移成本未知。
