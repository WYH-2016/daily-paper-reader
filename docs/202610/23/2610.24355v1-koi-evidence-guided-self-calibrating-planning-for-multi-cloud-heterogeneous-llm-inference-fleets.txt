## Abstract 

Deploying a large language model (LLM) requires choosing the right accelerator, parallelization strategy, engine con-figuration, and replica count amongst ∼140 other variables across clouds, regions, and markets. These decisions are inter-twined, and the best cluster-wide plan continually changes as jobs contend for shared capacity on shifting workloads. We present Koi, a self-calibrating cluster planner for het-erogeneous, multi-cloud fleets. Koi uses a Recursive Lan-guage Model (RLM) hierarchy to propose hypotheses and reason over deployment while deterministic components predict serving behavior, score candidates, and control place-ment. It represents inference behavior as a fixed causal graph linking decisions (e.g., accelerator, parallelism), runtime me-diators (e.g., KV-cache pressure, communication overhead), and outcomes (e.g., latency, throughput). Each deployment strengthens or weakens scoped causal relationships, build-ing a comprehensive playbook for inference that the planner employs to guide future decisions. Job-wise configurations are composed into cluster-wide plans and evaluated against serving objectives, resource constraints, SLO risks, and cost. Across benchmarks, Koi achieves 1 .18 × greater goodput than the strongest baseline while reducing $/token by 20% in a real heterogeneous cluster. Ablations isolate the contri-bution of Koi’s architecture: a pure language model attains a composite score of 35.3, the same model equipped with Koi’s deterministic tools reaches 51.6, and the full Koi planner reaches 70.8.

A job’s realized input/output distribution drifts, and engine and library updates change throughput for the same deployment, so a configuration profiled once does not stay optimal and the planner must keep recalibrating from what it observes. These choices are also coupled across jobs that compete for the same finite accelerators, quota, and budget. Most schedulers decide one job at a time, giving each arriving job its best-ranked feasible placement, so scarce capacity goes to whichever job arrives first. This is suboptimal whenever an earlier job has a workable second choice that a later job lacks. For example, an online chat job and a batch evaluation job both prefer the cluster’s only free H100 node, but only the batch job can meet its target on A100s. If the batch job arrives first, a greedy scheduler gives it the H100, and the online job must miss its SLO or wait. Even a correct per-job ranking cannot prevent this, because avoiding it requires weighing the opportunity cost of giving a scarce device to one job rather than another, which only a cluster-wide decision can do. Existing systems address parts of this problem. Serving engines optimize request execution within a given deploy-ment [3, 14, 31]. Multi-cloud orchestrators place workloads across clouds and markets but leave the accelerator type and configuration to the user [18, 30]. Configuration op-timizers and heterogeneous serving planners choose par-allelism, placement, or GPU types for a single model or a fixed set of models [11, 15, 19, 29]. Request schedulers de-cide how requests are queued and served on existing de-ployments [10, 22], and cluster schedulers allocate resources among competing jobs [7, 12, 25], but neither chooses the deployment configuration of an inference job. No existing system jointly chooses deployment configurations and allo-cates shared capacity for all online and batch inference jobs across a heterogeneous, multi-cloud fleet, while recalibrating those choices as observed behavior drifts. Joint planning is hard for two reasons. First, the space is vast. Each job’s deployment sets about 140 configuration knobs (Appendix A), including accelerator, parallelism, en-gine, quantization, batching, and KV-cache settings, which yields at least 2 140 configurations per job. A cluster plan chooses one deployment for every job under shared capacity, so the number of candidate plans grows exponentially with the number of jobs and cannot be enumerated. Second, the planner must predict the performance of never-run deploy-ments for every job and candidate. Analytical models and profile-based simulators [2, 29] rest on fixed assumptions about memory, communication, and engine behavior that break as workloads, hardware, and software change. In our measurements, even a roofline model calibrated with mea-sured peak compute and memory bandwidth errs by up to 4.7×. Language models encode broad systems knowledge but not calibrated, deployment-specific quantities. Two fron-tier models, Claude Opus 4.8 and GPT-5.6 Sol, overpredict throughput by 4 × and 9 ×. A planner therefore cannot trust predictions unless it corrects them from observed behavior. Search-based methods instead deploy candidate configu-rations, observe their end-to-end performance, and use it to choose the next candidates. Bayesian optimization fits a sta-tistical model to these observations [5, 8], and LLM-guided evolutionary search asks a language model to propose new candidates from high-scoring ones [6, 17, 27, 28]. These meth-ods have two fundamental limitations. First, because they learn only from end-to-end outcomes, they cannot tell why a candidate performed as it did, for example whether low throughput came from pipeline bubbles or KV-cache pres-sure, and therefore which fix applies or which other jobs the evidence should inform. Second, every trial is a live de-ployment that occupies capacity other jobs need and can breach a running job’s SLO. Evolutionary search needs many such trials, and Bayesian optimization restarts for each new workload. LLM-guided evolutionary search pairs a language model with measurement only loosely, because the model sees only a scalar score and measurements never confirm or refute its reasoning. A tighter pairing is difficult because the model’s knowledge is qualitative while telemetry is numeric. Koi pairs them tightly through a fixed causal graph on which both can operate. The graph links deployment deci-sions (e.g., accelerator, parallelism), runtime mediators (e.g., KV-cache pressure, communication overhead), and serving outcomes (e.g., latency, throughput). Scoped mechanisms 

compose its edges into testable hypotheses, which a language model can propose and telemetry can support or contradict. For example, one mechanism states that raising pipeline par-allelism lowers throughput through pipeline bubbles for a given model and hardware. Each edge and mechanism car-ries a confidence and an uncertainty updated from runtime evidence, so confident relationships guide exploitation and

uncertain ones identify deployments worth testing. Koi runs no separate trials, since every deployment both serves its job and tests the relationships it exercises, and the plan score val-ues both. Bayesian optimization also updates a model after each trial, but that model maps configurations to end-to-end outcomes for a single workload. Koi instead updates its be-liefs about mechanisms, so evidence from one job informs every job within the mechanism’s scope. Koi turns this evidence into a cluster plan by alternat-ing between language-model proposals and deterministic evaluation. For each job, the language model proposes can-didate deployments from the causal graph, the cluster snap-shot, the job’s workload, and the matching mechanisms. The graph lets it focus on the decisions that affect the job’s tar-gets, so Koi evaluates a few candidates per job instead of enumerating the space. Deterministic components predict each candidate’s behavior with a profile-based performance model whose error is tracked against observed outcomes, score it against the job’s weighted objectives, and compose candidates into a cluster-wide plan. The plan score balances serving value, the value of testing uncertain relationships, SLO risk under prediction error, and reconfiguration cost, subject to shared capacity. Because candidates for all jobs compete within one plan, this score exposes the opportunity costs that per-job optimization misses. Only deployment ev-idence updates causal confidence, and the language model only proposes and cannot override measured evidence or cluster constraints. We evaluate Koi on a real 104-GPU cluster spanning three regions and on simulated 400- and 800-GPU clusters, all het-erogeneous, against nine baselines including the approaches above (three on the real cluster). Against the strongest base-line, Koi delivers 1 .18 × the goodput at 20% lower $/token on the real cluster and 45% more goodput at 31% lower $/token in the 3-hour simulation. • We develop an evidence-guided agentic planning algo-rithm around a causal DAG that links deployment deci-sions, runtime mediators, and outcomes. Our RLM [33] hierarchy proposes candidates and scoped hypothe-ses, deterministic evaluation selects the cluster plan, and telemetry updates the evidence that guides subse-quent intervals.

## 2 Background 

2.1 Where deployment planning sits 

LLM serving spans three control layers. Serving engines admit and batch requests [3, 14, 31], routers distribute re-quests among running replicas [10, 22], and a deployment controller chooses the hardware, parallelism, engine configu-ration, replica count, and placement within which those lay-ers operate. Koi composes with serving engines and routers while operating at the third layer, where it plans and con-trols deployment. The separation is operational as well as temporal. Engine and router decisions are made per request and are reversible within milliseconds, whereas a deploy-ment decision commits model weights to devices. Changing one requires loading weights, warming caches, and draining in-flight work, which bounds how many configurations a controller can try in a given period and requires damping against churn. 

2.2 What determines deployment performance 

The deployment objective is not to maximize raw throughput or GPU utilization. Rather, the controller should select the least-cost configuration that satisfies the workload’s service objectives: online workloads must meet TTFT, TPOT, and throughput targets, while batch workloads must complete by their deadlines. Operating closer to saturation can reduce cost, but it also reduces queueing headroom and can sharply degrade tail latency under bursty demand. The lowest-cost feasible configuration is workload-dependent because different workload characteristics expose different hardware bottlenecks. Input-heavy requests make prefill compute the limiting resource and first manifest as elevated TTFT. Long-context and output-heavy requests increase KV-cache residency and HBM-bandwidth pressure, which can degrade TPOT and reduce the capacity available to concur-rent requests. Arrival rate and burstiness determine the repli-cation and queueing headroom required to preserve these objectives. Consequently, a model identifier and mean re-quest rate alone are insufficient to determine the appropriate GPU type, model-parallel configuration, or replica count. Configuration choices affect end-to-end objectives indi-rectly through runtime mechanisms. For example, pipeline parallelism can reduce per-GPU memory pressure but in-troduce pipeline bubbles and stage imbalance; similarly de-graded throughput can instead arise from KV-cache pressure or interconnect contention. These mechanisms require differ-ent corrective actions. Thus, a controller must use runtime evidence to identify the binding bottleneck and select the 

> 3

least-cost feasible intervention, rather than relying on re-peated configuration trials guided only by endpoint metrics. This motivates Koi’s evidence-conditioned control loop. 

## 3 Related Work 

3.1 Deployment configuration and placement 

Per-job optimizers evaluate alternative serving configura-tions against workload and SLO objectives. AIConfigurator predicts configurations across parallelism strategies, serv-ing modes, and engine-specific settings, then ranks them by derived latency and throughput [29]. Other systems extend deployment decisions to concur-rent jobs. AlpaServe places and parallelizes multiple models to improve serving efficiency under bursty workloads [15]. Prism improves multi-model serving through demand-aware cross-model GPU-memory sharing, model placement, and request arbitration [32]. Heterogeneous serving planners optimize a single model across mixed hardware: Mélange computes a minimum-cost heterogeneous GPU allocation for a given workload and latency target [11], while Helix jointly optimizes model placement and request scheduling over heterogeneous GPUs and network links [19]. Cloud systems operate at the infrastructure layer: SkyPilot places workloads across clouds [30], while SkyServe distributes spot and on-demand replicas across regions and clouds [18]. 

3.2 Feedback-driven and causal optimization 

Measurement-driven optimizers refine decisions from ob-served outcomes. CherryPick uses Bayesian optimization to test cloud configurations and select subsequent trials from ob-served execution [5]. SCOOT applies Bayesian optimization to inference-engine parameters, using learned constraints to avoid invalid configurations while optimizing SLOs [8]. Cluster schedulers also adapt from runtime feedback: Pol-lux models how resource allocation and batch size affect training goodput [25]; Cilantro learns online resource-to-performance mappings under application-level objectives [7]; and Tiresias schedules distributed training jobs from obser-vations and prior knowledge of job duration [12]. Causal methods instead use structure to determine which interventions or relationships should generalize. Invariant causal prediction identifies predictors whose relationship with a target remains stable across environments [24], while causal Bayesian optimization selects interventions on a sup-plied causal graph to optimize a target with fewer experi-ments [1]. 

3.3 LLM-guided search 

FunSearch uses an LLM to modify a target function and an evaluator to score each candidate [27]. AlphaEvolve extends this evolutionary search to larger programs and codebases, retaining evaluated programs to guide subsequent propos-als [6]. OpenEvolve maintains a diverse set of high-scoring programs and uses them to guide subsequent mutations [28]. EvoX further co-evolves candidate solutions and the search strategy that selects and varies them, allowing the explo-ration policy itself to adapt during optimization [17]. These systems evolve executable artifacts by repeatedly proposing and scoring candidate programs.

## 5 Koi 

5.1 Overview 

Each tick, Koi executes an eight-stage closed loop that up-dates evidence from the cluster and searches for a better cluster-wide plan (Figure 3). States S0–S3 refresh the planner state by snapshotting jobs, placements, and capacity (S0), collecting per-rank telemetry (S1), comparing observations against stored predictions (S2), and updating the evidence state (S3). Planning begins at S4, where the agent proposes a cluster-wide action for each job (place, reconfigure, re-tain, or defer). Deterministic evaluation at S5 scores the pro-posal against job-specific performance, expected evidence, SLO risk, and reconfiguration cost, and validates constraints 

C1–C5 . Invalid or non-improving plans return to S4 with scores and diagnostics. Once the search budget is exhausted, Koi commits the best feasible cluster-wide plan (S6) and closes the loop (S7). This design relies on two assumptions: near-optimal proposal coverage (Assumption 5.3) and con-vergence under stationary conditions (Assumption 5.4).

5.5 Agentic Planner 

The search space for a cluster deployment is vast and coupled. Each chain sets about 140 knobs (Table 7), giving at least 2140 configurations per chain before replica counts and multi-rank ladders are considered. A plan chooses one ladder for every job, so the number of candidate plans grows exponen-tially with the number of jobs, and the choices are coupled because jobs with different workloads and SLOs compete for the same capacity. Koi therefore never enumerates this space. Budget books and backward DAG queries, described next, narrow it for each job, an LLM proposes a small set of ladders within it, and deterministic code evaluates, scores, and selects among them. A root planner receives the frozen cluster snapshot and assigns each job a budget book , a soft upper bound on which GPU types and instance pools the job may consider. Budgets can overlap in resources selected, and contention is resolved later by a capacity-constrained solver that assigns at most one ladder per job to the available GPUs. The root planner 

> 7

invokes per-job specialist sub-agents to propose candidate ladders within each job’s budget. Each specialist sub-agent receives the job’s model architecture, workload profile, cur-rent deployment, budgeted hardware, and all mechanisms whose scope matches the job. It can query the DAG backward: given a target SLO, the sub-agent traces which 𝑋 decisions affect it through which 𝑉 mediators, focusing on the deci-sions that matter (Section 5.2). This division lets the root reason about cluster-wide tradeoffs (which scarce accelera-tors to reserve, which workloads can share resources) while sub-agents focus on the configuration details of individual models. These proposals are advisory: Koi first validates each can-didate for physical feasibility, then invokes the surrogate to predict and score its performance. The resulting ladders compete for finite capacity under the joint selector, which assigns at most one ladder per job to maximize cluster-wide gain (Section 5.3) while accounting for unserved demand, improvement over active deployments, and switching cost. The root planner may inspect the result and propose addi-tional candidates, but cannot override deterministic scores, capacity checks, or constraints C1–C5 .

5.6 Implementation 

Batch and online inference jobs are executed through two different pathways. For batch jobs, large prompt files are sharded and a custom shard manager coordinates shard as-signment and completion for each worker. This ensures that every rank and chain planned by Koi make progress on the same job without conflicts. Online jobs are deployed through the Nvidia Dynamo inference deployment framework. Koi decides on the exact chain configuration and desired num-ber of maximum replicas, while Dynamo autoscales within that maximum replica bound in response to request load and desired SLAs. Per-rank telemetry from all running jobs is continuously streamed from the different worker clusters to a unified cluster state store. At each five-minute tick, Koi reads a snapshot of this store to use for the next plan. 

## 6 Evaluation 

Our evaluation asks three questions. First, how does Koi com-pare with static, classical, outcome-learning, evolutionary, and language-model planners in goodput, SLO attainment, admission, and cost (§6.2)? Second, do joint optimization, ev-idence accumulation, and health-triggered recovery operate as intended, and how do these effects change with deploy-ment scale and duration (§6.3)? Third, what do deterministic planning tools, the causal evidence graph, and cross-tick learning contribute, and how sensitive are the results to the language-model backbone (§6.4)? 

6.1 Experimental Setup Benchmarks. We evaluate Koi in one real-hardware set-ting and three simulated settings: a 3-hour deployment on a 104-GPU heterogeneous GCP cluster, 3-hour and 12-hour het-erogeneous simulations, and a 12-hour homogeneous-cluster simulation. Each setting defines a benchmark consisting of a shared resource pool and a concurrent mix of online and batch workloads. For each benchmark, Koi and each of the ten baselines independently generate the placements and configurations used to serve the same workload. Each benchmark mixes 25 online and batch workloads across ten model architectures: Llama-3.2-1B, Llama-3.3-70B, Qwen2.5-Coder-32B, Phi-4, Mixtral-8x7B, Kimi-K2-Instruct, GLM-4.5-Air, Qwen3-Next-80B, DeepSeek-V3 and Qwen3-235B-A22B-Instruct, spanning 1B to 235B parameters and including dense, mixture-of-experts, and frontier models. Online workloads distribution range from short moderation (256/8 tokens, TTFT < 100 ms) to long-context summaries (24,000/1,200 tokens, TTFT < 3s) and decode-heavy agentic tasks (1,400/4,096 tokens). Six batch jobs carry fixed dead-lines ranging from 20 to 135 minutes. Request traffic follows Poisson, constant, and gamma arrival processes parameter-ized from production profiles to each job type. The work-loads used in simulation and real cluster are summarized in Figure 7 and Table 6 in the Appendix. 

Real-Hardware Execution. Each experiment is conducted with three Google Cloud Kubernetes clusters across three dis-tinct regions: us-central1, us-east5 and europe-west2. There are 104 GPUs in total, consisting of a heterogeneous mix of H100-80GB, A100-80GB, A100-40GB, and RTXPRO6000. Due to cost constraints, non-evolutionary algorithm based baselines were omitted from real experiments. 

Simulation Setup. For the simulation environment, we used LLMServingSim 2.0 [9], a discrete event simulator (DES) as the execution environment for the simulated clusters. Un-like Koi’s internal surrogate model, LLMServingSim 2.0 does not provide point estimates per placement, but rather sim-ulates request execution and queueing semantics for all re-quests routed to a deployed configuration. After a plan is selected by Koi, LLMServingSim 2.0 executes the correspond-ing configuration and provides the realized performance observations that would otherwise come from hardware telemetry. It simulates using per-operator compute profiles across GPU, model, and tensor-parallel configurations, and an ASTRA-SIM [26] backend for collective communication. To support all model–GPU combinations in our benchmark, we augmented LLMServingSim 2.0 with layer-wise profiles for the additional LLM models and GPU types used in the evaluation.

EDF [16] applies the same placement rule but prioritizes earlier deadlines. Best Fixed uses one static hardware and parallelism configuration per job, selected offline by GPT-5.6-Sol with access to the complete workload trace; at runtime, it reuses these configurations and falls back to VRAM-based placement when the selected configuration is unavailable. 

Per-job optimizers. Prism [32] estimates memory and KV-cache pressure to place preconfigured model-parallel groups, reallocating memory at runtime but never choosing GPU type, parallelism, or replica count. To adapt Prism to cluster scheduling, we enumerate policy-compliant GPU-pool and TP/PP placement candidates using workload-derived VRAM and KV-cache demand. Prism then admits waiting jobs by assigning high-KV-demand workloads to the least-pressured feasible pool under global capacity constraints. 

Global optimizers without mechanism learning. Rolling CP-SAT [23] solves ILP at each tick over the same candidate catalog and constraints as Koi. It enumerates policy-valid placements using checked-in maximum VRAM requirements and resource-map capacity, then optimizes lexicographically for priority-weighted admission, lower estimated reserva-tion cost, and lower GPU footprint. But it never learns from outcomes. Contextual Thompson sampling [4] maintains a Bayesian linear reward model over public job and candidate-placement features, updating only from terminal deployment outcomes. Its bounded reward combines online TTFT, TPOT, and throughput attainment with weights 0 .4, 0 .4, and 0 .2, re-spectively; for batch jobs, it combines throughput attainment and deadline completion with weights 0 .4 and 0 .6. 

LLM-guided planners. GPT-only (non-agentic) receives a frozen cluster snapshot, containing the same public job, re-source, policy, and model-catalog information available to Koi, and generates a placement plan without tools or cross-tick state. Its prompt requires a complete policy-compliant ac-tion for each job, specifying feasible GPU pool and TP/PP/DP 

> 9

configuration while respecting current capacity. Agentic ad-ditionally uses a REPL and the same read-only inspection and placement-validation tools available to Koi’s agent. 

Evolutionary search. Rolling EvoX [17] evolves a deter-ministic placement function at each tick, adapting its search strategy when progress stalls. OpenEvolve [28] retains a MAP-Elites database of diverse, high-scoring placement pro-grams across ticks. In each baseline, we used the similar objective function as Koi to make it comparable. EvoX’s each reasoning round takes ≈ 30 seconds. Considering reasonable scheduling overhead, we set it to max 8 rounds or 5 minutes whatever returns first. Again, we provided the same infor-mation with both EvoX and OpenEvolve baselines that was given to Koi. For the main performance evaluation, we used the same LLM model (GPT-5.6-Luna) for the policies that uses LLM. Additionally, we did LLM-backbone sensitivity study with different LLM models for Koi. To standardize the comparison, each baseline is given the same cluster snapshots, candidate catalog, and safety checks. Differences are limited to the plan-search policy and, for Koi alone, cross-tick mechanism learning. 

Metrics. A single evaluator computes every number from per-run traces. All denominators belong to the workload (offered requests, submitted jobs, full campaign sizes, a com-mon clock 𝑇 ), so no planner can improve a metric by refusing, dropping, or narrowing work. Stochastic planners report the mean and range over at least three runs. We collapse results into an overall score with three equally weighted pillars: Quality (TTFT SLO met, TPOT SLO met, deadline met), Coverage (online admission, batch admission, batch progress), and Efficiency (goodput and cost per SLO-token, each normalized to the best in each comparison). The score is their geometric mean; no pillar compensates for another. The problem formulation uses the same instanta-neous outcome vector for online and batch jobs (Section 4). The evaluation, however, judges batch jobs by completion progress and deadline attainment, which capture finite-work completion rather than instantaneous serving quality. 

SLO met is the fraction of offered online requests meeting both TTFT and TPOT p99 targets, averaged per job so one high-volume tenant cannot dominate. Deadline met is the share of batch jobs finishing before their deadline. Admission 

is the share of submitted jobs whose ranks materialized with-out a fatal interruption. Batch progress is request-weighted completion over all submitted jobs. Goodput is SLO-honoring output tokens per second: online tokens passing both latency gates plus the projected tokens of deadline-meeting jobs. Cost per SLO-token divides the fleet capacity cost by total SLO-token output; idle GPUs count as waste, so the cheapest planner produces the most SLO output from the same sunk fleet. Planner LLM cost is reported separately. 

6.2 End-to-End Performance 

End-to-End Performance overview. Table 1 reports the end-to-end results. Over three hours, Koi achieves 2,911 goodput tok/s, 45.24% more than the strongest baseline, while reducing cost per token by 31.23%; it also improves batch progress by 26.84% and TTFT/TPOT SLO attainment by 18.89/14.72%. Over twelve hours, Koi admits 95.65% of on-line jobs and all batch jobs, improves goodput by 5.72%, and leads TTFT/TPOT attainment by 15.99/11.78%, while batch progress is 1.10 points below EvoX and cost is 0.59% higher. Thus, Koi’s gain does not come from maximizing one work-load class: it sustains more admitted work and substantially better online latency while remaining competitive on batch progress and cost. 

6.3 Design Evaluation 

Joint optimization. In the real-cluster run, a Qwen3-235B job waits at tick 18 while ten services are running. The only reclaim candidate would reduce a Phi-4 service from two TP2 RTXPRO6000 replicas to one. This would halve its modeled capacity from 1,572 to 786 tok/s, below its 834 tok/s requirement, while its observed p99 TTFT already exceeds the 500 ms target at 645 ms. A full preemption would be worse, reducing that service’s availability. The joint selector rejects the reclaim as not Pareto-better than keeping Phi-4, defers Qwen for two ticks, and admits it at tick 20 after an-other batch finishes naturally. The ten-minute delay protects an existing service from a predicted SLO regression without sacrificing Qwen’s eventual admission. 

Deployment evidence makes planning more calibrated. 

In the 12-hour simulation on heterogeneous cluster, the mean causal uncertainty ¯ 𝑈 falls from a first-quarter median of 0.0215 to 0.00053 in the final quarter, a 41 × reduction. The fraction of predictions receiving a learned residual correction rises from 2.3% to 10.8%, while their median absolute log error falls from 0.965 to 0.823. During warm-up, the regret signal raises the exploration weight from 0.49 to 2.0 by tick 23. As evidence accumulates, the median DRO radius tightens from 0.379 to 0.260, then widens again after the late workload shift since the uncertainty increases again with it. Thus, Koi becomes more confident where observations repeat while retaining the ability to increase exploration and robustness when conditions change. 

Swap. In the real cluster experiment, a Mixtral service reaches critical health at tick 15 after only one of its two A100-80GB replicas materializes and observed p99 TTFT reaches 2,299 ms against a 700 ms target. The per-job sub-agent pro-poses one physically launchable TP8 A100 rank, and the deterministic scorer assigns a 25 .44 gain over keeping the failed deployment, including a 25 .00 critical-rehabilitation credit. The joint selector commits only this swap and keeps the other active jobs unchanged. The request-level TTFT 

> 10

pass rate rises from 2.4% before recovery to 99.9% on the relaunched rank, and the job is healthy by tick 18. This exam-ple connects telemetry, candidate generation, deterministic scoring, and cluster-wide commitment in one decision. 

Learning and performance improvement. We distin-guish fleet scale from elapsed learning time using two com-parisons. Over roughly three hours, the 104-GPU real clus-ter commits 20 deployments and selects eight mechanisms, whereas the 800-GPU simulation commits 80 deployments and selects 17 mechanisms. At a larger cluster scale (800 GPUs for 12 hours vs. 104 GPUs for 3 hours), Koi gath-ered more evidence, increasing from 407 to 2,272 pieces of evidence, and ran more CUSUM tests, increasing from 18,705 to 101,420. The share of decisive mechanism tests that support their predicted mediator–outcome path rises from 1.9% to 19.1%, and ICP acceptance for the same workload-to-mediator edge rises from 11.0% to 63.3%. These runs show that more concurrent deployments activate learning sooner and that a longer horizon strengthens its evidence. 

Evidence changes both allocation and planner state. 

Figure 4 shows Koi increasing its plan-declared allocation above 90% as jobs arrive while sustaining high served-job TTFT and TPOT attainment. As observed outcomes expose prediction-band misses, Koi widens its DRO radius from 0.15 to 0.191 rather than continuing to trust an under-covering bound. In parallel, the cumulative mechanism set grows to 64 as new workload contexts arrive. 

Balance between exploitation and exploration. Fig-ure 5 shows long stable placement intervals under Koi, with changes concentrated on a subset of degraded services. EvoX and the contextual bandit instead produce dense swap se-quences across nearly every online workload, while OpenEvolve and GPT-only perform no explicit swaps and largely preserve their initial choices; OpenEvolve’s additional transitions are failure-driven relaunches. Across the complete trace, Koi is-sues 201 swaps and 2,076 keeps, compared with 1,464 swaps for EvoX and 1,928 for the bandit. The timeline therefore places Koi between two failure modes: repeatedly perturbing productive deployments and never correcting a poor initial placement.

## 7 Discussion, Limitations and future work 

Koi benefits from a larger fleet as it runs more concurrent jobs, exercising more relationships per tick and covering more scopes. Evidence accumulates faster and applies to a wider set of future jobs. Additional headroom also makes exploration affordable without putting an SLO at risk, and planner cost is charged per tick and amortized over the jobs in it. Utilization rises 24.5% between the first and last quarter of the 12-hour run, but the run is too short to reach the con-vergence conditions. New decision axes enlarge 𝑋 without changing Koi’s per-tick cost, which is bounded by the num-ber of candidates evaluated rather than by the size of the space. Expert parallelism, prefill–decode disaggregation, and engine-level tuning are therefore straightforward to admit. Each requires only that telemetry report at least one medi-ator through which its effect passes, since an axis with no measured mediator can be scored but not tested. Enumera-tive and black-box search have no such property and require more samples as the space grows. New accelerators, includ-ing AMD and TPU can then be additional environments in 𝑅 𝑡 

and need no change to the planner. Training, post-training, and fine-tuning jobs have the same three properties Koi relies on: a configuration space that can be enumerated, runtime behavior the stack already reports, and evaluations too ex-pensive to run exhaustively. Extending the planner to admit them would let one controller allocate a fleet across all of these workloads rather than inference alone. 

## 8 Conclusion 

Heterogeneous LLM inference requires more than a better predictor. A useful controller must allocate scarce devices globally, act safely under prediction error, and decide which expensive deployments should improve its future knowledge. Koi addresses these requirements by attaching falsifiable, mediator-grounded mechanisms to deployment plans; us-ing a sandboxed LLM only to propose candidate plans; and keeping scoring, validation, and side effects deterministic. Telemetry closes a calibrated slow loop, while a stateless exe-cution plane keeps fast serving and recovery independent of the planner. The result is a cluster control architecture that can improve with use without making availability depend on an agent’s correctness.

## B Baseline Implementation Details 

This section describes the non-Koi baselines that were im-plemented. It excludes Koi and its ablations. 

B.1 Common Store-to-plan contract 

Each implemented driver independently reads one frozen Store snapshot at a planning tick: the resource map and the running, waiting, paused, and finished job groups for the evaluated user. It subtracts the footprint of running jobs from the resource map before making new assignments. It then emits exactly one lifecycle action for every visible job: keep 

for running jobs, place or defer for waiting jobs, defer for paused jobs, and preempt for finished jobs. A placement is serialized as a normal Store plan and is checked against the concrete environment or pool capacity before it is recorded. CP-SAT, contextual Thompson sampling, Prism, and EvoX each locally construct their candidate set from the same kinds of public facts, rather than reading Koi state. For every waiting job, they read the model, token and SLO fields, prior-ity, and an explicit or benchmark VRAM requirement. They enumerate available resource targets and policy-permitted TP values, choose the smallest PP sufficient for the VRAM requirement with DP fixed to one, and record each candi-date’s resource keys, GPU footprint, price, model-weight estimate, and KV-demand estimate. The drivers reject can-didates that violate the configuration policy or nested en-vironment/pool capacity. This gives the four methods the same job and resource-map interface while leaving their se-lection rules independent of Koi’s predictions, mechanisms, and objective. The contextual Thompson-sampling and EvoX drivers are currently registered in the simulator CLI. The best-fit, CP-SAT, AIConfigurator, and Prism drivers are implemented and unit-tested Store adapters, but still need factory registration before they can be selected through the CLI. 

B.2 Implemented baseline policies 

Best fixed configuration. The static control uses a checked-in mapping from benchmark job identity to hardware target and TP/PP/DP configuration. For each waiting job, it resolves that mapping against the current resource map and greed-ily places the job only when the required target still has capacity. If a mapping is absent or no longer fits, the im-plementation uses a VRAM-feasible fallback; otherwise it defers the job. The fallback lets the control produce a valid Store plan when a named benchmark configuration cannot be bound to the current fleet. It must be reported as a fallback, not as a development-selected fixed configuration. 

Rolling CP-SAT.. CP-SAT receives the static candidates and capacity constraints above. It creates one Boolean vari-able for each job–candidate pair, constrains each job to at most one selected candidate, and constrains every environ-ment and pool footprint to its available capacity. The solver first maximizes priority-weighted job admission. With that value fixed, it minimizes hourly price, GPU footprint, and a stable candidate-order tie break. It uses one worker, seed zero, and a declared time limit. We use a rolling solve be-cause capacity and the waiting queue change each tick; the re-solve is necessary to make the static optimizer operate on the actual current resource map rather than an offline snapshot. 

Contextual Thompson sampling. The contextual-bandit baseline uses a Bayesian linear reward model over 11 public action features: an intercept; job priority and queue depth; average input and output lengths; SLO tightness; candidate GPU count, memory, KV-cache pressure, price, and requested capacity share. Jobs are processed in priority order. For each job, the planner samples a weight vector from its current linear-Gaussian posterior, scores the feasible candidates with that sample, and chooses the highest-scoring candidate be-fore reserving its capacity. After the simulator returns an outcome, the driver applies the corresponding rank-one pos-terior update. Online reward is the fraction of offered output tokens that meet both latency targets, minus a normalized price penalty; batch reward is zero when the deadline is missed. We use Thompson sampling rather than LinUCB, epsilon-greedy, a neural bandit, or a tree/forest bandit because the action set is discrete, the context is a small explicit feature vector, and the controller needs to act from few observations. Sampling from the posterior performs probability matching: a candidate is explored when uncertainty gives it a plausible chance of being best, instead of using a fixed random-action rate or a separately tuned UCB bonus. The implementation is deliberately a linear Thompson sampler, not Bayesian optimization and not a claim that it dominates the other bandit families on these workloads. Its default posterior-draw scale is 0.25 and its random seed is zero for reproducibility.

B.3 Real hardware configuration 

Each of the real experiments are conducted on 3 Google Kubernetes Engine (GKE) clusters, in the following regions: us-central1 (Iowa, USA), us-east5 (Ohio, USA), europe-west2 (London, UK). The 3 clusters combine to a fleet of 104 het-erogeneous GPUs, consisting of a mix of Nvidia H100-80GB, RTX PRO 6000, A100-80GB and A100-40GB. The H100s and A100s are placed in 8-GPU instances, and the RTX PRO 6000 are placed in both 8-GPU instances and 4-GPU instances.
