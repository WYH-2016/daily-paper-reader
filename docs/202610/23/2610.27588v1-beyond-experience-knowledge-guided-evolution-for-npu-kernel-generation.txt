ABSTRACT 

LLM agents have become capable kernel engineers on mainstream GPU stacks, but they struggle on emerging accelerators such as Ascend NPUs, whose programming model is barely represented in pretraining data. Recent NPU agents address this gap largely through experience: they accumulate memory from their own generation and optimization trials and reuse it on later tasks. We argue that experience alone is not enough for kernel generation. An agent can only remember what it has tried, and it rarely tries a mechanism it does not know. As a result, such memory offers little help when a new operator calls for a different mechanism, and even familiar operators raise unseen situations as optimization proceeds. We present ASCEND EVOLVE , which grounds every step of an evolutionary kernel search in a large external knowledge base built from platform documentation, toolkit headers, and operator repositories. Because this corpus far exceeds any context window, ASCEND EVOLVE indexes it and routes each agent to a small, task-specific slice of evidence instead of the corpus itself. The retrieved knowledge seeds diverse implementation strategies, guides repair when a candidate fails, and constrains how strong candidates are recombined. On 53 Ascend C operators from CANN-Bench spanning four difficulty levels, A SCEND EVOLVE achieves an overall score of 71.39, improving over Reflexion and OpenEvolve by 11.6% and 17.2%. 

1 INTRODUCTION 

Trial-and-error agents learn from the programs they actually generate and evaluate. As a result, a memory built from past trials is naturally limited by what the agent has explored: it can reuse and refine discovered mechanisms, but does not guarantee access to mechanisms that have never appeared in its search. This motivates knowledge beyond self-generated experience. Recent work has demonstrated substantial progress in LLM-based kernel generation and optimization for GPUs. On CUDA and related programming stacks, iterative workflows that combine generation with compilation, execution, and profiling feedback can progressively improve both correctness and performance (Ouyang et al., 2025; Zhang et al., 2025; Wei et al., 2025; Baronio et al., 2025). These results establish iterative execution feedback as an effective ingredient for kernel optimization on mature GPU ecosystems. The problem becomes considerably more challenging on specialized accelerator programming stacks for which general-purpose LLMs have demonstrated substantially lower capability—a difficulty well documented for domain-specific programming languages more broadly (Joel et al., 2025). On Huawei’s Ascend NPU (Liao et al., 2021), recent work reports that general-purpose LLMs achieve very low success rates on complex kernel-generation tasks without domain-specific adaptation (Cao et al., 2026). Recent systems have addressed this difficulty in part by accumulating reusable experience from previous generation and optimization trajectories. However, these systems necessarily construct their reusable evidence from trajectories that the agent has already proposed and evaluated. This suggests a complementary limitation: the usefulness of experience depends not only on how much is retained, but also on what the agent has managed to explore. We refer to this coverage constraint as experience closure : the reusable evidence in a self-generated memory is derived from trajectories the agent has actually proposed and evaluated. As a result, such memory may provide limited guidance for mechanisms that have not yet appeared in those trajectories—particularly on platforms where the model’s familiarity with the programming stack is limited to begin with. Figure 1 shows three settings where self-generated experience provides limited guidance: (i) Coverage gap. An operator may require a mechanism family that no previous trajectory has explored; since such a mechanism is rarely proposed, it is also unlikely to be recorded. (ii) Repair gap. A familiar operator may encounter, midway through optimization, a constraint that has not appeared before—compiler diagnostics often identify the violated constraint without directly providing a valid alternative implementation. (iii) Validity gap. Experience collected under one software or hardware configuration may not transfer unchanged to another. Self-generated experience is not the only source of implementation evidence. Accelerator ecosystems expose additional information through programming guides, API definitions, installed headers, reference implementations, and vendor-maintained operator libraries (NVIDIA Corporation, 2017; Zhao et al., 2021). These sources can provide mechanism and constraint information before the agent has encountered the corresponding trajectory itself. We therefore view primary platform knowledge and execution experience as complementary: platform knowledge can broaden the set of mechanisms the agent considers, while execution experience provides empirical evidence about which candidates are correct and efficient on the target device (Wen et al., 2026). Our goal is not to replace trial-and-error with retrieval, but to inform it. We present A SCEND EVOLVE , a system that grounds every stage of an evolutionary kernel search in primary platform sources. The design follows three principles: 

① Hierarchical and version-aware. Platform information is organized hierarchically and with version awareness: a shared, versioned corpus of documentation, installed headers, and vendor operator libraries is distilled into per-operator evidence before search begins, avoiding repeated processing of a large heterogeneous corpus. 

② Demand-driven retrieval. Rather than placing the corpus in context, A SCEND EVOLVE routes each concrete implementation or optimization question to a small set of relevant sources. 2③ Bidirectional interaction. Retrieved platform evidence and execution experience interact bidi-rectionally: retrieved mechanisms seed candidate implementations, each trial records an empirical verdict on the knowledge it was grounded in, and outcomes influence subsequent retrieval. Because retrieved evidence may suggest multiple plausible implementation mechanisms rather than a single canonical solution, A SCEND EVOLVE maintains several mechanism-distinct implementation lines and progressively selects and recombines promising design choices through evolutionary search. On 53 Ascend C operators spanning four difficulty levels, A SCEND EVOLVE achieves an overall score of 71.39 , improving over Reflexion (Shinn et al., 2023) and OpenEvolve (Sharma, 2025) by 11.6% 

and 17.2% , respectively, with the largest gains on the operator categories where prior agents have the lowest correctness coverage. On L4 operators, A SCEND EVOLVE reaches 35.0% correctness coverage compared with 4.38% for Reflexion and 1.25% for OpenEvolve. Removing the knowledge base nearly halves the L3 score, showing how platform knowledge helps generate correct kernels. Our contributions are as follows: 

① Experience closure. We identify experience closure—a coverage limitation of experience-driven kernel agents on platforms outside the model’s familiarity—and characterize three settings where it is most pronounced. 

② Method. We propose A SCEND EVOLVE , which couples primary platform knowledge with procedural experience through hierarchical, demand-driven retrieval and bidirectional feedback within an evolutionary search that maintains mechanism-diverse implementation lines. 

③ Evaluation. We evaluate on 53 Ascend C operators from CANN-Bench (Gao et al., 2026) and show that knowledge grounding yields substantial gains, particularly on hard operators where experience-only methods have very low correctness coverage. We isolate the contribution of the knowledge base through ablation. 

2 PROBLEM FORMULATION 

Notation. Let o denote an operator specified by an executable reference implementation and a set of test cases T = {(xi, yi)}Ni=1 , where each (xi, yi) is an input–output pair. A candidate kernel x is a compilable Ascend C program that implements o. We write C(x) ∈ [0 , 1] for the fraction of test cases that x passes under a fixed numerical-tolerance criterion, and L(x) for the wall-clock latency of x measured on the target device under a fixed profiling protocol. KG is a shared, static knowledge base of platform documentation, vendor libraries and machine-observed facts. Ko is a per-operator knowledge base that fixes the task contract and links it to KG. E is a dynamic experience store that accumulates trial records during search. R(q | K o, KG, E) is a retrieval function that, given a concrete question q, returns a small evidence pack C from the knowledge bases, filtered by experience.

Figure 2 gives an overview. 3.2 KNOWLEDGE BASE CONSTRUCTION 

Writing a kernel requires answers to three questions: what the operator must compute, what the platform permits, and how experts implement similar operators on it. The first is specific to each task. The other two are shared across tasks. We organize knowledge along this line. 

Shared knowledge base. KG holds platform knowledge and is built from primary sources, not from hand-written summaries. It contains the official programming guide, API reference and compilable examples; the vendor’s open-source operator libraries, which expose production implementations across operator families; and facts recorded from the target machine, such as installed headers and the compiler in use. Each source d ∈ K G carries metadata m(d) that records its toolkit version, hardware scope and trust level; this metadata induces an authority order ≻ used during retrieval (§3.3). KG is immutable during search. Appendix A lists the sources and their statistics. 

Per-operator knowledge base. Ko fixes the task and tells the agent where to look. It has two parts. The contract freezes the operator semantics, the executable reference, the shape and dtype inventory, the target environment and the acceptance criteria; it is the sole authority on what the kernel must compute. The retrieval brief links the operator to KG: it names the operator family, the closest sibling implementations and the relevant API entries, and it records any disagreement found between these sources and the contract. Ko is produced fully automatically by a preparation pass that runs once per operator before search begins, with no human editing, and it stores references into KG,never copies. In one of our tasks, for example, the pass found that a closely related vendor operator places a numerical-stability constant differently from the executable reference. The brief records this mismatch, so later agents borrow the vendor’s tiling without its arithmetic. 43.3 RETRIEVAL FROM A LARGE KNOWLEDGE BASE 

KG exceeds the context window by orders of magnitude, and most of it is irrelevant to any single decision. Two properties of kernel code make standard dense retrieval (Lewis et al., 2021) a poor fit. Queries are frequently exact symbols, and a nearly identical passage from a mismatched toolkit version is actively harmful, since it leads to code that looks right and does not compile. We therefore design R as a hierarchical, demand-driven procedure with three steps. 

① Route. Retrieval is triggered by one concrete question qt, such as how a given API handles tail elements, and never by the task as a whole. The retrieval brief in Ko, backed by a global index over 

KG, maps qt to a short list of candidate sources. This step reduces the search space from the whole corpus to a handful of files. 

② Filter. Candidates are checked against the target environment using m(d). Sources of a mismatched version are either dropped or kept as explicitly labeled leads. When two candidates disagree, the authority order ≻ breaks the tie: facts observed on the target machine outrank official sources of the matching version, which outrank other versions and informal material. The disagreement itself is retained in the pack so that the agent is aware of it. 

③ Read. The agent reads the surviving sources directly, locating the relevant region by exact symbol or path. Implementation patterns are returned with their surrounding code, because a tiling loop is meaningless without the declarations it relies on. If a question remains unresolved after these steps, the scope widens one level along the index. Each item in Ct keeps its source identity, so that decisions in the final kernel are traceable to evidence. Appendix B gives the full procedure and an example pack. 3.4 INTERACTION BETWEEN KNOWLEDGE AND EXPERIENCE 

Knowledge and experience answer different questions. Knowledge states what is possible and legal; experience states what worked, on this operator and this device. Neither is sufficient alone. Knowledge without experience cannot say which of several legal mechanisms is fastest, and experience without knowledge is confined to the mechanisms the LLM already knows. A SCEND EVOLVE couples the two in both directions. 

Knowledge shapes experience. Every trial starts from a hypothesis ht that is grounded in an evidence pack, and the record written after evaluation keeps this link:

It is an empirical verdict on a piece of knowledge in a specific context, such as “the vectorized path from a sibling operator is valid here and reduces latency on large shapes” or “this API is documented but rejected by the installed compiler.” Because trials are seeded by retrieved mechanisms, the experience the agent accumulates covers regions of the design space that it would not have reached from its prior. 

Experience directs retrieval. The retrieval function in Eq. 2 is conditioned on E<t : the outcome of the last trial determines the next question (a compilation error routes to headers, a numerical mismatch to the reference and dtype constraints, a regression to profiles); evidence refuted for this operator is excluded from later packs; and when accumulated failures show that the current evidence is insufficient, retrieval widens its scope. In this way experience handles situations that arise only during optimization and that no static brief could anticipate. When knowledge and measurement disagree, the on-device result overrides documentation for the task at hand; the verdict is written to the task-local experience, never to KG, keeping platform facts free of candidate-specific outcomes. 3.5 KNOWLEDGE -G ROUNDED EVOLUTIONARY SEARCH

Stage I: tree exploration. The planner first proposes M implementation lines that differ in mecha-nism, for example in tiling scheme, vectorization strategy or dtype-specialized path. Diversity comes from the different mechanisms found in the retrieved evidence, not from prompt perturbation. Each line then runs for K iterations. In one iteration, following the role decomposition common to iterative code agents (Madaan et al., 2023; Shinn et al., 2023), a planner selects an accepted parent and states one falsifiable hypothesis with its expected effect; a coder realizes it as a child candidate; a debugger applies bounded repairs that preserve the hypothesis; and an evaluator runs the build, correctness and latency gates in order. If the child improves F , it becomes the next parent. Otherwise the line backtracks to an earlier accepted node and the planner forms a different hypothesis. The history of a line is therefore a tree. Rejected branches are kept as negative experience (Andrychowicz et al., 2017), which prevents a harmful change from contaminating later candidates and records which assumptions are already falsified. 

Stage II: mechanism-level crossover. Stage I returns the best correct candidate of every line together with a summary of its mechanism, its per-case latency and its known weaknesses. Stage II treats these candidates as a population. The best candidate under F serves as the base, and a donor is selected only if its mechanism addresses a specific weakness of the base, such as a slow shape regime or an inefficient tail path. Here the two information sources play complementary roles again: experience identifies which mechanism wins in which regime, and the knowledge base verifies 

whether the two mechanisms can coexist, in terms of tiling structure, dtype behavior and platform constraints. Crossover transplants the donor mechanism into the base instead of concatenating implementations. An offspring that improves F becomes the new base, and a failed combination is recorded so that the pairing is not tried again. The search ends when the budget B is spent or no compatible hypothesis remains, and the finalists are re-measured under the same protocol before the best kernel is returned.

5 RELATED WORK 

LLM-based kernel generation. LLM-based kernel generation has progressed rapidly on CUDA and Triton. K ERNEL BENCH (Ouyang et al., 2025) established a systematic benchmark for functional correctness and performance, while subsequent work explored multi-agent refinement (Zhang et al., 2025; Wei et al., 2025), reinforcement learning with execution feedback (Baronio et al., 2025; Li et al., 2025; Woo et al., 2025; Zhu et al., 2025), and evolutionary search (Novikov et al., 2025; Liao et al., 2025). Kernel generation is more challenging on specialized accelerator stacks such as Ascend C, where general-purpose LLMs show limited out-of-the-box capability (Cao et al., 2026). Recent work addresses this gap through domain adaptation (Cao et al., 2026), constrained intermediate representations (Wen et al., 2025), external knowledge augmentation (Wen et al., 2026; Qiu et al., 2026), and reusable experience accumulated from previous search trajectories (Zheng et al., 2026; Wu et al., 2026). Our work focuses on the complementarity between the latter two directions. 

Test-time search and experience for code agents. Test-time scaling improves agent performance through additional refinement, search, memory, or population-based exploration (Madaan et al., 2023; Shinn et al., 2023; Yao et al., 2023; Wang et al., 2023; Novikov et al., 2025). For kernel generation, compilation and execution provide strong verification signals, motivating iterative and evolutionary search guided by previous outcomes (Liao et al., 2025; Zhang et al., 2026; Zheng et al., 2026). However, increasing the number of trials does not necessarily increase the diversity of mechanisms explored when new candidates are generated primarily from previously discovered trajectories. Our method complements experience-driven search with retrieved platform knowledge, using external evidence to seed mechanism-diverse implementation lines and execution feedback to evolve them. Appendix C relates our setting to automated kernel optimization before LLMs and to retrieval-augmented generation for code. 

6 CONCLUSION AND LIMITATIONS 

ASCEND EVOLVE combines trial experience with hierarchical, demand-driven platform knowledge for evolutionary kernel search. On 53 Ascend C operators, it improves over Reflexion and OpenEvolve by 11.6% and 17.2%; ablations show that knowledge expands both the pool of candidates eligible for optimization and the diversity of correct mechanisms.

A KNOWLEDGE BASE CONSTRUCTION DETAILS 

Our knowledge base separates reusable platform knowledge from operator-specific context. The shared knowledge base KG contains information reusable across operators, while the per-operator knowledge base Ko specifies the target task and identifies the most relevant evidence in KG.

Shared knowledge base. KG contains 236 versioned sources drawn from four main categories (Table 7). These sources provide complementary information about platform APIs, implementa-tion mechanisms, target-specific constraints and operator semantics. Each source is associated with its toolkit version and hardware scope. Version-mismatched sources can still provide useful implementation patterns, but are treated as leads rather than authoritative platform facts. 

Authority and version consistency. We separate semantic authority from platform authority. The executable reference determines what the operator must compute, while the installed toolkit and compiler determine which platform mechanisms are valid on the target system. Matching official sources are used next, while sources from other toolkit versions are treated as lower-priority implementation leads. This allows the agent to reuse useful implementation structure without inheriting incompatible APIs or task semantics. 

Per-operator knowledge. Before search, an automatic preparation step constructs an operator-specific context Ko. It contains a task contract , describing the operator semantics, input regimes, target environment and evaluation requirements, and a retrieval brief , which identifies relevant APIs, related implementations and known version or semantic conflicts in KG. The preparation step requires no manual annotation and does not modify candidate kernels. This two-level organization keeps platform knowledge reusable while exposing only a small, task-relevant subset. 

B RETRIEVAL DETAILS 

Retrieval is question-driven rather than operator-wide. At each search step, the agent formulates a concrete implementation question, such as whether an API supports a particular dtype or how a related operator handles a boundary condition. Retrieval then proceeds in three stages. 

Route. The operator-specific retrieval brief maps the current question to a small set of relevant platform sources, related implementations and API entries. 

Filter. Retrieved evidence is checked against the target toolkit and hardware. Version-mismatched sources may be retained as leads, but cannot override facts observed on the target. 

Read. The agent reads the relevant source region directly, together with the local context required to interpret the implementation pattern. If needed, retrieval checks related sources. The resulting evidence pack therefore contains a small set of source-grounded facts and implemen-tation patterns relevant to the current decision, rather than a generic collection of documents that mention the operator. 

Example. For apply adam w , retrieval identifies a closely related vendor implementation whose update rule differs from the executable reference in the placement of ε. The reference is treated as the authority for operator semantics, while the vendor implementation remains useful for its tiling and vectorization structure. The agent can therefore reuse the implementation mechanism 13 without inheriting the semantic mismatch. This example illustrates why source identity and authority are preserved during retrieval: the agent borrows implementation structure from one source while adopting the arithmetic of another. 

C MORE RELATED WORK 

Automated kernel optimization before LLMs. Generating fast kernels without a human expert is a long-standing goal. Scheduling languages separate what a kernel computes from how it is executed, and search over the resulting schedule space, guided by auto-scheduling and learned cost models, has produced strong tensor programs (Ragan-Kelley et al., 2013; Chen et al., 2018; Zheng et al., 2020; 2021; Zhai et al., 2023). Polyhedral compilers instead derive loop transformations analytically from a dependence model (Bondhugula et al., 2008; Verdoolaege et al., 2013; Baghdadi et al., 2019), an approach that has also been carried to neural processing units (Zhao et al., 2021). These systems search within a space of transformations that the compiler fixes in advance, and the platform constraints that make a transformation legal are encoded in the compiler itself—an encoding that takes considerable expert effort to build for each new backend. Our setting is the one where that encoding does not yet exist: the difficulty is less to tune a schedule that is already known to be valid than to find a valid implementation mechanism at all, and the space of candidate mechanisms is not enumerated in advance. A SCEND EVOLVE therefore recovers mechanisms and constraints from primary platform sources at search time, rather than from a transformation space defined beforehand. 

Retrieval-augmented generation for code. Retrieval-augmented generation conditions a model on evidence fetched at inference time instead of relying on parametric memory alone (Lewis et al., 2021), and the idea transfers naturally to code: retrieving related snippets from a code base improves both generation and completion (Parvez et al., 2021; Lu et al., 2022). Two refinements are especially relevant here. Repository-level methods retrieve context scattered across files and iterate between retrieval and generation, using what has been written so far to drive the next query (Zhang et al., 2023). Documentation-level methods retrieve API descriptions rather than code, which lets a model use libraries and functions it never saw during training (Zhou et al., 2023). The second is the closer analogue to our setting: public code corpora are dominated by mainstream languages (Kocetkov et al., 2022), so a model’s parametric knowledge of an emerging programming model is thin, while the corresponding documentation, headers and vendor implementations do exist and can be consulted. Recent agents for Ascend accordingly inject external knowledge into generation (Wen et al., 2026; Qiu et al., 2026). Our use of retrieval departs from these formulations in three respects, each of which shapes the design in §3.3. Queries are frequently exact symbols, so lexical identity matters more than embedding similarity; a passage drawn from a mismatched toolkit version is actively harmful rather than merely unhelpful, so evidence has to be filtered against the target environment before it is used; and retrieval is driven not by the partial program, as in repository-level completion, but by an explicit search-time question informed by failed trials.
