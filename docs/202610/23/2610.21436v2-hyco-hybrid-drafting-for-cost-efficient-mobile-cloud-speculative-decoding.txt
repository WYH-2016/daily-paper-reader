# HYCO: Hybrid Drafting for Cost-Efficient Mobile–Cloud Speculative Decoding 

Hanbin Bae Heejin Choi Joohyung Lee Byoung Jin Choi Sangjun Park Hoon-Young Cho 

AI Solution Team, Samsung Research, Seoul, Republic of Korea 

{bhb0722.bae,hee_jin.choi,jooooh.lee,bj87.choi,sj0.park,h.y.cho}@samsung.com 

Abstract 

Device–cloud speculative decoding reduces server computation, but growing a deep draft tree with a small language model (SLM) re-quires repeated passes on a mobile neural pro-cessing unit (NPU). We present H YCO, which runs the server model’s native multi-token pre-diction (MTP) head on the device to build a deep chain and uses one SLM pass to add alter-native branches. The server returns the hidden state, input embedding, and key–value entries needed by the head instead of executing its se-quential steps. Quantization, a restricted vocab-ulary, and a 1K-token window fit both drafters to the NPU. An ϵ-threshold rule additionally relaxes exact preservation of the verifier’s sam-pling distribution. In single-client runs with a Galaxy S26 Ultra over LTE/5G, H YCO reduces server GPU time per output token relative to server-side MTP self-speculation by 38.6% on Spec-Bench and 29.2% on 32K-token summa-rization. With the same acceptance rule, three runs of each system on Spec-Bench show 9.0 percentage points more saving and 1.9× deliv-ery speed than an SLM-only drafter. H YCO

differs from Cloud+MTP by +0 .2 judge-score points (paired 95% CI: −0.9 to +1 .3); ex-ploratory translation favors SpecEdge-ϵ. With-out relaxation, H YCO exact saves 27.7% and 11.9% on the two datasets. 

1 Introduction 

Speculative decoding accelerates large language models (LLMs) by verifying several draft tokens in one forward pass; exact verification preserves the LLM’s sampling distribution (Leviathan et al., 2023; Chen et al., 2023). Serving engines sup-port this approach (Kwon et al., 2023; Zheng et al., 2024), and recent LLMs include native multi-token prediction (MTP) heads for server-side self-speculation (DeepSeek-AI, 2024; Gemma Team, 2026). Device–cloud speculative decoding instead places a small language model (SLM) on the user’s device and retains the verifier on the server (Park et al., 2025; Li et al., 2025a). This division can re-duce server work, but communication can make an individual request slower than server-only specula-tion (Lyu et al., 2026). The goal is therefore to save server computation while maintaining a practical mobile delivery speed. We evaluate this trade-off against two distinct reference points. On the server, the goal is to use less GPU time per output token than Cloud+MTP ,which already runs the LLM’s native MTP self-speculation. On the device, the goal is to deliver tokens at least as fast as the standalone SLM used in our evaluation. Cloud+MTP therefore measures the remaining server-side opportunity, whereas the standalone SLM provides a local alternative for the user. These goals concern server execution time and user-visible delivery, respectively, rather than a single shared speedup metric. The main obstacle is the cost of obtaining useful draft-tree depth on a mobile neural processing unit (NPU). A tree provides alternative tokens at each position and can be verified in one pass (Miao et al., 2024), but an autoregressive SLM requires another sequential pass for each additional level. Higher acceptance can amortize server work and commu-nication across more output tokens, although ac-ceptance varies across tasks (Liu et al., 2024a; Xia et al., 2024). In our deployment, the four-level SpecEdge-style tree increases the mean number of committed output tokens per round (MAT, includ-ing the bonus token), but its four SLM passes make delivery slower than standalone local generation. Integer-graph, memory, and context constraints fur-ther limit the device. The challenge is to obtain useful depth and alternatives without repeatedly executing the SLM. We present H YCO, which addresses this bottle-neck by dividing drafting work between two mod-els on the device (Figure 1). This separate choice raises accep-tance but is lossy. We contribute a native-head/SLM division of drafting work, implemented on a mobile NPU. 

2 Related Work 

We position H YCO along three related axes: where drafting executes, how draft trees are constructed, and how the verifier accepts proposed tokens. The first two define H YCO’s division of drafting work; the third determines the quality–efficiency trade-off of its default configuration. 

Draft placement. In the SLM-based device– cloud systems considered here, an independent device model proposes the tokens and a server model verifies them (Park et al., 2025; Li et al., 2025a, 2026c). Other work places early LLM lay-ers on the device, as in HAT (Xie et al., 2026), or drafts from hidden states returned by the server (Li et al., 2026a). Table 1 distinguishes these choices. Among the listed device–cloud systems, none uses the LLM’s native draft head as a mobile drafter. Cloud+MTP uses that head on the server; H YCO

instead executes it on the device together with an SLM Drafter. 

Draft construction. Trees provide alternative continuations for joint verification (Miao et al., 2024; Park et al., 2025), whereas target-alignment training and parallel-draft adaptation improve the proposal model (Zhou et al., 2024; An et al., 2026). Medusa and EAGLE variants also explore hidden-state-based drafting (Cai et al., 2024; Li et al., 2024, 2025b). HYCO combines a native head’s chain with independent SLM alternatives. It leaves the SLM’s weights unchanged and applies QAT to the head for mobile execution (§3.2). For an autoregressive SLM, additional depth re-quires sequential passes. Acceptance and verification. Synera reduces verification frequency by retaining confident de-vice tokens locally and sending only the rest to the server (Wang et al., 2025). H YCO instead checks every round, but its default rule is also lossy: it can accept draft tokens that the verifier did not sample. Verification methods differ in their acceptance criteria. BiLD, fuzzy speculative decoding, and E2-SCI use distributional divergence criteria (Kim et al., 2023; Holsman et al., 2025; Li et al., 2026b); Judge decoding uses a learned judge (Bachmann et al., 2025). Medusa applies an entropy-adaptive threshold to the target’s raw softmax (Cai et al., 2024; Hewitt et al., 2022). H YCO instead thresh-olds the verifier’s sampling distribution after tem-perature scaling and top-k/top-p truncation (§3.5). Token verification alone does not preserve selection probabilities; we therefore evaluate output quality. 

3 Method 

Upon a user request, the cloud verifier prefills the full prompt and computes its attention KV cache. In parallel, the mobile SLM Drafter prefills at most the last W prompt tokens and builds an initial SLM-only draft tree, since the MTP Drafter has not yet received verifier state. The server verifies this tree and returns accepted draft tokens, a bonus token, and the state needed to initialize the mobile head. Subsequent rounds use the Hybrid Drafter (Fig-ure 2; Algorithm 1). 3.1 Hybrid draft tree 

In each subsequent decoding round, the root xt+1 

is the bonus token returned by the previous verifi-cation. The mobile MTP Drafter receives its input embedding e(xt+1 ), the preceding verifier hidden state ht from which that token was sampled, and KV entries from the verifier’s last full-attention and last sliding-window layers. The head uses this state to propose K top-1 tokens sequentially. Its inputs are transferred as 8-bit integers: 5.6 KB per round for the input vector and approximately 6.1 KB per committed token for the KV entries. The server therefore returns state instead of exe-cuting the head’s K drafting steps; Appendix A specifies the transferred tensors. For the initial SLM-only round, the server’s first reply seeds the MTP Drafter’s KV window with up to W prompt positions. Subsequent replies transfer KV entries only for newly committed positions, enabling the hybrid workflow without local MTP prompt prefill. The standard configuration uses a K=4 chain and B=32 draft nodes. At the first two chain positions, the MTP Drafter also adds its second-3ranked token as a sibling of the top-1 token, pro-viding an alternative when that token is not ac-cepted. One pass of the SLM Drafter, Gemma 4 E2B from Google’s QAT checkpoint (Google Deep-Mind, 2026), then proposes children under the root and each MTP-generated node. These proposals can exceed B, so a common score ranks chain nodes, runner-up siblings, and SLM candidates be-fore pruning. H YCO-2P adds a second SLM pass over newly added nodes; its trade-off is evaluated separately. Let s(v) be the score of a parent node and let 

λ=0 .66 . A chain edge adds ln λ to s(v). A runner-up sibling adds 2 ln λ on its own edge, placing it below the corresponding chain token. An SLM candidate c instead adds ln q(c | v) + ln λ, where q

is the SLM Drafter’s distribution over the keep set. Scores accumulate along the path from the root. The value λ summarizes the chain’s measured conditional acceptance rates under exact verifica-tion: these rates are 0.65–0.68 across depths, with a geometric mean of 0.66. Thus, d ln λ serves as an acceptance-based score for a depth-d chain node. Appendix D provides the measurement setting. The device retains the B=32 highest-scoring draft nodes with their ancestors and sends token IDs and parent indices to the server. Including the root, verification uses 33 rows and the same CUDA-graph shape as SpecEdge-style. The server evaluates these rows in one forward pass with a tree attention mask (Miao et al., 2024). Under exact verification, it samples from ˜p(· | v) at each visited node and follows the matching child. The first sample without a matching child is committed as the bonus token and ends the round. MAT counts both accepted draft tokens and this bonus token, which becomes the next root. Section 3.5 changes only the acceptance rule, not the work split. This construction assigns depth to the MTP Drafter and alternatives to the SLM Drafter. To execute both on the NPU, H YCO must also fit their arithmetic, output layers, and context state to the device. The next three subsections describe these deployment constraints; their effects on proposal acceptance are distinct from the relaxation intro-duced in §3.5. 

3.2 Quantization 

Both drafters use static integer graphs to execute on the mobile NPU (Tan et al., 2024), but they reach this format differently. The released SLM QAT checkpoint has 2-, 4-, or 8-bit weights with floating-point computation (Gemma Team, 2026; Google DeepMind, 2026). We preserve its weights and convert it through graph surgery and activa-tion calibration, without retraining. The verifier’s MTP head is released in BF16, so we apply 4-bit QAT to its linear weights. Both models use 16-bit fixed-point activations and graphs compiled with QAIRT (Qualcomm Technologies, Inc., 2026). Final activation calibration and head QAT use 60 prompts from UC-tr, the train_sft split of UltraChat 200k. The head is trained for 100 steps to minimize KL divergence from the BF16 head on the verifier’s greedy answers. These prompts are separate from the UC-tr conversations used for vocabulary counts; no SB prompt is used for final calibration or QAT. Appendix A gives the formats, training details, and fidelity measurements. 

3.3 Restricted output vocabulary 

Both drafters have output layers over 262,144 to-kens. Evaluating these layers and searching their top candidates for every SLM row and MTP step contributes substantially to mobile work. Follow-ing frequency-based vocabulary restriction (Zhao et al., 2025), we use a shared keep set of 86,089 to-kens. It contains 81,131 frequent assistant-response tokens from 20,000 UC-tr conversations, together with 24 special tokens, 256 byte tokens, and all 4,678 Hangul tokens. Appendix A describes this construction; Appendix D compares keep-set sizes. Only the drafter output vocabulary is restricted. The verifier still samples from the full vocabulary, and a token outside the keep set can be returned as a bonus token. The SLM retains complete input tables, while the MTP Drafter receives the bonus token’s embedding in the hand-off and uses a local 8-bit, 242 MB table for its own drafted tokens. Un-der exact verification, these restrictions may reduce acceptance but preserve the output distribution. 

3.4 1K-token context window 

Both drafters use a W =1 ,024 -token context window, following bounded-context drafting ap-proaches (Sadhukhan et al., 2025; Valliappan, 2026). The SLM Drafter maintains its own KV ring over the latest 1,024 committed tokens, re-duced to 512 in sliding-window layers, and prefills at most the last 1,024 prompt tokens. The MTP Drafter instead reads a window of KV entries com-puted by the verifier and requires no local prompt prefill. The verifier itself processes the complete prompt; the mobile window does not truncate its 4context. The 1K window is a device-memory and prefill-time choice. The short UC-val prompts did not dis-tinguish the tested lengths reliably, so these com-parisons do not establish that 1K is optimal for long-context acceptance. The tested settings ap-pear in Appendix D; §4 evaluates 32K inputs. 

3.5 ϵ-threshold acceptance 

The mobile restrictions above change the propos-als available for verification. Even when the tree contains plausible continuations, exact verification ends a round if the verifier’s sample matches no child. Default H YCO trades exact distribution preservation for additional acceptance using an ϵ-threshold rule. A child c of node v is eligible if it matches the verifier’s sample or if ˜p(c | v) ≥ ϵ,where ˜p includes temperature scaling and top-k/top-

p truncation. The fixed probability threshold fol-lows ϵ-sampling (Hewitt et al., 2022). Under a one-hot greedy distribution, the threshold admits no additional token. Because several children can be eligible, the ver-ifier must select one path. It chooses the deepest path consisting entirely of eligible edges. Ties are broken first by the number of edges matching veri-fier samples and then by the product of ˜p along the path. The verifier appends its sample at the selected endpoint as the bonus token. This is a path-level preference: a sampled edge need not be retained if another eligible path is deeper. All committed tokens lie in the support of ˜p, but their selection probabilities can differ from ˜p. The rule is therefore lossy; support membership does not imply distribution preservation or equivalent quality. Setting ϵ=1 recovers exact verification, and §4.5 evaluates the quality trade-off of the de-fault ϵ=0 .005 configuration. We select ϵ=0 .005 on UC-val (Figure 3) using the screening procedure in §4.1 and Appendix D, and apply it at every node in the default config-uration. H YCO exact uses ϵ=1 , and SpecEdge-ϵ

uses the same threshold and path-selection rule as HYCO. Matching the rule does not match proposal distributions or establish equal output quality, so the experiments report both efficiency and quality. 

4 Experiments 

4.1 Setup 

The verifier is Gemma 4 26B-A4B (Gemma Team, 2026) with 4-bit activation-aware weight quantiza-tion (AWQ; Lin et al., 2024), served on one RTX PRO 6000 cloud GPU. A Galaxy S26 Ultra with an SM8850 chipset runs the drafters on its Hexagon Tensor Processor v81 over a commercial LTE/5G connection; the operator assigned LTE-CA or 5G NSA during measurement. The verifier samples with temperature 1, top-k 64 and top-p 0.95. Thus, exact verification preserves this sampling distri-bution, not a fixed greedy output. All configu-rations use SpecEdge’s verification server (Park et al., 2025), extended with our verifier and its MTP head, the same kernels, and one client at a time (Appendix B). 

Configuration selection. We compare candidate settings on UC-val, 60 prompts from UltraChat 200k’s test_sft split (Ding et al., 2023; Tunstall et al., 2024), and fix the selected configuration before the reported SB and ∞Bench Sum runs. Server cost g includes prompt-prefill and decoding GPU time divided by committed output tokens. Its decode-only component equals mean GPU time per round divided by MAT. The screening pro-cedure minimizes g among settings whose LLM-judge scores fall within the observed range of exact-verification runs. This range is an empirical screen, not an equivalence margin. Differences in g below the approximately 2% validation variation are re-solved using the stated device-cost or comparison rationale. Appendix D reports the range, session-specific settings, and earlier SB development trials. Figure 3 shows the UC-val MAT–judge-score trade-off used to choose ϵ=0 .005 at every node: MAT rises while the measured judge score remains within the shaded exact-reference range. This range is a screening heuristic, not an equivalence test (Appendix D).

4.3 Evaluation and uncertainty Benchmarks and quality metrics. We use all 480 Spec-Bench questions (SB-480; Xia et al., 2024) to measure decoding efficiency, including both MT-bench turns, with a 1,024-token output cap. For SB quality, GPT-5.4 scores first-turn non-QA answers from 0 to 100 using the question but no reference answer. This yields 398 paired ques-tions for H YCO–Cloud+MTP; complete-case re-peated comparisons involving SpecEdge-ϵ use 396. QA tasks are evaluated separately in Appendix E, and reference metrics supplement the question-only judge. Two summarization items consistently re-fused by the judge’s filter are omitted. For ∞Bench Sum, we evaluate the first 50 En-glish novels in HELMET’s seed-42 order, truncated to 32K tokens with its preprocessing (Zhang et al., 2024; Yen et al., 2025), with a 1,200-token out-put cap. We report ROUGE-L-Sum (Lin, 2004) and HELMET’s model-based fluency-weighted F1, key-point recall, and precision using GPT-5.4. Pre-cision measures consistency with the expert sum-mary, rather than factual accuracy against the full novel. 

Efficiency metrics. We report GPU time per out-put token g, including prompt prefill; MAT; and delivery speed, defined as pooled output tokens divided by mobile wall time from request start to last token. Mobile draft time excludes verification waits and prefill. These metrics separate server exe-cution, acceptance, and user-visible delivery rather than collapsing them into one speedup. 

Repeated runs and uncertainty. HYCO and SpecEdge-ϵ have three SB generations each, judged once per output; other setups use one run. The ±

values are run SDs. Paired 95% CIs use 2,000 ques-tion bootstraps, clustering MT-bench turns. For quality, we average scores per question before re-sampling (Appendix E). The CIs capture question-level uncertainty but do not separately estimate generation or judge variability.

A fixed ±20 -point screen of H YCO’s three-run per-question means against Cloud+MTP selects 13 decreases and 12 increases. Our manual inspec-tion identifies six substantive errors among the de-creases, as well as score/content discrepancies in both directions. We retain all measured scores; the selected cases are not an estimate of the overall error rate (Appendix F). 

4.6 Mobile costs and head transfer Mobile work and delivery. On SB, H YCO de-livers 35.0 tokens/s versus 26.4 for the SLM alone. Its 12.1 ms of mobile draft time per output to-ken is about a third of the SLM alone’s 36.8 ms. SpecEdge-style exact delivers 16.1 tokens/s and consumes 42.8 ms of mobile draft time per to-ken. The two efficiency goals therefore use dis-tinct references: less server work than Cloud+MTP, and faster delivery than the local SLM. Since Cloud+MTP was not streamed to the phone, we do not compare its user delivery speed with H YCO.

Head transfer and fidelity. In a separate paired 150-question experiment, the device-head config-uration (W4, 86K keep set, 1K window) has 4.0% lower MAT than the original BF16 server head (95% CI: 3.0–4.9%). In the full SB experiment, relaxing H YCO exact raises MAT from 3.84 to 4.71. These are separate comparisons, not additive estimates of independent component effects. 7Startup latency. The first hand-off introduces a startup cost. Single-run H YCO traces have mean time to first token of 846 ms on SB and 4.60 s on 32K inputs. Thus, higher average delivery speed does not imply a lower first-token delay. We report GPU-busy efficiency, not loaded-service capacity or energy savings (Appendix G). 

5 Discussion 

5.1 From server accelerator to client drafter 

HYCO’s central systems change is to turn a server-internal self-speculation component into a device– cloud protocol. Device–cloud systems commonly offload an independent draft model (Park et al., 2025; Li et al., 2025a, 2026c), while a server with a native draft head can already self-speculate (Lyu et al., 2026). HYCO moves that head’s sequen-tial drafting steps to the mobile device and returns the slice of verifier state the head reads. The in-dependent SLM then supplies alternative branches without taking over the chain’s depth. This split is most useful when server GPU time is constrained, the head is small enough for the de-vice, and its inputs fit the link. Our measurements establish the resulting single-client execution-time trade-off, not the capacity gain of a loaded ser-vice. Appendix D records the development-stage server/mobile exchange that motivated the place-ment choice. 

5.2 Choosing the mobile–cloud work split 

The measured configurations span several resource axes: server GPU time, mobile drafting work and delivery speed, first-token latency, and an unmea-sured energy cost. Prior systems adapt draft length to the channel (Li et al., 2026c), an acceptance threshold (Li et al., 2026b), or which tokens reach the server (Wang et al., 2025). Here, the choices also include where the native head executes and how many SLM passes accompany it. Figure 1 il-lustrates example deployment priorities rather than an evaluated online switching policy. The variants occupy different points in this space. A second SLM pass in H YCO-2P increases server saving but lowers delivery speed relative to de-fault H YCO. On long summaries, its additional server saving is small because prefill—which draft-ing does not shorten—accounts for about a fifth of g. Moving the head back to the server reduces mobile draft time but gives up server-side saving. Cloud+MTP removes mobile drafting altogether. Thus, no setting dominates every resource, and timing measurements alone do not determine an energy-optimal choice. 

5.3 Lossy acceptance revisited 

Wang et al. (2026) identify a general risk of truncation-based verification: restricting which to-kens can be accepted does not preserve the veri-fier’s relative preferences within that set. Our ϵ-threshold acceptance belongs to this family. The repeated SB generations and 32K summary evalua-tion in §4.5 characterize its observed trade-off on the evaluated tasks; they do not remove the under-lying distributional risk. Two comparisons separate the drafting design from the relaxed rule. Under exact verification, HYCO outperforms the exact SLM-only baseline on both SB and 32K inputs. Under the same ϵ

rule, it also retains an efficiency advantage over SpecEdge-ϵ. Matching the acceptance rule does not match the proposal distribution, and the translation result shows that task-specific quality differences can remain. The fixed-tree replay in Appendix D helps explain which proposal sources gain accep-tance, but it is mechanistic evidence rather than a quality guarantee for newly generated answers. 

6 Conclusion 

HYCO pairs the verifier’s native MTP head for draft depth with one SLM pass for alternative branches, moving sequential head steps to the device without repeated SLM passes for depth. Relative to Cloud+MTP, exact verification re-duces server GPU time per token by 27.7% on SB and 11.9% on 32K-token summaries. De-fault H YCO uses ϵ-threshold acceptance to in-crease these savings to 38.6% and 29.2%, with task-dependent quality–efficiency trade-offs eval-uated through repeated SB generations and long-summary metrics. SB delivery also exceeds stan-dalone local generation. These single-client results do not establish a uni-versal serving optimum. Full cross-family deploy-ment needs an on-device native head; Appendix H shows SLM transfer to Muse-Glimmer-30B via a token bridge without retraining. 

Limitations 

Deployment scope and cost. Our measurements establish single-client execution efficiency, not loaded-service capacity or end-to-end monetary 8or energy efficiency. Each round waits for one network round trip, which bounds mobile delivery speed, and the full hybrid deployment uses one mobile device, one commercial cellular network, one cloud GPU type, and one verifier family. All configurations serve one client at a time in our en-gine. Retaining unverified device tokens, as in Syn-era (Wang et al., 2025), would introduce a different lossy mechanism. 

Distribution and task coverage. Default H YCO

does not preserve the verifier’s sampling distribu-tion. The reported judge-score interval permits a modest quality decrease, and translation favors SpecEdge-ϵ in an exploratory comparison. The aggregate judge result covers scored non-QA first-turn answers, not QA or second-turn quality. The question-only judge and reference-summary-based HELMET metrics do not comprehensively assess factual consistency, and we do not establish how relaxed acceptance changes output diversity. 

Statistical scope. Only the two main relaxed sys-tems have three SB generations; the other con-figurations and Cloud+MTP have one. Question-bootstrap intervals condition on these recorded out-puts, and one judge evaluation per output does not separate judge variability from generation variabil-ity. The UC-val screening range is not an equiv-alence margin. Appendices A and D distinguish calibration and development data from the reported benchmark runs. 

Requirements and device costs. HYCO requires access to the verifier’s native head, intermediate hidden states, and KV entries, which may not be available from closed model services. The head must also fit the mobile device, and the SLM re-quires a shared tokenizer or token bridge. Heads that use more verifier layers (Chen et al., 2026) may require larger state transfers. The MTP Drafter adds about 20 ms per mobile round and up to 6.3 MB to the first reply of a long prompt, and the device stores 365 MB for it alongside the SLM’s 754 MB graph. These implementation requirements also con-strain where the measured acceptance rates may transfer. The UC-derived keep set and 1K window need not suit every language or do-main (Abramovich et al., 2026). Tokens outside the keep set comprise 3.0% of verifier bonus to-kens on UC-val and 6.8% on the 150-question SB subset of the head-configuration comparison (§4.6). Exact verification preserves the output distribution despite these proposal restrictions; relaxed accep-tance does not. The SLM accesses earlier context only indirectly through the MTP chain. We evalu-ate text only, not Gemma’s image or audio inputs. 

Information exposure. Each client holds the MTP head and part of the verifier’s input embed-dings. Transmitted activations and reply-size pat-terns may expose information beyond the text (Cun-ningham, 2026). We evaluate no safeguard.

B Verifier Engine 

We ported the verifier’s text model with static shapes into SpecEdge’s server (Park et al., 2025), replacing its model side, and checked it against the Hugging Face model. Attention projections run as 4-bit integer Marlin matrix products (Frantar et al., 2025) and the experts, 8 of 128 per token, through vLLM’s fused Marlin mixture-of-experts kernel (Kwon et al., 2023), while the dense MLP and the router stay in 16 bits. RMS normalization runs in FlashInfer (Ye et al., 2025), and attention in PyTorch (Paszke et al., 2019) with the tree mask. Tree verification uses the routed MoE kernel de-scribed above rather than a dense all-expert path. Each decode round is padded to the narrowest of ten attention windows that covers its context, 256, 512 and 768 positions and then powers of two up to the maximum context of 65,536, and replays that window’s CUDA graphs, while prefill runs ea-gerly in chunks. The verifier’s MTP head, which Cloud+MTP and the server head variant run on the server, replays its own graphs over the same windows, and its chains agree with eager execution on 99.2–99.6% of tokens, as often as two stock attention kernels agree.

E Quality per Task 

Scoring and missing observations. The SB judge sees the question and answer, each truncated to 6,000 characters by our scoring script, but not a reference answer. We retain the original scores and do not replace scores after manual inspection. Two summarization prompts are consistently blocked by the judge’s filter. H YCO has 398 eligible scored first turns in each run; SpecEdge-ϵ has 397, 397, and 398. The latter’s three-run complete-case inter-section has 396 questions. Consequently, H YCO–Cloud+MTP uses 398 paired questions, while both repeated comparisons involving SpecEdge-ϵ use 16 396. The final PD run provides 558 of 560 SB turns (479 questions), with 398 eligible first-turn judge scores, and 49 of 50 long-summary requests and scores. A failed score or incomplete response is not imputed. 

Bootstrap procedure. The release uses 2,000 percentile-bootstrap draws with seed 20261011 restarted per contrast, with question IDs sorted as strings. Both MT-bench turns are resampled to-gether for efficiency. Repeated quality averages all three available scores per question before complete-case pairing and resampling. These intervals reflect variation across recorded questions conditional on the observed runs; they are not an estimate of vari-ability across arbitrary deployments. The separate run SD combines generation and judging variability because each output has only one judge evaluation. Intervals may differ slightly from intermediate logs whose random-number streams were consumed in another order. 

QA diagnostics. The question-only judge is not a reference-based QA accuracy test, so we report QA separately from the non-QA aggregate. Our NQ-Open reference matching procedure matched 43 of the 80 QA questions; the remaining 37 were unmatched. Using the same normalized reference-containment rule as for RAG, Cloud+MTP scores 30.2%, H YCO 30.2%, H YCO exact 25.6%, and SpecEdge-ϵ 29.5% on these 43 items. For the two repeated systems, each question’s three bi-nary scores are averaged; the other systems use one answer. The H YCO–Cloud+MTP difference is 0.0 percentage points (95% CI: −13 .2 to +10 .9). Unmatched questions are omitted from this diag-nostic rather than counted as errors; containment is not strict exact match. The question-only QA judge means, covering all 80 questions, are 49.1 for H YCO and 45.1 for Cloud+MTP; they do not establish reference-answer correctness.

The RAG mea-sure checks normalized reference containment, not full answer correctness. F Failure Cases 

Server cost. Among 480 questions, H YCO has 2, 1, and 0 cases with ∆g ≥ 0 in its three runs. The non-saving cases are short RAG answers of approximately 40 tokens. This observation illus-trates an unfavorable operating condition; it does not establish that output length alone causes every cost difference. 

Quality-screened cases. We apply a fixed ±20 -point screen to the difference between each ques-tion’s three-run H YCO mean and Cloud+MTP’s single score. This selects 13 decreases and 12 increases. The following categories are our own judgments, not an independent adjudication or the overall error rate. Seven selected decreases have one especially low-scoring H YCO generation. In one inspected question (559), identical answer text received scores of 15 and 95, showing that at least some large changes can originate in the evaluator rather than different text. This does not establish that all score discrepancies are judge errors.
