# MemLLM: End-to-end In-Storage Acceleration of On-device Retrieval-Augmented Generation using Precomputed KV Caches 

Seungkwan Kang, Hyungseok Ko, Heemin Kim, Myoungsoo Jung 

Computer Architecture and Memory Systems Laboratory , KAIST Daejeon, Republic of Korea 

Abstract —Retrieval-augmented generation (RAG) on edge de-vices enables personalized large language model (LLM) inference while preserving privacy. However, RAG’s inherent length asym-metry makes the prefill phase the dominant bottleneck. While precomputing the KV caches offline alleviates the prefill cost on server systems, the multi-gigabyte caches over the narrow interconnect create a severe I/O wall for on-device systems. To mitigate this, we propose M EM LLM, an end-to-end in-storage processing (ISP) architecture that executes the complete attention pipeline based on precomputed KV caches within the SSD. MEM LLM utilizes per-channel accelerators to fully utilize the aggregated NAND channel bandwidth and accelerates all KV cache-related computations on the storage-side to minimize PCIe transfers. To efficiently handle the sparse updates required by RAG, M EM LLM introduces a fused recomputation-query kernel paired with a hardware-based filter logic to halve the NAND read volume and eliminate write-back penalties. Furthermore, M EM -LLM’s global SRAM-based stateful reduction engine enables a completely DRAM-less dataflow, thereby removing the internal memory bottlenecks and bounding the PCIe egress to an O(1) 

footprint. A full-stack software stack allows asynchronous, zero-copy transfers from the ISP to the host and provides transparent execution within modern ML frameworks. Evaluated across eight real-world RAG datasets and six on-device LLM models, MEM LLM achieves an average end-to-end speedup of 4.06 × over the GPU baseline. 

Index Terms —In-storage processing, retrieval-augmented gen-eration, large language model inference, KV cache, near-data processing, on-device machine learning 

I. I NTRODUCTION 

Large language models (LLMs) are rapidly migrating from cloud servers to edge on-device systems, driven by the demand for privacy-preserving inference over sensitive data, such as personal medical records [1]–[5], financial documents [6]– [10], and corporate knowledge bases [11]–[13], without depen-dence on centralized servers [14]–[17]. Retrieval-augmented generation (RAG [18]) is central to this vision. By grounding LLM responses in an external knowledge base, RAG elim-inates the need for costly fine-tuning and enables real-time, personalized answers on-device. However, RAG workloads exhibit a fundamental length asymmetry; the retrieved contexts typically span thousands of tokens, while the generated answers remain extremely short, often by a factor of 100–1000 ×. This asymmetry shifts the

inference bottleneck from the decode phase, which dominates standard LLM serving, to the prefill phase, where the LLM must process the massive retrieved context to build its KV cache. On resource-constrained edge devices, this prefill-dominated latency profile creates a severe performance barrier for practical on-device RAG deployment, especially for the long-context, short-answer regime. A promising software-level mitigation is to precompute the KV caches for documents in the knowledge base offline and load them from storage at inference time, replacing the compute-intensive prefill with a storage read [19]–[22]. On server systems equipped with high-bandwidth storage arrays, this trade of computation for I/O yields substantial speedups. However, on edge devices, the massive data movement across the narrow PCIe interconnect severely throttles performance. To make matters worse, the limited memory capacity of edge SoCs cannot accommodate these multi-gigabyte precomputed KV caches alongside the model weights, forcing the KV caches to be completely offloaded to persistent storage [23]– [28]. Streaming these precomputed caches from the SSD to the GPU over the limited PCIe bus takes longer than the compute time it was meant to replace, creating an I/O wall that negates the benefits of precomputation entirely. Existing in-storage processing (ISP) architectures offer a partial remedy. Prior works have offloaded decode-phase at-tention to storage devices to eliminate repeated KV cache transfers [23]–[25], or moved model-weight computation into flash to free GPU memory [29]. Yet, these approaches fail to address the defining challenge of precomputed-KV-based RAG: selective recomputation . Because independently pre-computed KV caches break cross-attention between retrieved documents, a small but critical subset of tokens ( ∼15%) must be recomputed using the full model weights to restore generation quality [20], [30]. This recomputation presents a highly heterogeneous workload consisting of compute-intensive, dense matrix multiplications (GEMMs), element-wise softmax operations and matrix-vector multiplications (GEMVs). This exceeds the capabilities of not only exist-ing decode-only ISPs, but conventional accelerator paradigms overall. Rigid 2D systolic arrays suffer catastrophic underuti-lization (zero-padding bubbles) when faced with 1D decode vectors or irregular sparse masks, while standard Single In-struction Multiple Data (SIMD) architectures lack the inter-arXiv:2610.22579v1 [cs.AR] 15 Oct 2026 PE data forwarding required for efficient GEMM execution. Unable to absorb the workload internally, current systems are forced into a disjoint execution flow: the entire KV cache must be first read from the storage and hauled to the GPU for recomputation, and read yet again for query attention; streaming multi-gigabyte data across the PCIe bus twice. To mitigate the issue, we present MemLLM , an in-storage processing architecture that eliminates this I/O wall by per-forming the precomputed-KV attention pipeline entirely within the SSD, without ever transferring the full KV cache to the host. M EM LLM targets on-device RAG with precomputed document KV caches and selective recomputation under long-context, short-answer workloads; we delineate this scope and its boundaries in Section VII. M EM LLM’s design is governed by three I/O minimization principles. 

Reduce NAND I/O. MEM LLM fuses selective recomputation and query attention into a single NAND-read pass via a unified kernel that constructs a combined query matrix ( Qf used ) from the recomputation targets and the user query. A hardware-based stream filter logic compacts the valid tokens from the irregular recomputation mask into a dense stream, allowing the compute units to process only the necessary tokens without wasting cycles on masking and zero-padding. This fusion halves the NAND read volume and completely eliminates the write-back penalty, as recomputed KV entries are consumed in situ within the same streaming pass. 

Utilize aggregated NAND bandwidth. Rather than funneling all NAND data through a centralized accelerator bottlenecked by the SSD’s internal bus, M EM LLM distributes lightweight Elastic-SIMD accelerators to each NAND channel endpoint. Each Elastic-SIMD dynamically reconfigures its datapath be-tween broadside mode (parallel GEMV for decode) and cas-caded mode (systolic-like forwarding for GEMM during pre-fill), maintaining high PE utilization across the heterogeneous RAG workload. This per-channel architecture delivers the full aggregate NAND bandwidth directly to computation without any internal bus contention. 

Eliminate internal DRAM I/O. A central coordinator logic merges per-channel partial attention outputs using a stateful online softmax reduction engine, hosted entirely in the con-troller’s global SRAM. Rather than repeatedly reading and writing partial sums to the controller’s DRAM, M EM LLM leverages RAG’s length asymmetry to avoid the internal band-width bottleneck entirely. II. B ACKGROUND 

A. Large Language Model (LLM) Inference 

Decoder-only transformers and KV cache. Modern large language models typically employ the decoder-only trans-former architecture [34], transforming input token embeddings into context-enriched representations via self-attention and feed-forward network (FFN) layers (Figure 1a). The core of this architecture is the scaled dot-product attention , which projects inputs into query ( Q), key ( K), and value ( V ) matrices to compute A = softmax (QK T /√dk)V . This captures the contextual relationships by weighting each token’s value pro-portionally to its relevance to the query. Multi-Head Attention (MHA [35]) further keeps separate K/V matrices per Q

head and inflating memory bandwidth. Recent models adopt Grouped-Query Attention (GQA [36]), sharing one K/V pair per head group to compress the KV cache. LLM inference operates in two phases. The prefill phase 

processes the entire input prompt in parallel via dense matrix-matrix multiplications (GEMM). The subsequent decode phase

Partial tile outputs are then merged by rescaling with the exponential difference between local and global maxima, enabling long attentions within a fixed SRAM budget without accuracy loss. 

B. Retrieval-Augmented Generation (RAG) 

Retrieval-augmented generation mitigates the hallucination and knowledge-cutoff limitations of LLMs by grounding in-ference in external, semi-static knowledge bases. As illustrated in Figure 2, when a user query arrives, a retriever performs a similarity search over a pre-indexed vector database to extract the top-k most relevant passages. These contexts are concatenated with the query to form an augmented prompt for the LLM. In this work, we assume that the retrieved chunks are finalized before attention begins [39], [40]. Further evaluation under retrieval methods that relax this assumption [41]–[44] are in Section VI-D. Unlike standard conversational LLM serving where the decode phase is often the primary bottle-neck, RAG workloads exhibit a drastic length asymmetry : the retrieved contexts typically span thousands of tokens, while the generated answers remain relatively short. Consequently, the prefill phase over these massive contexts dominates the end-to-end RAG inference latency (Section III). 

C. Precomputed KV Caches for RAG 

Because RAG knowledge bases are mostly static , the compute-intensive prefill cost for the documents can be amor-tized. The system can tokenize each document offline, run a prefill pass to generate its KV cache, and store it in persistent storage [19], [20]. At inference time, instead of recomputing the context from raw tokens, the LLM simply loads the precomputed KV cache . While precomputing KV caches independently per document saves prefill compute, it breaks the cross-attention between different retrieved doc-uments. By evaluating the cross-attention deviations at the first decoder layer, the system flags a small subset ( ∼15%) of tokens, termed as High KV Deviation (HKVD) tokens, that require full attention recomputation using the model weights, while the remaining are consumed directly from the storage. However, executing this selective recomputation introduces a highly inefficient, disjoint execution flow, as illustrated in Figure 3. First, the host GPU must load the entire precomputed KV cache from storage to start the recomputation (Phase 1). Because only a small portion of the tokens require updates, the Q matrix is a ”thin” dense matrix composed strictly of the embeddings for these targeted tokens. However, because these target tokens are scattered unpredictably across the absolute sequence positions, computing their attention scores requires an irregular, jagged attention mask to maintain positional correctness. Subsequently, for the query prefill, the host must re-read the entire precomputed KV cache to compute the at-tention against the newly appended user query (Phase 2). This structural separation of the KV caches and compute forces the system to stream the multi-gigabyte KV cache across the PCIe bus twice, creating a massive I/O bottleneck that severely limits the efficiency of on-device RAG deployments. III. C HALLENGE AND MOTIVATION 

Although on-device RAG promises privacy-preserving, low-latency inference over personalized knowledge bases, its long contexts create severe performance challenges on resource-constrained edge devices. In this section, we systematically analyze these challenges and derive the architectural require-ments for an on-device RAG accelerator.

KV cache offloading. The analysis so far assumed the KV caches fit in GPU memory (we shrank the layer count to fit on-device memory and extrapolated the measured latency to full-model scale), but this rarely holds in practice. Amodel’s footprint is its own weights plus the KV cache, whose size grows with the per-token KV size, the number of retrieved contexts (top-k), and the dataset’s average context length. Table II reports the maximum tokens each model fits in 8GB: even OPT-350M tops out at 40k tokens, too few for top-4 retrieval on CuAD, and at a moderate k=5 most model-dataset pairs exceed the budget. Consequently, for a significant fraction of practical on-device RAG workloads, the precomputed KV caches must reside in storage rather than GPU memory. This storage-resident regime, which we call KV cache offloading , is critical for on-device RAG as it amplifies the I/O wall, and is the focus of the rest of this section.

Roofline analysis. The key challenge for such an end-to-end ISP is that the RAG inference pipeline presents a het-erogeneous mix of operators with widely varying arithmetic intensities, all of which must execute within the power budget. Figure 8 presents a roofline analysis of these major operators mapped onto two conventional accelerator architectures: 2D systolic arrays and 1D SIMD arrays. For standard, dense GEMMs, systolic arrays reach near-peak compute utiliza-tion. However, their fixed two-dimensional dataflow is fun-damentally mismatched with the rest of the RAG pipeline. The most fatal degradation occurs during the decode-phase GEMV: when the sequence dimension drops to 1, the vast majority of processing elements (PEs) in a rigid 2D grid sit idle. Furthermore, processing the thin-GEMMs (due to the smaller sequence dimension of the 15% recomputation targets) required for selective recomputation exacerbates this underutilization, while handling the irregular attention masks introduces additional boundary zero-padding overhead. Under a strict 3W budget, dedicating precious silicon area to a large 2D array that remains heavily underutilized for the majority of the E2E latency is architecturally prohibitive. Conversely, SIMD-only architectures handle 1D GEMV and element-wise vector operations (e.g., softmax) efficiently, as each PE operates independently, but lack the low-cost inter-PE data forwarding necessary for dense GEMMs. Consequently, partial sums must be heavily routed through shared memory, creating an internal memory bandwidth bottleneck that severely limits the compute ceiling for projection operators. Since neither architecture alone covers the full spectrum of RAG operators, this analysis yields two architectural require-ments for an on-device RAG ISP. i) Elasticity : The ISP must switch seamlessly between parallel vector operations (GEMV) and matrix operations (GEMM). ii) Sparsity-awareness : The ISP must gracefully filter and compact irregular attention masks without incurring control or padding overheads. In the following section, we present M EM LLM, an architecture purpose-built to satisfy these requirements. IV. O VERVIEW 

To mitigate the I/O wall of KV caches, we designed M EM -LLM, an in-storage processing architecture that accelerates on-device RAG by performing the full attention computation within the SSD, completely eliminating massive KV cache transfers. Our design is governed by a unified I/O minimization principle applied across three levels of the memory hierarchy: fusing operations to halve NAND read volume, distributing compute to fully exploit aggregate channel bandwidth, and confining partial reductions to on-chip SRAM to bypass the controller’s DRAM. This section presents the overall system (Section IV-A), traces the end-to-end dataflow of a RAG query (Section IV-B), and quantifies the cumulative performance contribution of each design (Section IV-C). 

A. System Overview 

Figure 9 illustrates the M EM LLM system, consisting of a host GPU and a M EM LLM CSSD connected via PCIe. The host GPU retains model weights in its memory and executes projection and FFN layers. M EM LLM persists all KV caches in flash, including the precomputed caches and the newly computed ones, and performs attention over them. Commu-nication with the M EM LLM SSD bypasses the conventional block I/O stack. We adopt an NVMe vendor-specific command to carry tensor metadata and DMA addresses directly to the SSD, establishing a P2P DMA path for zero-copy transfers between the GPU and the ISP (Section V-E). At the center of the M EM LLM SSD, the controller houses the Flash-Coordinator , the central scheduling engine that orchestrates multi-channel synchronization and NAND timing. The controller also contains 1MB of global SRAM partitioned into two buffers. The Q broadcast buffer holds the query matrix received from the host and serves it repeatedly to all channels at on-chip bandwidth ( 1 ). The O reduction buffer accumulates partial attention outputs from all channels via a stateful reduction engine that performs online softmax correction in place ( 2 ). The controller’s DRAM is entirely excluded from the attention data path; it remains dedicated to Flash Translation Layer (FTL) management, avoiding band-width contention and power overheads ( 3 ). B. End-to-End Dataflow 

The selective-recomputation-based prefill comprises three steps: i) identifying the HKVD tokens, ii) recomputing the KV cache of these HKVD tokens, and iii) performing prefill for the user query using both the precomputed and recomputed KV caches. To execute these steps simultaneously without re-reading the KV caches, M EM LLM introduces a fused attention kernel . Figure 10 illustrates the end-to-end flow of this fused kernel. At the start of inference, the host uses the query and the retrieved-context tokens to fully compute the first decoder layer (layer 0), thereby obtaining the KV vectors of layer 1. It then reads the precomputed KV cache of the contexts from storage. Because only the layer-1 KV cache is read at this stage, less than 5% of the total KV cache is transferred. The host compares the newly computed KV cache against the precomputed KV cache, computes the token-wise deviation and selects roughly 15% of the tokens with the largest deviation as HKVD tokens. The mask of these HKVD tokens is transmitted to M EM LLM to initialize the Stream Filter. Here, the recomputation ratio (5–18% [20]) is a static, user-determined hyperparameter that controls the trade-off between generation quality and compute cost. In the same pass that handles the HKVD recomputation targets, M EM LLM’s fused kernel also performs the attention for the new user query; through the iterative computation of subsequent layers, the KV caches of both the HKVD tokens and the query are obtained in a single pass. To this end, the host recomputes the KV cache of the HKVD tokens selected in the previous layer and transmits it, together with the query’s KV cache, to M EM LLM. MEM LLM then combines this host-supplied data with the precomputed KV cache read from flash utilizing the Stream Filter logic into masked KV cache. It then performs the attention computation and returns the result to the host; the internal datapath that carries out this computation, comprising channel-parallel tiling, per-channel compute, and DRAM-less on-chip reduction, is detailed in Section V. At this point, the KV caches received from the host are stored out-of-place in flash and later used for the decode computation. Note that the original precomputed KV cache is preserved unmodified, since it is needed when processing other queries in the future. Based on the attention result computed by M EM LLM, the host performs the projection and FFN computations to produce the KV cache of the next layer; this process repeats for as many layers as the model has, computing the KV caches of the HKVD tokens and the query tokens across all layers in a single iteration. Crucially, the bulk precomputed KV cache never leaves the SSD; only the compact Qf used , the host-recomputed KV subset, and the returned Of inal cross the PCIe bus. The egress thus stays at an O(1) footprint regardless of context length, whereas storage-offloading baselines must repeatedly stream the full O(N ) KV cache.

A. Fused Kernel and Internal Dataflow 

MEM LLM executes both the GEMM-based fused attention kernel of prefill and the GEMV-based decode kernel on its per-channel Elastic-SIMD, keeping the bulk KV cache resident in flash and off the PCIe bus throughout inference. Figure 12 details the internal dataflow of each kernel. 

Fused kernel. For the fused kernel, the host supplies the query vectors of the HKVD recomputation targets and the new query tokens, which are stacked into a single dense query matrix 

Qf used and transmitted together with a bitvector we call the 

jagged attention mask . The kernel scores Qf used against the concatenated K vectors, i.e., the precomputed context K, the recomputed HKVD K, and the new query K, gated by this mask. The jagged attention mask captures the hybrid causal structure of Qf used : the upper rows correspond to a discontin-uous subset of original sequence positions (the HKVD targets), so their causal boundaries do not form a standard lower-triangular matrix but shift abruptly with each token’s absolute position, producing a irregular, jagged staircase; the lower rows, representing the new query, take a standard dense mask over the entire context. The Elastic-SIMD applies this mask during the in-situ softmax to guarantee causal correctness. 

Channel-parallel tiling. Since the KV cache resides per channel in flash, M EM LLM parallelizes this score compu-tation along the K dimension: as Figure 12a shows, each channel evaluates the jagged-masked scores for the KV slice it stores, an interleaved mix of precomputed-context and HKVD contexts. Because every channel must see the full query, the Flash-Coordinator deposits Qf used into the Q broadcast buffer (Qbuf ) and broadcasts it to all channels; a tile then pairs one KV page with a Qf used tile. The decode kernel reuses the identical tiling with Qf used collapsed to a single query row (GEMV). Overall, M EM LLM is a faithful hardware realization of CacheBlend[20], not an approximation: its tile-by-tile fused kernel and online-softmax reduction merely reorder otherwise-identical computations, so the output matches a software CacheBlend execution up to floating-point rounding, with negligible downstream accuracy impact (Section VI-B).

B. Elastic-SIMD Microarchitecture 

To execute the heterogeneous RAG pipeline within a strict 

∼3W storage power envelope, we designed Elastic-SIMD , a highly reconfigurable compute fabric situated at each NAND channel endpoint. Figure 13 details its internal organization. Unlike rigid 2D systolic arrays, the Elastic-SIMD is a 1D array of Processing Elements (PEs) – e.g., 128 to match the attention head dimension – over a reconfigurable routing network.A per-PE router (Figure 13b) toggles two dataflows on a single mode signal: broadside mode runs all PEs in parallel across the sequence to stream 1D KV vectors (GEMV) for decode, whereas cascaded mode forwards data row-to-row to reuse operands for the fused kernel’s thin-GEMMs (prefill), giving systolic-like efficiency without the rigid 2D area overhead. To avoid spilling intermediate matrices to shared memory for the non-linear operations, each Elastic-SIMD PE couples its multiply-accumulate (MAC) units with an in-situ vector ALU (Figure 13c): row-wise reduce-max/-sum comparators and an LUT-based exponential unit let the Elastic-SIMD run the entire online-softmax correction within its registers, without stalling the MAC pipeline. C. NAND-Aware Tiling Algorithm 

The fused kernel must be tiled onto the hardware while re-specting the physical constraints of NAND flash. Algorithm 1 outlines M EM LLM’s NAND-stationary tiling strategy. 

Page-aligned K/V tiles. To maximize aggregate bandwidth, the KV cache is interleaved across channels at a page gran-ularity. Since NAND reads whole pages (e.g., 16KB) and, at FP16 precision with head dimension d = 128 , a 16KB page accommodates exactly 32 tokens worth of both K and V vectors, M EM LLM fixes the K/V tile size Tk to 32 tokens. This ensures that every NAND read perfectly aligns with the page boundary without wasting interface bandwidth. 

K-stationary, Q-streaming loop order. As shown in Line 3– 4, the loop is structured with KV pages in the outermost loop. Each KV page is fetched from NAND exactly once into the local scratchpad, remaining stationary while Q tiles are streamed through it. Since Qf used is globally broadcasted from the controller’s SRAM to all channels simultaneously, the high-bandwidth SRAM interconnect easily hides the broadcast latency behind the slower NAND reads. 

Die-level pipelining. A NAND page read consists of a sensing phase ( tR, 5-20 μs) and a transfer phase ( tOut , a few μs). By striping consecutive token groups across multiple dies in a round-robin fashion, M EM LLM establishes a three-stage pipeline. While die i performs tR, die i−1 executes tOut , and the Elastic-SIMD processes the page from die i−2. Utilizing double-buffered local scratchpads, this die-level pipelining completely hides the dominant tR latency. At the coarser inter-layer granularity, M EM LLM further overlaps the NAND reads for layer l+1 with the host-side projection and FFN computation of layer l, hiding the remaining inter-layer latency across the multi-layer pipeline.

E. MemLLM Software Stack 

MEM LLM is realized through a full-stack system de-sign, which bridges the gap between tensor-level ML frame-works and block-level storage interfaces. Because conventional POSIX I/O stack operates on logical block addresses and strips the semantics required for tensor offloading, M EM LLM bypasses the virtual file system (VFS) and block layer through the NVMe passthrough interface ( NVME_IOCTL_IO_CMD )with a vendor-specific command, CMD_FUSED_ATTN . Note that, since the irregular recomputation mask can exceed several kilobytes for long contexts, it cannot fit within a standard 64-byte submission queue entry (SQE). The SQE instead carries a lightweight handle to the KV-cache layout together with the physical DMA addresses and lengths of the mask bitvector and Qf used , letting the controller fetch every operand by zero-copy peer-to-peer DMA with no OS context switch. To avoid bounce-buffer copies through host DRAM, M EM LLM uses the Linux dma-buf framework: the kernel driver maps the GPU VRAM holding Qf used into the NVMe driver’s DMA mappings, the controller reads it directly into global SRAM over a P2P PCIe transaction, and Of inal returns along the same path. Finally, M EM LLM exposes these capabilities transparently to application developers via a PyTorch C++ ex-tension ( torch.ops.memllm ) that extracts the raw tensor pointers and submits the NVMe commands through Linux 

io_uring asynchronous I/O. Because io_uring is non-blocking, it lets the host GPU overlap its projection and FFN compute with the storage-side attention, and on the completion interrupt (CQE), it resolves the pending future and returns the completed tensor directly into the PyTorch computation graph. VI. E VALUATION 

A. Methodology 

Prototyping and simulation. We prototyped the Elastic-SIMD microarchitecture based on Chisel [49] using the Chip-yard [50] framework. For comparison, the reference acceler-ator designs were prototyped using Hwacha [51] for SIMD arrays and Gemmini [52] for systolic arrays. All designs were implemented on a 16nm FPGA [31] to extract cycle counts, area, and power metrics, ensuring that the distributed Elastic-SIMD clusters and the Global Accumulator operate well within the 3W power envelope of an edge SSD controller. To estimate the area overhead of M EM LLM, we used CACTI [53] and Synopsys Design Compiler at the 45nm process node. In MEM LLM’s per-device flash coordinator, the buffer occupies more than 99% of the area, accounting for 1.6mm 2. The per-channel accelerator consists of i) the Elastic-SIMD, ii) the Stream Filter, and iii) the scratchpad, occupying 0.11mm 2,0.023mm 2, and 0.06mm 2, respectively. Elastic-SIMD is ap-proximately 4.2 × larger than AiF’s PE (0.026mm 2), as it supports high-bandwidth GEMM and attention operations in addition to GEMV. Although MEM LLM includes a flash coordinator and a larger PE, its total area is smaller (0.68 ×)due to its per-channel design compared to per-chip (AiF). To evaluate end-to-end performance, we developed a com-prehensive trace-driven, cycle-level simulator that integrates both host and storage models. To accurately model host GPU execution time, we natively profiled the LLM inference on an NVIDIA Jetson Orin NX using PyTorch, recording the exact latency of each CUDA kernel. Operations offloaded to the ISP were simulated using the cycle-accurate performance models derived from our hardware prototypes. Data transfer latencies between the GPU and the SSD were incorporated by empiri-cally measuring the PCIe interface delays on the host system. Finally, we integrated SimpleSSD [33] to faithfully model the internal storage dynamics, including NAND flash read latencies ( tR, tOut ), die-level pipelining overlap, and channel bandwidth constraints.The Jetson Orin NX ships in 8GB and 16GB modules, and we evaluate on the 16GB module. Because the Orin, like recent edge SoCs and smartphones, adopts a unified memory architecture in which the OS and applications jointly share the physical capacity [57], dedicating the full 16GB to inference is unrealistic; we therefore conservatively assume that roughly 8GB is available to the RAG workload. We further analyze the sensitivity to this budget by sweeping the available host memory in Section VI-D. 

Models and datasets. We evaluated the same model and dataset configurations described in Section III. LLM models include OPT [46] and SmolLM2 [47] in FP16 precision, cover-ing both GQA and non-GQA variants (Table II). RAG work-loads are drawn from eight datasets spanning four domains (Table I). Selective recomputation follows the algorithms from CacheBlend [20] with a default recomputation ratio of 15%, and top-k=5 retrieval unless stated.

Figure 19c quantifies die-level pipelin-ing in the distributed Elastic-SIMD accelerators, comparing the achieved aggregate NAND bandwidth between a naive sequential execution and the proposed three-stage pipelined execution using double-buffered local scratchpads. Under the naive approach, the NAND sensing time ( tR) is exposed to the critical path, frequently stalling the compute units and drop-ping the bandwidth to nearly half the theoretical maximum (∼11 GB/s). The pipelined execution overlaps NAND laten-cies with computation of previously fetched KV pages; this double-buffering completely hides the read latencies behind the compute, pushing effective throughput to ∼19 GB/s.

KV compression methods. Figure 25a evaluates the baseline and M EM LLM under optimizations that directly reduce the KV cache size: quantization to reduce the per-token size (Q-8b , Q-4b ) and entry-count reduction via SnapKV [59] and KVZip [60], representative runtime- and static-based methods, respectively. SnapKV can compress only after the query prefill completes, whereas KVZip compresses the con-texts through preprocessing. By shrinking the KV cache, these methods ease the limited PCIe bandwidth that bottlenecks edge environments; however they likewise cut the NAND reads of M EM LLM, so M EM LLM sustains a comparable 2.0– 4.4 × end-to-end speedup over the baseline across all methods. Crucially, these techniques are orthogonal to and composable with M EM LLM: while they shrink the I/O wall and thus narrow M EM LLM’s margin, they do not remove it, since even compressed caches can exceed on-device memory for long contexts and still cross PCIe. Figure 25b breaks the end-to-end latency into HKVD identification, recomputation, query prefill, and the decode steps. HKVD identification and MEM LLM’s recomputation are both compute-bound, domi-nated respectively by the host GPU’s full-attention pass and the fused kernel’s prefill operations. They are thus barely affected by compression, and their share grows with the compression ratio, reaching 8.8% and 75.5% under Q-4b .Since SnapKV compresses only after prefill, it benefits only the decode phase, whereas KVZip benefits all phases alike; consequently KVZip ’s recomputation share is 26.2%p lower than SnapKV ’s. Even under aggressive compression, M EM -LLM retains an advantage, as the recomputation still reads the precomputed KV that the baseline must stream across PCIe but MEM LLM keeps within storage. VII. D ISCUSSION 

Scope. MEM LLM targets on-device RAG with precomputed document KV caches, selective recomputation, long contexts, and short answers; the regime where the precompute-then-recompute prefill and its KV-cache I/O dominate. Its benefit narrows outside this regime: long answers shift the bottleneck to decode (Figure 23), and a memory-resident KV cache narrows the I/O wall, though M EM LLM still leads (Figure 22). As Section III shows, this memory-constrained, long-context regime is the common case for practical on-device RAG. 

Deployment requirements. MEM LLM assumes a computa-tional storage device that integrates per-channel accelerators with a central coordination logic. Although M EM LLM adopts a custom NVMe command, it i) occupies a vendor-specific op-code reserved by the specification, and ii) requires no host-side kernel modification when issued via the io uring-based NVMe passthrough introduced in Linux 5.19. The GPUDirect RDMA needed for GPU–device P2P DMA is already supported on the Jetson Orin; unified-memory SoCs like modern smartphones, where the GPU and storage share one physical address space, further simplify this path relative to conventional systems. NVIDIA’s GPUDirect Storage does not yet cover such SoCs, but its support is expanding rapidly. Once these conditions are met, our software stack handles the GPU/SSD split execution and exposes it as a single PyTorch operation. As demand for RAG over sensitive personal data spreads from medical and legal PCs toward smartphones, M EM LLM could enable efficient on-device RAG on such devices. VIII. R ELATED WORKS 

Precomputed KV cache. Prompt caching [21], [61]–[63] reuses the KV caches of frequent system prompts or sim-ilar queries to skip redundant prefill. For RAG, combining independently precomputed document caches disrupts cross-attention, so CacheBlend [20] and CacheClip [30] apply selective recomputation, updating only a minimal token subset to restore quality. These software optimizations speed up high-bandwidth servers but hit an I/O wall on resource-constrained edge devices; M EM LLM is the first to mitigate it. 

ISP for LLMs. Recent ISP studies alleviate the PCIe bot-tleneck of offloading-based LLM inference. Decode-phase offloading [24], [25] pushes memory-intensive attention to the SSD to eliminate KV cache transfers during decode; AiF [29] moves weight computation into flash to free GPU VRAM for the KV cache; and RAGX [16] accelerates RAG’s vector-database retrieval within storage. While effective for standard LLMs, these are mismatched for on-device RAG over precomputed KV caches: decode-only ISPs cannot handle the compute-intensive selective recomputation, and weight-offloading designs trigger OOM for long contexts. M EM LLM is the first to support end-to-end RAG compute. IX. C ONCLUSION 

MEM LLM is an end-to-end in-storage processing architec-ture that executes the complete RAG attention pipeline directly within the SSD. By leveraging distributed, per-channel Elastic-SIMD accelerators, M EM LLM fully exploits the aggregate NAND channel bandwidth and shifts all KV cache-related computations to the storage side to minimize PCIe trans-fers. Furthermore, M EM LLM mitigates internal I/O overheads through the co-design of a fused recomputation-query kernel and a DRAM-less global reduction engine. Evaluated across eight real-world RAG datasets and six on-device LLM models, MEM LLM achieves an average end-to-end speedup of 4.06 ×

compared to GPU-based systems. ACKNOWLEDGMENT
