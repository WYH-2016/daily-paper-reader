# Characterizing Predictability–Throughput Trade-offs of KV-Cache SSD Offloading in LMCache for LLM Serving Systems 

Ying He †, Dingsen Shi †, Yanbo Dai †, Donger Chen †, Harry Fu †, Chris Tsu ‡, Wang Feng †, Song Fu †

Initio Corporation, San Jose, California, USA. christsu@outlook.com 

Abstract —KV-cache offload is widely used to stretch GPU memory for LLM serving, but its storage behavior has not been characterized at the block-device level. In this paper, we study LMCache through realworld multi-session workloads that span same/different context × same/different prompt, using over 100 stateless requests per workload. Our comparison is observational rather than factorial: it contrasts two realizable deployment snapshots—LMCache 0.3.0 with buffered I/O and the kernel page cache, and LMCache 0.3.16 with prefix-aware deduplication and O_DIRECT . Key findings define the paper. First, the legacy stack appears almost read-free at the SSD layer in all four workloads, but a flush_ram experiment shows that this is conditional on page-cache warmth: once the cache is evicted, the same path issues about 1 GB of sequential reads in 683 ms. Second, deduplication delivers a dramatic write reduction only for the exact-repeat workload: one set collapses from 1.62 GB to 11.75 MB of writes, while the other three sets remain in the 2– 5 GB range. Third, O_DIRECT converts a hidden and bimodal read cost into an explicit and stable one: on one set, warm TTFT rises from 27 ms to 93 ms because each of the 99 warm requests re-reads the same ∼12 MB partial chunk from SSD. The main conclusion is therefore not “newer is better,” but a system trade-off: predictability versus average throughput .

Index Terms —LLM serving, KV-cache offloading, LMCache, SSD offloading, Direct I/O, page cache, latency predictability 

I. Introduction Modern LLM serving stacks increasingly behave like mem-ory hierarchies. GPU KV cache capacity is the first hard limit, and when contexts or batch sizes grow, systems must spill state to CPU memory, local SSD, or the network. Recent work has improved this stack from many angles: dynamic GPU KV allocation and serving kernels [1]–[4], iteration-level scheduling and batching [5], [6], heterogeneous or offloaded inference [7]–[12], prefill/decode disaggrega-tion [13]–[16], and structured or stateful runtimes with prompt reuse [17]–[19]. Parallel lines of work reduce KV memory itself through eviction, compression, quantization, sparsity, or selective loading [20]–[28]. Only recently have disk-mediated KV sharing and compute-vs-load orchestration been studied directly [29], [30]. Surveys consistently identify efficient inference and KV-cache management as first-order system bottlenecks [31], [32]. LMCache sits directly on this fault line. It is now a widely used open-source KV-cache layer for sharing, offloading, and moving KV state across engines and tiers [33]. In practice, however, operators do not choose LMCache as an abstract API. They choose a storage path : buffered I/O plus the kernel page cache, or direct I/O that makes storage traffic explicit. The performance consequences of that choice are still under-characterized. This paper studies exactly that question using LMCache traces collected from two versions that reflect two realizable deployment points in current systems. The older point, LM-Cache 0.3.0, uses buffered file I/O and naturally benefits from the Linux page cache. The newer point, LMCache 0.3.16, adds prefix-aware deduplication and supports O_DIRECT .Our main claim is not that one version dominates the other. Instead, the two points implement two different cost models:  

> •

Buffered I/O + page cache can make SSD reads disappear entirely in the common warm-cache case, but that benefit depends on host memory state outside LMCache’s control.  

> •

O_DIRECT + dedup makes read cost explicit and stable, but pays that cost on every retrieval, even when the same data would likely have remained hot in RAM. We make three major contributions. First, we provide a block-layer characterization across four stateless workloads that cover exact repetition, fixed-context/varying-prompt traf-fic, fixed-prompt/varying-context traffic, and fully varied traf-fic. Second, we use a page-cache-eviction experiment to show that the legacy stack’s “zero reads” are conditional rather than mechanism-free. Third, we show that the new stack’s strongest deduplication win is narrow: it appears only in the exact-repeat workload, while the more production-like varied workloads still write GB-scale data. The result is a clear systems narrative: LMCache’s current SSD offload path trades average throughput for predictability .II. Relation to Prior Work Our study sits at the intersection of three research threads. The first is LLM serving systems , which optimize batching, arXiv:2610.21249v1 [cs.OS] 15 Oct 2026 memory management, or phase placement to improve la-tency/throughput trade-offs [1], [2], [5]–[8], [13], [14], [17], [34], [35]. These systems establish that inference is often memory-bound, but they usually treat offloaded KV access as an abstract tier rather than characterizing how buffered and direct storage paths differ at the SSD layer. The second thread is KV-cache reduction and reuse . Prior work prunes, compresses, quantizes, or selectively keeps KV state [20]–[28], while systems such as ChunkAttention, CacheBlend, MemServe, and recent disk-based RAG caches aim to improve prompt reuse or cross-request sharing [16], [18], [19], [29]. These works show that KV reuse can save substantial compute, but they rarely ask what the storage device actually sees when reuse happens. The third thread is compute-versus-load coordination . Cake explicitly argues that prefill computation and KV load-ing should be co-optimized rather than treated as separate choices [30], and heterogeneous/offloaded systems similarly balance GPU computation against movement through CPU, SSD, or near-storage tiers [9]–[12], [15]. Our results provide a concrete block-level explanation for why such coordination matters: in short-context, partial-chunk regimes, loading the reused KV object can cost more than recomputing the tail it is meant to save. Relative to these threads, our paper investigates a previously unexplored problem and provides valuable insights through comprehensive experimental evaluation. We do not propose a new serving engine or a new KV policy. Instead, we characterize the observed storage behavior of a practical open-source KV-cache layer and show that the dominant trade-off is not simply write reduction, but the shift from hidden read cost to explicit read cost. III. Experimental Context and Evaluation Methodology 

A. Two deployment snapshots 

Our comparison is framed as observational . The legacy traces were archived from September 2025 using vLLM 0.9.0 + LMCache 0.3.0 on a Samsung 980 SSD. The new traces were collected in March–April 2026 using vLLM 0.11.0 + LMCache 0.3.16.dev11 on an RTX 5090 (32 GB) workstation with a Crucial P310 NVMe SSD. The new buffered-I/O path with save_unfull_chunk=True was unstable in our environment and appeared to trigger a use-after-free crash, so we compare two realizable points instead of a full factorial matrix over version, SSD, and I/O mode. We therefore interpret the paper as a trade-off characterization ,not a causal ablation.

IV. From Zero Reads to Hidden Reads 

A. Legacy LMCache looks almost read-free 

Table II summarizes the measurements. At first glance the legacy stack seems remarkable: across all four workloads, the SSD sees only 0–0.05 MB of reads at the block layer, even though LMCache logically performs get operations after the first identical request in Set A. At the same time, writes remain substantial and workload-sensitive, ranging from 1.62 GB (Set A) to 3.79 GB (Set B). This is consistent with the old path’s naive write-through behavior: repeated content is still written back out as chunk files because there is no prefix-aware dedup check. The temporal structure is equally important. Figure 1(a) shows Set A under LMCache 0.3.0. Instead of 100 regular write bursts aligned with requests, writes are spread across the full experiment window and released in irregular spikes by kernel writeback. In other words, buffered I/O obscures application rhythm: the block layer shows when dirty pages happen to be flushed, not when LMCache logically decided to persist a chunk. The few residual reads in the old traces are metadata reads (e.g., ext4 inode/journal activity), not LMCache data fetches. Across Set A–D, these metadata reads remain tiny compared with writes: the archived traces contain only 14–44 such events per scenario, while write counts range from 13,199 to 30,994. B. An eviction experiment reveals the hidden cost 

The natural hypothesis is that the old stack is not truly read-free; rather, its reads are satisfied from the page cache and therefore do not reach the SSD. We validated this directly. We first populated roughly 1 GB of LMCache data, then forced memory pressure and cache eviction ( drop_caches plus explicit RAM pressure), and finally re-read the same file while tracing the block layer. Figure 2 shows what happened next. The trace contains 8,002 128 KB read-ahead events, totaling ≈1 GB in 683 ms, for an observed sequential rate of about 1.43 GB/s. Once the page cache is cold, the “missing” reads become a dense sequential scan at the storage layer. This confirms the key point of the section: legacy LMCache’s zero-read appear-ance is conditional on RAM residency . The cost model is therefore bimodal: effectively zero in the warm-cache regime, but suddenly storage-bound once the working set no longer fits or host memory pressure changes. V. Current LMCache: Explicit Reads and Narrow Dedup Gains 

A. Set A becomes predictable and slower 

Set A provides the clearest contrast between the two stacks. With LMCache 0.3.16 + O_DIRECT , writes drop from 1.62 GB to 11.75 MB, i.e., about a 138 × reduction. This is the upside of prefix-aware deduplication: only the first request persists the chunk; subsequent identical requests reuse it. But Figure 1(b) shows the hidden cost of that win. The 99 warm requests trigger 9,405 reads and 1.16 GB of SSD traffic in aggregate, which is exactly 95 reads and 11.75 MB per warm request. This explicit retrieve cost also appears in user-visible latency. The archived Set A logs for the legacy stack report 27 ms mean warm TTFT, while the new stack reports 93.1 ms. The ∼66 ms gap is not a small perturbation; it is the dominant warm-path cost of forcing the retrieve through SSD on every request. Figure 3 shows that the resulting latency is nevertheless very stable after the first request. In our trace, the 99 warm requests fall mostly into the 89–105 ms range, with only a few lower outliers early in the run. This is the practical meaning of “predictability” in the title: the warm path is slower, but its variance is narrow because it no longer depends on whether the kernel still happens to cache the chunk. 

B. Why the read cost is high: partial-chunk amplification 

The most interesting mechanism is a granularity mismatch between two caches. In our setup, vLLM’s GPU prefix cache works at 16-token blocks, while LMCache persists 256-token chunk files. Set A contains only about 94 chat-template tokens, so the first 80 tokens fit into five full GPU prefix blocks, but the remaining 14-token tail does not. LMCache still stores the entire partial chunk as one file. The result is that a warm Set A request must read the full ∼12 MB chunk file from SSD even though only the tail remains logically useful after GPU prefix matching. Relative to the unmatched 14-token tail, this is about a 6.7 × read amplification. This also explains an otherwise surprising observation in Table II: Set A warm TTFT (93.1 ms) is higher than Set B warm TTFT (49.5 ms), even though Set B recomputes a much longer prompt. In our short-context regime, loading the partial chunk from SSD can cost more than simply recomputing a few hundred tokens on the GPU. Put differently, exact KV reuse is not automatically a latency win when the reused object is too coarse. 

C. Set B/C/D show dedup gains are narrow 

The remaining three workloads tell the second half of the story. Set B, Set C, and Set D write 3.97 GB, 2.03 GB, and 4.83 GB, respectively, under the new stack. These are the same order of magnitude as the legacy results. Their read volume is essentially zero because there is little or nothing to retrieve: prompt or context variation changes the chunk content and therefore the dedup key. In the new logs, these runs correspond to LMCache hit tokens: 0 on almost every request. This matters because Set B/C/D are not pathological corner cases; they are closer to common stateless production traffic than exact repetition is. Set B is particularly revealing. Even though all 100 requests share the same short context, the prompt variation is enough to move the full request into a new chunk hash, so the shared prefix is still rewritten. The new trace writes 3.97 GB in total, or about 39.7 MB per request, while reading nothing back. In effect, LMCache behaves like a write sink rather than a reuse layer. Set C and Set D complete the picture. Set C writes 2.03 GB total (∼20.3 MB per request) and sees only one 128 KB read across the whole run, which is too small to represent meaningful KV reuse. Set D is the worst case: 4.83 GB written, no reads, and warm TTFT of 59.2 ms. Together, these runs show that when prompt or context changes at short lengths, deduplication at chunk-file granularity is usually defeated before it can help. The broader implication is that LMCache’s advertised write collapse is not a property of “having dedup” in the abstract; it is a property of workloads whose repeated content survives chunking boundaries unchanged. A. The real choice is predictability versus average throughput 

The old and new stacks each solve a real problem, but not the same one. The legacy stack optimizes the common warm-cache case. If host RAM is abundant and the working set remains resident, SSD reads vanish and Set A warm TTFT stays near 27 ms. The cost is that this behavior depends on external memory conditions that LMCache does not control. When those conditions change, the flush_ram experiment shows that the read path can suddenly surface as a GB-scale storage burst. The new stack removes that external dependency. Every Set A warm request behaves similarly: about 95 submitted reads, about 11.75 MB transferred, and about 93 ms TTFT. This is worse on average in our single-user short-context setting, but more predictable for operators who care about tail latency or service-level objectives. The key insight is therefore not a version ranking. It is a cost-model distinction: 

buffered I/O hides cost opportunistically; direct I/O exposes cost deterministically. 

Table III makes this concrete on Set A, where the two stacks drive the SSD into opposite regimes from the same user-visible workload. 

B. Implications for KV-cache design 

Our results also interact with recent KV-cache research. Work on context reuse and fusion [16], [18], [19], [29], [30] implicitly assumes that loading a cached object is worthwhile once it exists. Our Set A result refines that assumption: whether loading wins depends on object granularity and the boundary between GPU-resident and storage-resident reuse. Fig. 2. If the remaining unmatched suffix is tiny, retrieving a whole partial chunk may be worse than recomputation. This suggests two concrete design directions:  

> •

Finer-grained persistence for partial tails. If LMCache could materialize only the unmatched suffix, it could preserve dedup benefits without paying full-chunk read cost.  

> •

Chunk-aware dedup and layout. Persisting shared prefixes separately from varying tails would let short stateless API traffic benefit from dedup even when only part of the request is repeated. The expected gain scales with how much of a request is shared: for Set B’s 48-token shared context ( ∼19% of a chunk), an aligned layout would save only ∼15% of the writes; but for a chunk-aligned 1024-token shared context typical of RAG, the saving jumps to ∼80%. The mechanism is therefore most valuable exactly where today’s LMCache helps least.  

> •

Hybrid compute-or-load policies. Systems like Cake [30] already argue that loading and recomputing should be co-optimized. Our measurements provide a block-level explanation for why that policy is necessary even on local SSDs. 

C. Operational takeaways 

The measurements suggest a simple decision rule based on two workload properties: repetition structure and memory slack . If the deployment mostly serves short repeated prompts on a machine with abundant host RAM and little interference, buffered I/O remains attractive because the page cache can eliminate warm reads almost completely. Our legacy Set A trace is exactly that regime: the SSD sees essentially no data reads and warm TTFT stays low. In contrast, if the operator needs a stable storage budget and stable warm latency independent of host memory pressure, O_DIRECT 

is the safer choice because it exposes the true retrieve cost upfront. A second practical lesson is that “cache hit” is too coarse a metric for SSD-backed KV reuse. Set A does hit, but the hit is expensive because the reusable object is a whole partial chunk. Set B/C/D mostly miss, but their warm TTFT is still lower than Set A because there is no retrieve path to pay. For operators, this means that hit rate must be interpreted jointly with retrieved object size . A system that reports many hit tokens can still underperform if those hits map to coarse storage objects whose load time exceeds the saved compute. Finally, the four workloads in Table I can be read as a small decision map. Exact repetition (Set A) flips the I/O pattern from “always write” to “write once, read many.” Varied traffic (Set B/C/D) remains write-dominated under both stacks, so the dominant question is whether writes should be buffered and hidden by the kernel or submitted directly and predictably. We expect the crossover point to move for longer contexts, larger shared prefixes, and chunk-boundary-aligned RAG prompts. But even without those extensions, the present results already show that SSD-backed KV reuse should be treated as a workload-specific optimization, not as a universally positive switch. VII. Conclusion This paper characterized LMCache SSD offload as asystems trade-off rather than an upgrade story. The legacy buffered-I/O path appears almost read-free only because the kernel page cache hides retrievals; once that cache is cold, the same path issues GB-scale reads. The newer O_DIRECT path makes storage traffic explicit and stable, but on short repeated prompts it pays that cost on every request, raising warm TTFT from 27 ms to 93 ms. Prefix-aware deduplication still matters, but its largest write-saving benefit is confined to exact-repeat traffic and largely disappears once prompt or context varies. The practical takeaway is: for current LMCache SSD offload, the central design question is whether the deployment values predictable latency more than average warm-path speed .Resolving the buffered-path instability in the new version is the highest-leverage next step.
