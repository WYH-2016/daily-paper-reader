## Abstract 

Approximate nearest neighbors search (ANNS) over cloud-hosted vector databases raises a critical privacy concern: the query vec-tor, which often encodes sensitive user intent, is exposed to the server. Private ANNS (PANNS) allows a client to retrieve nearest neighbors without revealing its query. The state-of-the-art single-server scheme, Pacmann (ICLR’25), achieves high accuracy via graph-based search with private information retrieval (PIR), but incurs substantial communication overhead because each PIR query retrieves only a single vertex. We present Amora , a communication-efficient PANNS system that applies SimplePIR to a partitioned graph index so that one PIR query is amortized over many vertices. To retrieve as much of the distance and neighbor information the search needs under a limited communication budget, Amora adopts a dual-PIR split layout with two heterogeneous PIR matrices that stay balanced in dimension: VecPIR retrieves inner products for an entire partition of vertices as their distance at once, while Nbr-PIR retrieves necessary neighbor lists at subgroup granularity for graph traversal. This layout shifts the cost model of PIR query from per-vertex to per-partition, which significantly reduces the com-munication overhead. To further improve efficiency by reducing the number of scans and query rounds in the PIR database, Amora 

introduces batch PIR to pack multiple queries into one matrix mul-tiplication, centroid-based pruning to filter unpromising partitions, and TopCand exploration that seeds jump-style graph navigation with the closest vertices from each retrieved partition. We evaluate 

Amora on five datasets spanning 96 to 1024 dimensions and up to 10 million vectors. Compared to Pacmann, Amora reduces online communication by 93–99% while achieving higher search accuracy.

## 1 Introduction 

Vector similarity search has become a foundational operation in modern intelligent systems, underpinning recommendation en-gines [13, 19], semantic search [40, 43], and retrieval-augmented generation (RAG) [28, 33] for large language models. At its core lies the 𝑘 -nearest neighbor search ( 𝑘 -NNS) problem: given a high-dimensional database and a query, find the 𝑘 vectors in the database closest to the query. Exact 𝑘 -NNS is prohibitively expensive at scale, so practical systems rely on approximate nearest neighbors search (ANNS), which trades a small loss in accuracy for speedups via graph-based indices [15, 25, 37, 38, 51], hash-based [17, 24], or cluster-based partitioning [7, 26]. As these ANNS systems increas-ingly migrate to cloud-hosted vector databases [27, 52], a critical privacy concern arises: the search query, which often encodes sen-sitive user intent such as medical symptoms, legal questions, or personal preferences, is transmitted to the server, exposing what the client is searching for. Private ANNS (PANNS) addresses this by allowing a client to retrieve the 𝑘 nearest neighbors of a query vector without revealing the query to the server. One line of work builds PANNS under a multi-server setting [46, 49], where the database is replicated across servers assumed not to collude. However, since the non-collusion assumption is diffi-cult to enforce in practice, clients may trust such schemes less than single-server ones. Recent single-server schemes avoid this as-sumption and fall into two families: cluster-based and graph-based schemes. Cluster-based schemes SANNS [6], Panther [35], and Tip-toe [22] group similar vectors into clusters and use oblivious RAM (ORAM) [18, 50] or private information retrieval (PIR) [12, 34, 54] to privately search the clusters whose centroids are closest to the query. However, a centroid summarizes an entire cluster, and thus can only coarsely guide nearest neighbor searches. A plaintext ANNS system compensates by searching more clusters at little ex-tra cost, but in the private setting each additional cluster costs one expensive PIR query. As a result, coarse guidance and a limited com-munication budget together leave some true neighbors in unvisited clusters, fundamentally capping accuracy. Graph-based schemes Pacmann [56] and Compass [57] instead organize the vectors into a proximity graph such as HNSW [38], in which each vertex stores one vector and its neighbor list. The search maintains a candidate set and expands the closest candidate with PIR or ORAM at each hop to protect the query privacy. The edges

Pac-mann is the state of the art for query privacy over a public database and achieves high accuracy, but it incurs substantial communication overhead in both search and preprocessing, making it impractical for bandwidth-constrained clients. This stems from Pacmann’s un-derlying PIR scheme, Piano [55], whose preprocessing requires downloading the entire database. More critically, Pacmann exhibits low information density in its online search: each PIR query incurs 

𝑂 (√𝑁 ) communication yet retrieves only a single vertex’s vector and neighbor list. We refer to this as the per-vertex cost model, and it is the fundamental source of Pacmann’s inefficiency. We observe that SimplePIR [23] offers an inherent information-density advantage. It organizes the database as a matrix in which one query retrieves an entire column, and attains the optimal com-munication on a balanced matrix. Thus, one target vertex costs the same 𝑂 (√𝑁 ) communication, and every other vertex in that column comes for free. A direct application of SimplePIR partitions the graph and stores each partition’s vertices in one column, so a single PIR query returns a group of closely connected vertices. How-ever, this naive method fails to realize the advantage. Since each vertex carries its neighbor list together with its vector for graph navigation, the two payloads make a vertex heavy and fill many entries of a single column. Such heavy payloads create a dilemma in designing the PIR matrix layout. One option is to adopt a balanced PIR matrix for the optimal communication cost. However, the heavy payloads then allow only a small number of vertices per column, so each query returns little information, and the search needs far more queries and rounds to reach high accuracy. The other option stores more vertices per column to raise the information per PIR query, but the matrix then becomes unbalanced, and every query costs more. The first challenge is therefore: C1. how to organize the PIR database so that a single PIR query carries as much useful vertex information as possible for the nearest neighbor search while keeping the optimal communication cost. Moreover, graph-based ANNS requires multi-hop traversal, and each hop invokes PIR to protect query privacy. Although SimplePIR is built on lightweight Learning with Errors (LWE) [44], each query must scan the entire database, so it incurs 𝑂 (𝑁 ) computation and makes memory band-width a bottleneck. The second challenge is therefore: C2. how to reduce the number of scans and query rounds in the PIR database to improve search efficiency. To address both challenges, we build Amora , a communication-efficient PANNS scheme with high accuracy. For C1 , our insight is that a vertex’s two payloads serve the search differently: its distance can improve the candidate set, whereas its neighbor list matters only if the search expands it. Amora therefore adopts a dual-PIR split layout that organizes the two types of payloads into two separate PIR databases with vertices grouped by graph partition: (1) VecPIR 

spreads each vertex’s vector horizontally across columns, so that each partition holds far more vectors and one PIR query computes inner products with an entire partition to return its distance to every vertex in it; (2) NbrPIR stacks neighbor lists vertically and cuts each partition into subgroups to return the neighbor lists of only the can-didates that the search expands. As a result, both PIR matrices stay balanced, and the search alternates between them. A round of PIR queries now amortizes its communication over a whole partition, which shifts the cost model from per-vertex to per-partition. As for C2 , we introduce three optimization techniques that reduce the PIR queries needed to reach a target accuracy: (1) Batch PIR merges concurrent PIR queries into a single matrix multiplication, reducing several communication rounds to one and amortizing SimplePIR’s linear database scan across queries; (2) Centroid-based pruning ranks pending partitions by the plaintext distance from the query to their centroids and processes only the most promising ones, avoiding PIR queries to distant regions; (3) TopCand exploration extracts the clos-est vertices (top candidates) from each retrieved partition as seeds in the candidate set, enabling jump-style navigation into distant regions rather than strictly following edges. In general, our contributions are as follows: 

• We design a dual-PIR split layout that combines SimplePIR with graph partitioning, storing vectors horizontally and neighbor lists in subgroup columns. Both PIR matrices stay balanced, so ev-ery PIR query keeps SimplePIR’s optimal communication, while a round of PIR queries amortizes its cost over a whole partition, shifting the cost model from per-vertex to per-partition. 

• We propose three optimization techniques to reduce rounds and database scans: batch PIR merges concurrent queries into a single matrix multiplication, centroid-based pruning ignores partitions with distant centroids, and TopCand exploration extracts seeds from each retrieved partition for jump-style graph navigation. 

• We open-source Amora 1, prove query privacy, analyze commu-nication and computation complexity, and evaluate it on five datasets spanning 96–1024 dimensions and up to 10M vectors. Compared to Pacmann, Amora reduces online communication by 93–99% while achieving higher search accuracy. 

## 2 Related Work 2.1 Approximate Nearest Neighbors Search 

Approximate nearest neighbors search (ANNS) algorithms can be broadly divided into cluster-based, hash-based and graph-based categories. Cluster-based methods such as IVF [26], ScaNN [21], and SPANN [7] partition the vector space and restrict the search to the most promising partitions. Their fixed access pattern is eas-ier to protect with PIR, but restricting search to a few clusters limits accuracy when the true neighbors span multiple partitions. Hash-based methods [17, 24] such as Locality Sensitive Hashing (LSH) [11] map vectors into hash buckets so that nearby vectors are likely to collide, offering sublinear query time with theoretical guarantees but requiring many hash tables to achieve high recall in practice. Graph-based methods build a navigable proximity graph and answer queries via greedy traversal, exploiting the small-world property to reach nearest neighbors in logarithmic hops; represen-tative schemes include NSW [37], HNSW [38], NGT [25], NSG [15], and DiskANN [51]. Graph-based methods currently achieve the best accuracy–throughput trade-off on most benchmarks, but their iter-ative, data-dependent traversal pattern makes privacy protection challenging, as each hop reveals which vertex is being accessed.

## 2.2 Private Approximate Nearest Neighbors Search 

Some PANNS works adopt a multi-server setting. Servan-Schreiber et al. [46] combine LSH with distributed point functions [4] across two non-colluding servers, and Song et al. [49] further reduce the required subsets. However, the non-collusion assumption is difficult to enforce in practice, motivating single-server approaches. Among single-server schemes, cluster-based methods appear first. SANNS [6] combines ORAM [18] and garbled circuits [53] but incurs several gigabytes of communication per query. Pan-ther [35] replaces ORAM with a co-design of batch PIR [1], secret sharing [47], and homomorphic encryption [16], reducing commu-nication while protecting both query and database privacy. Tip-toe [22] focuses on query privacy only and uses somewhat ho-momorphic encryption [5] to privately compute distances within 

𝑘 -means clusters in a single round. Wally [2] improves Tiptoe by batching anonymous queries and relaxing privacy to differential privacy [14]. However, all cluster-based schemes restrict the search to a small number of partitions and lack iterative refinement, fun-damentally limiting their accuracy. To overcome this accuracy barrier, graph-based schemes leverage multi-hop traversal. Pacmann [56] runs graph-based search using Piano PIR [55] to privately retrieve per-vertex information at each hop, achieving significantly higher accuracy than cluster-based methods. Compass [57] combines HNSW with Ring ORAM [45, 50] under a setting where the client owns the encrypted database, matching plaintext accuracy. However, both of them require signifi-cant client-side storage and communication overhead. PrivANN [8] uses a combination of ORAM and a Trusted Execution Environ-ment (TEE) [10] to provide high-accuracy and low communication PANNS, but its security assumptions rely on a TEE, which intro-duces additional side-channel attacks [30, 32, 41]. 

## 3 Background 3.1 Private Approximate Nearest Neighbors Search 

3.1.1 Approximate Nearest Neighbors Search. Given a 𝑑 -dimensional metric space with a distance function 𝑓 Δ (· , ·) and a database DB =

{® 𝑣 1, ®𝑣 2, . . . , ®𝑣 𝑁 } ⊂ R𝑑 containing 𝑁 vectors, the ANNS problem is: given a query vector ®𝑣 𝑞 ∈ R𝑑 , find an index set 𝐼 = {𝑖 1, . . . , 𝑖 𝑘 }

such that the corresponding vectors {® 𝑣 𝑖 1 , . . . , ®𝑣 𝑖 𝑘 } approximate the true 𝑘 nearest neighbors of ®𝑣 𝑞 in DB under 𝑓 Δ. The quality of the approximation is measured by Recall (the fraction of true nearest neighbors returned) or mean reciprocal rank (MRR). 

3.1.2 Graph-Based ANNS. Graph-based ANNS builds a proximity graph 𝐺 = (𝑉 , 𝐸 ) over the database, where each vertex 𝑣 ∈ 𝑉 

corresponds to a database vector and each directed edge (𝑣, 𝑢 ) ∈ 𝐸 

connects 𝑣 to one of its approximate nearest neighbors. Every vertex maintains a neighbor list of at most 𝑀 0 outgoing edges. Given a query ®𝑞 (ANNS for vector ®𝑣 𝑞 ), search proceeds by greedy traversal: starting from an entry vertex, the algorithm maintains a candidate heap W (a min-heap ordered by distance to ®𝑣 𝑞 ) and a result set R

(max-heap of capacity ef ≥ 𝑘 ). At each step, the closest unvisited vertex is popped from W, its neighbors are retrieved, their distances to ®𝑣 𝑞 are computed, and those closer than the current worst result in R are inserted into both W and R. The search terminates when 

W is empty, and the top-𝑘 entries of R are returned. 

3.1.3 Single-Server PANNS. In many applications the query vector encodes sensitive user intent and should not be revealed to the server hosting the database. The privacy requirement for a PANNS protocol focused on in this paper is query privacy only, the server learns negligible information about the query ®𝑞 , and the database is public and does not require protection. Following prior work [22, 56], we consider the single-server preprocessing model, in which the private protocol proceeds in two phases: (1) Preprocessing. The server holds the public database DB ∈

R𝑑 ×𝑁 . The client and server interact to generate a compact hint that the client stores locally for use during subsequent queries. (2) Query. The client issues a query ®𝑞 . The client and server engage in one or more rounds of communication, after which the client outputs the index set 𝐼 of 𝑘 -approximate nearest neighbors.

## 3.3 Threat Model 

Amora targets the same setting as Pacmann [56]: a single server 

S holds a public vector database DB ∈ R𝑑 ×𝑁 of 𝑁 vectors each with 𝑑 dimensions, and a stateful client C wishes to perform ANNS without revealing the query vector to the server. The database is public and does not require protection, i.e., we focus exclusively on 

query privacy . We assume the adversary is semi-honest (honest-but-curious). That is, the adversary follows the protocol specification but may attempt to learn additional information about the query from leakages. The privacy of the protocol requires that the server learns negligible information about the query ®𝑞 . Formally, we use a simulation-based definition for the privacy of the protocol: 

Definition 1 (Query Privacy). An ANNS protocol is private if there exists a simulator Sim such that for any probabilistic polynomial-time (PPT) adversary A acting as the server, the views of A in the following two experiments are computationally indistinguishable w.r.t. the security parameter 𝜆 2:

• Real: The client interacts with A ( 1𝜆 , DB ) who acts as the server. The client may issue multiple ANNS queries sequentially and each ANNS query ®𝑞 takes a series of PIR searches as input and involves multiple rounds of communication between the client and the server. After observing the transcript of previous queries, 

A may adaptively choose the next query ®𝑞 for the client. 

• Ideal: The simulated client Sim (1𝜆 , 𝑁 ) interacts with A ( 1𝜆 , DB ).

A still may adaptively choose the next query ®𝑞 . However, the simulator is invoked with only the knowledge of the database size 𝑁 , and without the information of the chosen query ®𝑞 .We note that client-side timing side channels are out of scope: a server can observe how long the client takes to respond between rounds. If needed, they can be removed by padding the client’s per-round work to a fixed budget. 

## 4 Design Overview 

Amora follows the graph-based paradigm: the client keeps a candi-date heap and, at each of a fixed number of hops, picks the vertex closest to the query and retrieves its neighbor list from the server via PIR. Each vertex therefore carries two payloads: its vector for distance computation and its neighbor list for traversal. To amor-tize one PIR query over many vertices, the direct design applies SimplePIR to a graph partitioned by METIS [29] into 𝐶 partitions of at most 𝐾 vertices each, and stores each partition’s vertices in a single column of the PIR matrix, forming the combined layout in Figure 1(a). Since a vertex carries both payloads, it fills many entries of a column, which creates a dilemma: (1) Keeping the PIR matrix balanced for the optimal communication cost limits each column to a few vertices, so one PIR query amortizes its cost over too few of them; (2) Packing more vertices per column instead makes the matrix unbalanced, raising the communication of every PIR query. The first challenge C1 is therefore: how to organize the PIR database so that a single PIR query carries as much useful vertex information as possible for the nearest neighbor search while keep-ing the optimal communication cost. Our key insight is that the search needs the two payloads in different amounts: every retrieved vertex contributes its distance, whereas only the few vertices that the search expands need their neighbor lists. The combined lay-out ignores this asymmetry by coupling one neighbor list to every vector, so each PIR query spends part of its communication budget on unnecessary neighbor lists. The two payloads therefore call for different arrangements, each retrieved at the granularity the search actually needs. Amora addresses C1 by splitting the two payloads into a dual-PIR split layout, as Figure 1(b) shows. The VecPIR matrix stores only vector information: each partition occupies a block of

𝑑 consecutive columns, and within that block every vertex takes one row, with its 𝑑 -dimensional vector spread horizontally across the 𝑑 columns. Each column then stores only one dimension per vertex, so a balanced matrix holds far more vectors per partition. One query computes inner products with all 𝐾 vertices at once, giv-ing their distances to the query. The client then selects candidates from these distances and uses NbrPIR to retrieve only the neighbor lists it needs to expand the candidates. Storing an entire partition’s neighbor lists in one column, that is, 𝐾 vertices with 𝑀 0 neighbors each, would both exceed this need and make the NbrPIR matrix highly unbalanced. We therefore organize the NbrPIR matrix into fine-grained subgroups of 𝑆 vertices within each partition, so that each subgroup occupies one column, keeping the matrix balanced. The dual-PIR layout improves the information density of PIR queries. The remaining cost is the number of scans and query rounds in the PIR database that the traversal needs, and how to reduce them is the second challenge C2 . Amora introduces three optimization techniques: (1) Batch PIR packs multiple independent PIR queries into a single matrix multiplication, reducing multiple communication rounds to one and alleviating SimplePIR’s memory-bandwidth bottleneck; (2) Centroid-based pruning ranks pending partitions by the plaintext distance from the query to their centroids and discards the distant ones, which incurs zero privacy cost since centroids are public metadata; (3) TopCand exploration extracts the 

𝑡 𝑐 closest vertices from each retrieved partition and injects them as seeds into the candidate heap, enabling jump-style graph navigation that leaps into distant regions rather than strictly following edges. The system operates in two phases. In the offline phase (exe-cuted once), the server constructs the graph index, applies graph partitioning, decomposes each partition into subgroups, and builds the VecPIR and NbrPIR databases. The server also computes the partition centroids which will be sent to the client. The server then runs Setup for each PIR module, computing hint matrices that the client downloads and stores locally. In the online phase (per query), the client first performs centroid entry: it computes ®𝑣 𝑞 ’s distance to all 𝐶 partition centroids locally and selects the 𝐾 𝑒 nearest parti-tions as entry points, requiring zero communication. The search then proceeds for 𝑇 iterations, each consisting of a batched NbrPIR 

query followed by a batched VecPIR query. Because the number of iterations and the batch sizes are determined by public system parameters, the communication pattern is identical for every query and leaks no information about the query content. Figure 2 illus-trates this two-phase workflow.

## 5.2 NbrPIR : Neighbor Retrieval 

5.2.1 Split encoding. Each neighbor is identified by its partition index 𝑐 ∈ { 0, . . . , 𝐶 − 1} and its local index ℓ ∈ { 0, . . . , 𝐾 − 1}

within that partition. Let 𝑏 ℓ = ⌈log 2 𝐾 ⌉ and 𝑏 𝑐 = ⌈log 2 𝐶 ⌉ denote the number of bits required for each field. The plaintext modulus for NbrPIR is 𝑝 𝑛 = 2𝑏 , far smaller than VecPIR ’s, so its scaling factor is correspondingly larger and NbrPIR has ample noise margin.

## 5.3 Efficient Private Search 

The dual-PIR split layout amortizes the communication of a private search: each VecPIR query returns distances to all 𝐾 vertices in a partition, and each NbrPIR query retrieves neighbor lists for all 𝑆 

vertices in a subgroup, so one round trip yields far more information than in per-vertex PIR systems. The search proceeds iteratively: pop the closest candidate from the heap, issue one NbrPIR query for its subgroup to decode its neighbors, then issue one VecPIR 

query for each neighbor’s uncached partition to obtain distances. We further improve this basic search with the following techniques. 

5.3.1 Batch PIR. The PIR database matrices db vec and db nbr can occupy multiple gigabytes of server memory, and each PIR query requires a full matrix-vector multiplication that scans the entire database. When 𝐵 PIR queries are issued independently, the server must scan the database 𝐵 times, making memory bandwidth the dominant performance bottleneck. Batch PIR addresses this by packing multiple queries into a single matrix multiplication. For 

VecPIR , to query 𝐵 𝑣 partitions {𝑐 1, . . . , 𝑐 𝐵 𝑣 } simultaneously, the client constructs a (𝐶 · 𝑑 ) × 𝐵 𝑣 query matrix 𝑄 where each column is one partition’s query vector as in Eq. (1). The server computes

5.3.2 TopCand exploration. Standard graph search navigates solely by following edges, visiting one vertex at a time. In Amora , to pro-tect the query privacy, each VecPIR query privately selects one par-tition, and the server computes the distances to all vertices inside it within a single encrypted operation. The distances to all 𝐾 vertices in the partition are thus a byproduct of one privacy-preserving query, providing a complete view of that partition without any additional queries. We call the 𝑡 𝑐 closest vertices per partition the 

TopCand (top candidates). These vertices are added to the candi-date heap W (min-heap) as additional navigation seeds, enabling jump-style exploration: the search can leap directly to promising regions of a partition without following graph edges step by step, ef-fectively supplementing neighbor-based navigation with partition-level shortcuts. The remaining 𝐾 − 𝑡 𝑐 vertices are not promoted to W (which would overwhelm subsequent NbrPIR rounds), but their distances, obtained for free from the amortized VecPIR query, are still valuable. Like standard graph search, Amora maintains W

for exploration and a result heap R (max-heap, capacity ef ) for the answer set. The graph neighbors decoded from NbrPIR and the 𝑡 𝑐 

TopCand vertices enter both W and R, while the top-𝑘 vertices in the partition enter R. These free distances tighten the admission threshold of R faster, so that fewer candidates qualify in subsequent rounds and fewer PIR queries are wasted. 

5.3.3 Centroid-based pruning. During neighbor processing, discov-ered neighbors may point to many uncached partitions. Without prioritization, all would compete for the limited VecPIR batch bud-get 𝐵 𝑣 , and distant or irrelevant partitions waste valuable slots. The saved partition centroids can naturally serve as directional indicators. Since centroids are public metadata, this sorting is performed entirely on the client without online communication. When selecting partitions for the next VecPIR batch, the sorted order ensures that the top-𝐵 𝑣 entries are always the closest parti-tions to the query, directing the communication budget toward the most promising regions. 5.3.4 Selective decryption and caching. Each NbrPIR query retrieves an entire subgroup column containing 𝑆 vertices’ neighbor data, but the search typically visits only a few vertices per subgroup. Decrypting all 𝑆 · 𝑀 0 · 𝑡 entries would waste computation. When later candidates fall into the same subgroup, the cached ciphertext is reused without additional communication.

## 7.5 Ablation Study 

7.5.1 Optimization techniques. We ablate three key optimization techniques described in §5.3 to quantify their individual contribu-tions. For each ablation, we disable one technique (denoted "w/o") while keeping all others enabled. Figure 5 reports accuracy against latency as the iteration count 𝑇 grows. 

Batch PIR reduces latency. Without batching, each PIR query occupies its own communication round, so one search iteration costs 𝐵 𝑣 + 𝐵 𝑛 rounds instead of two. At the operating points in Table 2, the unbatched search needs 9 rounds on SIFT1M, 13 on SIFT10M, 16 on Deep1M, 6 on AGNEWS, and 15 on MSMARCO, adding proportionally more RTT delays. Each unbatched round also requires an independent full database scan, whereas batching amortizes the scan across multiple queries in a single wider matrix multiplication and consumes less memory bandwidth. Across all datasets and round counts, disabling batching raises the computa-tion by 1 .4–2 .0×, and at the operating points it grows from 0.039 s to 0.059 s on SIFT1M and from 1.588 s to 3.022 s on MSMARCO. Figure 5 shows that the "w/o batch" results track Amora in accuracy but are shifted right along the latency axis. At matched accuracy, the latency rises by 1 .6–2 .3×, for example from 0.29 s to 0.51 s on SIFT1M and from 1.84 s to 3.77 s on MSMARCO. All standard devi-ations of computation and latency here are below 0 .02 s. 

TopCand exploration improves accuracy under a tight budget. 

Disabling TopCand exploration forces the search to follow graph edges only. At the operating points in Table 2, Recall@10 drops by 0.034 ±0.004 on Deep1M, 0 .018 ±0.004 on SIFT10M, and 0 .016 ±0.001 on AGNEWS, and MRR@10 drops by 0 .016 ±0.007 on MSMARCO, while on SIFT1M the gap stays within 0.007 at every round count. 

TopCand exploration seeds the candidate heap with each partition’s closest vertices, so the search reaches promising regions that the candidates’ edges cannot within the round budget. 

Centroid-based pruning improves accuracy under a tight budget. Disabling centroid-based pruning reverts to a first-come-first-served ordering with no pruning. At the operating points in Table 2, accuracy falls on all five datasets: Recall@10 by 0 .118 ±0.006 on AGNEWS, 0 .088 ±0.002 on SIFT10M, 0 .048 ±0.002 on SIFT1M, and 0 .036 ±0.004 on Deep1M, and MRR@10 by 0 .014 ±0.011 on MS-MARCO. Each round admits only 𝐵 𝑣 partitions, and centroid-based pruning directs this limited budget toward the closest partitions rather than toward whichever ones are discovered first. The gain is therefore largest under Amora ’s tight round budgets.

## 8 Conclusion 

We presented Amora , a communication-efficient PANNS system with high accuracy. The core is a dual-PIR split layout built on SimplePIR and graph partitioning: VecPIR retrieves distances to all vertices in a partition at once, and NbrPIR retrieves neighbor lists at subgroup granularity, maximizing the information retrieved per PIR query. Based on the dual-PIR, batch PIR merges concurrent queries to reduce communication rounds and the number of database scans, centroid-based pruning directs the limited PIR budget toward the most promising regions, and TopCand exploration seeds jump-style graph navigation from each retrieved partition. Experiments on five datasets of different scales and dimensionalities show that Amora 

reduces online communication by 93–99% over the competitors while achieving higher search accuracy.
