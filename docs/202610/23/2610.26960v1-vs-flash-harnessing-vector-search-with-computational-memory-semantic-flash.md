## 摘要
随着生成式人工智能持续发展，检索增强生成（RAG）系统正推动向量数据库容量需求的快速增长。当数据集规模超出主机DRAM容量时，向量数据库转而依赖基于内存映射（MMap）的SSD服务以扩展容量。然而，高扇出近似最近邻（ANN）搜索会产生大量并发且不规则的访问，导致主机内存与存储资源争用，在混合负载下降低批量吞吐量并显著增加尾部延迟。本文通过内存语义化容量扩展与面向工作负载的计算单元动态部署来应对上述挑战。VS-Flash将闪存暴露为大容量、具备内存语义的空间，并依据运行时查询特征与工作负载特性动态选择执行引擎：将面向吞吐量的大批量查询卸载至计算型内存语义闪存（CMS-Flash）设备执行，而将对延迟敏感的小批量查询保留在主机CPU上执行。两条路径均访问相同的驻留数据分段，无需在主机DRAM中维护独立副本。在三个十亿级规模数据集上的实验表明，VS-Flash相较原始Milvus平均提升批量搜索吞吐量36.8倍，最高可达57.4倍；在混合负载下，VS-Flash将延迟敏感请求的p99尾部延迟最多降低24.8倍，同时维持设备端的批量搜索能力。结果表明，VS-Flash可在突破主机DRAM容量限制的前提下，协同提升批量吞吐量与小请求尾部延迟性能。

## Abstract
As generative AI continues to evolve, retrieval-augmented generation (RAG) systems are driving rapid growth in vector database capacity requirements. As datasets outgrow host DRAM, vector databases rely on MMap-based serving over SSDs to extend capacity. However, high-fan-out ANN searches generate concurrent irregular accesses that contend for host memory and storage resources, degrading bulk throughput and inflating tail latency under mixed workloads. In this paper, we address these challenges through memory-semantic capacity and workload-aware compute placement. VS-Flash exposes flash as a large-capacity memory-semantic space and dynamically selects the execution engine according to runtime query and workload characteristics. It offloads throughput-oriented large-batch queries to a Computational Memory-Semantic Flash (CMS-Flash) device, while executing latency-sensitive small-batch queries on the host CPU. Both paths access the same resident segments, avoiding a separate host-DRAM replica. Across three billion-scale datasets, VS-Flash improves bulk-search throughput over vanilla Milvus by 36.8X on average, with up to a 57.4X improvement. Under mixed workloads, VS-Flash reduces the p99 latency of latency-sensitive requests by up to 24.8X while sustaining device-side bulk search. These results show that VS-Flash delivers scalable vector search beyond host DRAM capacity while jointly improving bulk throughput and small-request tail latency.

## 1. 核心问题与整体含义（研究动机和背景）

- **根本挑战**：随着 RAG 系统爆发式增长，向量数据库规模远超单节点主机 DRAM 容量（如百 GB → 数 TB），传统依赖 `mmap` + SSD 的方案在高扇出近似最近邻（ANN）搜索下遭遇严重性能瓶颈。  
- **关键症结**：  
  - 高并发、不规则的图遍历（如 HNSW）引发频繁页错误（page fault）与页缓存抖动（page-cache thrashing）；  
  - 主机 DRAM、TLB、I/O 带宽成为共享瓶颈，导致**吞吐型大批次查询**（如 batch-600）与**延迟敏感型小批次查询**（如 batch-25）相互干扰；  
  - 混合负载下出现“大压小”现象：p99 尾延迟随后台批量负载增加而指数级恶化（图2b），最高达 326× 增长。  
- **整体含义**：VS-Flash 并非改进 ANN 算法本身，而是重构**存储-计算协同范式**——将闪存升格为“内存语义容量层”，通过硬件感知的执行路径分离，在**不牺牲召回率、不修改索引结构**的前提下，实现容量扩展、吞吐提升与尾延迟保护的三重协同优化。

## 2. 方法论：核心思想与关键技术细节

- **核心思想**：  
  > **“段级驻留 + 双路径动态路由 + 共享内存语义”**  
  > ——以 segment 为最小调度单元，统一数据视图，按需分流计算，消除冗余副本与跨域搬运。

- **关键技术细节**：  
  - **Memory-Semantic Flash 抽象**：  
    利用 CXL Type-3 设备（XCENA MX1P）将 NVMe 闪存+设备 DRAM+RISC-V 多核封装为单一内存语义地址空间，主机 CPU 与设备核均可通过 CXL 直接访问同一段数据（无需 memcpy 或格式转换）。  
  - **Segment-Oriented Preloading（段级预载）**：  
    放弃细粒度 demand paging，改为整段（默认 1 GB）预加载至设备 DRAM；Preload Manager 维护段级等待队列，并通过**自适应前摄窗口（Look-Ahead Window）控制器**动态调节预载深度 *N*（如 *N*=4 最优），确保设备核始终有数据可算，避免 starvation。  
  - **Batch-Aware Dual-Path Routing（批大小感知双路径）**：  
    - **Device Path（CMS-Flash）**：batch size > *T*（初始 *T*=25）→ 卸载至 RISC-V 多核并行执行子搜索（query-segment pair），仅回传 per-segment top-k 结果（不传原始向量/索引页）；  
    - **Host CPU Path**：batch size ≤ *T* → 由主机 CPU 执行，直接访问 CXL 映射的同一 resident segment；  
    - **动态阈值 *T***：Batch Dispatcher 实时监控 RISC-V 核利用率（>80%）与主机 CPU 空闲状态，自动下调 *T*，仅将最小 pending batch 导流至 CPU，最小化干扰。  
  - **无副本共享机制**：因 CXL 提供统一地址空间，host 与 device 共享 segment 内存布局（ANN index + vector payload），彻底规避 host-DRAM replica 开销。

## 6. 主要结论与发现

- VS-Flash 在**突破 DRAM 容量约束**前提下，首次实现：  
  - **吞吐与延迟的协同优化**：平均 bulk-throughput 提升 **36.8×**（最高 **57.4×**），同时 p99 延迟降低 **24.8×**；  
  - **资源解耦有效性**：双路径隔离使大批次负载无法挤压小批次响应，且小批次导流反而提升设备核利用率（减少 queue blocking）；  
  - **硬件协同价值**：CXL 共享内存语义是零拷贝双路径的基础；RISC-V 多核适合高并行低单核强度任务（如 Deep1B 中 HNSW traversal 占主导）；  
  - **自适应策略鲁棒性**：Look-Ahead 控制器收敛至最优 *N*=4，性能达手动调优的 **93.9%**（相差仅 6.1%），无需离线 tuning。

## 7. 优点

- ✅ **问题定位精准**：直击 mmap 在 ANN 场景下的结构性缺陷（不规则访问 × 共享缓存），而非泛泛优化 I/O；  
- ✅ **架构简洁高效**：不修改 ANN 算法/索引结构，兼容现有 Milvus 生态，部署成本低；  
- ✅ **设计正交解耦**：段预载（数据移动）、双路径（计算放置）、自适应路由（策略控制）三层职责清晰，易于模块化验证；  
- ✅ **硬件特性深度利用**：CXL 内存语义 + RISC-V 多核 + 闪存容量三位一体，体现“Near-Data Computing”在向量检索中的新范式；  
- ✅ **工程务实性强**：所有优化均在真实硬件（XCENA MX1P）上实测，非仿真或理论推导。

## 8. 不足与局限

- ❌ **索引类型覆盖有限**：仅验证 HNSW，未测试 IVF-PQ、DiskANN 等磁盘友好型索引，其对预载粒度/带宽需求可能不同；  
- ❌ **部署场景受限**：当前为单 Query Node 架构，未验证在 Milvus 分布式集群（multi-node, multi-query-node）中段预载一致性、跨节点路由协调等挑战；  
- ❌ **硬件依赖性强**：高度依赖 CXL Type-3 设备（目前商用生态尚不成熟），缺乏对 PCIe/NVMe-only 平台的兼容方案；  
- ❌ **小批量定义主观**：路由阈值 *T* 以 batch size 为判据，但实际延迟敏感性还取决于向量维度、top-k、ef 参数等，未引入更细粒度特征（如 query complexity estimation）；  
- ❌ **长期稳定性未验证**：未报告长时间运行（如 7×24h）下的段预载老化、设备 DRAM 碎片、flash wear-leveling 对性能的影响。
