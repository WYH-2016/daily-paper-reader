Abstract —Top-Down Microarchitecture Analysis (TMA) is the standard for identifying CPU bottlenecks. However, TMA implicitly models performance via asingle causal path: Workload(dataset, algorithm) ⇒

CPU(CPI) ⇒ System(Performance) (microarchitectural efficiency path). It overlooks two hidden causal paths: Workload(dataset, algorithm) ⇒ Instructions(Retired) ⇒

System(Performance) (algorithmic efficiency path) and Workload(dataset, algorithm) ⇒ Instructions(Retired) ⇒

CPU(CPI) ⇒ System(Performance) (microarchitecture-algorithm efficiency path). This causal blindness often misleads architects into futile hardware optimizations. To address this, we propose Causal Top-Down Microarchitecture Analysis (CTMA). Utilizing the object causal model, CTMA explicitly models these three causal paths among the workload, instructions, CPU, and system. We validate CTMA across Intel, AMD, and ARM plat-forms. Our experiments reveal counterintuitive insights: (1) CPI Profiling Blindness : Algorithmic instruction bloat can double elapsed time while the CPI profile remains frozen. (2) Over-Speculation Congestion : Throttling the Frontend paradoxically improves performance in pointer-chasing algorithms. (3) ILP Window Collapse : Extreme data topologies shift bottlenecks from Backend ROB capacity to Frontend fill-rate starvation. (4) Op-Cache SMT Overlap : Ultra-small footprints yield SMT speedups on Intel but cause severe thrashing on AMD. (5) “Ghost State” Artifact : Stale pipeline mitigations on Intel Xeon Gold 5120T artificially boost performance by 22.75% on SPEC CPU2017 and 42.2% on SPEC CPU2026. Based on this, we propose a dynamic speculation throttling mechanism. 

I. I NTRODUCTION 

Modern processor design and optimization heavily rely on Top-Down Microarchitecture Analysis (TMA). By cat-egorizing CPU pipeline slots into Frontend Bound, Back-end Bound, Retiring, and Bad Speculation, TMA pro-vides a clear snapshot of pipeline bottlenecks and guides pipeline efficiency optimizations (i.e., minimizing CPI). Viewed through the lens of causal modeling, TMA im-plicitly models performance via a single, oversimplified causal path: Workload(dataset, algorithm) ⇒ CPU(CPI) ⇒

System(Performance) . In this article, we use the object causal model (OCM) in Evaluatologly as the causal modeling language and methodology [43], [44]. Here, the causal path 

A(p) ⇒ B(q) denotes that object A (via its property (observed metric) or mechanism p) causally impacts object B (altering its property or mechanism q). By fixing the workload inputs, traditional TMA tacitly assume the workload emits a static stream of instructions, placing the root cause of performance variations squarely on the CPU’s microarchitectural efficiency (e.g., CPI). This oversimplified causal path creates severe “causal blindness,” completely ignoring two hidden but critical causal paths. Real-world workloads are algorithmically dynamic: as the topology, distribution, or locality of input dataset changes, algorithms adapt, causing pipeline bottlenecks to drift significantly. This activates two completely hid-den causal paths. First, the Algorithmic Efficiency Path :

Workload(dataset, algorithm) ⇒ Instructions(Retired) ⇒

System(Performance) , where algorithmic instructions bloat can silently drastically alter elapsed time while the CPU’s CPI remains perfectly stable (Details in Section III-B). Second, the Microarchitecture-Algorithm Efficiency Path :

Workload(dataset, algorithm) ⇒ Instructions(Retired) ⇒

CPU(CPI) ⇒ System(Performance) , where changes in instructions volume can fundamentally reshape microarchi-tectural states, artificially altering the CPI (Details in Sec-tion III-E). Ignoring these paths would trick architects into optimizing hardware for what are essentially software anoma-lies. To address this critical flaw, we introduce a Causal Top-Down Microarchitecture Analysis (CTMA) . CTMA aims to infer unconfounded architecture insights that can be extended to real-world settings. In the rest of this article, we use the term treatment to describe the change of a target object while keeping the others the same to understand its causal effect. As shown in Figure 1, instead of passively profiling the static workload configuration, CTMA intentionally generates and profiles several workload configuration treatments by mu-tating specific algorithmic traits (e.g., graph randomness, re-cursion depth, spatial locality) to expose the TMA-overlooked Algorithmic Efficiency Path and Microarchitecture-Algorithm Efficiency Path. This treatment is to model how the algorithm adapt, and how the pipeline bottlenecks transit shift as the topology, distribution, or locality of input dataset changes. Meanwhile, CTMA uses non-invasive hardware treatments to establish unconfounded baselines on real silicon across three major microarchitectural platforms (Intel, AMD, ARM). With the cross-validation of hardware treatments and/or workload configu-ration treatments, CTMA validates all exposed causal paths. By exposing and controlling the aforementioned three causal paths, CTMA can infer unconfounded architecture insights that can be applied to real-world settings. Utilizing CTMA, we have achieved five counter-intuitive architectural insights. 

• CPI Profiling Blindness (the leela r workload from SPEC CPU2017): We prove the existence of “Algorithmic In-structions Bloat,” where modifying spatial locality of the dataset causes a more than 100% elapsed time variation while leaving the CPI profile completely frozen. Cross-ISA validation confirmed a universal mathematical con-stant of 2.06 × instructions inflation, effectively proving that microarchitectural tuning is futile against algorithmic degradation. 

• Over-Speculation Congestion (mcf r): In pointer-chasing algorithms, highly regular data improves branch pre-diction but halves performance. Aggressive speculation continuously pushes memory requests into the Backend, overflowing the Line Fill Buffers and causing memory controller congestion. Manually throttling the pipeline by injecting NOP instructions alleviates this traffic jam and slightly improves performance. 

• ILP Window Collapse (cactuBSSN r): Spatial topol-ogy distortion causes dense short-loops and frequent branch mispredictions. By using SMT to partition the Reorder Buffer (ROB) via pause process, we found that the perfect-topology datasets suffer severe degradation (∼23% on the Intel Platform and ∼12% on the AMD Platform), while distorted datasets are relatively immune (∼9% on the Intel Platform and ∼10% on the AMD Platform). This indicates that extreme dataset distortion shifts the bottleneck from ROB capacity to dynamic fill-rate, rendering deep out-of-order Backend useless. 

• Op-Cache SMT Overlap (xalancbmk r): Deep recursion causes severe Frontend Bandwidth bottlenecks. Tradition-ally, co-running two identical copies of the workload on the two SMT sibling logical cores worsens Frontend contention. However, when the recursion’s instructions footprint is extremely small, it resides perfectly within Intel’s Decoded Stream Buffer (DSB), enabling cycle-level overlapping and yielding SMT speedups. In con-trast, AMD Zen3 suffers more than 50% degradation, exposing rigid Op-cache sharing policies. 

• “Ghost State” artifact on the Intel Xeon Gold 5120T: We discovered that forcefully terminating (via kill -9 )an SMT sibling process without an OS-level microar-chitectural flush leaves the CPU pipeline in a highly aggressive state, resulting in an average of 22.75% artifi-cial performance boost on SPEC CPU2017 and 42.20% performance boost on SPEC CPU2026. This exposes a critical measurement artifact linked to spectre v2 mitiga-tion toggles on specific unbalanced-designed CPUs. We propose a dynamic speculation throttling mechanism for real-time congestion control in the next-generation CPU. Our contributions are summarized as follows. 1) For the first time, we introduce the causal modeling methodology, specifically, the object causal model in architecture research. 2) We expose that TMA based on static workload evalua-tion severs causal blindness and completely ignores two hidden but critical causal paths. 3) We introduce a Causal Top-Down Microarchitecture Analysis framework, bridging the semantic gap between algorithmic data treatment and microarchitectural hard-ware behavior. We open source our workload configu-ration treatment tools for SPEC CPU2017. 4) We provide empirical evidence of counter-intuitive hard-ware behaviors across three major microarchitectural platforms: CPI Profiling Blindness, Over-Speculation Congestion, ILP Window Collapse, and Op-Cache SMT Overlap. 5) Based on the “Ghost State” and over-speculation dis-coveries, we offer actionable architectural recommenda-2tions, proposing a dynamic speculation throttling mech-anism to online throttle pipelines for CPU design. Section V shows the evaluation, and Section VI concludes and discusses our future work. II. B ACKGROUND AND RELATED WORK 

To fully comprehend the dynamic interplay between soft-ware workloads and hardware pipelines, it is essential to establish the foundational concepts of modern performance analysis and causal inference. This section introduces the terminology and highlights the systemic causal gaps in current benchmarking methodologies. 

A. Traditional Benchmarking and Top-Down Analysis 

Traditional Benchmarking Paradigms. Computer archi-tecture heavily relies on empirical methodologies, utilizing benchmark suites [3], [6], [7], [10], [12], [14]–[17], [20], [24], [28]–[30], [39], [40] (e.g., SPEC CPU [31]–[37], PARSEC [5], [6], [45], SPLASH [40]) to proxy real-world performance. The canonical approach aggregates execution outcomes across predefined, static system configurations to yield a synthesized metric (e.g., the SPEC score). 

The Top-Down Microarchitecture Analysis (TMA). To understand why a CPU achieves a certain score on the given benchmark, the industry standard is Intel’s Top-Down Mi-croarchitecture Analysis (TMA) [41]. By utilizing Hardware Performance Counters (PMUs) [1], [2], [21], [24], [39], TMA classifies CPU pipeline stalls into a hierarchical tree: Frontend Bound, Backend Bound, Bad Speculation, and Retiring. While TMA is a powerful “speedometer” that accurately measures the pipeline efficiency (e.g., CPI), it inherently treats the workload configuration as a static entity. It provides a snapshot of the hardware’s status but lacks the mechanism to trace performance variations back to shifts in the input data or algorithmic adaptations. 

B. Bridging Algorithm and Microarchitecture 

To break down the system performance, we must explicitly decouple the software algorithmic behavior from hardware ex-ecution efficiency based on the Iron Law of Performance [13]: 

Elapsed T ime = Retired Instructions ×CP I F requency . We define two key architectural concepts pivotal to our later analysis. 

Algorithmic Instructions Bloat. This occurs when achange in the input dataset’s distribution (e.g., spatial locality) forces the software algorithm to take a longer execution path (e.g., traversing deeper search trees). The total retired instruc-tions ( Retired Ins ) surge exponentially, increasing elapsed time, even if the hardware CP I remains perfectly stable.

C. Causal Inference and the Object Causal Model 

To rigorously model complex system interactions, we es-tablish our framework on the foundational concepts of cause and effect. Traditional Structural Causal Model (SCM) [18], [26], [27] formalize causal relationships (Cause A → Effect 

B) between variables A and B. Recent hardware bottleneck quantification frameworks [11], [23] can be viewed as domain-specific instantiations of these variable-level causal models. However, computer architecture operates across abstracted, hierarchical objects (e.g., Workload, Instructions, and CPU). Purely observation-based, variable-driven SCM often fail to capture interactions across structural depth. To bridge this semantic gap, Zhan et al. [42], [43] introduced 

Evaluatology and the object causal model (OCM) . Unlike SCM, OCM centers its modeling on system objects (Evaluated Object EO ⇒ Affected Object AO ), characterized by their in-ternal mechanisms and properties (observable metric) . Within a Self-Contained System (SCS) [38], [43], we can model performance evaluation across four fundamental interacting objects, identifying the dominant causal path among complex interactions: 1) Workload Object: Its underlying algorithm serves as the mechanism, and the configuration parameters (e.g., dataset) represent its observable properties. 2) Instructions Object: Represents the compiled instruc-tion execution trace. Its observable property is the Re-tired Instructions Count .3) CPU Object: The microarchitecture. Its mechanism is the out-of-order pipeline and microarchitectural behavior (e.g., branch predictor behavior), and its observable properties are the efficiency metric ( CPI ) and behavior metric (e.g., Branch MPKI ). 4) System Object: The overarching computer system, with

III. M OTIVATION : T HE PITFALLS OF TRADITIONAL TMA 

A. The Causal Blindness of TMA 

The fundamental goal of CPU design and optimization is to reduce elapsed time. The classic performance equation dictates that Elapsed T ime = Retired Instructions ×CP I F requency .The Top-Down Microarchitecture Analysis (TMA) attempts to optimize this equation by breaking down pipeline stalls to minimize the CPI. However, the community predomi-nantly evaluates TMA using statically prescribed workload configurations (e.g., SPEC CPU ref inputs). This implic-itly models performance through a single explicit causal path: Workload(dataset, algorithm) ⇒ CPU(CPI) ⇒

System(Performance) . Because TMA only profiles microar-chitectural efficiency (the property of the CPU object), it blindly assumes that the workload emits an invariant stream of instructions on the given static configuration. Consequently, performance variations are strictly dictated by how fast the CPU processes that work. However, from an OCM perspective, this single-path model is fundamentally incomplete and misleading. Real-world appli-cations dynamically adapt to data space properties. Changing the workload activates two entirely overlooked causal paths that completely bypass or perturb the CPU’s CPI. 1) The Algo-rithmic Efficiency Path (Workload(dataset, algorithm) ⇒

Instructions(Retired) ⇒ System(Performance)): Variations in data topology can dictate the algorithm’s execution depth (e.g., algorithmic instruction bloat). This path can double elapsed time while the CPU’s CPI remains perfectly sta-ble. 2) The Microarchitecture-Algorithm Efficiency Path (Workload(dataset, algorithm) ⇒ Instructions(Retired) ⇒

CPU(CPI) ⇒ System(Performance)): An exponential surge in instructions volume can fundamentally alter the execution footprint (e.g., shrinking entirely into the Op-cache). The algorithmic scale dynamically reshapes the hardware state, causing an artificial shift in CPI. In the rest of this section, we apply treatment to four diverse SPEC CPU2017 workloads on the Intel Gold 5120T Machine in Table I. For each workload, as shown in Table II, we strictly fix the absolute data scale (e.g., total nodes, grid volume, or file size) same as SPEC ref to ensure an “apples-to-apples” comparison. We then actively mutate specific treatment (e.g., spatial locality, structural randomness) to generate orthogonal extreme datasets (denoted as Q1-Q4) and smooth parameter gradients (Grad-0.1 to 0.9). By doing so, we activate the TMA-overlooked causal paths ( Workload(dataset, algorithm) ⇒

F. Summary: The Need for Causal TMA 

These four cases demonstrate that TMA snapshots suffer from severe causal blindness. This blindness is why relying solely on TMA is dangerous—it inevitably misleads architects into optimizing hardware for what are essentially software anomalies (e.g., blindly expanding ROB capacity for cactuB-SSN r when it is fill-rate-bound). IV. T HE CAUSAL TOP -D OWN MICROARCHITECTURE 

ANALYSIS (CTMA) As demonstrated in Section III, traditional TMA suffers from causal blindness when algorithmic-related causal paths dynamically adapt. To systematically decouple these complex system interactions, we propose Causal Top-Down Microar-chitecture Analysis (CTMA) .Rather than a rigid set of specific experimental steps, CTMA is designed as a generalized, plug-and-play framework based on the object causal model (OCM). As illustrated in Figure 6, it establishes a tight feedback loop between System object and a casual modeling and performance profiling engine. Instead of passively profiling a static workload, CTMA explicitly defines 6two abstract treatment interfaces: the Software Interface 

(intervening on the Workload Object ) and the Hardware Interface (intervening on the CPU Object ). This framework identifies and models dynamic bottleneck migrations and rigorously cross-validates the modeled causal paths. CTMA operates in three fundamental phases. 

A. Phase I: The Software Interface (Intervening on the Work-load Object) 

The first phase aims to activate the hidden causal paths overlooked by TMA by systematically intervening the Work-load Object . In the OCM paradigm, a workload’s underlying algorithm acts as its mechanism, and its configuration param-eters act as its properties. Therefore, the Software Interface is designed to mutate the workload properties (e.g., s, compiler flags, concurrency) to trigger dynamic algorithmic adaptations. To ensure scientific rigor, this phase operates strictly around an anchor point: the “Default Configuration” (e.g., the official SPEC ref inputs). We generate a spectrum of “Treat-ment Configurations” by dialing specific workload properties (e.g., spatial locality of dataset) known to change algorithmic instructions behaviors and stress microarchitectural bottle-necks, while strictly preserving other properties same with the default. 

Our Reference Implementation: In this article, we imple-ment the Software Interface via DataSet Treatment . To main-tain the “apples-to-apples” anchor, we fix the absolute data scale (e.g., maintaining exactly 84 3 vertices in cactuBSSN r ,or 600 moves in leela r ). By keeping the total scale constant while morphing its topological distribution, any fluctuation in the retired instructions is definitively isolated as an algorithmic adaptation (e.g., boundary pruning), rather than a trivial change in raw input size. 

B. Phase II: Dynamic Bottleneck Analysis (Using OCM for Causal Modeling and Performance Profiling) 

Once the treated Workload Objects are compiled to Instruc-tions Objects and applied to the CPU Objects, the resulting computer system (System Objects) yield performance profiles. Then CTMA transitions to causal modeling (right side of Figure 6). Unlike traditional TMA that collapses all system be-haviors into an opaque overall system metric (CPI or Elapsed Time), CTMA utilizes the object causal model (OCM) to track interactions across the four fundamental system objects: Workload, Instructions, CPU, and System. By mapping the bottleneck migration across treated configurations, CTMA models three distinct causal paths. 1) Workload(dataset, algorithm) ⇒ CPU(CPI) ⇒

System(Performance) : The traditional microarchitectural efficiency path. Variations in input data directly alter hardware behavior (e.g., spatial distortion destroying prefetcher strides). 2) Workload(dataset, algorithm) ⇒

Instructions(Retired) ⇒ System(Performance) : The algorithmic efficiency path. This formalizes how algorithmic instructions bloat dictates elapsed time, successfully explaining why performance plummets even when pipeline efficiency (CPI) remains completely frozen (as seen in Figure 2 and Figure 7). 3)

CPU(CPI) ⇒ System(Performance) : The microarchitecture-algorithm efficiency path. Changes in instructions volume can fundamentally alter the execution footprint (e.g., shrinking entirely into the Op-cache), thereby artificially inflating the CPU’s pipeline efficiency. These decoupled causal paths provide a robust, mathematical blueprint of the real-world system constraints, transcending the “black-box” nature of traditional TMA under the static workload configuration. 

C. Phase III: The Hardware Interface (Cross-Validation on the CPU Object) 

The final phase addresses a profound challenge in sys-tems research: validating theoretical model predictions against physical execution. To prevent correlational illusions, CTMA implements a “Cross-validation” loop using Treatment Hard-ware Probes .As a generalized plug-and-play framework, the Hardware Interface of CTMA accepts any mechanism capable of probing or constraining the CPU Object . Traditional Top-Down Microarchitecture Analysis (TMA) suffers from causal blindness . By profiling static workloads, it blindly attributes performance variations solely to microarchi-tectural efficiency (CPI), fundamentally ignoring algorithmic instructions bloat and dynamic bottleneck migrations. To cure this causal blindness, we proposed Causal TMA (CTMA) . Grounded in the object causal model (OCM), CTMA pairs software treatments with hardware probe (e.g., core frequency clamping, SMT resource partitioning) cross-validation across Intel, AMD, and ARM platforms. We systematically proved that predictable data triggers “Over-Speculation Congestion,” geometric distortions shift pipelines from capacity-bound to fill-rate-bound, and Op-cache foot-prints dictate SMT overlap. Furthermore, uncovering an av-erage of 42.20% performance boost of the “Ghost State” artifact exposed the severe penalties of unbalanced pipelines. Ultimately, CTMA prevents architects from falling into corre-lational traps and optimizing the wrong bottlenecks. 11 CTMA lays the groundwork for a new performance analysis and CPU DSE paradigm. We plan to extend this work in below directions: 1) Simulator Integration: Extending our hardware probing interface to simulators for register-level causal interventions beyond the limits of commercial silicon. 2) Dynamic Speculation Throttling: Developing closed-loop hardware controllers that dynamically regulate Frontend dispatch based on Backend congestion, achieving pipeline balance without expanding pipeline buffer.
