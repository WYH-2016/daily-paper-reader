# CMM-MP: A Novel Memory Pooling Architecture using Purpose-built Memory Device with CXL and Ethernet 

Michael Wasef, Gongjin Sun, Edmund Au, Ranjitha Gopalakrishna, Elham Movahedian, Dongyang Li, Senthil Murugesapandian, Caroline Kahn, Shuyu Lyu, Brian Luu, Jason Scott, Namita Kumar, Mehdi Nik, Kwan Huen, Xuebin Yao, Amir Beygi, Luis Vitorio Cargnini, Member, IEEE , Ramdas Kachare 

Abstract —CXL Memory Module – Memory Pooling (CMM-MP) introduces a novel memory pooling architecture to meet the unique requirements of emerging memory-intensive workloads. This industry-first, purpose-built memory-pooling device combines the benefits of Compute Express Link (CXL) with the scalability and cost advantages of Ethernet. Multiple CMM-MP devices together provide a flexible, composable, and disaggregated memory expansion solution. The CMM-MP enables 100s of TB capacity for GPU/CPU applications without modifications. The memory pool is exposed as a large-capacity logical aggregate memory, with all pool discovery, composition, and backend network datapath tasks fully offloaded to the device. CMM-MP supports both memory pooling and sharing usage modes. It provides an application latency of 2.7 us and up to 23 GB/s of memory throughput. Our evaluations demonstrate that CMM-MP significantly outperforms RDMA-based solutions in latency and throughput. We also evaluated real-world use cases of Valkey+YCSB and DiskANN using CMM-MP. 

Index Terms —CXL, Memory Pooling, Disaggregated memory, Ethernet 

I. I NTRODUCTION 

# THE rapid growth of memory-intensive applications in modern datacenters, including machine learning, graph processing, cloud-native services, and large language models, has intensified the demand for large, adaptable memory capac-ity [1]. Conventional server architectures limit the amount of memory available to the running applications. The current sys-tem architectures lead to underutilization and memory scarcity, depending on the application workload [2]. As workloads evolve, it is difficult to predict the proper memory capacity requirements in advance. Power, space, and thermal constraints limit the ability to scale memory independently [3], [4]. As a result, applications whose peak memory requirements exceed the limits of a single node are poorly served by the traditional tightly integrated memory model. Another challenge for data center operators is efficiently sharing idle or lightly loaded server memory with other hosts without compromising perfor-mance, thereby impacting the overall TCO of data centers [5]. Memory disaggregation has been pursued through a vari-ety of technologies, including RDMA, CXL, and proprietary technologies. A common technique for memory pooling is Remote Direct Memory Access (RDMA) [14]. RDMA can provide scale and capacity for memory resources. However, it incurs the over-head of explicit remote-memory calls and intrusive software changes [15], [16]. The RDMA approach has improved latency and throughput in key-value systems [17]. Aggregating DRAM from multiple servers into a shared pool accessible via RDMA is shown to improve the performance of remote memory [18]. As for the CXL solutions [6], they can overcome the software complexity of RDMA by offering native load/store semantics [13] seamlessly to unmodified applications [19], remaining confined to rack-level deployments. Memory pool-ing through a dedicated CXL switch is another solution [20], [21] that enables memory expansion and improves coherence, but it has limited scalability, higher cost, and deployment constraints. Efforts have been made to extend the CXL switch architecture with an external memory controller [5] to meet cloud performance requirements and reduce memory costs. Another solution introduced for CXL2.0 uses the Multi-Logical Device (MLD) [22] feature with the CXL switch. It provides transparent, cache-line-granular memory sharing across hosts. However, this approach is limited by physical reach (rack-scale only), switching latency, higher costs, and scalability challenges. The CXL MLD concept later evolved into a Multi-Headed Device in CXL 3.0 [12], effectively eliminating the physical CXL switch. It enables a single memory device to expose multiple memory channels to the shared pool, but the physical reach limitation remains. Hybrid designs that combine CXL and RDMA [23] aim to capture the best of both worlds, yet they still inherit RDMA’s overheads and the complexity of an additional soft-ware layer on the host, preventing a seamless, transparent memory-pooling solution. Another CXL memory approach is CXL Memory Module -Hybrid (CMM-H). It combines DRAM and NAND memory to 3

provide a low-cost, large capacity memory expansion solution [24] , [25] . This approach provides a large memory capacity, but it does not support the memory sharing feature. CXL-over-Ethernet [26] is yet another approach that pre-serves the low-latency benefits of CXL for individual remote accesses but does not provide a genuine pooled memory accessible by multiple servers. Other approaches have attempted to reuse existing intercon-nects. For example, connecting two CPUs via the Ultra Path Interconnect (UPI) [27] and Ethernet [28] enables memory sharing within a single server but is limited in scalability, short-range, and consumes high power. A. Memory Pool Address Resolution 

The CMM-MP device performs a critical function: mapping and translating host addresses to appropriate internal pool memory addresses. This allows participating hosts to share a common, consistent view of the pool memory address range, which enables seamless access. This process is shown in Figure 6. Each CMM-MP device on a server node advertises the entire pool capacity to the host. During server boot, BIOS/UEFI maps the advertised pool capacity to the system memory map. The physical base address of the mapped pool memory is programmed to the Host Managed Device Memory (HDM) Base Address register of the device. During runtime, when applications access the allocated pool memory, those memory requests are fulfilled via the CMM-MP device. The Host address (HA) range of these memory requests is from HDM Base to HDM Base + Pool Capacity. The Normalized Host address (NHA), that spans from zero to the pool capacity (logical address), is determined as follows: 

N HA = HA − HDM Base (1) The next step is to locate the data corresponding to this normalized host address. This is achieved by looking up NHA in the Pool Address Map Table (PAMT). PAMT contains 4K entries of configurable granularity (e.g., 1GB, 4GB, ... up to 64GB). Using 64 GB granularity as an example, the pool can reach a maximum capacity of 256 TB. As shown in Figure 6, a 12-bit index is used to look up the PAMT entry corresponding to the normalized host address. The valid PAMT entry provides two pieces of information: 1) Device ID, and 2) Device Pool Offset. The PAMT Device ID is used to route traffic to the target device. The Device Pool Offset is used to determine the memory offset within the target device memory.

C. Ethernet Subsystem 

The Ethernet subsystem provides a data transport service for memory pool operation. It implements three logical layers: the Transport Layer, the Data Link Layer, and the Physical Layer. It enables a host to access data on remote devices in the memory pool. Additionally, ARM firmware uses this sub-system to exchange control packets among the pool memory devices. It implements essential network reliability functions to provide lossless, high-throughput, low-latency data trans-port. The Ethernet subsystem ensures end-to-end reliability through automatic retransmission, duplicate-packet handling, and packet-loss detection and recovery. This provides robust and predictable data movement across the memory pool fabric. Figure 8 shows the micro-architecture of the Ethernet subsys-tem. E. ARM Subsystem 

The ARM subsystem functions as the control plane of the disaggregated memory pool. CMM-MP firmware performs autonomous pool device discovery, pool memory map com-position, and datapath configuration without host intervention. This subsystem comprises an ARM CPU core, a CXL General-Purpose Control and Status Register (GP-CSR) interface, and an Ethernet Packet interface module, as shown in Figure 15. IV. H OST INTERFACE 

This section describes the software interface and the mem-ory allocation process for CMM-MP. CMM-MP advertises the pool memory as CXL Type 3, NUMA memory to the Host. Hosts can use CMM-MP as a memory resource in pooling, sharing, or both modes simultaneously. In pooling mode, all or part of the pool memory can be allocated to one or more hosts for exclusive access. Multiple hosts can access their allocated memory concurrently from the pool. In the sharing mode, an allocated pool memory address range can be accessed concurrently by multiple Hosts. When pool memory is used as shared memory, CMM-MP devices guaran-tee atomicity of host accesses, but not the order of execution of host requests. For this reason, data coherency must be handled by the upper-layer software in the relevant hosts, if necessary. Such shared memory can be used in common usage modes such as producer-consumer and writer-reader, with explicit out-of-band synchronization and communication between participating hosts. We developed a host management utility called Memory Pool Control (mpctl). It runs on each host and facilitates online or offline allocation of the memory pool segments. VIII. C ONCLUSION 

In this paper, we propose CMM-MP, a highly cost-effective yet scalable memory pooling architecture. To the best of our knowledge, we have developed an industry-first, purpose-built memory pooling device that enables flexible and scalable compute and memory disaggregation. CMM-MP requires no application changes to utilize the memory pool and preserves traditional software interfaces such as load/store, devdax, and fsdax. This architecture offloads and abstracts all the memory pool composition and management functions from the Host OS to the device. The CMM-MP device effectively uses Ethernet to connect multiple memory devices on the backend while presenting a standard CXL Type 3 memory interface to the host. Our experiments demonstrate that CMM-MP can provide an easy-to-use solution compared to tradi-tional RDMA-based solutions, while delivering significantly lower latency and higher throughput. CMM-MP provides a practical, cost-effective foundation for future memory-centric data centers. Our future work will focus on developing more advanced features. We plan to support emerging scale-up and scale-out backend protocols, such as Ethernet Scale Up Network (ESUN), Scale Up Ethernet - Transport (SUE-T), 11 

Ultra Accelerator Link (UALink), and Ultra Ethernet (UE), for efficient, high-bandwidth data transfers to xPUs. We also plan to explore device-side caching to fully capture and utilize application workload spatial and temporal localities. Another focus area is to extend current static memory management to a dynamic approach for more robust pool usage. We also plan to explore and investigate fine granular, dynamic allocation and management of pool memory. ACKNOWLEDGMENT
