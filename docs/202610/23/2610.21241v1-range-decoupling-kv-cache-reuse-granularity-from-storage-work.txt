# Range: Decoupling KV-Cache Reuse Granularity from Storage Work 

## Dingsen Shi 1, Jiahao Zhang 2, Liqiang Lv 2, Boming Huang 2, Yanbo Dai 1,Ying He 1, Donger Chen 1, Harry Fu 1, Wang Feng 1, Song Fu 11University of North Texas 2SageShield Co., Ltd.

## Abstract 

LLM serving reuses cached key-value (KV) state to skip pre-fill, and growing contexts push that state past GPU HBM and CPU DRAM onto NVMe SSDs, placing prefix restore on the critical path of time-to-first-token (TTFT). We find that on a well-configured host-issued path the SSD is not the bot-tleneck: restoring the same 6 GiB of KV takes 2.1 s as 192 objects but 3.0 s as 6,144 objects, and more under layerwise loading, because every layer of the storage stack—lookup, al-location, I/O submission, GPU delivery, store, index—charges per logical object while the bytes stay the same. This cost grows with the KV footprint: longer contexts, deeper models under layerwise loading, and tensor parallelism each multiply the object count. Prior systems move this per-object work from the CPU to the GPU; the work remains per object. This paper presents Range, a KV-cache storage engine for vLLM and LMCache built on one principle: every cost on the storage path scales with bytes or physical batches, never with logical objects. Range tickets replace per-key lookup and ownership with token metadata and physical leases; byte stripes make the on-media layout independent of reuse granu-larity; completion-owned GPU transfer banks batch delivery and extraction and release each layer to attention as it lands. Range keeps the kernel cuFile path and changes four lines of vLLM. On a fixed 6 GiB restore, Range’s median TTFT stays at 1.79–1.80 s across a 32 × range of object counts and under layerwise delivery, within 70 ms of the prefix already being resident in GPU memory, while tuned in-process LMCache rises from 2.12 s to 3.01 s. Range improves on the fastest mul-tiprocess DRAM-bounced path by 0.44 s at coarse granularity while moving no payload through host memory, and holds layerwise reuse at the cost of coarse-grained reuse, where the best stock path takes 2.24 s. 

## 1 Introduction 

Prefix caching has become a standard optimization in LLM serving: the key-value (KV) state computed for a prompt prefix is kept and reused, so a request that shares that prefix skips its prefill and pays only for its new tokens [8, 9, 26, 30]. The benefit is bounded by how much KV a server can retain. As context windows and concurrency grow, KV footprints exhaust GPU HBM, then CPU DRAM, and serving stacks add NVMe SSDs as the next tier to keep hours of conversation and agent state reusable [5, 12, 19, 20, 28]. Once KV lives on SSD, restoring a cached prefix sits on the critical path of time to first token (TTFT): the request cannot start until its prefix is back in GPU memory. The received view is that SSD-backed KV reuse is slow because of the path between the SSD and the GPU. Tutti attributes the slowdown to the fragmented, page-based layout of GPU memory, which turns a restore into many small I/Os, and to the CPU that must initiate each of them, and concludes that host-issued I/O—even with GPUDirect Storage—is the bottleneck [20]. Its answer, following BaM and GeminiFS, moves I/O issuance and completion onto the GPU [2, 20–22]. LMCache’s multiprocess tier takes the opposite route: it keeps issuance on the host, moves it into a native worker pool that prefetches at scheduling time, and stages every byte through a pinned DRAM slab on its way to the GPU [12]. We find that on a well-configured host-issued path the SSD is not the bottleneck, and neither is the processor that issues the I/O. Restoring the same 6 GiB prefix through tuned in-process LMCache over cuFile takes 2.124 s when the prefix is cached as 192 objects and 3.012 s as 6,144 objects; under real layerwise loading, which is how a serving engine creates fine granularity, it takes 2.664 s (Figure 1). The bytes are identi-cal. What changes is the number of logical objects , and every layer of the storage stack—lookup, allocation, I/O submission, GPU delivery, store submission, index maintenance—charges per object. This cost grows with the KV footprint itself: longer contexts add objects, layerwise loading multiplies them by the number of layers, and tensor parallelism multiplies them again. A 128K-token prefix on an 80-layer model under layerwise loading with eight-way tensor parallelism is over 300,000 objects for one request. Range’s median TTFT stays at 1.788–1.803 s at every point, within 47–68 ms of the resident-prefix control, while stock in-process paths rise from 2.124 s to 3.012 s. At coarse granularity it improves on the multiprocess filesystem path by 438 ms while moving no payload through host memory; under layerwise loading it is 447 ms faster than the best stock path (direct I/O) and 876 ms faster than in-process cuFile. This paper makes the following contributions: • A diagnosis of SSD-backed KV reuse in which the cost is per logical object rather than per byte or per issuing processor—and therefore grows with context length, model depth under layerwise loading, and tensor parallelism—together with a fixed-payload sweep that isolates it. • Range tickets, physical byte stripes, and completion-owned transfer banks: a storage representation that keeps lookup, I/O, delivery, store, and lifetime management per byte or per batch. • An implementation in LMCache and vLLM, and an eval-uation showing that fixed-payload KV reuse becomes insensitive to object count—so that Range’s cost, un-like the stock path’s, does not grow as finer granularity, deeper models, or larger contexts multiply the object count—with the cost of each mechanism attributed by ablation. 

## 2 Background and Motivation 

This section first reviews how LLM inference produces and reuses KV state and how serving engines lay it out in GPU memory (§2.1). It then measures where an SSD-backed reuse path loses time and shows that the loss is charged per logical object, not per byte (§2.2). It surveys how existing systems answer that loss and where each leaves the per-object work in place (§2.3), and closes with the three challenges a storage path must meet to make its work independent of object count (§2.4), which the next section’s mechanisms address one by one. 22.1 LLM inference, KV cache, and paged lay-out 

Prefill, decode, and the KV cache. Transformer inference has two phases. Prefill processes the whole prompt in parallel and computes, for every layer, the key and value tensors of every token; it is compute-bound and ends when the first token is emitted, so its cost is time to first token (TTFT). Decode then generates one token per step, attending over the keys and values of all previous tokens. Engines keep those tensors in a KV cache so that decode does not recompute them. The cache is not bound to one request: two prompts that share a prefix produce identical KV for that prefix, so a serving engine that retains it can skip the shared part of prefill entirely. This prefix caching is a standard optimization in vLLM, SGLang, and LMCache, and it turns a compute-bound phase into a data-movement problem—the cached prefix must be back in GPU memory before the new tokens can be processed [8, 9, 26]. 

Paged KV memory and its objects. Because sequences grow and vary in length, engines allocate KV in fixed-size blocks rather than contiguous tensors. vLLM’s paged layout stores each layer’s keys and values in blocks of a few tokens (16 in our configuration), indexed through a block table per request [26]. A cached prefix is therefore not one buffer but a set of blocks per layer, and a KV tier outside the GPU has to name and move that set. LMCache groups tokens into chunks (256 tokens by default) and names each chunk by a hash of its token prefix; with layerwise loading the unit becomes one chunk of one layer, so a 32-layer model produces 32 objects per chunk. For Llama-3.1-8B, whose KV is 128 KiB per token, a 256-token chunk is 32 MiB and a per-layer object is 1 MiB; a 49,152-token prefix is 6 GiB in either case, as 192 objects or as 6,144. The object count is a choice of representation, not a property of the data. 

Units, callbacks, and paths. A logical cache object names reusable state and must match the request’s model, represen-tation, tokens, and destination slots; a physical byte batch 

moves a byte range. Smaller objects refine where a partial hit ends, while neighboring bytes can still move together. The vLLM connector exposes the points at which storage can delay or overlap a request: the start of loading, a per-layer readiness wait, per-layer store callbacks, and the final save wait [26]. cuFile exposes host-issued reads and writes on registered handles and buffers; its compatibility path stages through host memory [15]. We use GDS for a cuFile transfer whose payload moves between storage and GPU memory without traversing host DRAM, and judge the path of every run from its configuration rather than the backend’s name [9]. 

## 2.2 Where SSD-backed reuse loses time 

We restore the same 6 GiB prefix on the hardware of §4 and vary only how it is partitioned (Figure 2). 

① The device is not the bottleneck. The native cuFile tool reads the same 6 GiB as 32 MiB requests at 15.61– 16.10 GiB/s with one host thread and 22.91–23.10 GiB/s with four, against a 22.8 GiB/s array ceiling, with every returned buffer verified (Figure 2, left). A host-issued path saturates the media with a handful of threads; whatever the serving stack loses, it does not lose it at the drive. 

② The same bytes cost more as objects multiply. Through LMCache’s cuFile backend, the same restore takes 2.713– 2.774 s of client TTFT as 192 objects, 3.738–3.810 s as 6144 objects, and 4.455–4.620 s under real layerwise loading (Fig-ure 2, right). The payload, the model, the cached tokens, and the GPU compute are identical across the three; only the object count changes. Layerwise loading, whose purpose is to overlap I/O with computation, is the slowest of the three because it creates the most objects. 

③ The cost is per object. In an offline diagnostic of the same backend, doubling the payload at a fixed 1 MiB object size (6,144 to 12,288 objects) doubled every line item: the media phase from 0.325 to 0.655 s and the serial host phase from 0.418 to 0.819 s, with a 2 ms residual. The two phases do not overlap—the host phase begins when the last read returns—so the host cost lands on the request’s critical path in full, about 67 μs per object. 

④ Deployments multiply the object count. Object count is the product of chunks, layers, and tensor-parallel ranks. A 128K-token prefix is 512 chunks; on an 80-layer model under layerwise loading that is 40,960 objects, and with eight-way tensor parallelism, each rank holding a slice of every object, 327,680. The stock stack charges each of them at every stage: the batched retrieve API constructs a key, a path, and an allocation per object before dispatch; each object is a file and a native call; each object is delivered by its own GPU transfer; the batched store API iterates over objects and submits each to the scalar path; and each object adds a record to an index that only grows [11]. A batch-shaped interface with a per-object loop inside is still per object.

backend combines fixed slots with bounded write groups and aggregated reads [13]; Dynamo KVBM exposes physical layouts with vectorized copies [16]; ObjectCache separates reuse chunks from layerwise delivery [34]; SGLANG-LSM separates a prefix-ordered index from tensor logs [32]. Each batches or packs one stage of the path. A stage that is still per object—a lookup, a launch, a store submission, an index record—keeps the whole path per object, because the stages are serial. Reuse policy, which decides what to compress, retain, or evict [1, 3, 4, 7, 8, 18, 25, 27, 30, 31, 33], is orthogo-nal: this paper holds reuse decisions and the uncompressed payload fixed. 

## 2.4 Challenges of object-count invariance 

Making every stage of the path scale with bytes or batches rather than objects raises three problems that the logical-object representation had been solving implicitly. 

Naming reuse without enumerating objects. A partial hit ends at a token boundary that need not align with any batch; two requests may share a prefix but diverge inside a batch; a batch written by one request may be read by another before the writer has retired. A batched path must still answer “which tokens are reusable, and who owns their bytes” exactly, without constructing a key per object (§3, range tickets). 

Landing fixed byte batches in a paged, per-layer GPU memory. The engine’s destination is not a buffer but a set of blocks per layer, bound to a request only when it is scheduled, and attention for layer ℓ must not start before layer ℓ’s bytes have landed. A fixed-size stripe on media therefore has to be scattered into slots it did not know at store time, and released to the model one layer at a time, without turning each block into its own transfer (§3, byte stripes and delivery). 4Owning batches through asynchronous completion. One batch spans many logical objects and outlives the call that issued it; completion is asynchronous on a GPU stream; a re-quest may be cancelled while its reads are in flight; and a bank reused one step too early silently corrupts the next request’s KV—exactly the failure we observed in a stock multiprocess GDS pipeline at two requests in flight. Ownership of buffers, descriptors, and source pages must follow the completion fence, not the API return (§3, completion-owned banks). 

## 3 Design and Implementation 

This section presents Range. We first walk one request through the engine (§3.1), then describe the three mecha-nisms that answer the challenges of §2.4: range tickets, which name reusable KV without enumerating objects (§3.2); phys-ical byte stripes, which fix the transfer unit independently of reuse granularity (§3.3); and completion-owned transfer banks, which connect stripes to paged GPU memory and to the model’s layer dependencies (§3.4). We then give the own-ership and recovery rules (§3.5) and the implementation in LMCache and vLLM (§3.6). 

## 3.1 Overview 

Range applies one rule to the whole storage path: charge work to payload bytes and to bounded byte batches, never to logical cache objects. A stripe layout alone would still construct a key per object; a batched index alone would still issue object-sized transfers. Range changes both interfaces and carries the batch representation through lookup, read, delivery, store, and retirement. ## 3.2 Range tickets 

The first challenge of §2.4 is to answer “which tokens are reusable, and who owns their bytes” without constructing a key per object. Range replaces the per-key index with a range directory : a compressed prefix tree over packed token iden-tities whose leaves reference physical pack records. Lookup takes the scheduler’s packed token buffer and a bounded iden-tity header, compares token bytes against the tree’s path labels, and returns an opaque ticket bound to the request, scheduler session, attempt, worker rank, namespace, and the storage generations that supply the hit. Index work follows token-metadata bytes, tree branches, and physical ranges, each with an explicit capacity bound; for the evaluated unbranched pre-fix a lookup selects six pack records, against 192 or 6,144 chunk records in the stock index (Table 2). A partial hit ends at a token boundary: the ticket clips the selected physical ranges at the promised endpoint, so partial-prefix semantics stay an index decision while transfer aggregation stays a separate one. The connector rounds the hit to the framework’s unchanged logical reuse boundary, so Range cannot obtain a higher hit rate by changing its layout. 5Ownership crosses requests through generations: pack invali-dation removes physical records and prunes dead branches, and a physical lease taken by a ticket survives until deliv-ery retires, independently of Python garbage collection. The worker claims a ticket before delivery by checking its enve-lope, owner epoch, generations, exact tokens, and promised endpoint; a repeated lookup cannot silently replace the query behind a ticket. Restoring per-key indexing in the ablation costs 23 ms at 32 MiB objects and 911 ms under layerwise loading (§5.4). 

## 3.3 Physical byte stripes 

The second challenge is to land fixed byte batches in a paged, per-layer GPU memory. Range stores KV in packs inside one preallocated regular file. A pack holds one stripe per model layer; a stripe is a fixed byte bound W (32 MiB) of token-major KV in the schema [token , K/V, hidden ]. For pack base 

a, layer l, token offset t, and per-layer token size s (4096 bytes for the evaluated model), the address is a + lW +ts ; a 32 MiB stripe holds 8192 tokens and 32 stripes form a 1 GiB pack. A value payload follows its token’s key payload, so a partial stripe keeps the same addressing rule and reads or writes only its valid extent. Restore and store jobs follow physical spans, not objects. For payload B and P separately represented partial bound-aries, planning and native calls follow the spans covering B

at bound W plus boundary work for P; logical object count does not appear. Every span is checked against file bounds, registered-buffer bounds, alignment, and storage generation, and disjoint ranges remain separate spans. Figure 4 draws the consequence: the same 6 GiB, partitioned into 192 or 6,144 logical objects, maps onto the same 192 stripes, six packs, eight banks, 32 layer events, and one range lease. Each completed stripe is delivered by one call of the existing single-layer paged-KV transfer, which scatters the stripe’s tokens into their slots; the stock path invokes the multi-layer transfer once per object. Replacing coalesced stripe reads with object-sized issuance in the ablation costs 8 ms at 32 MiB objects and 93 ms under layerwise loading (§5.4).

Stores and publication. Layer-production callbacks record dependencies on the model stream; a byte group becomes eligible when its source layers are ready. The store uses eight 256 MiB banks, eight group workers, and 32 write workers; a full group covers four layers and at most eight stripes. ## 3.5 Ownership and recovery 

Generations, read leases, and completion fences protect phys-ical reuse; Table 1 lists the owners and the evidence each needs before it may be retired. Publication requires success-ful writes for every selected layer, including groups that com-plete on different workers; a group failure prevents visibility, and reclamation waits for all other accepted writes to drain. Cancellation or an exception is not completion evidence, and an unproved CUDA fence quarantines its resources rather than releasing them. Duplicate stores join the existing reser-vation. Clean shutdown drains owners, synchronizes payload, and publishes a file-identity-bound metadata snapshot before clearing the dirty marker; a dirty reopen discards the index rather than reconstructing it from payload. 

## 3.6 Implementation 

Integration with LMCache and vLLM. Range adds 6,889 lines of Python in 34 files under lmcache/v1/range_engine 

and a 71-line CUDA gather kernel to LMCache’s in-process engine. The diff against the LMCache release touches 50 paths ( +8,304 /−285 lines); the change to vLLM is four lines in one file ( +3/ − 1). The engine source, the patches against LMCache 0.5.2 (commit cd2c0d6a ) and vLLM 0.25.1 (com-mit e04a30a7 ), and the SHA-256 manifest of the installed package ( 77dfae8b... ) are part of the artifact. The engine lives entirely behind the existing KV-connector interface and preserves vLLM’s block-granular KV management: atten-tion, the KV dtype, and the paged-cache allocator keep their ordinary implementations. On the scheduler side, Range ex-tends LMCache’s lookup transport; the response preserves the connector’s integer hit API while carrying serialized, rank-specific tickets, and when vLLM allocates cache slots the 7adapter moves the tickets into scheduled-request state and attaches them to the request sent to the worker. On the worker side, Range implements the connector’s restore callbacks (start of loading and per-layer readiness wait) and store call-backs (per-layer production and final save wait); the plain and layerwise connector modes drive the same stripe, bank, and readiness machinery, differing only in which callbacks the engine invokes. Restores run on the request’s critical path; stores are queued behind layer-production events and continue after the connector returns. Finishing or abandoning a request cancels unclaimed lookup ownership and retires its scheduler state. The coordinator is constructed after LMCache’s stor-age manager and closes before the registered allocation is disposed. 

Identity. The namespace binds model revision, semantic configuration, KV dtype, parallel geometry, and application tags; a change in any of them selects a separate namespace rather than reusing incompatible persisted tensors. Scheduler messages carry exact token bytes and request, session, and attempt identities. After allocation the connector binds an immutable mapping from token positions to paged-cache slots, so a transfer batch position never identifies a destination. 

Multi-GPU. Under tensor parallelism vLLM runs one worker per GPU, and one Range engine runs in each, with its own pack file, directory, banks, and rank-qualified namespace. The scheduler’s lookup is broadcast to every rank and com-pletes only when every rank has answered; each rank returns a ticket bound to its own rank and namespace, and the sched-uled request carries the full rank map, so a worker can claim only the ticket that names it. Each rank’s stripes hold that rank’s slice of every layer, so the per-rank operation counts are those of §3.1 scaled to the slice, and the per-object mul-tiplication that tensor parallelism imposes on the stock path (§2.2) does not arise. Scheduling-time prefetch is currently en-abled only for a single rank with vLLM’s own prefix cache off and no load clipping, because a promise made at lookup that is later clipped by another rank or by the framework would need an explicit surplus-read policy. Pipeline parallelism, a local DRAM tier, cache blending, asynchronous loading, dis-aggregated transfer, and per-request LoRA namespaces are rejected at startup rather than silently degraded. Our evalua-tion uses one GPU; multi-rank serving is implemented but not measured in this paper. 

Testing. The ownership rules of §3.5 are exercised by CPU fault tests over temporary pack files that replay stale tickets, divergent prefixes, partial completion, cancellation during in-flight reads, dirty reopening, and clean reopening from a snapshot. ## 4 Experimental method 

We measure client latency, storage traffic, delivered KV, and process resources on the same request. A separate loop-back HTTP client process times request submission to the first complete generated-token event. Storage observations must pass delivered-KV, recompute-output, sector, hit-count, loaded-source, and process-identity checks. All experiments serve one request at a time; concurrent serving is future work. 

Platform and workload. The final experiment uses vLLM 0.25.1 and LMCache 0.5.2 with Llama-3.1-8B-Instruct and BF16 KV on one H100 NVL. Two NVMe drives form the ext4 array. The fixed request uses a document excerpt 8and original question from L-Eval [17]. It contains 65,280 tokens, of which 49,152 are cached: the restore is 6 GiB and the newly computed suffix is 2,016 MiB of KV. Each request asks for two generated tokens; tensor parallelism is one. The plain partitions contain 192, 768, 3,072, or 6,144 objects; the final category uses actual layerwise callbacks and 6,144 layer objects. The finest plain point is a control separating object count from layer dependencies. Every arm at a point uses the same request and hit boundary. Recompute and an HBM-resident prefix supply reference paths. The storage arms are Range, tuned stock in-process cuFile, multiprocess fs_native at the coarse points, and in-process O_DIRECT at the fine points. Stock receives direct I/O, a tuned worker pool, sufficient staging, and the same disabled cyclic GC as Range. Shared alignment, lifetime, layerwise-adapter, and integrity repairs receive no engine credit. The artifact records each allocator and buffer setting and the exact installed Python and native libraries; changing them requires a new matched comparison. 

Paired observations. The evaluation arms were measured on the same day with interleaved order; the motivation diag-nostics were measured earlier on the same machine. The pri-mary sweep has three attempts per cell, with storage-arm order rotated. ## 5 Serving results 

Our evaluation answers three questions. Q1: With the pay-load, model, and cached tokens fixed, does TTFT depend on how many logical objects name the prefix (§5.1–§5.3)? 

Q2: Which mechanism accounts for how much of the result (§5.4)? Q3: What host resources does each path reserve and move to obtain its latency (§5.5)? ## 5.2 Layerwise reuse 

Real layerwise Range achieves 1.788 s TTFT, compared with 2.664 s for the stock cuFile path and 2.235 s for stock direct-disk. Its paired contribution is 47.4 ms, the lowest point in the sweep. This reduces TTFT by 20.0% against the faster stock path and reduces the paired contribution from 502.0 to 47.4 ms. Logical layer boundaries therefore preserve the near-resident result rather than multiplying the cost of the physical storage plan. The multiprocess filesystem connector has no layerwise delivery path. Its native workers and early prefetch are useful for whole-prefix loading; they do not provide the per-layer readiness contract used here. Range applies the same physical representation to plain and layerwise reuse, with completion published at the layers that computation can consume. 

## 5.3 The multiprocess comparison 

At 768 objects, Range takes 1.796 s and multiprocess 

fs_native takes 2.235 s, a 438 ms reduction. The latter re-mains a strong stock architecture: its native pool, queued reads, and scheduler-time prefetch already avoid exposing much of the repeated work to the request. Its two completed coarse requests at 192 objects take 2.187 and 2.225 s. These observations and the complete 768-object cell show a nearly flat coarse path, unlike the in-process cuFile line. After re-pairing the client fixture, supplementary MP requests at 3,072 objects take a median 2.320 s (2.318–2.335 s). Range also eliminates the application’s host-to-GPU re-store copy. That advantage concerns payload movement, 10 rather than all resource costs: Section 5.5 measures the host memory each path reserves and the payload each moves through host memory. The multiprocess design provides a shared tier for serving instances; Range’s evaluation concerns one serving engine using local storage. What limits Range now. The 47–68 ms that separate Range from a GPU-resident prefix are the parts of the storage path that no batching hides: the first layer’s stripe reads, which cannot overlap any computation because there is no earlier layer to hide behind; the ticket claim and slot binding, which run once per request before any read is scattered; and the store’s admission and extraction waits, which gate the first token when the suffix’s early layer groups become eligible. None of these scales with object count, which is why the sweep is flat; they scale with the number of layers and the size of the first stripe group, which is where further work on Range would go.
