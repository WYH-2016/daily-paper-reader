# Where the SRAM Goes: Per-Symbol Attribution of Static Memory in FreeRTOS-C and Embassy-Rust IoT Firmware on a 64 KB RISC-V Microcontroller 

> Romi Fadli, Jan Everhard Riwurohi, Wahyu Ramadani Putri Utami, Zulfa Malika Amana
> Magister Ilmu Komputer, Universitas Budi Luhur, Jakarta, Indonesia Corresponding author: Romi Fadli (2511600872@student.budiluhur.ac.id)

Abstract Selecting a firmware stack for a memory-constrained microcontroller is usually guided by aggregate binary sizes, which report how much SRAM a build consumes but not where it goes or why. We address that gap with a per-symbol attribution method that decomposes static RAM into architectural categories — scheduler heap, network buffers and pools, task stacks, and linker-reserved regions — by bounding sized ELF symbols to the .data, .bss and .stack section ranges. The method is validated by reconciling every category sum exactly against the size-based totals for all sixteen builds. We apply it to eight cumulative firmware milestones, from a bare task scaffold to a full MQTT-over-Ethernet client, implemented twice — in FreeRTOS-C and in Embassy-Rust — on the CH32V203RBT6, a RISC-V microcontroller with 64 KB SRAM and an on-chip Ethernet MAC and PHY, with functional parity verified on hardware at every milestone. The decomposition shows that both stacks spend a nearly identical share of their RAM on networking (63.8% versus 63.9%), yet the absolute cost differs by 4.4 times: 40,719 bytes for lwIP against 9,316 bytes for smoltcp. FreeRTOS task stacks grow linearly at roughly 1 KB per task while Embassy async state grows with state-machine complexity. We also report that lwIP could not be integrated under an all-static discipline on this platform, requiring a 20 KB arena that smoltcp does not. The measurement harness, the attribution tool, and the sixteen firmware implementations are released as artefacts. 

Keywords: Embedded firmware, Static memory analysis, RISC-V, Embassy-Rust, FreeRTOS, IoT 

# 1 Introduction 

1.1 Background 

The Internet of Things (IoT) industry has driven increasing demand for resource-constrained microcontrollers capable of handling real-time networking workloads. RISC-V, a free and open reduced instruction set architecture, has gained considerable traction in this segment owing to its royalty-free licensing, competitive performance per watt, and a growing ecosystem of open-source toolchains [1], [11]. Among the most capable low-cost RISC-V microcontrollers currently available is the CH32V203RBT6, manufactured by Nanjing Qinheng Microelectronics Co., Ltd. (WCH). This device integrates a 32-bit QingKe V4B core running at up to 144 MHz, 128 KB Flash, 64 KB SRAM, and — uniquely for its price tier — a fully integrated on-chip 10 Mb/s Ethernet MAC and PHY [3]. This last feature eliminates the need for an external PHY component, making it attractive for cost-sensitive IoT applications that require network connectivity, such as industrial sensor nodes, home automation bridges, and MQTT-based data loggers. Delivering a complete networked application on a device with 64 KB SRAM, however, presents a significant memory-management challenge. The dominant firmware paradigm for such devices combines the C programming language with a real-time operating system (RTOS). FreeRTOS is the most widely deployed open-source RTOS for microcontrollers [2], and its combination with the lwIP lightweight IP stack forms the de facto standard for networked RISC-V and ARM Cortex-M firmware. Yet this combination carries a substantial static memory overhead: the FreeRTOS scheduler, lwIP buffer pools, and C runtime together consume a significant fraction of available SRAM before the application logic itself is accommodated [5]. As IoT firmware grows in complexity — adding DNS resolution, ICMP, NTP synchronization, and MQTT Quality-of-Service — this overhead scales non-linearly, and the risk of running out of SRAM on a 64 KB device becomes real [6]. A concurrent development in the embedded systems community is the emergence of Rust as an alternative to C for firmware programming. Rust offers memory safety without a garbage collector through its ownership and borrow-checking type system, which eliminates entire classes of undefined behavior — null pointer dereferences, use-after-free, and buffer overflows — at compile time rather than at runtime [11], [17]. Embassy is an asynchronous Rust framework specifically designed for bare-metal microcontroller firmware [9]. Embassy eliminates the need for a traditional RTOS scheduler by leveraging Rust's async/await cooperative tasking model, implemented as a zero-cost abstraction at the language level. This design philosophy results in dramatically smaller runtime overhead compared to a 2

preemptive RTOS: no thread stacks, no heap, and no scheduler data structures need to be allocated in SRAM [9]. 

1.2 Problem Statement 

Despite the theoretical memory advantages of Embassy-Rust, empirical evidence on resource-constrained RISC-V microcontrollers — particularly those with integrated Ethernet — remains limited. Prior comparative studies have been conducted on ARM Cortex-M platforms [11], [10] or at a conceptual level without systematic milestone-by-milestone measurements across a full IoT networking stack. The question of how much SRAM Embassy-Rust actually saves compared to FreeRTOS-C on a 64 KB device, and whether the savings are sufficient to make otherwise impractical applications feasible, has not been answered for the CH32V203 class of RISC-V microcontrollers. This paper addresses that gap through a structured empirical investigation. A set of eight firmware milestones was designed, each building incrementally on the previous: from a minimal idle task (M00) through GPIO, USART, ADC, Ethernet with DHCP, DNS, NTP, and finally MQTT with QoS 0 (M07). Both a FreeRTOS-C and an Embassy-Rust implementation were developed for each milestone, compiled with size-optimizing compiler flags, and measured using ELF binary analysis tools that report precise static memory allocation for text, data, and BSS segments. To the best of the authors' knowledge, this is the first study to conduct a quantitative milestone-by-milestone comparison of FreeRTOS-C and Embassy-Rust on a RISC-V microcontroller with an integrated on-chip Ethernet MAC/PHY, and to hold both implementations to a no-dynamic-allocation policy at the application level throughout. 

1.3 Contributions 

This paper makes the following contributions: 

1. A per-symbol static memory attribution method. We decompose static RAM into architectural categories (scheduler heap, network buffers and pools, task stacks, linker-reserved regions) by bounding sized ELF symbols to the .data, .bss and .stack section ranges. Unlike aggregate size reporting, the method explains where SRAM goes; unlike hand estimation, every category sum reconciles exactly with the size-based total for all sixteen builds. 

2. An empirical characterisation of the networking memory cliff. Applying the method across eight cumulative milestones shows that both stacks commit a nearly identical proportion of RAM to networking (63.8% versus 63.9%) while differing 4.4-fold in absolute cost, and that FreeRTOS task stacks scale linearly with task count whereas Embassy async state scales with state-machine complexity. This separation predicts how the comparison moves on other platforms. 

3. A reproducible measurement harness and firmware corpus. Sixteen functionally verified firmware implementations (eight milestones, two stacks) and an automated build-and-measure harness that emits per-milestone binary metrics with both cold- and warm-cache build timings. 

4. A diagnosed toolchain defect and its workaround. The Embassy HAL for this device does not build out of the box: 32-bit general-purpose timer support is compile-gated to two chip families, yet the CH32V203RBT6 instantiates such a timer, so the generated code references a conditionally absent enum variant. We diagnosed this, patched it locally to obtain a working build, and report it as an instance of the ecosystem-maturity gap that distinguishes the two stacks in practice. An equivalent fix was independently proposed upstream while this work was in preparation. The remainder of the paper is organised as follows. Section 2 positions the work against prior art. Section 3 describes the hardware platform, the two toolchains, the eight-milestone protocol, and the attribution method. Section 4 reports the measurements and the decomposition. Section 5 concludes. 

# 2 Related Work 

2.1 RISC-V in Embedded and Real-Time Systems 

RISC-V has emerged as a credible architecture for embedded real-time applications [1]. Balas et al. [12] introduced CV32RT, an enhancement to the open-source CV32E40P RISC-V core that achieves interrupt latency as low as 6 clock cycles through a custom fast-IRQ extension to the RISC-V Core Local Interrupt Controller (CLIC). Their work demonstrated that RISC-V cores can achieve interrupt performance comparable to ARM Cortex-M and Infineon TriCore, a prerequisite for reliable real-time networking. Behnke et al. [4] addressed the challenge of deterministic IP packet processing on embedded real-time devices, showing that without priority-aware modifications to the network driver the reception of bursty IP traffic degrades real-time task deadlines. Their work is directly relevant to the Ethernet-over-DHCP and MQTT milestones examined in this paper, where lwIP's interrupt handling and FreeRTOS 3

task priorities interact under load. The ESP32-C3, another popular RISC-V IoT microcontroller [14], has been used as a baseline reference for comparing Ethernet-capable embedded Linux versus RTOS deployments, but it lacks the integrated on-chip Ethernet MAC/PHY present on the CH32V203, making it a less direct comparison for the networking milestones studied here. 

2.2 FreeRTOS and lwIP Architecture 

The FreeRTOS kernel provides task scheduling, inter-task communication (queues, semaphores, event groups), and software timers [2]. The kernel was designed to be minimal but configurable: heap management, tick rate, stack sizes, and the presence or absence of optional features are all controlled at compile time through FreeRTOSConfig.h. In a static-allocation-only configuration, FreeRTOS eliminates dynamic heap allocation entirely, committing all task stacks and kernel data structures to the BSS section at link time [2]. This configuration was used throughout the present study. The integration of FreeRTOS with the lwIP network stack requires that lwIP buffer pool sizes be specified statically at compile time; these pool tables dominate SRAM consumption at the networking milestones [6]. Mannella et al. [15] studied FreeRTOS dependability under fault injection, characterizing the vulnerability of scheduler data structures (task control blocks, ready lists) to radiation-induced soft errors, which motivates the interest in smaller, simpler software stacks for safety-critical IoT deployments. 

2.3 Embedded Rust and Embassy 

Rust's memory safety guarantees have attracted growing interest from the embedded systems community as a means of reducing firmware defects without incurring garbage-collection overhead [11], [17]. Vandervelden et al. [17] provided a comprehensive overview of embedded Rust operating systems and frameworks — including RTIC, Tock OS, Hubris, Drone OS, and Embassy — comparing their concurrency models, hardware abstraction layer designs, and ecosystem maturity. Among these, Embassy was identified as the most actively maintained framework offering a complete asynchronous networking stack (embassy-net over smoltcp) that targets both ARM Cortex-M and RISC-V. Frank et al. [18] presented Ariel OS, a multicore-capable embedded Rust OS that incorporates Embassy's asynchronous executor and provides performance benchmarks across ARM, Espressif Xtensa, and RISC-V targets. Seidel and Beier [16] examined the use of Rust in space-qualified embedded systems, concluding that Rust's compile-time safety guarantees are directly applicable to safety-critical microcontroller firmware with no measurable runtime overhead. Molz et al. [20] mapped MISRA-C++ coding guidelines to their Rust-language equivalents (MISRust), providing evidence that the Rust type system enforces a large subset of MISRA-C++ safety rules statically and without annotation overhead. 

2.4 Comparative Studies of C and Rust Firmware 

Sharma et al. [11] performed the first systematic study of the current state of Rust for embedded systems, surveying 225 developers and analysing 6,408 Rust embedded software repositories. They found that while the Rust ecosystem has matured significantly, challenges remain in SAST tooling for embedded targets and interoperability with existing C codebases. Thapa et al. [10] reported an industrial case study in which two teams — one in C and one in Rust over Ariel OS — developed the same IoT sensor logger firmware concurrently on STM32 hardware. Their analysis showed no strong advantage for C over Rust in either memory footprint or execution speed on ARM Cortex-M, and that Ariel OS provided a smaller runtime footprint than the reference baremetal C stack. The present study extends this line of investigation to the RISC-V architecture and to a device with integrated Ethernet MAC/PHY, providing the first milestone-by-milestone comparison that isolates the memory cost of each networking layer. Tock OS [22], a Rust-based embedded OS designed for extreme isolation and correctness, has been deployed on over 10 million production devices, providing evidence of Rust's long-term viability for MCU firmware in commercial products. Yoshimura et al. [7], [8] explored Rust component frameworks (TECS) for RTOS systems, showing that Rust's type system can enforce inter-component contracts that previously required dynamic runtime checking in C-based OS frameworks. 

2.5 Research Gap 

No prior published work has conducted a quantitative eight-milestone comparison of FreeRTOS-C versus Embassy-Rust on a RISC-V microcontroller with an integrated on-chip Ethernet MAC/PHY and only 64 KB of SRAM. The CH32V203RBT6 represents a class of affordable RISC-V IoT devices that are too resource-constrained for lwIP's default configuration yet capable enough to host a full MQTT stack under the right firmware framework. This paper fills that specific empirical gap. 4

Both implementations were held to a no-dynamic-allocation policy for all application-level objects, in line with NASA JPL Rule 3 [24] and MISRA-C Rule 21.3 [25], which prohibit dynamic allocation after initialisation to prevent fragmentation and to permit static worst-case analysis. Every task, queue, semaphore and timer in the FreeRTOS-C application code is created through the xXxxCreateStatic() family, and the Embassy-Rust workspace links no GlobalAlloc implementation at all, so an attempted heap allocation there is a compile-time error. The two stacks could not, however, be held to the same policy at the network layer, and this asymmetry is itself a result rather than a caveat. The lwIP port layer allocates its mailboxes, mutexes and its internal thread through the FreeRTOS dynamic API (sys_mbox_new, sys_mutex_new, sys_thread_new), which the static API cannot satisfy. Integrating lwIP therefore required enabling configSUPPORT_DYNAMIC_ALLOCATION and reserving a bounded arena from the milestone at which networking is introduced: 14 KB at M05, raised to 20 KB at M06-M07. Milestones M00-M04 remain strictly heap-free (configTOTAL_HEAP_SIZE = 0). The arena is reserved exclusively for the lwIP port; no application code calls pvPortMalloc after initialisation. Embassy-Rust required no equivalent concession: smoltcp accepts caller-provided static buffers, so the Embassy builds remain allocator-free at every milestone. Because the arena is a fixed reservation in BSS it remains fully visible to static analysis, and it is reported as its own category in Section 4.

3.5 Memory Measurement Protocol 

Static memory consumption was measured using the riscv-none-embed-size utility (GNU Binutils) applied to the compiled ELF output of each milestone build. The size command reports the sizes of three ELF segments: text (executable code and read-only constants, contributing to Flash); data (initialized global/static variables, occupying both Flash and RAM at runtime); and bss (zero-initialized global/static variables, occupying RAM only). Flash consumption was computed as: text + data. RAM consumption was computed as: data + bss. All measurements were performed on release-mode (optimized) builds. Build time is the wall-clock time of the build command alone (make, or cargo build --release), excluding the preceding clean step, and was measured in two regimes. In the cold regime every dependency is rebuilt from scratch (make clean for FreeRTOS-C; cargo clean of all crates for Embassy-Rust). In the warm regime the Embassy dependency cache is kept and only the firmware crate is rebuilt (cargo clean 6

-p firmware); FreeRTOS-C has no separate dependency cache, so its warm build is again make clean followed by make. Both tools were invoked with their default parallelism: make without -j (one compilation unit at a time) and cargo with one job per hardware thread. Each regime was run five times, sequentially and never overlapping, on the same machine (Lenovo Legion 5 15ARH7 laptop with an AMD Ryzen 7 6800H, 8 cores/16 threads, 16 GB DDR5 RAM, and NVMe Gen 4 storage), and the median of the five runs is reported. 

3.6 Measurement Validity 

To ensure reproducibility: each build was executed from the clean state defined for its regime in Section 3.5 before measurement; binary sizes were checked to be byte-identical across all repeated runs; compiler flags were verified to be identical between measurement runs; the same ELF analysis script was applied to both toolchain outputs; all FreeRTOSConfig.h parameters were fixed across milestones M00-M07, with only the set of compiled source files changing at each milestone; and the Embassy Cargo workspace pinned all dependency versions in Cargo.lock.

3.8 Per-Symbol Static Memory Attribution 

Segment totals report how much SRAM a build consumes but not what consumes it. To recover that, a second measurement pass attributes each byte of static RAM to an architectural category. The procedure is: (i) read the .data, .bss and .stack section headers from the linked image, which are authoritative for what occupies SRAM; (ii) enumerate sized symbols and retain only those whose address falls inside those ranges; (iii) assign each retained symbol to a category by name pattern; and (iv) report any SRAM reserved by the linker script but carrying no sized symbol as its own category rather than discarding it. Step (ii) is what makes the result trustworthy. Filtering on symbol type alone over-counts, because a symbol may carry a BSS or data type code while residing outside those sections; bounding by address range removes that error. Step (iv) captures the 4 KB main and interrupt stack reserved through __stack_size, which occupies real SRAM that the application cannot use but which no symbol describes. The method is self-validating: because the categories partition the same address ranges the size utility measures, their sum must equal the segment total. This identity holds exactly for all sixteen builds, which distinguishes the resulting figures from the component estimates commonly reported in comparisons of this kind. Categories are architectural rather than stack-specific, so the same taxonomy applies to both implementations and the comparison remains like-for-like. The implementation is released with the firmware corpus.

4.2.1 Pre-Ethernet Milestones (M00-M04) 

At the baseline milestone M00, FreeRTOS-C required 6,928 bytes of RAM compared to Embassy's 556 bytes (12.5x ratio). This gap reflects the FreeRTOS kernel allocating idle task control blocks, ready-list arrays for all priority levels, and tick counter in BSS at startup, while Embassy's executor is a minimal static array of waker slots. The four milestones M01-M04 added GPIO, USART, ADC, and PWM peripherals. FreeRTOS-C RAM grew from 6,928 to 12,652 bytes (+5,724 bytes), while Embassy grew from 556 to 1,488 bytes (+932 bytes). Each FreeRTOS peripheral required at least one task stack (min 512 bytes) and a queue handle; Embassy async futures carry no stack overhead beyond the precisely-sized coroutine state. 8

4.2.2 Ethernet Introduction (M04 to M05) 

The most dramatic transition occurred at M05. FreeRTOS-C RAM jumped from 12,652 to 51,272 bytes (+38,620 bytes, +305%), consuming 59% of total SRAM in a single step. The root cause is lwIP's pool table architecture: the stack pre-allocates all network buffer pools, ARP table entries, UDP/TCP PCBs, and queues as static arrays at startup regardless of active connections [6]. Embassy-Rust's smoltcp stack at M05 grew from 1,488 to 9,424 bytes (+7,936 bytes), because smoltcp uses const-generic static buffers sized exactly to the application declaration. The composition of the M04-to-M05 delta is reported in Section 4.3, where it is derived from the linked images rather than estimated. In summary, the step introduces 34,351 B of network-related storage in FreeRTOS-C (a 14,336 B lwIP arena plus 20,015 B of buffers and pool tables) against 7,244 B of socket and DMA buffers in Embassy-Rust, together with a further 3,072 B of additional task stacks on the FreeRTOS-C side for the lwIP input task. The remaining difference is kernel-object growth and miscellaneous static data. 

4.2.3 Full Stack (M05-M07) 

From M05 to M07, adding DNS/ICMP/NTP and MQTT QoS 0 added 12,504 bytes to FreeRTOS-C (total: 63,776 bytes, 97.3%) and 5,144 bytes to Embassy-Rust (total: 14,568 bytes, 22.2%). FreeRTOS-C had only 1,760 bytes free; Embassy-Rust retained 50,968 bytes free (29x more). The absolute RAM reduction at M07 is 49,208 bytes (77.2% reduction).

Three findings follow, none of them visible in the aggregate figures. First, the networking share is almost identical in relative terms and vastly different in absolute terms. At M07 the network subsystem accounts for 40,719 B in FreeRTOS-C (the 20,480 B lwIP arena plus 20,239 B of buffers and pools) against 9,316 B for Embassy-Rust: 63.8% versus 63.9% of each stack's own RAM, but a 4.4-fold difference in bytes. Both architectures devote nearly the same proportion of their budget to networking; they differ in what that proportion costs. Second, the two stacks scale along different variables. FreeRTOS-C task stacks grow linearly with task count, from 2,048 B at M00 to 15,360 B at M07 at roughly 1 KB per task, because every task receives a conservatively sized stack whether or not it uses it. Embassy-Rust async task state grows from 65 B to 4,585 B over the same range, scaling with the complexity of each task's generated state machine rather than with task count, since an async task stores only the locals live across await points. This is the structural reason the gap widens as firmware grows, and it is the component of the comparison most likely to transfer to other platforms: it depends on the concurrency model, not on this device. Third, the lwIP arena is the single largest category in the FreeRTOS-C build at M07 and has no counterpart on the Embassy-Rust side. Its 20,480 B is 31.3% of the device's entire SRAM, committed before any application data. Together with the pool tables this confirms that the cost is architectural: lwIP pre-commits capacity for peak load, whereas smoltcp sizes buffers to the sockets the application declares. 9

4.4 Flash Consumption Analysis 

Figure 4 shows cumulative Flash usage and Figure 5 shows per-milestone incremental Flash growth. At pre-Ethernet milestones M00-M04, Embassy-Rust used less Flash due to aggressive link-time dead-code elimination. At M07 the stacks converge: FreeRTOS-C 76,824 bytes (58.6%) vs. Embassy-Rust 73,164 bytes (55.8%), a difference of only 3,660 bytes (4.8%). This convergence reflects that protocol code dominates Flash at high milestones. Flash is therefore not the binding constraint on this device class - SRAM is.

The two regimes give opposite answers, and conflating them would misrepresent the comparison. Cold, FreeRTOS-C builds faster at every milestone. The practical reading is therefore about iteration rather than the first build: a cold Embassy-Rust build costs somewhat more than its C counterpart, but each subsequent edit rebuilds in about a tenth of a second. Run-to-run variation is small relative to these differences; the largest single deviation was an Embassy-Rust cold build 21% above its median (M07). 

4.6 Practical Implications 

The results confirm that deploying a complete MQTT-over-Ethernet stack with FreeRTOS-C on the CH32V203RBT6 leaves only 1,760 bytes free. As shown in Table 9, no TLS implementation is feasible under FreeRTOS-C on this device: even the most compact option (WolfSSL in static memory mode, ≈ 10,000–18,000 B) requires more than 5× the available 1,760 bytes. With Embassy-Rust, the 50,968 bytes remaining at M07 are sufficient to accommodate WolfSSL or embedded-tls, along with additional sensor drivers and an OTA update buffer. Separately from memory, the warm-build advantage of Embassy-Rust (27-75x across M00-M07, Table 8) shortens the edit-build cycle during firmware development; it does not carry over to first, cold builds, where FreeRTOS-C is faster.

The RAM saving in this study (77.2%) substantially exceeds that reported by Thapa et al. (44.8%). The primary explanation is platform constraint: on the 786 KB STM32U585, lwIP's pre-allocated pools represent a small fraction of total SRAM, so their absolute cost is less impactful. Furthermore, the networking scope in this study is broader — full wired Ethernet with DHCP, DNS, ICMP, NTP, and MQTT — versus the SPI-connected MQTT client in Thapa et al., making the lwIP pool cost more prominent. 

4.8 Functional Parity and Qualitative Observations 

Both implementations passed all functional verification tests described in Section 3.7. Identical observable behaviour was confirmed on the same CH32V203RBT6-R1 board at every milestone: LEDs toggled on button press, USART output matched the expected format, ADC readings responded to the sensor input, DHCP leases were obtained within 5 seconds, ICMP ping responded under 100 ms, NTP synchronization was observed, and MQTT messages were published and received by the same broker. Embassy's async cooperative scheduling produces equivalent functional outcomes to FreeRTOS's preemptive multi-tasking for the IoT workloads studied. Several qualitative differences were noted during development. First, Embassy's Rust type system detected a compile-time error when two async tasks attempted unsynchronised access to the ADC peripheral — a condition that constitutes a silent runtime race in FreeRTOS-C and is not detected by the 11 

compiler. Second, FreeRTOS-C benefited from an official WCH-provided kernel port and a well-tested lwIP integration; Embassy required a locally patched ch32-hal fork, reflecting the relative ecosystem maturity for this specific MCU at the time of study. Third, FreeRTOS-C provides runtime introspection APIs (vTaskList(), uxTaskGetStackHighWaterMark()) useful during debugging; Embassy offers no equivalent runtime memory-usage API, making static BSS analysis the primary observability mechanism. Fourth, application-layer source code size was comparable in both implementations, at approximately 1,200–1,400 source lines of code (SLOC) for the non-driver application layer, indicating that the memory savings are architectural rather than due to code brevity. 

4.9 Limitations 

Several limitations apply. First, metrics were collected on a single hardware specimen; device-to-device variation was not characterised. Second, this study focused on static (compile-time) memory and did not measure runtime stack high-water marks or interrupt stack usage. Third, execution-time performance (interrupt latency, Ethernet throughput, task jitter) was not measured. Fourth, the Embassy HAL for CH32V203 is an unofficial fork; as the upstream matures, binary sizes may change. Fifth, the relative SRAM advantage will differ on devices with larger SRAM where lwIP pool saturation is less critical. Sixth, only single compiler versions were used for each toolchain (GCC 8.2.0 for FreeRTOS-C; stable Rust, edition 2021, for Embassy-Rust); alternative versions or optimization settings could alter binary sizes by up to 5–15%. Seventh, Embassy's cooperative scheduler is sufficient for the studied IoT workload, but applications requiring hard real-time guarantees at the microsecond level may still benefit from FreeRTOS's preemptive scheduling model — a trade-off not quantified here. 

# 5 Conclusion 

This paper introduced a per-symbol attribution method that decomposes the static RAM of a linked firmware image into architectural categories, and applied it to sixteen builds spanning eight cumulative milestones implemented twice, in FreeRTOS-C and in Embassy-Rust, on a 64 KB RISC-V microcontroller with on-chip Ethernet. Because the categories partition the same address ranges the size utility measures, their sums reconcile exactly with the segment totals for every build, which makes the decomposition a measurement rather than an estimate. The principal findings are as follows. First, Embassy-Rust consumed substantially less RAM than FreeRTOS-C at every milestone. At the full MQTT milestone M07, Embassy required 14,568 bytes of RAM (22.2% of capacity) versus 63,776 bytes for FreeRTOS-C (97.3%), a reduction of 49,208 bytes (77.2%). The FreeRTOS-C stack left only 1,760 bytes free, which is insufficient for TLS or additional application logic; Embassy-Rust left 50,968 bytes free. Second, the attribution shows that both stacks commit nearly the same proportion of their RAM to networking (63.8% against 63.9% at M07) while differing 4.4-fold in absolute cost, 40,719 bytes against 9,316 bytes. The stacks also scale along different variables: FreeRTOS-C task stacks grow linearly at roughly 1 KB per task, whereas Embassy-Rust async state grows with state-machine complexity. That distinction, rather than any device-specific constant, is what should be expected to carry to other platforms. Third, the no-heap discipline could not be sustained symmetrically. The lwIP port layer requires the FreeRTOS dynamic API, forcing a bounded arena of 14 KB at M05 and 20 KB at M06-M07 — 31.3% of the device's SRAM at M07 — while Embassy-Rust's smoltcp remained allocator-free at every milestone. This asymmetry is a property of the network stacks, not a configuration choice. Fourth, Flash consumption converged at higher milestones: at M07, FreeRTOS-C used 76,824 bytes (58.6%) and Embassy-Rust 73,164 bytes (55.8%), a difference of only 3,660 bytes. Flash is therefore not the binding constraint; SRAM is. Fifth, the build-time comparison depends entirely on the regime measured. In cold builds that recompile every dependency, FreeRTOS-C is faster at every milestone: Embassy-Rust takes 2.4-2.6x longer before networking is added and 10-12% longer at the networked milestones. In warm incremental builds, the regime of day-to-day development, Embassy-Rust is 27-75x faster. Both figures are medians of five sequential runs; reporting either alone would misstate the result. These results confirm that Embassy-Rust is a practical and demonstrably superior choice for deploying full IoT networking stacks on RISC-V microcontrollers with 64 KB or less of SRAM. For the CH32V203 class of devices, FreeRTOS-C with lwIP requires careful lwIP pool minimization and leaves almost no headroom; Embassy-Rust provides comfortable memory margins even for future extensions such as TLS, additional sensors, or OTA firmware update. Future work could extend this comparison in several directions. First, runtime execution performance — interrupt latency, Ethernet throughput, and task jitter — was not measured and should be characterised to 12 

complete the picture. Second, actual TLS integration under Embassy-Rust using embedded-tls or WolfSSL in static memory mode would validate the feasibility estimates in Table 9. Third, a migration effort study could quantify the developer-hours required to port an existing FreeRTOS-C codebase to Embassy-Rust on the same hardware. Fourth, replicating the eight-milestone methodology on the CH32V307 (128 KB SRAM, same RISC-V/Ethernet family) and the ESP32-C3 (400 KB SRAM, RISC-V, Wi-Fi) would validate generalization across the RISC-V device family. Fifth, power consumption during active networking and idle periods was not measured; Embassy's event-driven async model is hypothesised to enable earlier and longer sleep states than FreeRTOS's tick-driven scheduler. Sixth, measuring interrupt response latency using an oscilloscope would resolve the open question about the CH32V203's PFIC hardware stack versus a standard RISC-V CLINT implementation.
