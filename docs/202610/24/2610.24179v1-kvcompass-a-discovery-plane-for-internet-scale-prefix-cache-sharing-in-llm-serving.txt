# KVCompass: A Discovery Plane for Internet-Scale Prefix Cache Sharing in LLM Serving 

SHIYI LING, University of California, Santa Cruz, USA 

FEI FANG, University of California, Santa Cruz, USA 

CHEN QIAN, University of California, Santa Cruz, USA KV cache reuse is one of the most effective ways to reduce LLM inference cost, but today its benefits are largely confined to a single cluster. When a provider serves the same model across geographically distributed regions, each region may repeatedly prefill the same popular prefixes, wasting GPU time and increasing time-to-first-token (TTFT). Exploiting reuse across regions involves discovering which worker currently holds a reusable KV cache for each request’s prefix. We show that this KV cache discovery problem is structurally harder than conventional object lookup. Unlike hash-placement mechanisms such as DHTs, where an object’s location is a deterministic function of its key, KV caches are created on the workers that serve requests, and their holder sets change with subsequent requests and KV cache evictions. KV cache discovery therefore calls for decoupling KV cache identity from placement. We present KVCompass, a discovery plane for Internet-scale KV cache sharing. The discovery index supports variable-length prefix lookup with constant-time local table reads at the edge, allowing each request to be forwarded to the worker that best balances KV cache reuse against load and network distance. Evaluation includes a 64-worker geo-distributed simulation and a 14-worker three-continent real-machine testbed. Evaluation shows that KVCompass achieves 1 .3–14 × lower P99 TTFT than the baselines, up to 3 .7× lower P99 end-to-end latency, up to 4 .7× the throughput, and a peak load factor within 2% of the Oracle floor. 1 Introduction 

Large language models (LLMs) have rapidly become a core building block of modern computing, supporting a wide range of applications like interactive assistants, code generation, and document analysis [21, 27, 56, 58]. As LLM adoption expands, inference workloads are growing in both scale and diversity. Processing a single request can cost orders of magnitude more than a traditional query [3, 7, 38], and cloud providers face increasing pressure to reduce cost while meeting strict latency requirements such as time-to-first-token (TTFT) [36, 42], making efficient LLM serving a first-order systems challenge [21, 36, 51]. In practice, many LLM requests share common prefixes, such as system prompts, retrieved documents, or conversation histories [22]. A large-scale measurement study at a major cloud

A widely adopted technique to exploit this structure to improve LLM serving efficiency is KV cache reuse [11, 21, 28, 36, 58]: when multiple requests share a common prefix, the computed KV cache can be shared among requests, avoiding expensive prefill computation and reducing latency and serving cost. Commercial prefix caching APIs already exploit this within a single cluster, reducing cost by 50–90% for long prompts [1, 33]. However, these gains remain confined to a single cluster, while real-world LLM serving is fundamentally a global, cross-region problem [6, 17]. The demand for LLM serving is geographically dispersed: in WildChat [55], a corpus of nearly one million ChatGPT interactions, requests span 201 countries and 178,724 users. At Internet scale, as major inference providers increasingly deploy the same model across tens of geographic regions to serve global users with low latency [9, 35], each region independently prefills the same popular prefixes, wasting GPU compute at scale. When we replay WildChat [55] in its arrival order, Figure 2 shows that 6 .6% − 21 .2% reusable prefixes exist only in other regions at arrival time. However, these reuse opportunities are invisible to any KV cache confined to a single cluster or region, no matter how well it is managed. Harvesting them requires extending KV cache reuse to Internet scale, which in turn requires answering a new question for every request: which worker currently holds a reusable KV cache for this prompt’s prefix? 

This is the KV cache discovery problem, a challenge that is fundamental to Internet-scale LLM serving and unaddressed by existing systems. KV cache discovery at Internet scale is harder than it appears. A centralized directory maps prefix hashes to KV cache locations, but each query pays a wide-area round trip that adds directly to TTFT. The natural alternative is to turn to distributed hash-based schemes such as consistent hashing [20] or distributed hash tables (DHTs) [30, 37, 39, 43]. However, DHTs share a fundamental limitation :an item’s placement is determined by its content hash rather than by where it was created [29, 46], which breaks down for KV caches: a cache entry materializes on whichever node happened to serve the prior request, not on a node designated by a hash. Forcing KV caches onto hash-designated nodes would incur migration and replication costs that negate the savings that reuse is meant to provide. KV caches thus demand placement–identity decoupling , which structurally rules out the entire hash-placement family, regardless of how such schemes are tuned. Therefore, no prior distributed naming or location service addresses KV cache discovery at Internet scale. We propose a KV cache discovery plane for Internet-scale KV cache sharing. KVCompass is the 

first system to apply space-efficient minimal perfect hashing (MPH) [4] to Internet-scale LLM serving . MPH’s space efficiency allows the full KV cache index to be replicated in the DRAM of edge nodes in every region, making every lookup a local memory operation rather than a round trip to a remote coordinator. Its explicitly written values achieve placement–identity decoupling: the index tracks where caches land, with no control over where they go, so any worker can register a KV cache entry and any region can discover it with a local lookup. The prefix hash identifies the KV cache entry, while its value records the workers holding it and their storage tiers. Updating the value changes the holder set without changing the prefix identity. The index is organized as parallel tables at prefix lengths derived from the network latency from the edge to each region, so a lookup matches at the lengths where the prefill time a match saves exceeds the network latency of reaching its holder. Sharded maintenance units own all writes to the index, so the read path needs no locks and no cross-node coordination. At forwarding time, a joint score evaluates every worker rather than only the KV cache holders, combining network distance, queuing delay, cache tier, and residual prefill. Together, these properties allow KVCompass to reduce serving cost at Internet scale and provide the first principled answer to the KV cache discovery problem. 2 Background and Motivation 

This section motivates an Internet-scale discovery plane for cross-region KV cache reuse. We first quantify the cross-region reuse opportunity in a production workload (Section 2.1), then derive four requirements for an effective discovery plane (Section 2.2), and finally explain why directly deriving cache locations through hash-based placement does not satisfy these requirements (Section 2.3). 

2.1 Cross-region LLM Serving 

An LLM serving system [21, 58] hosts model replicas on multiple GPU workers and responds to each user prompt by generating a stream of output tokens. A request is processed in two phases: a 

prefill phase that receives the prompt and computes its KV cache , followed by a decode phase that generates one token per step. Serving quality is measured along both the latency and throughput dimensions. Users experience time to first token (TTFT), which is largely determined by queueing and prefill, as well as end-to-end latency, which additionally includes autoregressive decoding. Nowadays, production providers deploy serving clusters in geo-distributed regions. These clusters serve the same model independently, and each keeps its own local KV cache. 2.2 Objectives for a KV Cache Discovery Plane 

The preceding analysis establishes a substantial opportunity for cross-region prefix KV cache reuse. Realizing this opportunity, however, requires a discovery plane that can locate reusable caches across regions without adding significant latency or creating new load imbalances. Suppose a provider operates a serving worker pool across 𝑅 geo-distributed regions. The KV cache for a prefix may be stored in a different region’s worker from the request that could reuse it. Realizing cross-region reuse therefore requires an Internet-scale KV cache discovery plane . For each incoming request, this layer identifies workers that currently hold reusable prefix KV caches and combines those matches with network and load information to select the locally estimated fastest serving worker. To discover reusable KV caches across regions correctly and efficiently, KVCompass needs to satisfy four objectives. 

(O1) KV caches need to be discoverable wherever the requests that compute them land, not where their identities hash to. In conventional location services using hash-based placement, an item lives where its identity dictates: a content hash maps the item to a designated node, and a lookup recomputes that mapping to find it. However, a KV cache entry obeys no such rule. It is not a deliberately placed object, but a by-product of computation that materializes on whichever worker happened to serve the request that produced it. Therefore, a KV cache discovery plane cannot derive a KV cache’s location from its prefix’s hash value; it needs to locate KV caches wherever they have been served, with no control over where they go. We call this requirement 

placement–identity decoupling .

Therefore, looking up every candidate at one fixed length considers only a fraction of the matches longer than that length, and misses the matches shorter than the length entirely. Extending the index to a fixed length of multiple chunk sizes does not resolve this problem either, because at Internet scale the length worth matching is not a property of the prompt itself alone. Reusing a KV cache in a remote region pays off only when the prefill time it saves exceeds the network latency of reaching the worker holding the KV cache, and that latency depends on which region the request is forwarded to. As Figure 5(a) shows, the shortest prefix length worth forwarding ranges from a few hundred to a few thousand tokens, depending on the distance between regions. Suppose every region used one fixed grid of lengths. For any given region, many of the grid’s lengths then fall below its shortest worthwhile length toward some remote region, and a match found at those lengths saves less prefill time than the forwarding latency it pays, so these are matches we do not want to discover. Thus, the discovery plane needs to judge each candidate at match lengths that reflect both the prompt’s sharing structure and the geographic distance between the user and the KV cache holder. 

(O3) Lookups need to be local and effectively free. A lookup that triggers a network round trip to a remote node adds directly to TTFT, eliminating the time savings that KV cache reuse is meant to provide. Thus, every lookup has to resolve locally at the edge node, without off-node coordination. At Internet scale this imposes two demands. First, the state behind a lookup needs to be small enough to reside at every edge node rather than at a centralized directory. Second, each lookup needs to be fast. Because an edge node performs a lookup for every request at tens of candidate prefix lengths, the index answers tens of queries for every request served. Multiplied across all requests, even a small cost per lookup becomes the dominant work on the edge, and an overloaded edge stalls every request behind it. O2 sharpens this objective further. Because the worthwhile match length varies with the geographic location of each holder, a lookup cannot settle for a single fixed depth, yet it has to check all relevant lengths within this same tight local budget. 

(O4) Discovery needs to avoid creating hotspots. Popular prefixes are the most valuable to discover, and they also attract the most requests. But forwarding every matching request to the few workers that already hold a popular prefix’s KV cache will overload those workers while the rest of the workers sit idle. As requests concentrate on one worker, its queueing delay grows and eventually outweighs the prefill time saved by reusing the KV cache. Therefore, the discovery plane needs to weigh this saving against each worker’s load and network distance, and may prefer an idle worker that recomputes the prefix over a congested or distant one.

2.3 Why Hash-Directed Cache Placement Is Insufficient 

A natural idea for a location service in an Internet-scale system is a DHT such as Kademlia [30] or Chord [43], a distributed implementation of consistent hashing used within clusters for prefix KV cache affinity [36]. However, they all assume placement equals identity : an item’s location is determined by its hash value, as Figure 4 (a) illustrates, the assumption that O1 rules out. To mediate a KV cache’s created and hash-designated locations, a hash-placement scheme would have to migrate each entry to its hash-designated node, which costs hundreds of megabytes of wide-area bandwidth per entry. In the other direction, the scheme would index only the entries that already sit at their hash-designated nodes; since KV caches are rarely at these nodes, most KV caches would become undiscoverable. Therefore, the entire hash-placement family, including Chord, Kademlia, consistent hashing, and Rendezvous hashing, is invalid as a foundation for this discovery plane. The KV cache discovery plane instead needs a data structure whose value field is explicitly written 

by whoever holds the KV cache, not derived from the key, as Figure 4 (b) illustrates. Hashing may decide where a mapping is stored inside the index , but never where the KV cache itself lives. Such an explicit-write structure satisfies placement–identity decoupling (O1) by construction. Section 3 shows how KVCompass builds on this principle to meet the remaining objectives. 

3 Design of KVCompass 3.1 System Overview 

We target an LLM serving deployment that spans multiple regions . Regions are geographically distributed, in different countries or even continents. Each region hosts a set of workers . A worker is one inference instance, holding the full model replica on one or more GPUs, and it keeps the KV caches of the prefixes it has served in its VRAM and host DRAM. A worker reports a KV cache event whenever its local KV cache changes state, admitting a newly computed prefix, moving one between VRAM and DRAM, or evicting one. Workers within a region share a high-speed datacenter network, while traffic between regions crosses the wide-area network, with round-trip times orders of magnitude larger. Each region also runs several edge nodes , CPU-only gateways separate from the workers. A user request arrives at its nearest edge node, and is forwarded to a worker, in the same region or in a remote region. KVCompass is a KV cache discovery plane for this distributed LLM serving. Forwarding every request to the few workers holding popular prefixes would create the hotspots that (O4) warns against, so KVCompass balances KV cache affinity and worker load jointly. For each incoming request, it identifies which workers across all regions hold a reusable KV cache for the request’s

KVCompass is built from a single logical data structure and two kinds of software components that act on it. Maintenance units are the sole writers of the index and apply KV cache events to it. Lookup units answer the discovery query of every request: which workers hold a reusable KV cache for its prefix, and in which storage tier; each holds a local view of the discovery index, a compact slot-only copy without the keys (Section 3.3). The components act on the discovery index through four operations, lookup for forwarding the request and insert , update , and remove for the KV cache events (Section 3.4). KVCompass scores all workers across regions using residual prefill time, load, and network distance, then forwards the request to the winner. Workers report KV cache admissions, tier changes, and evictions to maintenance units, which update the discovery index and lookup units. KVCompass does not control when a worker admits, demotes, or evicts a KV cache. Figure 6 compares four eviction policies on three workloads. LFU achieves the highest KV cache hit ratio on Mixed, while LRU performs best on WildChat and LMSYS. With no policy best across workloads, KVCompass leaves the choice to each worker and only tracks the resulting KV cache events. 

3.2 The Multi-Level Ludo Discovery Index 

The discovery index is the shared state of KVCompass: lookup units read it and maintenance units write it. We first recall the hash structure it builds on and why it is suitable for our problem, then describe the modifications that the KV cache discovery plane demands of the discovery index. The index builds on Ludo hashing [40], a key-value lookup engine that combines a minimal perfect hash function (MPH) [4] with cuckoo displacement: given any set of key-value mappings, it constructs a compact lookup structure that returns a key’s value in 𝑂 (1) with a few memory accesses, without storing the keys themselves, cutting space by up to 90% compared with state-of-the-art hash tables. The Ludo table is sized at build time for its expected entry count and does  

> Proc. ACM Meas. Anal. Comput. Syst., Vol. 10, No. 3, Article 68. Publication date: December 2026. 68:8 Ling et al.

not grow in place. Its use of hashing is fundamentally different from the hash-placement family dismissed in Section 2.3: Ludo hashes a key only to locate the table slot holding a mapping that the writer chose, so the value can name any node, and two workers that independently cache the same prefix register their own locations under the same key, with no migration and no structural conflict. The explicitly written value yields the placement–identity decoupling that (O1) calls for, letting the plane track KV caches wherever computation leaves them. The keyless compactness makes parallel tables at many match lengths affordable, so multi-granularity matching (O2) need not multiply memory cost, and, combined with 𝑂 (1) lookup, lets the discovery index replicate in the local memory of every edge node, keeping lookups local and effectively free (O3). However, a flat Ludo table does not yet satisfy these objectives. As a key-value design it maps each key to a single value, hence exactly one worker, while in Internet-scale sharing the same prefix is often cached by many workers at once. It operates at one fixed prefix length, treating a nearby holder and a distant one equally, and because it stores no keys, a lookup for a prefix that was never inserted can return a false hit. Therefore, KVCompass redesigns the structure in three ways, which are described below. 

Tracking dynamic, multi-holder KV cache sets. The same prefix is cached by whichever workers happened to serve requests for it; the holder set churns continuously as KV caches are admitted under load and evicted under memory pressure, and each holder independently moves the prefix between VRAM and host DRAM, so a discovery index needs to resolve to a mutable set of holders and their storage tiers under a high rate of updates. KVCompass organizes the index as Ludo tables. Each entry indexes one prefix at one length within its table. For example, the entry indexing the first 𝑐 tokens of a prompt is keyed by a 63-bit key, the truncated SHA-256 digest of those 𝑐 tokens; 𝑐 here is drawn from the network latency-derived set of indexed lengths constructed below, so entries at many different lengths coexist in the same table. Each entry stores a packed value with one 2-bit tier field per worker in its table. The field is 01 for vram, 10 for dram, and 00 

otherwise. Each region has its own table. A 32-bit value holds tier fields for up to 16 workers, and a 64-bit value holds up to 32. Each field uses 2 bits. Every edge node keeps all region tables and combines their lookup results to find the holders. A region with more than 32 workers requires additional tables. When an entry is created, all worker fields in its table are initialized to 00 . A worker’s field becomes 01 or 10 when it caches the prefix. One read returns all worker fields in that table, and a tier change is an in-place 2-bit write. We exclude SSD because fetching a prefix on request arrival adds an SSD read to the serving path, typically costing more than recomputing it. 

Matching prefixes at distance-aware granularities. The discovery index needs to answer one question after finding the matched prefix: is this prefix match long enough to be worth forwarding to that region to reuse? Fixed chunk sizes of prefix cannot answer it (O2). Forwarding to another region to serve the request adds the round trip from the edge to the target region, while the match buys skipped prefill time, which grows linearly with the matched tokens at the per-worker prefill rate 𝛽 in ms/token. A match of 𝑛 tokens saves about 𝛽𝑛 ms, so this forwarding decision pays off once this KV cache reuse saving covers the added round trip. Therefore, KVCompass cuts the first indexed length at exactly this point. This shortest profitable prefix length is the first latency-derived prefix length 𝑛 1, and it scales with the measured latency from the edge to that region. Within the edge’s own region the round trip is so small that this formula would put 𝑛 1 at a few dozen tokens, guarding a cost that hardly exists, so same-region matching starts at a short fixed minimum. But one level per region is still not enough. The first latency-derived prefix length only tells the edge whether that forwarding is worthwhile; to pick among candidates, the forwarding decision needs to know how much each match saves. With a single indexed length a very long token match and a barely profitable one would look identical. KVCompass thus indexes several levels of increasing lengths above each region’s 𝑛 1, with the same number of levels toward every region.

KVCompass adopts these steps. We also measured multiplicative growth, but a match falls to the nearest indexed length below it, and multiplicative spacing grows coarsest exactly where matches are longest and most valuable, whereas the equal-step spacing keeps the under-crediting bounded by half of 𝑛 1 at every match length. The same-region lengths instead double from the short minimum, following the chunk sizes by which workers organize their KV caches. All the level lengths derive from a stable WAN latency matrix and per-worker prefill rates, so the whole structure can be computed offline and adds no extra overhead to the request serving path. 

Suppressing false hits without inflating the discovery index size. Because Ludo does not store the keys it indexes, a lookup for a prefix that was never inserted may collide with an unrelated entry and name a worker that does not actually hold it, so the request is forwarded to a worker without the prefix and pays a needless WAN round trip. Storing full keys at every edge node would eliminate these false hits but inflate the discovery index far beyond DRAM budgets, defeating the space efficiency that makes edge local lookup possible. KVCompass instead lets a false hit surface and absorbs it cheaply: the worker a request is forwarded to serves only the prefix it truly holds and recomputes the rest, so the answer is always correct and the only cost is one forwarding that saves less prefill than expected. To keep such forwardings rare, each edge node discounts a worker’s claimed match by a cache belief maintained from past responses, so a worker that often does not actually hold what it claims stops attracting requests, while the maintenance units keep the full keys off the forwarding path and use them only for collision detection when updating the index. 

3.3 System Components 

There are two kinds of software components that act on the discovery index. Lookup units resolve which workers hold how much of a prompt’s prefix at the edge node. Maintenance units turn KV cache events into the discovery index writes and propagate them to the lookup units. 

Lookup units. A lookup unit runs on the edge node and holds a view of every shard. Each lookup unit queries the multi-level tables at multiple lengths, derived from its measured network latencies toward each region. The lookup view stored on every edge node is identical. A worker registers each cached prefix at the union of lengths that any edge may query, so only the queried lengths differ across regions. Identical views keep the edges interchangeable. A new or recovering edge can bootstrap from the maintenance units or copy any other edge, and if every edge node of a region fails, another region’s edge can stand in. Holding everything at every edge node also costs little, since a view does not store the keys. Answering a query needs only the slot states, so the keys stay with the maintenance units. When a request arrives, KVCompass computes the prefix digests at the edge’s query lengths, reads the ⟨worker , tier ⟩ holders at each length from the lookup unit’s view, evaluates the joint score over all workers across regions, and forwards the request to the winner. Queries are plain memory reads with no locking, because each shard has a single writer and its update messages are applied in the order they were sent. 

Maintenance units. Maintenance units construct and update the discovery index and are its sole writers. Each unit owns one shard, the keys whose hash (𝐾 ) mod 𝑁 matches its identifier, and runs as a CPU-resident process co-located with a worker. Shards split the key space among the 𝑁 

writers, while views replicate the whole key space at every edge. Each maintenance unit therefore sends its shard’s updates to every edge when KV cache events happen, and each edge receives the update information of all 𝑁 units. On each KV cache event, the unit locates the key in its shard,

Within a region the replica is copied worker-to-worker connected by a high-bandwidth network. 3.5 Performance Modeling and Analysis 

We analyze discovery index memory, operation costs, and control traffic. 𝐸 is the total entry count across all tables, 𝑊 the worker count, 𝑅 the region count, 𝐿 the number of indexed levels, and 𝛽

Memory footprint. Following the Ludo analysis [40], at 95% occupancy a table requires about 0.263 four-slot buckets and 2.33 classifier bits per entry. With 32-bit values, the lookup view costs 2.33 + 0.263 × ( 5 + 4 × 32 ) ≈ 37 bits per entry. Retaining 63-bit keys raises the maintenance cost to about 104 bits per entry. With 64-bit values, these costs rise to about 71 and 137 bits per entry. Total memory sums these costs over all table entries, with additional allocation overhead. As workers and regions are added, more tables may be needed, and prefixes held in multiple tables occupy separate entries. Each edge stores all tables, so more edges increase total lookup-view memory.

4 Implementation 

As shown in Figure 10, we implement KVCompass in two forms: a real-machine prototype for end-to-end validation and an event-driven simulator for large-scale evaluation. The real-machine prototype couples instrumented SGLang workers with the KV cache discovery plane, while the simulator reuses the discovery-plane logic and models workers and network execution as events. 

Real-machine prototype. The prototype consists of SGLang workers and the KV cache discovery plane. SGLang workers are built on SGLang v0.5.10. Each worker serves one model replica deployed on one or more GPUs, provides request scheduling and model execution, manages the two-tier KV cache through admission, demotion, promotion, and eviction, and exposes a control module for load reporting, KV cache state-event reporting, and replica migration coordination. Cross-region requests are forwarded over the real WAN to the selected worker. The discovery plane builds on the reference C++ Ludo implementation [40] and comprises multi-level lookup units at edge nodes, sharded maintenance units, and the joint-score forwarding logic. Maintenance units process worker-reported KV cache events and propagate the resulting state updates to the lookup units. Edge nodes then rank workers with the joint score (Section 3.4) under their local view. 

Simulator. The simulator reuses the same lookup, maintenance, and cache-state logic, while replacing physical workers and the real network with their event-driven counterparts. Its request loop advances a virtual clock, replays requests in arrival order, and, for each request, models forwarding, queueing, service, and subsequent KV cache state updates. The simulated worker pool captures queueing delay, prefill and decode time, inter-region network latency, and the two-tier VRAM and DRAM KV cache, with prefill, decode, and WAN costs calibrated to hardware benchmarks and network measurements. This calibration and the shared discovery-plane logic connect the simulator to the prototype, but we have not quantified simulation error against a testbed run under identical settings.

5.8 False Hits in the Keyless Discovery Index 

The edge lookup view stores no keys, so a query for a never-inserted prefix can return a false locator from an occupied Ludo slot. Table 5 reports two rates. The structural false-positive rate measures how often a never-inserted key returns a false locator, reaching 45.3% at 95% table load. These rates use different query populations and measure different stages. Real requests can query prefixes already in the discovery index, and a false locator affects forwarding only if its worker wins the joint score. Cache belief discounts the claimed matches of workers that repeatedly reuse fewer tokens than claimed. A false lookup may reduce KV cache reuse, but the selected worker recomputes any missing prefix, preserving answer correctness. 

6 Discussion 

Serving multiple models. Our main evaluation serves one model across all workers, while Internet-scale deployments may serve several models. Even for the same prefix, different models, precisions, or parallel partitions produce incompatible KV tensors [11, 28]. Including model identity and configuration in the discovery index key would keep these KV caches separate. A lookup would then return only workers holding KV caches compatible with the request’s model and configuration. Entries for different models could coexist in one table without changing the discovery index structure, operations, or lookup views. The orchestration layer would still decide which workers load each model and when to replace its weights [10, 52]. 

Prefill–decode disaggregation. Our main evaluation runs prefill and decode on the same worker. Disaggregated systems separate the two phases because prefill is compute-bound and decode is bound by memory bandwidth [34, 36, 59]. In this setting, KVCompass routes prefill requests and tracks KV caches on prefill workers, since reuse saves prefill computation. Decode output becomes part of the next turn’s prefix and enters the discovery index when that prefix is prefilled. The serving stack selects decode workers and transfers KV caches. Appendix C evaluates this integration on a three-region testbed with SGLang and Mooncake, where KVCompass achieves lower median and

P99 TTFT than all evaluated baselines. Decode scheduling, transfer scheduling, and pool sizing remain the responsibility of the disaggregated serving stack. 

Security and privacy. KV cache reuse requires matching the entire indexed prefix, so a lookup does not return another user’s unknown prompt content. However, timing differences can reveal whether a known or guessed prefix is cached [9, 13, 41]. Existing timing attacks extend guesses a few tokens at a time. In KVCompass, indexed prefixes span at least hundreds of tokens, which may make incremental guessing more difficult, although an attacker who knows a suspected prefix may still infer its presence. Including a user or user-group identity in the discovery index key would restrict KV cache sharing to that group. The provider could choose the sharing boundary, while timing side channels within each group may still need mitigations such as response padding [2]. 

7 Related Work 

Geo-distributed LLM serving. KDN [6] and Prefill-as-a-Service [35] motivate KV cache sharing across datacenters. PlanetServe [9] supports decentralized serving with a radix-tree index for regional prefix reuse, while SkyWalker [48] balances load across regions. GORGO [44] optimizes cross-region routing using KV cache locality, network latency, and queue state, an objective close to KVCompass’s joint score. Its KV cache index estimates prefix availability without directly observing worker evictions. KVCompass instead tracks KV cache holders and storage tiers through KV cache events and replicates compact lookup views at every edge node. Our main contribution is how reusable KV caches are discovered across regions. 

Intra-cluster prefix caching. SGLang [58], ChunkAttention [50], and Hydragen [19] reuse shared prefix KV cache, while CacheBlend [49] reuses KV cache for arbitrary chunks. Mooncake [36], MemServe [18], and Infinite-LLM [24] pool KV cache across storage tiers. DualMap [54], Helix [31], Preble [42], LMCache [26], and LoongServe [47] support KV cache reuse and scheduling within a cluster. KVCompass’s joint score builds on prior KV cache-aware and load-aware routing, while its discovery plane finds KV caches across regions at prefix lengths chosen from network latency. 

Distributed naming and discovery. Chord [43], Kademlia [30], Pastry [39], and IPFS [5] map an item’s identity to a hash-designated node that holds or routes to it. KV caches are created on the workers that serve requests, so their locations cannot be derived from prefix hashes. KVCompass decouples KV cache identity from placement by tracking holders wherever KV caches are created. 

Compact key-value lookup structures. Othello [53] provides keyless 𝑂 (1) lookups, Ludo [40] adds dynamic updates, and Smash [29] applies explicit-write lookup to distributed storage placement. Cuckoo filters [8] address set membership. KVCompass tracks changing KV cache holders and storage tiers at latency-derived prefix lengths for Internet-scale LLM serving. 

8 Conclusion 

This paper presents KVCompass, a KV cache discovery plane for Internet-scale prefix sharing in LLM serving. By decoupling KV cache identity from placement, KVCompass discovers reusable KV caches wherever workers create them. Hash-placement schemes cannot provide this decoupling because they determine KV cache placement from its identity. Compact local lookups and a joint score balance prefix reuse, worker load, and network distance. Real-machine experiments and large-scale simulations show that KVCompass achieves lower TTFT and end-to-end latency and higher throughput than all baselines, while maintaining good load balance.

B Results over a Smaller Region Range 

The testbed of Section 5.2 spans three continents. To check that the discovery plane holds up under a very different geography, we also ran the full evaluation on a second testbed over a much smaller region range. It uses 11 RTX 5090 workers across four North-American regions, with 2 GPUs in Pennsylvania, 4 in Ohio, 1 in New York, and 4 in Calgary, and one-way WAN latencies of 5.8 to 16.6 ms among the three eastern regions and 24.9 to 37.4 ms to Calgary, far shorter than the intercontinental links of Section 5.2. Figure 17 reports the same three workloads and seven schemes. At 16 req/s, KVCompass achieves P99 TTFT 1.7 to 2.2 × below the hash-placement schemes and the Central Directory on Mixed and up to 29 to 33 × on WildChat and LMSYS, and maintains competitive throughput. The advantage carries over to this much closer region range, which shows the design is robust and not tuned to one geography. 

C Prefill-Decode Disaggregation 

KVCompass assumes prefill and decode run on the same worker, but serving systems increasingly disaggregate the two phases onto separate pools [34, 36, 59]. KVCompass adapts naturally, because KV cache reuse saves prefill computation, so the discovery plane routes only the prefill request and indexes only the prefill workers, while the decode instance and the KV transfer are left to the disaggregated stack. D Cross-Region Reuse in Production Traces 

Section 2.1 measures the cross-region reuse opportunity on WildChat. Here we repeat the analysis on production KV cache traces from two other providers, to show the opportunity is not specific to one workload. We replay four Qwen-Bailian usage traces [45] with chat, coder, and reasoning traffic, and the Mooncake conversation and tool-agent traces [36]. These traces carry no user locations. We assign each root session to one of 16 North-American regions in proportion to population, and follow-up turns inherit its region. We replay first-turn requests in arrival order and classify each reusable prefix of at least 1024 tokens as cold, cached in the local region, or cached only in another region, over 20 seeds. Figure 19 reports the remote-only share of hits. Across the six traces, 10 to 78% of reusable prefixes are cached only in another region when a request arrives, and 96 to 100% of shared-prefix reuse volume involves users from more than one region. These additional traces support cross-region reuse opportunities under the assigned region model, rather than measure actual cross-region traffic from these providers.
