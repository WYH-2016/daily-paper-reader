DRAM-based Processing-in-Memory (PIM) addresses the “memory wall” by executing computations directly inside main memory. However, memory interleaving and virtual memory limit contiguous data size visible to PIM units, constraining PIM task granularity. Fine-grained PIM tasks incur significant offloading overhead that negates PIM performance benefits. To mitigate this, existing PIM systems drastically isolate PIM memory or disable memory interleaving. These design choices, however, decrease the CPU memory bandwidth and introduce extra data transfer, leading to an additional “system memory wall” that degrades CPU performance and must be resolved to realize PIM’s full potential. In this work, we propose GUMPIM, a PIM system that allows interleaved CPU pages and non-interleaved PIM pages to coexist in a Unitary and Malleable memory space with Guaranteed PIM page allocation. GUMPIM enables zero-copy during PIM task offloading and maintains CPU memory bandwidth while ensuring low PIM offloading overhead. First, we propose a dual-track memory management mechanism consisting of independent page allocation and address translation for CPU and PIM pages. Second, we design GUMPIM interface hardware on PIM-enabled DRAMs to provide a dynamic address mapping for the different data layouts of CPU and PIM pages. Third, we propose a PIM-assisted page migration mechanism that transparently migrates pages while preserving CPU access bandwidth, thereby enabling guaranteed and accelerated PIM page allocation. GUMPIM requires no changes to commodity DRAM standards; all hardware modifications are limited to the DRAM side, ensuring full compatibility with existing CPUs and enabling immediate deployment on current HBMx- and LPDDRx-based PIM platforms. Our results show only <0.1% performance degradation for CPU workloads on GUMPIM, in contrast to the 25.8% degradation on PIM systems with memory interleaving turned off. For PIM workloads, GUMPIM reduces memory allocation and CPU-part computation times by 2.7× and 4.93×, respectively, yielding an end-to-end 2.3× speedup over a state-of-the-art baseline system. 1 Introduction 

DRAM-based Processing-in-Memory (PIM) is an emerging technology to overcome the “memory wall” [78] between processing units and main memory, by integrating computational components (PIM units) into DRAM. The PIM units are distributed in various levels of DRAM organization including arrays [16, 33, 51, 65, 71, 72, 81], banks [17, 19, 30–32, 48, 55] or ranks [8, 13, 56]. These PIM units can directly access data in their own memory device, bypassing the global memory bus and achieving much higher bandwidth than CPUs, making them suitable for memory-intensive operations. The PIM units are usually customized to accelerate specific memory-bottlenecked applications, such as graph computing, artificial intelligence, databases, genome analysis, and recommendation systems [1, 7, 9–11, 21, 24, 47, 49, 50, 53, 54]. General-purpose PIM systems emerge to support a broader range of workloads [2, 4, 6, 12, 17, 25, 26, 28, 29, 40, 56, 64, 70]. These systems allow memory-bound program segments to be offloaded to PIM units as PIM tasks while keeping compute-bound segments executed by CPUs. Therefore, the compatibility of these PIM systems with host CPUs becomes critical to ensure cooperation between CPUs and PIM units. Modern CPU-centric memory systems prevent PIM units from accessing large physically con-tiguous data due to two mechanisms: First, in virtual memory , the operating system (OS) maps

When offloading PIM tasks, the CPU needs to take a series of actions, including context switching [77] and locking memory regions [75]. For certain general-purpose PIM systems, this offloading overhead is even more than 50 𝜇 s [17]. Such offloading overhead results in PIM units having to process more data at each offload to amortize the cost. This requires PIM units to have access to even larger contiguous regions of data (like in Fig. 1(a)), further contradicting the design of modern CPU-centric memory systems. To ensure PIM efficiency, existing systems resort to extreme measures that incur significant overhead or degrade CPU performance. (i) Isolated memory space. A dedicated PIM memory space is physically isolated from main memory, as shown in Fig. 1(c) [17, 18, 57]. The CPU accesses this space via physical addresses, enabling manual placement of data on specific memory modules. However, PIM task offloading requires explicit data transfers between the two spaces over the memory bus (Steps 3 and 5 ), introducing an additional “memory wall.” (ii) Software data re-layout. CPU software explicitly reorganizes data layout to place contiguous blocks within a single memory module [17, 18, 34, 50, 56]. This further increases the offloading overhead – over 90% on tasks with frequent, fine-grained data re-layout as in BFS and NW, as evaluated on a real PIM system [31]. (iii) Globally disabling memory interleaving. Disabling memory interleaving can reduce the data re-layout overhead at rank and channel levels [17, 20, 56]. However, doing so greatly degrades CPU memory bandwidth, aggravating the “memory wall” between CPU and DRAM. To truly break the “walls”, a unitary, malleable memory space is essential for general-purpose heterogeneous CPU-PIM systems, as depicted in Fig. 1(d). CPU and PIM pages, with different data layouts (Fig. 1(a, b)), coexist in the memory space. This memory management strategy fulfills the requirements of PIM units for contiguous data layout while avoiding the negative consequences of the above extreme measures. First, the memory space enables zero-copy by eliminating data transfers (no 3 and 5 in Fig. 1(d)) during offloading. Second, CPUs access PIM pages efficiently and transparently without requiring software-level address remapping and data re-layout. Third, CPU bandwidth is preserved as in CPU-centric systems because CPU pages can still leverage standard memory interleaving. To preserve compatibility with existing CPU hardware and OS, the following challenges should be addressed. (i) CPU and PIM page coexistence. A unitary memory space requires the PIM unit to share the CPU-managed virtual memory, necessitating that adjacent virtual PIM pages be kept

Efforts should be made to alleviate the bank conflicts when the host CPU accesses the non-interleaved PIM pages, which potentially degrades CPU memory bandwidth. (iv) Compatibility. Hardware modifications should primarily focus on the DRAM side to maintain compatibility with existing CPUs and motherboards. In this work, we propose GUMPIM, a general-purpose PIM system with a unitary, malleable memory space and dual-track memory management for CPU and PIM pages. Existing memory allocation and address mapping mechanisms for CPU pages are kept unchanged to preserve compatibility. For PIM pages, we propose chunk-based memory management to enable locality for PIM pages and maintain low address translation overhead. We propose GUMPIM interface hardware for efficient address mapping and improve memory bandwidth available to the CPU when it accesses CPU and PIM pages. Additionally, chunk-based memory management requires allocating contiguous memory for PIM pages, which existing CPU systems lack because memory fragmentation leaves only scattered, non-contiguous free regions [22, 66, 84]. We propose a PIM-assisted page migration mechanism to enable contiguous memory allocation for PIM pages. All our hardware modifications are limited to the DRAM side. An earlier version of this work (UM-PIM) was published in the proceedings of ISCA 2024 [85]. This journal version significantly extends the previous work with the following new mechanisms and results: (1) A PIM-assisted page migration mechanism that enables successful allocation of PIM pages while maintaining full compatibility with existing CPU-side hardware, and significantly accelerates the page allocation (Section 6). (2) A generalized design for dual-track memory management extended beyond the original architecture to support diverse DRAM types, including LPDDRx and HBMx, with complete implementation details that were previously only discussed at a high level (Section 7). (3) Evaluation of the memory allocation speedup with the proposed PIM-assisted page migration mechanism, and demonstration of the effectiveness of the unitary memory design on LPDDRx- and HBMx-based DRAM PIM (Section 8.4-8.6). Consistent with the design principle of the original UM-PIM [85], these new techniques also confine hardware modifications strictly to the DRAM side and ensure compatibility with the CPU-side hardware and DRAM standard protocol. The main contributions of this paper are: 

• We identify the root cause of excessive data orchestration overhead in existing processing-in-memory systems: the additional memory wall imposed by isolated PIM memory spaces that are not directly accessible by the host CPU. 

• We propose GUMPIM, a general-purpose PIM system with a unitary and malleable memory space, which incorporates dual-track memory management along with dedicated hardware support. We demonstrate that this approach naturally extends to other DRAM standards, including HBMx and LPDDRx, without PIM-side modifications. 

• We design a high-level programming interface with collective communication primitives inspired by NCCL [63]. By exploiting the shared address space and fine-grained inter-PIM connectivity of GUMPIM, these primitives dramatically reduce synchronization and data movement overhead across PIM units. 

• We introduce a PIM-assisted transparent page migration mechanism that dynamically con-structs large contiguous physical memory regions for PIM workloads, eliminating host-side fragmentation and enabling efficient and correct huge-page allocation. 2 Background 2.1 Address Mapping and Memory Interleaving 

In modern systems, the virtual address (VAddr) is mapped to the DRAM hardware location in two steps. First, the memory management unit (MMU) translates the virtual address to the physical address (PAddr). The virtual page number (VPN) is translated to the physical page number (PPN) by the OS-managed page table, while the page offset is kept unchanged. After that, the memory controller maps the physical address to the hardware address (HWAddr) using the address mapping rule saved in the BIOS-defined target address decoder (TAD) register, which is fixed after boot. Memory interleaving enhances memory bandwidth by mapping adjacent data across different DRAM devices for parallel access. For example, the DDR4 DRAM hierarchy levels, in descending order of switching overhead, are row, rank, bank, column, and channel [41]. The simplest inter-leaving scheme maps lower-order address bits to memory hierarchy levels with lower switching overhead, (Fig. 2(a)). At the device level, devices (i.e., chips) are grouped to expand data bus width [41]. Individual devices are not separately addressable and share common bank address signal lines within a rank [41]. Therefore, they must be accessed simultaneously, and device-level interleaving cannot be controlled via CPU-side address mapping. To accommodate various access patterns, practical memory interleaving strategies often employ sophisticated mapping [14, 37, 67, 76, 79]. Nevertheless, they all depend on the high-order bits of the physical address to select rows due to significant row-switching overhead. Additionally, they scatter contiguous data across different banks and devices, which goes directly against good data mapping for PIM systems. PPN  Offset

In contrast with CPUs, general-purpose PIM units require the ability to access a contiguous block of data in their own memory. Therefore, the ideal PIM address mapping maps lower-level memory hierarchy addresses to lower-order bits, as shown in Fig. 2(b), ensuring contiguous physi-cal addresses to reside inside a DRAM device. This requirement contradicts the CPUs’ memory interleaving. Current general-purpose PIM systems adopt a software-only approach to emulate the address mapping for PIM units. They allocate or reserve a large block of contiguous physical addresses as PIM memory space and lay out the data in the PIM memory space with CPU software [17, 31, 50, 75]. IMPICA [39] proposes to use huge pages to reduce the address translation over-head in PIM memory space. However, due to the byte-level memory interleaving in DRAM, these software-only methods introduce significant data re-layout and address mapping overheads.

Li et al. [58] compare the address translation overhead of hardware and software methods, finding that the hardware approach reduces overhead by 4.5×. Therefore, a hardware solution is necessary to reduce the dynamic address mapping overhead in PIM systems. 

2.3 Dynamic Memory Mapping 

Dynamic address mapping is widely researched in CPU systems [23, 38, 59, 62, 83]. DReAM [23] and PAE [59] add hardware on the DRAM memory side to dynamically recognize the better-performing address mapping and transparently change the address mapping method. However, this transparency hides device physical addresses from the host, failing to guarantee the operand co-location required by PIM units. Multiple physical mappings [38] and software-defined address mapping [83] enables dynamic mapping by configuring memory controllers and adding CPU-side hardware, respectively. However, these methods limit interleaving control to levels above the bank level due to memory controller constraints. Moreover, the method in [83] modifies the memory management model, requiring changes to the system software as well as hardware. It is important to enable control over the interleaving of all DRAM hierarchy levels solely via DRAM-side hardware modifications, without requiring changes to system software. 

3 Dual-Track Memory Management 

GUMPIM’s dual-track memory management adopts separate management for CPU pages and PIM pages in the unitary, malleable memory space, allowing both to be optimized without compromising the other. Global memory interleaving is turned on to preserve CPU memory bandwidth. On top of this interleaved memory space, we keep the existing virtual page management and address mapping rules unchanged for CPU pages to preserve compatibility, while proposing chunk-based memory management for PIM pages to enable locality. 3.1 Chunk-based Memory Management for PIM Pages 

On the software side of the GUMPIM system, the key idea to prevent the OS from arbitrarily mapping PIM pages in an interleaved memory space is to enforce a uniform distribution of PIM pages across all PIM units’ local memory. We thereby present chunk-based address management for PIM pages. A chunk is a large virtual address block, which is mapped to a contiguous block of physical addresses. In Linux, the chunk can be allocated through the transparent huge page (THP) mechanism. As mentioned in Section 2.1, most interleaving strategies map the Row address to the highest-order bits of the physical address. Based on this observation, if the chunk size ( 𝑆 𝐶 ) is large enough ( 𝑆 𝐶 ≥

#Channels × #Ranks × #Banks × #Devices × row buffer size), with the global memory interleaving turned on, the chunk is evenly distributed across all memory banks. For example, the memory system configuration shown in Fig. 2 comprises 8 channels, 4 ranks per channel, 8 banks, and 8 devices per rank. If the chunk size is set to 256 MB, each bank would contribute 𝑆 𝐵 = 𝑆 𝐶 /( 8 × 4 × 8 × 8) =128kB of data, i.e., the PIM page size. This means that when a PIM chunk is allocated, each PIM unit gets a 128kB PIM page in its PIM local memory. 

3.2 CPU Addressing PIM Pages 

A preferred address layout inside PIM chunks is shown in Fig. 4(b), where adjacent addresses are preferentially mapped to the same PIM unit. Fig. 4(a) shows its corresponding address mapping, including the composition of the virtual, physical, and hardware addresses and their translation and mapping. VAddr[47:28] serves as the virtual chunk number (VCN) to select the chunk and is translated to the physical chunk number (PCN) that is used for recognizing PIM pages. VAddr[27:0] is the chunk offset and is passed unchanged to PAddr[27:0] during address translation. PAddr[27:17] in the chunk offset are mapped sequentially to channel, rank, bank, and device, encoding the unique identifier of the target PIM unit ( PIM unit ID ) for software tracking. Finally, PAddr[16:0] are mapped to row and column inside the 128kB PIM pages, referred to as PIM offset .In practice, one 128kB PIM page for each PIM unit might not be enough for PIM tasks, so multiple chunks are allocated. The CPU host program records the virtual chunk numbers of these chunks in an array ( 𝑉𝐶𝑁𝑠 ). 3.4 Chunk Size Selection 

Chunk size is a critical system parameter. Generally, allocating a huge page larger than 4MB may require page migration to accommodate it. A larger chunk size inherently encompasses more occupied pages, thereby increasing the number of pages that must be migrated. Conversely, a small chunk size necessitates allocating more chunks to satisfy PIM units’ capacity demands. This in turn requires a larger PIM Chunk List to store PIM chunk numbers, increasing storage overhead. Fig. 5 displays the migration overhead and PIM Chunk List area across varying chunk sizes. Critically, since PIM memory allocations are typically long-lived and reused throughout the application execution, multiple runtime allocations and releases of PIM chunks can be largely avoided. Therefore, we prioritize minimizing the PIM Chunk List area and select 256 MB as the chunk size. In practice, this size can be adapted to any standard huge page configuration supported by the host OS.

4.1 CPU-side Address Mapping 

As mentioned in Section 3, CPU and PIM pages have different data layouts and require dynamic address mapping. For CPU pages, the address mapping path is kept unchanged as configured in the BIOS. The address mapping for a PIM page involves two steps: above-bank and below-bank address mapping. Above-bank address mapping is implemented by configuring the CPU’s BIOS. For below-bank address mapping, hardware modules are introduced on the DRAM side. This is because the intra-rank device organization is entirely transparent to the host CPU and cannot be configured via BIOS. 

4.1.1 Above-Bank Address Mapping. For address mapping of hierarchies at and above the bank level (i.e., channel, rank, and bank in DIMM DRAM), we adopt the multiple address mappings technique [38]. With this approach, an address alias with a different address mapping is added by configuring the memory controllers through the BIOS. For example, in the Xeon processor, an alias can be implemented by appending a TAD region, 𝑇 𝐴𝐷 1, to the PCI configuration space. 

𝑇 𝐴𝐷 1 points to the same memory space as the default 𝑇 𝐴𝐷 0 (Fig. 6(c)), but with a non-interleaved address mapping, as shown in Fig. 6(b). In our example with a 256GB memory system, the interleaved physical address space spans [0, 256GB), while the non-interleaved address alias spans [256GB, 512GB). Bit 37 of the physical address determines which TAD region an address belongs to. If bit 37 is 0, the address is from a CPU page, using 𝑇 𝐴𝐷 0 for address mapping. Otherwise, the address is from a PIM page and 𝑇 𝐴𝐷 1is used. After determining the used TAD, the memory controller performs partial address mapping. In this step, only physical address bits for rank, channel, and bank are mapped to the real hardware address. The remaining bits are transferred to the DRAM side GUMPIM interface for below-bank address mapping. This means that the hardware address generated by the memory controller at this step is an intermediate result and is to be further mapped by the GUMPIM interface presented in Section 4.1.2. To comply with the DRAM protocol, the remaining bits are divided into row and column addresses ( 𝐶𝑜𝑙 _𝑎𝑑𝑑𝑟 and 𝑅𝑜 _𝑎𝑑𝑑𝑟 in Fig. 6(b)) and sent to DRAM.

4.1.2 Below-Bank Address Mapping. Dynamic address mapping of levels below the bank (i.e., row, device, and column), as illustrated in Fig. 6(b), is carried out by three main hardware modules, the Rank Chunk List (RCL), Address Translation Module (ATM), and Command Generator (CG), in the GUMPIM interface. The three hardware modules are integrated into the RCD chip, as shown in Fig. 6(a). The Rank Chunk List determines the page type, while the Address Translation Module maps the remaining bits of the intermediate hardware address to row, column, and device addresses. Command Generator (CG) generates a command with the real address for the DRAM interface. 

Rank Chunk List . Each row of the Rank Chunk List stores the physical chunk number of one chunk. Upon receiving a row address, the highest 9 bits of the address are matched against the list. A hit (HIT=1) indicates a PIM page, while a miss (HIT=0) indicates a CPU page. 

Address Translation Module and Command Generator . As depicted in Fig. 6(c), if the Rank Chunk List detects that the address belongs to CPU pages, the Address Translation Module keeps the row and column addresses unchanged. Otherwise, the Address Translation Module maps bits 9-7 of the original column address ( 𝐶𝑜𝑙 _𝑎𝑑𝑑𝑟 ) as the device address ( 𝐷𝑒 _𝑎𝑑𝑑𝑟 ), and other bits are left-shifted by 3 (zero-padded at the least significant bits) to generate the real column address (𝐶𝑜𝑙 _𝑎𝑑𝑑𝑟 _𝑟 ). The row and column addresses are sent to the DRAM interface for data access, and the device and bank addresses are sent to the Re-layout Cache (RC) for further data selection. We present the procedure in Section 4.3. After mapping the address, the Command Generator generates the real command for the DRAM interface. 

Timing of Address Mapping. Although the GUMPIM interface is in the critical path between the memory controller and the DRAM interface, it preserves native DRAM device timings. Fig. 8(a) depicts a read ( RD ) request and its prerequisite requests, precharge ( PRE ) and activate ( ACT ). After receiving a precharge request, the GUMPIM interface starts to convert the address and then sends the real precharge request to the DRAM interface. The memory bus, GUMPIM interface, and DRAM interface form a pipeline. As a result, the DRAM timing 𝑡𝑅𝑃 and 𝑡𝑅𝐶𝐷 are kept unchanged. In effect, only a fixed delay 𝑡𝑈 𝐼 is incurred on end-to-end read latency without accumulating across pipelined commands, so its impact on the overall read latency is minimal. 

4.2 PIM-side Address Translation 

PIM Chunk List. The PIM Chunk List contains the physical chunk numbers allocated by the CPU, where each entry is indexed by its corresponding PIM chunk number ( 𝑁 ). When the PIM unit generates a virtual address, the PIM Chunk List looks up the 𝑁 th row and gets the corresponding physical chunk number. The physical chunk number is further combined with the PIM offset to obtain the physical address. 

4.3 Data Re-layout 

The DRAM is designed to access data at burst granularity [42–44]. Assume a DRAM burst size of 64B and a bit width of 64 bits. In each burst, the DRAM interface accesses 8B of data from every device to fully utilize the device-level parallelism. For example, as illustrated in Fig. 7, one burst consists of data 00 , 10 , . . . , 70 , which are distributed across all devices of a rank. However, according to the mapping rules of PIM pages, a consecutive 64B range of a PIM page, denoted as 

PIM burst , is mapped to the same device. For instance, one PIM burst comprises data 00 , 01 , . . . , 07 .Accessing such a complete 64B range requires 8 normal burst accesses, with each device providing 64B of data. The remaining 7 × 64B, however, remain unused, resulting in a waste of memory bus bandwidth and requiring CPU intervention to filter out these unused cache lines. Therefore, we propose adding a Re-layout Cache module to buffer, re-layout, and assemble the contiguous 64B on the DRAM side, conserving memory bus bandwidth and mitigating the need for CPU involvement.

5 Software Support for GUMPIM 

In this section, we provide API support for memory management and specific memory access modes. We also provide APIs for specific data transfer operations between PIM units, i.e., scatter, broadcast, and gather. 

5.1 Memory Allocation 

For CPU pages, we keep the malloc() function in glibc unchanged. For PIM pages, we define an API function malloc_pim( 𝑙𝑒𝑛 ) to allocate memory with length 𝑙𝑒𝑛 for all PIM units. The API calculates the required chunk count based on 𝑙𝑒𝑛 , allocates chunks through the mmap() system call, and marks them as THPs through madvise() . Due to demand paging, the CPU must access at least one byte per chunk to trigger physical page allocation. Since PIM units cannot handle page faults, the mlock() system call is invoked to prevent PIM chunks from being swapped out. Finally, the API queries /proc/pid/pagemap for the physical address and extracts the physical chunk number, which is then registered to the Rank Chunk List and PIM Chunk List via the ACN instruction. Upon program termination, the CCL instruction clears the two Chunk Lists. 

5.2 Unit-Aware Memory Access 

To simplify memory access across multiple chunks within a PIM unit, we provide unit-aware APIs that allow developers to access data by specifying the PIM unit ID and PIM offset, without manually computing virtual addresses. The unit-aware APIs are summarized as follows: 

• pim_get_ptr( 𝑢𝑛𝑖𝑡 _𝑖𝑑 , 𝑜 𝑓 𝑓 𝑠𝑒𝑡 ) returns a pointer to the memory at the specified offset within the given PIM unit’s local memory, facilitating random access. 

• pim_copy( 𝑑𝑠𝑡 _𝑢𝑛𝑖𝑡 _𝑖𝑑 , 𝑑𝑠𝑡 _𝑜 𝑓 𝑓 𝑠𝑒𝑡 , 𝑠𝑟𝑐 _𝑢𝑛𝑖𝑡 _𝑖𝑑 , 𝑠𝑟𝑐 _𝑜 𝑓 𝑓 𝑠𝑒𝑡 , 𝑙𝑒𝑛𝑔𝑡ℎ , 𝑑𝑖𝑟𝑒𝑐𝑡𝑖𝑜𝑛 ) han-dles memory copy operations with automatic cross-chunk boundary management, where

5.4 High-level APIs for Inter-PIM-Unit Data Transfer 

We provide several high-level APIs for widely used inter-PIM-unit communication operations whose performance is significantly affected by the Re-layout Cache hit rate. Due to the significant cost of communication between PIM units, existing PIM systems often adopt a fork-join computing mode [17, 31, 50, 56]. therefore, we adopt communication modes from NCCL [63] and present the nested-loop order for these modes to better utilize the Re-layout Cache. 

Scatter. Scatter reads a contiguous data block from a single DRAM bank and distributes its subblocks across all banks. Fig. 9(a) presents a scatter that involves 4 PIM units. In each iteration of the outermost loop 𝑙 , a burst length of data is read from each bank and written to the destination PIM bank. The Re-layout Cache in each rank buffers data from 8 devices and performs batch writes, thereby fully utilizing its locality.

Broadcast. Broadcast reads a data block from a single DRAM bank and writes it to all banks. Fig. 9(b) depicts a broadcast originating from PIM 0. In each iteration of the outermost loop 𝑙 , a 64B block is read from PIM 0 and written to every PIM bank. This order fully leverages the locality of the Re-layout Cache. 

Gather. Gather is the reverse of scatter, reading data blocks from all DRAM banks and consoli-dating them into a single bank. As shown in Fig. 9(c), PIM 0 gathers data from every bank. The outermost loop 𝑙 iterates over data block offsets, similar to scatter. By reading data with the same offset 𝑙 in adjacent iterations, the locality of the Re-layout Cache is fully utilized. 

6 Guaranteed PIM Chunk Allocation 6.1 Memory Fragmentation and Chunk Allocation 

As presented in Section 3.1, chunk-based PIM page management requires allocating a large block of contiguous memory space. However, allocating a chunk is challenging in modern operating systems due to severe physical memory fragmentation. Our experiments on a 256GB memory system show that even at only 25% memory occupancy, allocating a single 256MB chunk can fail. Although the OS attempts to form contiguous space via page migration, this approach falls short for two reasons: First, page migration overhead (~4 𝜇 s per page [84]) can offset PIM’s performance gains. Second, unmovable pages (e.g., slab and DMA pages that have strict access latency constraints) are scattered throughout the memory, preventing the OS from consolidating contiguous physical memory. Consequently, chunk allocation fails and falls back to normal 4kB pages, violating the contiguous memory requirement of PIM. Static memory reservation (e.g., hugetlbfs [74]) avoids migration but lacks flexibility and wastes memory for CPU applications. Thus, overcoming the latency and mobility bottlenecks of dynamic page migration offers a far more practical path to guaranteed chunk allocation. 

6.2 Challenges in CPU-Assisted Page Migration 

Page migration overhead fundamentally stems from three components: Translation Lookaside Buffer (TLB) shootdown, Page Table Entry (PTE) updates, and data copying. To reduce these costs, state-of-the-art CPU-assisted designs like Contiguitas [84] introduce hardware extensions in the Last-Level Cache (LLC) to buffer migrating pages, allowing host CPUs to access them during migration. This method reduces the page migration overhead by 2× by eliminating the need for locking and TLB shootdown, and enables migration of otherwise unmovable pages. Despite these improvements, this cache-based approach introduces two critical limitations. First, the migrating page copy is buffered in the LLC, forcing I/O devices to redirect accesses to the CPU-side cache and requiring substantial CPU-side hardware modifications. Second, because data must still be transferred between main memory and the CPU, migration overhead remains high. The memory copy accounts for 58% of the total migration overhead (TLB shootdown is excluded) according to our simulation. 

6.3 PIM-Assisted Page Migration 

PIM architectures offer a promising alternative to fundamentally alleviate migration bottlenecks and achieve flexible, on-demand chunk allocation. By offloading transparent page migration entirely to custom hardware components on the DRAM side, we can eliminate expensive bus-crossing data movements while keeping the migration process nearly transparent to the host CPU. The core insight of PIM-assisted page migration is to introduce an address redirection scheme in DRAM, coupled with data movement performed directly by the PIM units. This ensures that CPUs and I/O devices access the correct data throughout the entire migration process without

We deliberately constrain all hardware modifications to the DRAM side, which is architecturally principled: DRAM serves as the ultimate memory layer that is physically shared and directly accessible via physical addresses by all system agents (e.g., CPUs, GPUs, and I/O controllers). Implementing address redirection directly inside DRAM leverages this universal visibility, enabling seamless, transparent access across all system agents throughout the migration process. 

Row Migration Table (RMT). The Row Migration Table is a lightweight hardware component that resides in each memory bank and tracks data location and migration status, enabling row address redirection throughout migration (Fig. 10(a)). Each Row Migration Table entry contains two key fields: (1) a location field ( loc ) indicating whether the row has been physically migrated, and (2) a copying field identifying the row currently being migrated. Fig. 10(c) illustrates the redirection principle for three cases, covering all possible situations during migration. In case 1, a PIM unit is copying 𝑅 0 ( copying = 𝑅 0). The data being copied is loaded into the PIM buffer, and the Row Migration Table redirects the access to the PIM buffer if the CPU accesses 𝑅 0. In case 2, when the CPU accesses 𝑅 0 while the data is still in the source row ( loc = 0), the Row Migration Table redirects the access to the source row. In case 3, the migration of 𝑅 0 completes ( loc = 1), and the Row Migration Table routes the access to the new physical row 𝑅 2. This hardware-supported redirection ensures the correct data access during migration, maintaining coherence for CPUs and I/O devices until the OS updates the page tables. Migration Workflow. When the PIM program allocates a chunk, the OS selects a candidate physical region. The OS identifies the occupied pages within this region and allocates an equivalent capacity of free physical pages via native memory allocation mechanisms (e.g., the Linux Buddy System [27]) to accommodate these pages. Fig. 10(b) illustrates the subsequent page migration process. The OS issues the SRMT instruction (summarized in Table 1) to initialize the Row Migration

Table with source-destination row address ( src -dest ) pairs ( 1 ). The location field of every entry is initialized to 0. After the Row Migration Table is populated, the CPU triggers the PIM units to perform the migration row by row ( 2 ). To copy a row, the PIM unit first loads it entirely into the PIM buffer. Upon migration completion, if the buffered data remains unmodified, the PIM unit clears the buffer and sets the corresponding location field to 1. Otherwise, the PIM unit re-writes the dirty buffer to the destination row. This mechanism ensures that the CPU can always access the right data during migration. The CPU periodically polls the Row Migration Table to monitor progress, determining that the migration is finished once all location fields are set to 1. Subsequently, the OS performs the necessary software updates to ensure translation consistency, which include: (1) leveraging reverse mapping (rmap) to locate all virtual pages and page-table entries (PTEs) that reference the migrated physical pages, (2) updating those PTEs to point to the new physical destination ( 3 ), and (3) issuing a global TLB flush as in conventional page migration ( 4 ). Although the rmap phase may incur significant latency, it does not access the old physical frames, which have already been vacated, and therefore does not block the PIM program from utilizing the newly allocated chunk. Finally, the CPU issues a CRMT instruction (summarized in Table 1) to clear the entire Row Migration Table ( 5 ), preparing it for the next migration. To avoid the complexity of multi-level redirection or migration chains, the system enforces serialized chunk allocation by allowing a new allocation only after the Row Migration Table is fully cleared. This strict ordering ensures that any subsequent memory access or migration request starts with a clean Row Migration Table state, preventing circular lookups and ensuring that the destination of one migration does not prematurely overlap with the source of another. While this mechanism enables seamless in-DRAM redirection, a fundamental design question remains: why must this migration and redirection operate at the DRAM row level rather than the standard OS page level? We justify this granularity choice below. 

6.4 Justification of Migration Granularity 

Note that for each bank, the minimum page migration granularity of GUMPIM is an entire DRAM row. This constraint is imposed by the DRAM access protocol defined in JEDEC standards [42–44]. During each access, the memory controller first issues an ACT command with the row address, which physically activates the target row. Only afterward are column addresses sent via read or write commands to access data within the activated row. To comply with strict DRAM timing constraints, the Row Migration Table must resolve the target physical row address (either src 

or dest ) immediately upon receiving the ACT command. Crucially, because the column address is not yet issued, the Row Migration Table cannot make decisions based on the column address. Otherwise, a sub-row migration would leave the Row Migration Table unable to determine the correct row to activate, inevitably causing subsequent column accesses to read corrupted data. Thus, per-bank migration must occur at the granularity of a complete DRAM row, typically 4–16kB per rank in DDR4 (e.g., 8 devices with 0.5–2kB each) [43]. At the system level, per-bank migration must be coordinated across interleaved memory channels. If only one channel’s bank were migrated, a page striped across multiple channels would become only partially migrated, breaking data contiguity. The OS must therefore coordinate migration at the granularity of a row stripe, which aggregates co-aligned physical DRAM rows across all interleaved channels (e.g., spanning 64kB in an 8-channel system with an 8kB row size). Accordingly, GUMPIM adopts this row-stripe granularity as its fundamental unit for both hardware redirection and software management.

During execution, we periodically sample the number of fully free row stripes (i.e., no page allocated within the row stripe), and plot the results in Fig. 10(d). Even at high occupancy levels (e.g., >90%), there are still over 5000 free row stripes, sufficient to accommodate the entire capacity of a chunk. This indicates that, under typical workloads and the Linux kernel’s page allocation policy, memory fragmentation smaller than a row stripe size can be effectively avoided. Consequently, the assumption of available destination rows for row-stripe-granular PIM-assisted migration is valid in practice.

8.4 Chunk Allocation Overhead 

In this experiment, we explicitly include the overheads of memory allocation and data loading before the workload execution, as shown in Fig. 15. The page migration and memory allocation overhead is obtained using the full-system (FS) mode of GEM5, running a Linux kernel (Ubuntu 6.8.0). We compare GUMPIM’s PIM-assisted allocation mechanism against a conventional CPU-driven approach, where occupied pages are migrated by first reading them into the last-level cache and then writing them back to DRAM [84]. Fig. 15(a-c) compares the two approaches under different migration ratios (i.e., the fraction of occupied pages that require migration during chunk allocation) when only one round of computation follows each allocation. The results show that the PIM-assisted allocation reduces chunk allocation time by 2.7×, thereby lowering the average end-to-end latency of PIM workloads by 2.3× at a 50% migration ratio. For most PIM benchmarks, including UNI, SCAN-RSS/SSA, SEL, and HST-S, chunk allocation alone accounts for over 95% of the total end-to-end latency. This highlights a characteristic trait of PIM workloads, which is large memory footprints but modest computational demands. Consequently, for these workloads, the PIM-assisted allocation mechanism achieves an average end-to-end speedup of 2.65×. We also compare the end-to-end time under different computation-to-allocation ratios (C:A) in Fig. 15(a,d-f). The computation-to-allocation ratio is defined as the number of computation task rounds following each allocation. As the computation-to-allocation ratio increases, the speedup of GUMPIM decreases as the proportion of computation time increases. However, even when “C:A=100:1”, PIM workloads with large memory footprints but modest computational demands (e.g., UNI, SCAN-RSS/SSA, SEL, and HST-S) can still benefit from the PIM-assisted allocation mechanism. These benchmarks achieve an average speedup of 2.6×. This demonstrates that reducing allocation latency remains critical for real-world PIM workloads, even when computation dominates the nominal execution profile. The time breakdown of PIM-assisted page migration is shown in Table 5. The breakdown is measured by injecting M5ops [73]. With PIM-assisted page migration, the data copy proportion is reduced from 58% to less than 1%, reducing the chunk allocation time by 2.7×.

8.6 GUMPIM on LPDDR5 and HBM3 

We also compare GUMPIM with PIM-Ioff on LPDDR5 and HBM3. The detailed configuration is summarized in Table 3. We keep the number of banks in the LPDDR5 and HBM3 systems the same as that in the DIMM system. As there is no device level for word expansion in LPDDR5 and HBM3, the total number of PIM units is 1/8 of that in DIMM. The address mapping configuration is kept the same as that in the DIMM system, with higher hierarchy levels mapped to higher-order bits of the physical address. We plot the CPU-part time, including CPU computing and data transfer, in Fig. 17. We select 5 typical benchmarks from Table 4, and GUMPIM reduces the CPU time by 6.0× on average across these benchmarks. For PIM-Ioff on the LPDDR5 system, GUMPIM reduces the CPU time by 5.9× on average. The advantage is slightly smaller than that on the DIMM system because the LPDDR5 system does not have the device level, resulting in software data re-layout working at the cache-line level instead of the byte level. Therefore, the transfer overhead is originally smaller than that in the DIMM system. For PIM-Ioff on the HBM3 system, GUMPIM reduces the CPU time by 5.2× on average. This is because HBM3 DRAM originally has larger memory bandwidth, resulting in smaller transfer overhead in PIM-Ioff. Although GUMPIM provides a smaller advantage on these two DRAM systems, it can still achieve a significant speedup over PIM-Ioff. 

8.7 Area 

The area and power overhead of the proposed modules is summarized in Table 6. The PIM Chunk List and Row Migration Table introduce 0.13% overhead compared with the 130 mm 2 DRAM die area derived from CACTI. The Rank Chunk List, Address Translation Module, and Command Generator contribute 0.72 mm 2 additional area (~0.48%) to the RCD chip [69]. The Re-layout Cache occupies 0.21 mm 2, which is significantly smaller than the DRAM buffer chip (100 mm 2). 

9 Conclusion 

In this work, we propose GUMPIM, a new system architecture with a unitary and malleable memory space for both CPU and PIM units. GUMPIM provides fine-grained interleaving for CPU pages, eliminates data transfer overhead between CPU and PIM units, and reduces PIM page allocation latency. The method can be adapted to various DRAM architectures, including DIMM DRAM, LPDDRx, and HBMx. GUMPIM achieves only 0.1% performance loss for CPU tasks while delivering a 2.3× overall speedup for PIM tasks by reducing CPU-part time and memory allocation time by 4.93× and 2.7×, respectively.
