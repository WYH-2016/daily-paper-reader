## Abstract 

The growing adoption of large language models (LLMs) has significantly increased the compute and memory demands of inference serving. A key challenge arises from the mis-match between compute-bound prefill and memory-bound decoding: when executed together, the two phases interfere, while separating them via prefill–decode (PD) disaggregation leads to substantial resource underutilization. Specifically, prefill leaves memory bandwidth underutilized, whereas de-coding underutilizes compute resources. Prior approaches, such as GPU Streaming Multiprocessor (SM) partitioning, attempt to improve utilization by spatially dividing GPU resources. However, these approaches remain fundamentally limited, as memory-bound decoding still requires a large number of SMs to saturate bandwidth, reducing the compute resources available for prefill and resulting in an inherent trade-off. To address this limitation, we propose DuoPD , a hybrid PD-disaggregation architecture that integrates light-weight Processing-Near-Memory (PNM) units into the HBM logic die. Unlike prior PIM/PNM designs that rely on costly internal bandwidth scaling and offload only partial decod-ing operations, DuoPD enables full decoding execution on PNM by leveraging bandwidth sharing with the GPU over a shared HBM interface. This allows compute-bound prefill and memory-bound decoding to execute concurrently with minimal interference, improving both compute and memory utilization. To realize this design, we develop a compact PNM microarchitecture, a TSV-level bandwidth sharing mecha-nism, and a hierarchical data mapping scheme tailored for hy-brid GPU–PNM execution. Evaluations on server-scale LLMs demonstrate that DuoPD achieves up to 2.23 × higher end-to-end throughput than conventional PD-disaggregation.

## 1 Introduction 

The demand for efficient Large Language Model (LLM) [1– 3] inference has surged with the rapid growth of applica-tions such as chatbots and machine translations [4, 5]. Due to their massive parameter sizes, LLMs require substantial compute and memory resources. To meet these demands, modern GPUs [6, 7] integrate a large number of compute cores and high-bandwidth memory (HBM) stacks [8, 9], but this trend significantly increases data center cost and power consumption. To improve throughput and reduce serving cost, batching techniques process multiple user requests to-gether [10–12]. However, when prefill, which processes long contexts at once and decoding, which processes one token at a time, are executed within the same batch, decoding la-tency becomes bound by the longer prefill latency, leading to excessive tail latency in decoding. Prefill–Decode (PD) disaggregation [13–16] addresses this problem by executing the two phases on separate devices (Fig. 1(a)). This eliminates cross-phase interference and al-lows prefill and decoding requests to be batched indepen-dently. However, PD-disaggregation suffers from a major inefficiency: prefill workloads are compute-bound and un-derutilize memory bandwidth, while decoding workloads are memory-bound and underutilize GPU compute resources. As both compute and memory dominate system cost, this asymmetry leads to significant resource inefficiency. arXiv:2610.26131v1 [cs.AR] 19 Oct 2026 Sanghyeok Han, Inseong Choi, Byungkuk Yoon, Gyeonghwan Park, and Jae-Joon Kim 

Recent works attempt to mitigate this inefficiency via Streaming Multiprocessor (SM) partitioning [17, 18], which spatially divides GPU resources between prefill and decoding. While this improves utilization compared to conventional PD-disaggregation, it fails to fully resolve the imbalance. In particular, even the memory-bound decoding requires relatively large number of SMs to fully utilize the DRAM bandwidth due to the complex cache and NoC architectures of GPU. As a result, substantial number of SMs must still be allocated to decoding despite the use of Tensor Memory Accelerator (TMA), leading to persistent contention with prefill and limiting overall efficiency, especially in modern GPUs with extremely high HBM bandwidth. In this work, we present DuoPD , a hybrid GPU–Processing-Near-Memory (PNM) architecture which highly improves utilization of both compute and memory bandwidth (Fig. 1(b)). DuoPD is based on two key observations. First, prefill inher-ently cannot maintain peak bandwidth of HBM due to its high arithmetic intensity, leaving substantial bandwidth con-sistently underutilized. Second, decoding’s low arithmetic in-tensity underutilizes GPU compute resources, making it well suited for lightweight near-memory compute units, which can directly exploit HBM bandwidth without requiring large compute resources. Leveraging these insights, DuoPD offloads the entire de-coding execution to lightweight PNM units integrated within the HBM logic die, while dedicating all GPU compute re-sources to prefill. In DuoPD, GPU prefill and PNM decoding execute concurrently over a shared HBM interface. Specif-ically, their memory accesses are interleaved at the TSV interface: while the GPU consumes previously fetched data to perform compute-intensive prefill, the PNM simultane-ously streams data from HBM at high bandwidth to serve memory-bound decoding. This complementary overlap en-ables DuoPD to reclaim otherwise idle memory bandwidth without requiring additional hardware bandwidth. DuoPD differs fundamentally from prior PIM/PNM-based approaches in two key aspects. First, prior works primar-ily focus on increasing internal memory bandwidth to im-prove parallelism, often incurring significant area, power, and capacity overheads. In contrast, DuoPD improves effec-tive bandwidth utilization by exploiting underutilized band-width already available in existing systems, without requir-ing additional bandwidth provisioning. Second, prior ap-proaches typically adopt intra-decode disaggregation , where memory-intensive components such as attention are offloaded to PIM/PNM while the remaining decode operations are ex-ecuted on GPUs within a conventional PD-disaggregation framework. In contrast, DuoPD performs inter-phase disag-gregation within a single device, executing prefill on the GPU and the entire decoding phase on PNM over shared mem-ory. This unified execution model enables tightly coupled compute–memory co-execution. To realize this design, we develop a compact PNM mi-croarchitecture that fits within the tight area and power con-straints of the HBM logic die while maintaining full memory bandwidth utilization. We further introduce two key mecha-nisms to enable efficient GPU–PNM coexistence. First, we design a direct data forwarding path from TSVs to the PNM buffer, bypassing the memory controller to eliminate redun-dant data movement and I/O contention. Second, we propose a memory management unit (MMU) that arbitrates GPU and PNM memory requests over the shared datapath, minimizing interference between prefill and decoding. In addition, we propose a hierarchical data mapping scheme that efficiently distributes model parameters and KV caches across multiple PNMs while preserving compatibility with GPU execution. Our contributions are summarized as follows: 

• We identify structural resource underutilization 

as a fundamental limitation of PD-disaggregated LLM serving and show that it cannot be resolved by existing GPU-only approaches. 

• We present DuoPD , a hybrid GPU–PNM architecture that enables concurrent compute-bound prefill and memory-bound decoding over shared HBM, improv-ing both memory/compute utilization. 

• We demonstrate that improving effective memory bandwidth utilization , rather than scaling physical bandwidth, achieves higher performance without in-curring the area, power, and capacity overheads of prior PIM/PNM designs. 

• We design a lightweight PNM microarchitecture, a TSV-level data forwarding mechanism, and an MMU-based arbitration scheme to enable efficient GPU– PNM co-execution. 

• We show the simulation results that DuoPD achieves up to 2.23 × higher end-to-end throughput and lower latency than GPU-based PD-disaggregation under the same GPU budget. 

## 2 Background 

2.1 Interference between Prefill and Decoding 

LLM inference is divided into two distinct phases: prefill and decoding. In the prefill phase, the model processes the entire input sequence to construct the KV cache, and is dom-inated by compute-intensive GEMM operations. As long-context workloads such as retrieval-augmented generation (RAG) [19] continue to grow, prefill becomes increasingly compute-bound. In contrast, decoding generates one token at a time in an autoregressive manner. It mainly involves compute-light GEMV operations but requires frequent access to the KV cache, making it strongly memory-bound. Batching is essential for improving LLM inference through-put. While naïve batching amortizes weight loading, it be-comes inefficient as diverging output sequences shrink the effective batch size. Continuous batching [10, 20] addresses A Hybrid GPU and Processing-Near-Memory Architecture with Shared DRAM for Efficient Prefill–Decode Disaggregation

This serializes short-latency decoding behind long-latency prefill, leading to excessive tail latency in Time Per Output Token (TPOT). Even with chunked prefill [20], this interference remains a major source of latency overhead: small chunks improve TPOT over continuous batching but increase Time To First Token (TTFT) due to repeated KV cache loading for prefill at each chunk, whereas large chunks inflate TPOT as decoding becomes synchronized with the chunk prefill time. 

2.2 Prefill-Decode (PD) Disaggregation 

To eliminate interference between prefill and decoding, PD-Disaggregation [13–16] has been proposed. The core idea is to separate two phases by allocating dedicated GPU pools: prefill instances execute compute-intensive operations, while decoding instances handle memory-bound ones. As illus-trated in Fig. 2(b), the decoding latency remains independent of concurrent prefill requests. This decoupling reduces tail la-tency in TPOT, enabling the system to meet Service Level Ob-jectives (SLOs) compared to continuous batching. However, PD-disaggregation also introduces several new challenges. The KV cache generated from prefill instance is transferred to the decode instance via device-to-device interconnects such as InfiniBand [21] or NVLink [22]. Due to its large size, this transfer incurs significant overhead, motivating tech-niques such as layer-wise transfer to hide latency [15, 23]. Furthermore, these systems suffer from systemic resource imbalances stemming from the rigid partitioning of devices into dedicated prefill and decode clusters (§3.1). 

2.3 High Bandwidth Memory (HBM) 

HBM is a 3D-stacked DRAM designed to deliver extremely high memory bandwidth. It consists of a base logic die con-nected to the external processor through a silicon interposer, with multiple DRAM dies stacked vertically using through-silicon vias (TSVs). High bandwidth is achieved through a large number of I/Os connected to the logic die. Although each DRAM die is connected to only a subset of these I/Os, the 3D-stacked structure enables HBM to operate as mul-tiple independent channels. Consequently, all I/O lines are effectively utilized, providing massive aggregate bandwidth

## 3 Motivation and Analysis 

3.1 Resource under-utilization in PD-disaggregation 

In PD-disaggregation systems, hardware resources are sys-tematically underutilized [14, 23]: compute units remain largely idle during decoding, while memory bandwidth re-mains underused during prefill. Fig. 3(a) shows that prefill reaches peak bandwidth only briefly, and spends most of its runtime at much lower bandwidth levels, indicating substan-tial memory underutilization. In contrast, decoding main-tains near-peak HBM bandwidth throughout execution. Roofline analysis (Fig. 3(b)) on a high-end GPU [7] further shows that decoding requires far fewer compute resources than prefill. Prefill achieves near-peak GPU throughput due to its high arithmetic intensity, whereas decoding is strongly memory-limited. Fig. 3(c) also shows that decoding benefits little from the GPU’s large L2 cache: reducing L2 capacity by 16 × increases prefill DRAM accesses by up to 4 ×, indicating strong data reuse, but leaves decoding largely unchanged, implying minimal cache locality. From these observations, we derive two key insights:  

> 1

Prefill cannot maintain peak HBM bandwidth. Due to its high arithmetic intensity, prefill exhibits limited memory demand and leaves substantial HBM bandwidth underuti-lized for most of its execution.  

> 2

Decoding is compute-light and exhibits minimal cache locality. Decoding utilizes only a small fraction of the GPU’s compute resources and gains little benefit from the L2 cache, making it well suited for a lightweight compute substrate with minimal performance impact. 3.2 Limitations of SM-partitioning strategies 

Prior works [17, 18] proposed spatial partitioning of stream-ing multiprocessors (SMs) in GPU to enable single-device PD-disaggregation for improving resource utilization. These methodologies determine an optimal partitioning ratio based on workload characteristics under the Service Level Objec-tive (SLO) targets. While this approach improves resource utilization compared to traditional PD-disaggregation, the in-herent SM contention between prefill and decoding remains a significant barrier to maximizing efficiency. Although decoding is memory-bound and requires limited computation, it still demands a large number of SMs to fully utilize DRAM bandwidth. This is because each SM supports only a limited number of in-flight memory requests. As a result, using a small number of SMs is insufficient to hide GPU memory latency, including DRAM access, NoC routing and cache hierarchy [29–32], and fails to fully utilize the DRAM bandwidth. We observed the minimum number of SMs required to sat-urate memory bandwidth across various GPUs (Fig. 4). The A6000, which provides 768 GB/s via GDDR6, requires only 16 SMs (19%) to reach 80% of its peak bandwidth when all SMs are utilized. However, the B200 (with TMA), equipped with 8-stack HBM3e providing 8 TB/s, requires 72 SMs (48.6%) to achieve the same saturation level. This allocation for the B200 translates to approximately 1.2 PFLOPS (FP16), which is nearly three times higher than the 422 TFLOPS required for GPT3-175B decoding (at a batch size of 32) as shown in Fig. 3(b), implying the severe idleness of the computation. As a result, the contention between SMs makes it nearly im-possible to achieve high resource utilization, limiting overall efficiency. Recent NVIDIA GPUs introduce the Tensor Mem-ory Accelerator (TMA) to improve bandwidth utilization with fewer allocated SMs. By offloading per-tile address gen-eration and enabling asynchronous bulk data transfers, TMA has been reported to saturate NVLink bandwidth using rela-tively small number of SMs [33]. However, this result does not imply that memory bandwidth utilization is indepen-dent of SM allocation. Because the peak HBM bandwidth is substantially higher than the NVLink bandwidth, saturating HBM still requires a much larger number of SMs. These ob-servations motivate a decoupled architecture. By offloading decoding to lightweight PNM units embedded in the HBM logic die, memory requests can be generated directly at the source of data, eliminating dependence on SMs and avoiding cache-induced or NoC routing bottlenecks. 

3.3 Limitations of previous PIM/PNM approaches 

Recent PIM/PNM-based works [34–36] propose heteroge-neous systems that couple high-performance GPUs with near-memory compute units. These approaches accelerate LLM inference by offloading memory-bound components of decoding (e.g., attention or MoE), and therefore rely on increasing internal memory bandwidth. However, existing PIM/PNM designs suffer from fundamental limitations. On-die PIM approaches [35–38], which integrate compute logic within DRAM arrays, impose significant overhead on DRAM dies, resulting in severe cell density loss. On the other hand, HBM PNMs integrate compute units within the logic die, avoiding this density penalty [39]. How-ever, HBM PNMs are typically constrained by the shared TSV-to-interposer interface: the internal bandwidth available to PNM via TSV is the same as the external I/O bandwidth exposed to the GPU in current HBMs. To overcome this limitation, a recent PNM work, Du-plex [34] introduces additional TSVs in the power TSV region to expand internal bandwidth. However, this approach in-curs substantial area and power overheads. The additional TSVs extend beyond the logic die into the DRAM dies, intro-ducing a 9% area overhead in DRAM [34]. This overhead can translate into even larger cell capacity loss due to DRAM pe-ripheral circuit expansion (e.g., HBM-PIM [38] reports a 25% area overhead leading to a 50% capacity loss). Furthermore, Duplex underestimates this overhead by assuming linear scaling with TSV count. In practice, densely integrating TSV I/Os within the power TSV region introduces severe rout-ing contention with existing TSV-to-interposer datapaths, significantly increasing layout complexity. Moreover, the 4× bandwidth expansion incurs a substantial power over-head of 100.48 W per stack under HBM4 configurations [40], corresponding to a 2.42 × increase over the baseline of 41.6 W per stack. Overall, such aggressive bandwidth scaling compromises the feasibility advantages of PNM. In addition to physical overheads, the increase in band-width also introduces a fundamental compute scaling bot-tleneck. To fully utilize the increased memory bandwidth, compute resources must scale proportionally. Otherwise, the system becomes compute-limited. This constraint signifi-cantly restricts the effective operating range of Duplex when offloading the full decoding. For example, in HBM4 configu-rations, Duplex is limited to an arithmetic intensity of 4 Op/B, constraining it to small batch sizes (e.g., batch size 4) and limited GQA group sizes. Scaling compute resources further to match the expanded bandwidth would incur prohibitive area and power costs, making such designs impractical. ## 4 DuoPD: Hybrid GPU-PNM Architecture 

4.1 System overview 

Unlike conventional PD-disaggregation systems that use separate GPU pools, DuoPD eliminates this partitioning by executing prefill on GPU cores and decoding on lightweight PNM units in the HBM logic die (Fig. 5). This design is moti-vated by the limitations of SM partitioning in GPUs: many SMs are required to saturate memory bandwidth, while PNM can achieve full utilization with fewer resources. DuoPD shares TSV I/Os between the GPU and PNM without altering the DRAM core die. This allows PNM to leverage idle band-width during the prefill phase, distinguishing it from prior PIM/PNM approaches [34–36] that necessitate increased in-ternal bandwidth. Consequently, it supports asynchronous and concurrent execution of prefill and decoding within a single GPU–PNM engine with minimal interference. DuoPD is built on three key design techniques. First , we design a compact PNM architecture that supports optimized dataflow for GQA and batching, while enabling full decoding under the area and power constraints. Second , to mitigate data movement conflicts on shared TSV I/O, we propose a

Finally ,we adopt a hierarchical data mapping scheme optimized for PNM while remaining transparent to GPU execution. 

4.2 Microarchitecture of DuoPD 

To enable concurrent prefill on GPU cores and decoding on PNM units, we design a DuoPD device as shown in Fig. 5 (b). Following the Blackwell architecture [7], each GPU is paired with eight HBM4 stacks, and each HBM4 stack has a PNM unit on its logic die. The die-to-die (D2D) interface bridges the TSVs ascending to the DRAM cores and the in-terposer routing to the GPU. With HBM4, the transition to an advanced logic process reduces the interface circuitry footprint, enabling the relocation of the memory controller from the GPU to the HBM logic die, which is essential for the centralized arbitration to manage memory access between the PNM units and the GPU [24–27] (§4.3). DuoPD supports inter-PNM communication (e.g., All-Reduce) using a GPU DMA engine with an in-flight reduction unit (e.g., sum, max), leveraging GPU die area freed by memory controller reloca-tion to avoid impacting compute resources [41, 42]. The PNM module comprises the following components: 

Processing units: The SIMD unit contains 16 lanes to support 16 Op/B arithmetic intensity, with each lane operat-ing on 1,024 elements wide and equipped with FP16 multi-pliers and 8-way adder trees for dot-product operations. At 1 GHz, it delivers a data rate of 2 KB per cycle (2 TB/s), fully matching the bandwidth of an HBM4 stack with 2,048 TSV I/Os. The SIMD unit is further optimized for MLP and atten-tion layers through a flexible lane architecture (Fig. 6). For Sanghyeok Han, Inseong Choi, Byungkuk Yoon, Gyeonghwan Park, and Jae-Joon Kim

MLP layers, it processes batched requests by broadcasting weights across lanes for parallel execution, while attention layers exploit a sublane structure, where each lane is divided into eight 128-wide sublanes to enable concurrent processing across heads and requests. With HBM channel interleaving and KV-head broadcasting for GQA, the unit maximizes par-allelism under the coordination of the PNM controller. The vector unit (VU) handles non-MAC operations, such as activation functions and softmax. In particular, it supports online softmax [43], enabling FlashDecoding [44] for effi-cient attention with sequence parallelism [45–47]. The buffer is sized at 1MB based on performance sweeps, as decoding performance saturates beyond this capacity. It stores inputs and partial results while serving as a dedicated write buffer for PNM requests. Jointly managed by the memory and PNM controllers for TSV data forwarding, the buffer requires 64KB in HBM4, consisting of 32 entries of 32B per pseudo channel across 64 channels, which is well within the 1MB budget. 

Control units: The PNM controller orchestrates all PNM operations. It receives the configuration of decoding work-loads and a start signal from the host, and manages the overall decoding process using instructions stored in the instruction buffer. The PNM controller forwards tensor meta-data (e.g., base address and size) and load/store instructions to the MMU for SIMD and VU operations. The MMU efficiently arbitrates concurrent GPU and PNM memory requests to minimize prefill–decode interference. GPU requests are directly enqueued into the GPU request queue, while the PNM load-store unit (LSU) translates dynamic-shape tensor load/store instructions from the PNM controller into 32-B memory requests compatible with the Memory Controller (MC). During this process, the PNM LSU also en-forces memory protection checks on the accessed address ranges to ensure system stability between GPU and PNM. 

4.3 GPU-PNM Interference Challenges in DuoPD 

We introduce solutions to address several challenges of GPU-PNM interference in DuoPD as follows, aiming the minimal performance impact between prefill and decode. 

Mitigating Shared I/O Confilct. As shown in Fig. 5(b), the D2D interface and MC, connected to the GPU via the interposer, are placed on one side of the TSV array, while PNM units reside on the opposite side due to area and routing constraints. Consequently, PNM requests must traverse the

However, due to keep-out zone constraints and dense I/O routing [48, 49], the TSV region offers limited routing resources for high-throughput data movement between the MC and PNM. To alleviate this limitation, we extend the TSV I/O interface to be shared between the MC and a PNM-side buffer. However, this shared TSV I/O introduces contention, as the MC and PNM buffer cannot simultaneously utilize the TSV I/Os. For example, Fig. 7(a) illustrates the case when the MC receives data from the DRAM core that corresponds to a PNM request. In this case, the data must be arbitrated by the MMU and then routed back to the PNM buffer, reoc-cupying the TSV I/O. This interferes with continuous data transfers between the DRAM core and MC, which are criti-cal for achieving peak bandwidth. Importantly, duplicating MCs on both sides of the TSV is not viable, as a shared MC is required to maintain a unified memory space for model parameters across prefill and decode. To mitigate this contention, we enable direct data forward-ing to the PNM units, effectively bypassing the MC for data movement, as illustrated in Fig. 7(b). In this architecture, data is transferred directly between the DRAM core and the PNM buffer, while the MC maintains global synchronization. For read operations, the MC issues the command and tracks the deterministic timing for the data return; the PNM controller, synchronized with the MC, then latches the data directly from the TSVs. Similarly, for write operations, the MC coor-dinates the timing by sending a synchronization signal to the PNM controller. This ensures that the PNM buffer drives the write data onto the TSVs in precise alignment with the MC’s request to the DRAM core. Consequently, our shared TSV I/O interface avoids PNM routing complexity and the MC–PNM interface carries only lightweight control signals, while the heavy data payloads are offloaded to the direct forwarding path, effectively reduc-ing data round trip latency, and data movement energy.

The MMU schedules requests from both queues according to a configurable ar-bitration policy, which directly impacts the Time To First Token (TTFT) and Time Per Output Token (TPOT). As shown in Fig.9, we evaluate three arbitration policies under prefill–decode interference: prefill-first , decode-first ,and mixed . The results reveal that TTFT is more sensitive to the arbitration policy than TPOT. This is because decoding generates more persistent and bandwidth-intensive memory traffic than prefill. Under the decode-first policy, PNM re-quests dominate the MC transaction queue, causing GPU star-vation and significantly increasing TTFT. In contrast, TPOT shows limited sensitivity to the policy. Although bursty pre-fill requests can temporarily delay decoding, this effect is amortized over the long execution time of decoding due to the low total memory footprint of prefill. As a result, the average TPOT remains similar across policies. To further assess the impact of stalls caused by bursty prefill requests, we measure the p99 Time-Between-Tokens (TBT). For GPT3-175B with a batch size of 16 and a con-text length of 16K, the p50 TBT is 15.71 ms, while the p99 TBT increases only slightly to 17.18 ms. This limited impact arises because the stalls typically affect only one or two lay-ers within each decode step, while the dozens of remaining layers proceed uninterrupted, effectively amortizing the over-head over the entire step. Moreover, when measuring TPOT, the stall overhead is further amortized across all generated tokens. Overall, the prefill-first policy provides the best end-to-end performance. While prioritizing prefill slightly increases TPOT for models with high decode bandwidth demand (e.g., LLaMA and Qwen), this overhead is outweighed by the reduc-tion in TTFT. Moreover, even under the prefill-first policy, DuoPD achieves higher decoding performance than con-ventional PD-disaggregation, as it allocates more effective memory bandwidth to decoding under the same GPU budget. After servicing requests at the MC, memory responses are re-arbitrated by the MMU and routed to their destination. The MMU matches each response address with entries in the pending request queues to identify whether it corresponds to a GPU or PNM request. To mitigate the in-flight request bottlenecks, PNM request entries are created at tensor gran-ularity and include the request type, target (GPU/PNM), ten-sor base address, access size, destination address in the PNM buffer, and a bitmap tracking completion of constituent 32-B requests. The bitmap is updated upon each sub-request completion, and the entry is retired once all bits are set, trig-gering a completion signal to the PNM controller. For GPU requests, both data and address are returned to the GPU. For PNM requests, the data is directly forwarded to the PNM buffer upon arrival, and only the resolved destination ad-dress is sent to the PNM controller. This design eliminates redundant data movement through the memory controller and minimizes prefill–decode interference, enabling efficient concurrent execution of GPU and PNM workloads. 

## 5 Data Mapping Techniques for DuoPD 

Model parallelism addresses how to efficiently distribute parameters and KV cache across multiple GPU nodes during LLM inference serving. Commonly used techniques include Tensor Parallelism (TP) [50, 51], which partitions weights and merges partial results via all-reduce, Pipeline Parallelism (PP) [52, 53], which splits layers across devices but suffers from low batching efficiency, and Expert parallelism (EP) [54– 56] in Mixture-of-Experts (MoE) models, which distributes experts across devices, with tokens dynamically routed to a subset of experts for scalable execution. Unlike traditional designs, DuoPD experiences a hierar-chical execution environment: GPU-level parallelism across GPU instances, and PNM-level parallelism within a single GPU-HBM engine. We explore this two-tier structure con-sidering system efficiency with prefill-decode concurrency. Additionally, we discuss memory space management for PNM and GPU to enable concurrent access to a shared ad-dress space, where model parameters are shared while KV caches are exclusively allocated and accessed by each device. 

5.1 GPU-Level Model Parallelism 

In DuoPD, GPU-level model parallelism differs from conven-tional PD-disaggregation in a key aspect: GPU-level paral-lelism must be identical for both prefill and decoding, be-cause the two phases share the same model parameters. Mis-matched partitioning would make parameter sharing infeasi-ble. Prefill prefers PP due to its high compute intensity, while decoding prefers TP because batch sizes are small. However, with high-bandwidth interconnects such as NVLink, TP com-munication overhead is modest, whereas PP significantly degrades decoding throughput. Therefore, DuoPD adopts 

TP over PP at the GPU level. For MoE models, we further incorporate EP at the GPU level, following prior systems. 

5.2 PNM-Level Model Parallelism 

Parallelizing decoding across PNMs is fundamentally con-strained by both architectural and algorithmic factors. Con-ventional PP is ineffective in this setting because distributing transformer layers across PNMs serializes prefill accesses, activating only one HBM stack at a time and severely under-utilizing memory bandwidth. Also, applying EP at the PNM Sanghyeok Han, Inseong Choi, Byungkuk Yoon, Gyeonghwan Park, and Jae-Joon Kim 

Figure 10. Model parallelism for inter-PNM model mapping. level is inefficient, as dynamic expert selection creates load imbalance across PNMs, leaving some HBM-PNM stacks idle while the most heavily loaded PNM determines the overall decoding latency. TP, while effective for most layers, faces a critical limitation in the attention stage. Since GPU-level TP is already required for high decoding throughput, applying additional TP across PNMs multiplies the overall parallelism degree, which quickly becomes too large to support atten-tion head partitioning (Fig. 10(a)). This leads to impractical mappings with fractional heads per device, particularly for models with a limited number of KV heads (e.g., GQA). To overcome these limitations, we adopt sequence paral-lelism (SP) [45–47] that partitions the KV cache along the sequence dimension rather than across attention heads, as il-lustrated in Fig. 10(b). This avoids the scalability bottlenecks in TP while enabling balanced utilization of PNM resources. Sequence partitioning introduces a challenge for softmax normalization, which requires reduction across the full se-quence. To address this, we leverage FlashDecoding [44], which performs attention in a tiled manner with numerically stable partial reductions. Each PNM computes attention lo-cally while maintaining intermediate statistics, followed by a lightweight inter-PNM all-reduce to complete normalization. Inter-PNM communication in DuoPD such as SP is con-fined within a single GPU/HBM package and therefore re-quires neither GPU-GPU synchronization nor communica-tion over external interconnects such as NVLink. Even as-suming a conservative GPU NoC latency of 400–500 ns based on [57], the resulting overhead is only ∼2% of the >24 𝜇 ssingle-layer decode time. Thus, inter-PNM communication introduces only a minor latency overhead. Overall, this approach enables scalable and efficient PNM-level parallelism without excessive TP scaling or bandwidth underutilization, allowing DuoPD to effectively exploit ag-gregate HBM bandwidth across PNMs while remaining com-patible with GPU-level parallelism. 

5.3 Memory Space Management 

Because the GPU and PNM share a unified memory space, DuoPD enforces access protection for LLM inference data. Model parameters are read-only during inference and can therefore be shared by both GPU and PNM without coher-ence mechanisms. In contrast, KV cache and intermediate values are mutable, but they are accessed exclusively by ei-ther the GPU or the PNM during their respective execution phases and are not concurrently shared for read-write up-dates. Thus, DuoPD avoids GPU-PNM coherence overheads, requiring only a prefill-to-decode handoff that makes GPU-written KV cache visible to PNM before decode begins. On the PNM side, the lightweight MMU and LSU enforce the read-only policy for shared model parameters. Before issuing a request to the shared memory controller, the PNM LSU validates that accesses to the parameter address space are read-only. This localizes protection to the PNM path while enabling safe concurrent execution with the GPU.

6.1 Evaluation setup Baselines: We evaluate two types of baseline systems: PD-disaggregation, where prefill and decoding are executed on separate GPUs, and chunked prefill, where both phases run within the same GPU. For a fair comparison, we assume that all systems are configured with eight GPU chips, each equipped with eight HBM4 stacks, providing 2 TB/s band-width [58] and 48 GB capacity [9] per stack. The GPU cores provide 2.5 PFLOPS in FP16, consistent with GB300 [59]. In the PD-disaggregation setup, we assume that the prefill and decoding instances are connected through NVLink5 [22], which provides 900 GB/s bandwidth for KV cache transfer. We evaluate two configurations: a 1:1 ratio between prefill and decoding instances, and a 3:1 ratio, which allocates more GPUs to the prefill side. In the chunked prefill setup, we use a chunk size of 1K for dense models, and 4K for MoE models, to avoid excessive degradation in TPOT and TTFT. 

PNM Configuration: We configure the PNM in DuoPD using SIMD-style processing elements (PEs). All PNM units operate at 1 GHz, and each SIMD lane consists of 1,024 FP16 multipliers with 8-way adder trees. Each lane delivers a throughput of 2 TFLOPS, and with 16 lanes operating in parallel, the total peak performance reaches 32 TFLOPS. The PNM is also equipped with a 1 MB on-chip SRAM buffer. 

Simulation: To evaluate performance, we built a cycle-level simulator 1 that emulates both GPU and PNM opera-tions. The simulator was integrated with DRAMSim3 [60] to accurately capture prefill-decode memory interference. The simulator receives user configurations (e.g., TP, PP, EP, hardware specifications), allocates parameter and KV cache addresses to HBMs, and generates inference requests. For each request, separate prefill and decoding instructions are generated for the GPU and PNM. The GPU scheduler and PNM controller modules execute these instructions indepen-dently.

6.2 Throughput 

Fig. 11 reports normalized end-to-end throughput. DuoPD consistently outperforms all baselines, achieving average improvements of 1.46–2.23 × on GPT3-175B, 1.29–1.61 × on LLaMA2-70B, and 1.45-1.78 × on Qwen3-235B-A22B. In par-ticular, DuoPD achieves up to 1.76 × and 2.23 × higher through-put than 1:1 and 3:1 PD-disaggregation, respectively. This improvement stems from the DuoPD architecture, which fundamentally changes resource allocation across phases. In baseline PD-disaggregation systems, GPUs and their at-tached HBMs are partitioned between prefill and decoding (e.g., 4:4 or 6:2), thereby limiting prefill to only a fraction of GPU resources and decoding to a fraction of available HBM bandwidth. As a result, prefill cannot fully utilize GPU compute, while decoding is constrained by reduced memory bandwidth. In chunked prefill systems, prefill and decoding are executed on the same GPU, but their conflicting resource demands introduce contention for compute, cache, and mem-ory bandwidth, resulting in degraded throughput. In contrast, DuoPD assigns all GPU compute resources to prefill while offloading decoding entirely to PNM units that exploit oth-erwise underutilized HBM bandwidth, with minimal cross-phase interference. This separation enables simultaneous and efficient utilization of compute and memory resources, resulting in significantly higher end-to-end throughput. For long outputs at batch size 32, the gain decreases as PNM is optimized for batch size 16, which leads to suboptimal decod-ing performance. Nonetheless, DuoPD consistently achieves the 1.31-3.44 × higher performance than baselines. Additionally, even in prefill-heavy cases ( 𝐿 𝑜 = 32), DuoPD achieves 1.25–1.60 × and 1.08–2.42 × higher throughput than 3:1 PD-disaggregation and chunked prefill, respectively, de-spite their larger prefill compute pools. Note that chunked prefill is suboptimal for MoE models due to the overhead of repeatedly loading experts. For long output lengths ( 𝐿 𝑜 

= 512), DuoPD achieves 1.31–3.92 × higher throughput than both 3:1 PD-disaggregation and chunked prefill. 

6.3 TPOT, TTFT, E2E latency 

Fig. 12 shows TPOT, TTFT, and End-To-End (E2E) latency results measured under varying queries per second (QPS) for each model. To emulate a dynamic serving environment, requests arrive according to a Poisson distribution based on the target QPS, and the request lengths follow a Gaussian distribution. Across all evaluated cases, DuoPD consistently achieves lower latency than the other baselines and main-tains stable latency at higher QPS. DuoPD reduces TPOT by up to 42.61% and 77.66% com-pared to 1:1 and 3:1 PD-disaggregation, respectively. Chun-ked prefill experiences excessive tail latency as QPS increases due to prefill–decode interference. DuoPD also achieves lower TTFT by utilizing more GPUs for prefill, and this advantage becomes more pronounced as QPS increases. As TTFT grows rapidly under high QPS due to queuing delays, DuoPD can maintain stable TTFT at higher QPS. We use the TTFT at the lowest QPS as a no-queuing baseline and measure the QPS at which TTFT increases by 3 ×, which serves as a proxy for the onset of significant queuing delays and service-level degradation. At this point, DuoPD sup-ports up to 2.13 ×, 1.39 ×, and 3.12 × higher QPS than 1:1 PD-disaggregation, 3:1 PD-disaggregation, and chunked prefill, respectively, with similar trends observed for E2E latency. Overall, these results show that DuoPD maintains stable performance under dynamic request arrivals and can achieve higher QPS, resulting in improved serving goodput. 6.5 Comparison with SM partitioning 

We also compare DuoPD with intra-GPU PD-disaggregation via SM partitioning. To this end, we extend our simulator us-ing the measured relationship between memory bandwidth and the number of SMs on the B200, as characterized in §3.2. We evaluate three SM partitioning configurations (pre-fill:decode= 9:1, 7:3, and 5:5) using GPT3-175B and Qwen3-235B-A22B, measuring p50 TPOT, TTFT, and E2E latency. As shown in Fig. 14, DuoPD consistently achieves lower latency than SM partitioning across all metrics. SM parti-tioning exhibits an inherent trade-off between TPOT and TTFT: allocating more SMs to decoding improves TPOT but degrades TTFT, and vice versa. For example, a 5:5 partition achieves TPOT comparable to DuoPD, but increases TTFT by 1.93 × and 1.66 × even at the lowest QPS. Conversely, a 9:1 partition matches DuoPD’s TTFT, but incurs over 5 ×

higher TPOT. This trade-off arises because prefill and de-coding share the same GPU resources in SM partitioning, leading to contention for both compute and memory band-width. Even with dynamic SM partitioning schemes [17, 18], such contention cannot be fundamentally eliminated, as both phases compete for shared on-chip and off-chip resources. In contrast, DuoPD separates compute-bound prefill and memory-bound decoding across GPU and PNM, respectively, reducing cross-phase contention and enabling efficient si-multaneous utilization of compute and memory resources.

6.7 Area and Power analysis 

To evaluate the area feasibility of integrating the PNM unit into the HBM logic die, we use the estimated logic die area based on die photographs of HBM4 [65], which is approxi-mately 140.8 mm 2. Out of the area, 38.6 mm 2 remains avail-able after excluding TSV and PHY regions. We synthesize all logic components of the PNM using Synopsys Design Compiler in a 28 nm CMOS process and estimate SRAM area via CACTI [66]. All results are then scaled to 7 nm fol-lowing standard scaling rules [67]. The total PNM area is 6.51 mm 2, which agrees with published 7 nm SRAM macro densities [68] and is consistent with prior PNM implementa-tions such as Duplex [34]. The SIMD unit accounts for the largest area of 3.64 mm 2, and PNM buffer and Vector unit occupies 1.25 mm 2 and 1.56 mm 2, respectively. This suggests that the proposed PNM comfortably fits within the available logic die budget of future HBM generations such as HBM4. Moreover, it does not require modifications to the DRAM core die, thereby avoiding cell density loss. We also estimate power from the synthesized PNM com-ponents in a 28 nm CMOS technology and scale them to 7 nm node similar to area analysis. The total PNM power per HBM stack is 6.45 W, dominated by the SIMD unit (4.9 W), which are similar values to that of previously reported compute units [69–71]. To evaluate the thermal impact of the PNM units, we conduct simulations using HotSpot [72]. We model a server-grade cooling solution based on a vapor-chamber heat sink, consistent with prior works [73, 74]. We use an effective convection resistance of 0.0146 K/W [75] and configure a 16-high HBM stack. Each DRAM core die dissipates 2 W [76], and the PNM units are distributed within the 38.6 mm 2 available region of the logic die. Our thermal model also accounts for the heat generated by the GPU core die and its thermal coupling with the HBM stack. ## 7 Related Works 

Prior work has explored heterogeneous deployments for pre-fill and decoding in PD-disaggregation systems, leveraging the distinct compute and memory characteristics of the two phases. Splitwise [15] exploits GPU heterogeneity by deploy-ing NVIDIA A100s for memory-bound decoding and H100s for compute-bound prefill. Hybe [23] offloads decoding to a custom NPU with low compute density to alleviate the compute underutilization of decoding GPUs. However, Hybe does not address the bandwidth underutilization of prefill instances and incurs higher cost than DuoPD because it re-quires separate memory systems built from expensive HBM devices. More recently, NVIDIA announced Rubin CPX [79], designed to accelerate long-context inference workloads. In this architecture, prefill is executed on CPX while decoding is executed on HBM-equipped Rubin GPUs, and CPX employs GDDR7 [80] instead of HBM to reduce the memory cost of prefill instance. While heterogeneous deployment with the Rubin-CPX alleviates memory bandwidth utilization ineffi-ciencies, it still suffers from the compute under-utilization of GPUs dedicated to decoding and require separate DRAMs for prefill and decode instances. 

## 8 Conclusion 

In this work, we presented DuoPD, a hybrid GPU–PNM archi-tecture that addresses the resource underutilization problem in conventional PD-disaggregation systems through inter-phase disaggregation. Unlike prior PIM/PNM approaches that rely on increasing internal bandwidth, DuoPD improves resource utilization by leveraging bandwidth sharing, ex-ploiting the idle bandwidth of prefill phase through concur-rent execution of GPU-prefill and PNM-decoding. To realize this design, we introduced a compact PNM microarchitecture, an MMU design to manage shared TSV I/O, and a hierarchical data mapping scheme for efficient GPU–PNM execution. Our simulation results show that DuoPD achieves up to 2.23 ×

higher throughput and 77.66% lower TPOT than state-of-the-art PD-disaggregation systems, demonstrating a practical and cost-efficient path toward high-throughput LLM serving.
