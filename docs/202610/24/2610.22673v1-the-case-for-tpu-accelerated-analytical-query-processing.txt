# The Case for TPU-Accelerated Analytical Query Processing 

## Jaehyun Ha, Yeounoh Chung *, Helena Caminal, Aditya K Kamath, Fatma Özcan, Arvind Krishnamurthy, Henry M. Levy

## ABSTRACT 

Large-scale analytical query processing requires computing sub-strates capable of immense distributed scale-out. Tensor Process-ing Units (TPUs) perfectly embody this extreme-scale architecture, offering massive computational density and highly scalable opti-cal pod-level interconnects. Despite these advantages, TPUs have so far remained largely unexplored for analytical database work-loads. In this paper, we present the first comprehensive case for TPU-accelerated analytical query processing by running all the TPC-H queries entirely on the TPUs. We introduce Native TPU Accelerator (NTA) for analytical query processing, which provides hardware-conscious algorithm design and optimizations in JAX/XLA. By exposing the TPU’s structural mechanics, we demonstrate how dynamic, memory-bound database operations can be rewritten into deterministic JAX programs. We engineer a suite of novel execu-tion strategies that leverage both the TPU’s TensorCore and Spar-seCore to trade sparse, unpredictable memory accesses for dense, hardware-aligned ones. At the core of NTA, a compiler uses cat-alog statistics to assign guarded static capacities and a hardware-calibrated local cost model to select a TPU-native implementation for each relational operator before JIT compilation. We evaluate our system using the TPC-H benchmark. Taking full advantage of TPU slices and JAX distributed computing, we seamlessly scale our execution environment to run TPC-H bench-mark up to Scale Factor 1000 (SF1000). Evaluated against a rigorous CPU ground truth (DuckDB), our native TPU accelerator achieves 

state-of-the-art performance, achieving a 7 .0× single-device speedup over DuckDB at SF100 and a 68 .6× speedup with 16 TPUs at SF1000 (1TB). The results establish TPUs not merely as dense neural com-pute hardware, but as a highly competitive, massively scalable sub-strate for the next generation of analytical query processing.

## 1 INTRODUCTION 

Hardware-accelerated query processing is gaining significant mo-mentum across both academic and commercial analytics systems [3, 14, 17, 25, 37], which require computing substrates capable of im-mense, distributed scale-out. Tensor Processing Units (TPUs) per-fectly embody this capability: powering massively large-scale search and AI/ML workloads, they offer extreme computational density and highly scalable optical pod-level 1 interconnects [19]. Despite these massive structural advantages, TPUs remain largely unex-plored for analytical database systems. This paper fundamentally explores running relational queries on TPU architectures, reveal-ing precisely what it takes to map analytical queries to what is conventionally assumed to be a static execution paradigm built ex-plicitly without hardware-managed caches or dynamic execution. TPU and especially its main compute units, TensorCores, re-quire a fixed and deterministic execution environment where mem-ory access and shapes must be compiled and pre-determined. In contrast, relational operators rely on data-dependent dynamism [26], which is hard to predict. The number of rows produced by a filter (shape dynamism ) and the memory locations where matching tu-ples reside in a join ( address dynamism ) are strictly runtime prop-erties determined by the data. The TPU TensorCore, however, en-forces completely static evaluation: every instruction, buffer size, and DMA transfer must be predictably scheduled at query compile time. Naively mapping relational operations onto such a static sub-strate creates immense sparsity out of forced worst-case padding, and HBM pipeline stalls resulting from irregular gather/scatter 2.Traditional CPUs and GPUs mask these erratic access patterns dy-namically using large, hardware-managed caches and massive multi-threading architectures [21]. Fortunately, modern TPUs added Spar-seCore units to accelerate sparse, non-uniform memory accesses that can run in parallel with TensorCore computations. In this work, we argue that TPUs can be used as efficient pro-cessors for analytical workloads by fundamentally neutralizing dy-namic memory accesses, using a new TPU hardware co-processor, SparseCore [18]. We introduce Native TPU Accelerator (NTA), a tensor-based execution engine built entirely in JAX and XLA [2] 3.Rather than treating the TPU as a black-box HW accelerator, NTA co-designs relational operators directly around its memory and compute hierarchy. Our core insight is that dynamic, memory-bound database operations can be meticulously rewritten into predictable,

Providing highly optimized kernels is insufficient unless a dy-namic relational plan can be converted into a well-orchestrated TPU program. To achieve this, NTA introduces an end-to-end query compilation and execution pipeline (Section 3). Given an incoming logical plan, NTA uses catalog statistics to assign guarded capaci-ties (bounded static shapes) to intermediate results, derives exist-ing logical and physical properties, and selects a cost-optimal exe-cution target (TensorCore vs. SparseCore) kernel implementation for each operator. NTA then stitches individual physical operators into a physical plan, which is then lowered (program transforma-tion) into a statically shaped JAX program with Pallas kernels 4.Finally the JAX program is compiled and further optimized using the XLA compiler. To evaluate NTA at large scales (up to SF1000), we leverage JAX distributed (XLA SPMD [34]) computing over TPU v5p [11] slices. For a rigorous baseline, we compare our performance against DuckDB, a state-of-the-art SIMD-vectorized in-memory CPU database en-gine [13, 14, 17]. NTA achieves state-of-the-art performance, out-performing DuckDB on all 22 TPC-H queries and achieving geometric-mean speedups of 7 .0× at SF100 (100GB) and 68 .6× at SF1000 (1TB). When measured by total query-set runtime, the corresponding total-runtime speedups are 5 .7× and 50 .1× over the CPU baseline. In summary, this paper makes the following contributions: 

• The case for TPU-Accelerated Analytical Query Pro-cessing : We present the first deep architectural analysis of mapping relational algebra onto TPU semantics, explicitly identifying core anti-patterns (shape dynamism, sparsity, gather/scatter stalls) and standardizing their mitigation. 

• Native TPU Kernels via Pallas & SparseCore: We in-troduce a suite of highly optimized, TPU-native execution strategies , designed to address gather/scatter bottlenecks and HBM anti-patterns (round-trips and fusion breaks). 

• Compilation and Local Physical Planning: Given a fixed logical plan, NTA bounds intermediate cardinalities, filters physical implementations by applicability and resource con-straints, and selects among them using TPU v5p-calibrated operator costs before JIT compilation. 

• Comprehensive Evaluation at Extreme Scale: We demon-strate state-of-the-art analytical performance on TPC-H, utilizing JAX distributed computing to scale smoothly to SF1000 across orchestrated TPU slices. Section 3 details our native TPU-accelerated query processing algorithms. Section 4 describes our compiler and hardware-conscious intelligent kernel selection. Sec-tion 5 details extreme scale orchestration. Section 6 presents our extensive experimental evaluation. Finally, Sections 7 and 8 offer discussion and conclusions.

## 2 BACKGROUND 2.1 TPU Architecture 

To understand the difficulty of porting database workloads to TPUs, one must examine the execution model. A modern TPU chip hosts 

TensorCores , each combining Matrix Multiply Units (MXUs)—systolic arrays for dense matrix math—with a Vector Processing Unit (VPU) for element-wise operations. Each TensorCore owns a VMEM , a software-managed scratchpad serving as its fast memory. Unlike a hardware-managed CPU or GPU cache, VMEM is filled and drained exclusively by explicit DMA transfers, each statically described at program/binary compile time as a burst with a base address, stride, and count. Crucially, sizes and exact memory addresses need to be known at compile time to generate the memory instructions and DMA descriptors to move the right data to the vector lanes of the TensorCore. To appreciate the potential of the TPU for analytical query pro-cessing, one must understand how fundamentally its design dif-fers from traditional hardware. Rather than relying on hardware-managed caches, branch predictors, or fine-grained thread-level parallelism to intuitively hide the latency of irregular memory ac-cesses, the TPU operates on a philosophy of deterministic sim-plicity. Memory is explicitly managed via software, and execution proceeds via a statically scheduled Very Long Instruction Word (VLIW) pipeline. This extreme architectural minimalism makes TPUs vastly more efficient at predictable, dense tensor mathematics, but creates a challenging (but tractable) environment with the data-dependent dynamism inherent in relational algebra. One key component of the TPU is the SparseCore , recently added as an ally to the TensorCore. SparseCores traverse irregular in-dex streams, performing gathers and scatters from HBM, on behalf of TensorCores or as their own compute engines. However, Spar-seCore and TensorCore programs inherently exist separately and transfers between them require explicit DMA staging and synchro-nization via CMEM (common memory). These architectural trade-offs share a single premise: a careful mapping of operators to the right cores in the TPU is necessary. Beneath XLA, Pallas allows pro-grammers to write custom TPU kernels with explicit control over blocking and the HBM-VMEM pipeline, enabling advanced query optimizations (Section 4). XLA’s most critical optimization is operator fusion . GPUs excel at this: a selection equates to a boolean mask, and a join relies on index com-putations followed by gathers. GPUs mask the latency of dynamic gathers using hardware-managed caches and SIMT multithreading optimizations. These mappings were designed for hardware that resolves dynamism at runtime; however, when ported directly to a TPU, performance collapses due to the dynamism (Section 2.4).

## 2.4 Data-Dependent Dynamism on TPUs 

The gather/scatter bottlenecks highlight a fundamental architec-tural tension: relational query processing is inherently data-dependent, whereas the TPU’s compile-time optimization stack (XLA) relies on static shapes and deterministic execution graphs for performance optimization. This section defines the resulting performance gaps and presents the core design principles that guide our Native TPU Accelerator (NTA). 

> 3

A Taxonomy of Dynamism. Data-dependent dynamism mani-fests in two distinct forms. Shape dynamism arises when the out-put cardinality of an operator depends on its input data. This im-poses the cost of sparsity : every dynamically sized tensor must be declared at a worst-case bound, and every padded element is com-puted. Address dynamism arises when where each row belongs in the output is decided by runtime key values (e.g., gathers and scat-ters). This imposes the cost of stalls : every data-dependent access breaks operator fusion, forces its intermediate to be materialized in HBM, and stalls the TensorCore while it waits for the HBM round trip. Moreover, these two forms of dynamism compound each other. When address dynamism forces an intermediate ten-sor to materialize in HBM, it must do so at the worst-case size (for the output tensor) dictated by shape dynamism. 

The Compound Cost of Sparsity and Stalls. Sparsity taxes ev-ery unit on the chip. When sweeping the fraction of padding, the execution time of operations on both the TensorCore and SparseC-ore stays flat on the TPU, as padded rows consume identical cy-cles to valid rows. Address dynamism introduces even a deeper cost; inserting a single data-dependent gather into a fused chain of element-wise operators forces the XLA compiler to inevitably split the chain. This is because the compiler cannot fuse element-wise operations across a dynamic look-up or gather. When the fu-sion breaks, the TPU is forced to materialize intermediate results to HBM, causing execution stalls on the TensorCore. While offload-ing the gather to the SparseCore mitigates the inefficiency of using TensorCore systolic arrays for scalar lookups, the mathematical op-erations chain (fusion) still breaks causing the TensorCore units to stall while waiting for the HBM roundtrip. Crucially, these costs multiply. Worst-case bounds compose across operators, generating massive padding factors in deep pipelines. And every materialization heavily inflates the HBM stall, as it is written at the worst-case, padded size. A single operator may sur-vive dynamism; a query plan does not. 

System Design Implications. These constraints translate into three non-negotiable requirements for a TPU accelerator. R1: dy-namic shapes must be bounded tightly . R2: data-dependent mem-ory accesses must be mathematically translated into predictable tensor arithmetic (e.g., boolean masking) to sustain pipelined exe-cution and avoid fusion breaks. R3: unavoidable dynamic accesses must execute via SparseCore and its Scatter-Gather Engine (SGE) rather than relying on the TensorCore path. 

## 3 NTA SYSTEM OVERVIEW 

Modern TPUs offer distinct architectural advantages for massive tensor computation throughput, dedicated hardware gather-scatter acceleration (SparseCore), programmable on-chip scratchpad mem-ories, and ultra-fast ICI inter-chip networks. In order to unlock theses hardware capabilities for analytical query processing, we present Native TPU Accelerator (NTA) . Rather than treating the TPU as a black-box coprocessor, NTA co-designs relational operators directly around its memory and compute hierarchies. NTA selects highly optimized physical Pallas kernel implementa-tions, further optimizes and distributes its execution over available TPU topology and across different TPU computing units (e.g., Ten-sorCore, SparseCore). Figure 3 illustrates the compilation and dis-tributed execution workflow of NTA. (1) Plan Ingestion and Shape Planning (Section 5.1): NTA in-gests logical query plans and uses catalog statistics to compute compile-time cardinality bounds ( B𝑜 ) for every intermediate re-lation, sizing static tensor buffers with calibrated safety mar-gins. (2) Physical Operator Selection (Section 4, 5.2): Using compiled bounds, key distributions, and target TPU hardware cost pro-files, NTA selects the optimal physical operator from its TPU-native catalog (e.g., Sorted-Hash Lookup Join vs. SparseCore Gather Join). (3) Lowering to JAX and Pallas (Section 5.3): Non-materializing operators (filters, projections) are fused into adjacent kernels. The physical plan is lowered to a statically shaped JAX program with embedded Pallas custom kernels for specialized memory-movement routines. (4) XLA SPMD Compilation and Scale-Out (Section 6): The lowered program is compiled via XLA SPMD into a single device-mesh executable. During execution, relations are co-partitioned across TPU devices, each device processes local partitions via 32-bit local tuple identifiers, and partial results are merged into the final relation. 

## 4 TPU-NATIVE RELATIONAL OPERATORS 

NTA represents each intermediate relation as statically shaped col-umn tensors with a validity mask and compiles relational opera-tors into JAX or Pallas programs. Selections and projections are fused into the next materializing operator, whereas joins, aggrega-tions, duplicate elimination, and sorting may each admit multiple TPU-native implementations. Table 3 summarizes this physical op-erator catalog, including the input data property required by each implementation and its key execution primitives. The following subsections explain how each implementation preserves relational semantics and why its listed property makes it applicable. Section 5 then describes how NTA combines these properties with planned cardinality bounds and calibrated crossover rules (e.g., “small” do-main) to select among the applicable implementations. 

## 4.1 Joins 

NTA specializes join kernels to exploit physical properties of the input relations, including row alignment, bounded PK–FK fanout, and build-key uniqueness. The following paragraphs describe three implementation families: layout-specialized joins, indexed PK–FK joins, and sorted-hash joins over a unique build key. Indexed PK– FK joins assume a prebuilt lookup index, whereas sorted-hash joins construct their lookup structure on the fly when selected. 

Layout-specialized joins. A clustered PK–FK layout stores at most 

𝑘 child rows for each parent in fixed-width slots. Fanout-Reshape Join views the child columns as parent-by-𝑘 tensors and broad-casts each parent payload across its child slots. Unused slots re-main invalid, preserving join semantics without an indexed lookup. Key-Aligned SIMD Join applies to a 1:1 join whose inputs are al-ready aligned on the join key: at every row position, the two inputs contain the same key. Having the same key domain is not sufficient because the relations may order their keys differently or contain different key multiplicities.

Indexed joins. A PK–FK lookup index maps each probe key to a build-side row identifier. VPU Index Lookup Join gathers the cor-responding payloads with jnp.take , whereas SparseCore Gather Join sends the same row identifiers through plsc.Indices and a pipelined SparseCore transfer. Unmatched probes are directed to a safe sentinel position and invalidated by the output validity mask. The multi-payload specialization reuses one row-identifier vector across multiple projected columns, amortizing the index lookup. 

Sorted-hash lookup. For a unique-build equijoin without a pre-built lookup index, Sorted-Hash Lookup Join constructs a tempo-rary lookup structure during query execution. It packs and hashes the build keys, sorts the build rows by hash, and uses binary search to locate the matching hash range for each probe. It then scans a bounded number of candidates and compares the original keys be-fore accepting a match, preventing hash collisions from producing false matches. An overflow guard detects a collision range that ex-ceeds the compiled scan bound. Build-key uniqueness guarantees at most one exact match per probe row. 

Join semantics. All implementations expose a common output contract: a build-side row identifier and a match predicate for each probe row. Inner joins invalidate unmatched probes, whereas left-outer joins retain the probe row and invalidate the unmatched build-side payloads. Semi and anti joins consume only the match predicate without materializing build-side payloads. A bounded-fanout layout extends the same contract to at most 𝑘 child slots per probe. The physical implementation therefore changes how matches are located without changing the logical join semantics. 

## 4.2 Aggregations 

Aggregation implementations differ in how they map grouping keys to aggregate state. NTA specializes this mapping to proper-ties of the grouping keys and input layout: a bounded dense key 

> 5

domain, an aggregate-state array that fits in VMEM, an existing group-key order, or a clustered layout with bounded fanout. When none of these applies, NTA uses segment reduction as the fallback. 

Dense-domain aggregation. When group identifiers form a bounded domain (group key range), One-Hot MatMul Aggregation en-codes them as a masked one-hot matrix and evaluates additive ag-gregate state with jax.lax.dot_general on the MXU. For a com-posite grouping key, Radix-Packed Aggregation first maps each key tuple to a dense integer identifier with jnp.ravel_multi_index .This implementation applies when the product of the domains re-mains within the calibrated bound for the dense reduction. 

Histogram and segment aggregation. When the aggregate state array fits in VMEM, VMEM Block Histogram processes the input in tiles and updates the group state on chip before writing the com-pleted state to HBM. Segment Reduction handles large or sparse group domains through the statically shaped reduction exposed by jax.ops.segment_sum . Unlike the dense-domain implementa-tions, these operators do not materialize an input-cardinality-by-domain-size one-hot matrix. 

Structure-aware aggregation. Sorted-Run Aggregation applies when the input is already ordered by the grouping key. It identifies contiguous runs of equal keys and reduces each run into one group result. Fanout-Reshape Aggregation applies when a clustered layout stores at most 𝑘 input rows for each group in fixed-width slots; it reshapes the input into group-by-𝑘 tensors and reduces along the slot dimension. These implementations use the existing order or layout rather than sorting or repartitioning the input. 

Aggregate state. NTA represents the SQL aggregates associated with each group as fixed-width state. COUNT and SUM use additive accumulators, AVG maintains a sum–count pair, and MIN and MAX 

use masked extrema. Aggregates sharing the same grouping keys also share the group-to-state mapping. The product of the group-domain size and aggregate-state width determines the state foot-print and, in particular, whether the VMEM-resident histogram im-plementation is applicable. 

## 4.3 Distinct 

Distinct implementations differ in how they represent value mem-bership. For a single integer-valued expression with a bounded do-main, NTA records the values present in the input directly. Other-wise, it sorts value tuples and retains one row from each equality run. The sort-based implementations differ in how much inactive data they carry into the sort and whether the resulting working set fits the on-chip memory budget. 

Dense-domain distinct. When the encoded value domain is within the calibrated one-hot limit, MXU One-Hot Distinct assigns one presence slot to each domain value and an additional slot to NULL ,when required. It forms a masked membership indicator, reduces each slot on the MXU, and emits the values whose presence bits are set. The output size is determined by the encoded domain rather than the input cardinality. 

Sort-based distinct. The sort-based implementations order value tuples, identify boundaries between unequal adjacent tuples, and retain the first active row of each run. Compact-Then-Sort Dis-tinct first compacts the input when only a small fraction of its compiled rows are active, reducing the number of rows entering the sort. VMEM Bitonic Distinct uses jax.lax.sort when the active tuple payload fits the calibrated VMEM budget. Direct-Sort Distinct applies jnp.unique(size=...) to the full compiled in-put as the general fallback. All three produce fixed-size output ten-sors with a validity mask identifying the unique rows. 

Grouped distinct. For COUNT(DISTINCT x) grouped by keys g,NTA treats (g, 𝑥 ) as the distinct identity. It removes duplicate valid pairs and then counts the surviving values for each group. The intermediate may therefore contain nearly as many rows as the input, even when the final number of groups is small. 

## 4.4 Sort and Top-K 

Sort implementations differ in how much ordering they materi-alize and where they complete it. For ORDER BY ... LIMIT K,In-Kernel Top-K masks invalid keys, extracts key–row-identifier pairs with jax.lax.top_k , and gathers non-key payload columns only after the winners are known. Global Sort uses jnp.argsort 

when the entire relation must be ordered. For a small statically bounded candidate set, Host-Hybrid Sort transfers only keys and row identifiers to the host for final ordering and fetches the se-lected payload columns lazily, limiting host–device traffic. 

## 5 TPU HW-CONSCICOUS COMPILATION & OPTIMIZATION 

To address the shape and address dynamism described in Section 2.4, NTA compiles a logical query plan into a statically shaped JAX/Pallas program through three steps. (1) Static shape planning uses catalog statistics to assign each intermediate a compiled cardinality bound, which determines its tile-aligned tensor shape and buffer alloca-tion. (2) Physical operator selection uses these planned bounds, the physical properties available at each operator, and calibrated cost models to choose a TPU-native implementation for every logical operator. (3) Plan finalization groups the selected implementations into fusion-compatible producer–consumer regions and lowers the resulting physical plan to JAX/Pallas for XLA JIT compilation. TPUs shift scheduling and memory management from hardware to software. When intermediate cardinalities, data movement, and operator schedules can be bounded and planned before execution, NTA exposes compact, statically bounded, and fusable work to XLA, enabling dense pipelines with high hardware utilization.

## 5.2 Physical Operator Selection 

After static shape planning determines the compiled cardinality bounds, NTA selects one physical implementation for each logical operator. Selection first applies hard constraints: an implementa-tion is considered only when its required constraints and input lay-out are available and its working set fits the target TPU. Performance-dependent branches then use crossover rules calibrated for the tar-get hardware. Figure 4 shows the resulting decision paths for joins and grouped aggregations. 

Join and aggregation choices. Figure 4 applies the required prop-erties in Table 3. For joins, NTA first exploits identical row align-ment or clustered PK–FK fanout. An existing PK–FK lookup index enables either VPU Index Lookup Join or SparseCore Gather Join, with the hardware profile and calibrated probe-size crossover selecting the backend. Without an index, a unique-build equijoin enables Sorted-Hash Lookup Join. For aggregation, NTA con-siders a small dense domain, VMEM-resident histogram state, a small packed multi-key domain, existing key order, and clustered bounded fanout in turn. Large or sparse group domains use Seg-ment Reduction. 

Other operators. Distinct and Sort/Top-K use the same property-first procedure. For DISTINCT , a small bounded integer domain se-lects MXU One-Hot Distinct; otherwise, a low active-row frac-tion selects Compact-Then-Sort Distinct, a working set that fits VMEM selects VMEM Bitonic Distinct, and Direct-Sort Dis-tinct is the general fallback. For ORDER BY , a bounded LIMIT or 

OFFSET selects In-Kernel Top-K. Without such a bound, a small host-finalization boundary enables Host-Hybrid Sort; remaining cases use Global Sort. Selections and projections have no inde-pendent physical implementation and fuse into the selected con-sumer unless materialization is required. 

Selection thresholds. Terms such as “small” and “above crossover” refer to target-specific thresholds rather than universal constants. Some choices follow directly from input properties: NTA selects SparseCore Gather for PK–FK joins with a prebuilt index and Sorted-Hash Lookup when no such index is available, as shown in Figure 8. When both VPU and SparseCore indexed joins are applicable, the v5p policy switches to SparseCore at 50K probe rows. In the 600M-row aggregation sweep, NTA selects One-Hot MatMul through

For Distinct, One-Hot admits at most 128 value slots, Compact-Sort requires an active-row fraction at most 20% over an input of at least 100K rows, and VMEM sort admits at most 8 MiB of active payload. ## 5.3 Plan Finalization and Lowering 

After selecting a physical implementation for each operator, NTA assembles the selected operators into a complete physical plan. It fuses non-materializing operations, such as selections and pro-jections, into the adjacent operators that consume them and con-structs any composite keys required by joins and grouped aggre-gations. This removes unnecessary intermediate tensors and keeps adjacent computation together where possible. NTA then applies the tile-aligned tensor shapes determined in Section 5.1, propa-gates validity masks through the plan, and adds overflow checks to operators with data-dependent output cardinalities. Finally, it low-ers regular tensor computation to JAX and custom data-movement kernels to Pallas. XLA compiles the resulting statically shaped pro-gram, allocates its buffers, and schedules its execution.

NTA uses JAX’s distributed runtime ( jax.distributed ) and XLA’s GSPMD partitioner [34] to execute a physical query plan across a TPU slice. The devices in the assigned slice form a logical JAX device mesh used for both SPMD compilation and data (relation) placement. XLA compiles the physical query plan for this execution layout, and each device processes the relation partitions assigned to it. A naive execution strategy partitions each relation independently and relies on XLA to route indexed lookups to the device con-taining the referenced tuple. This can turn PK–FK joins into dis-tributed joins that require communication for every lookup. Re-taining global tuple identifiers also requires 64-bit indices once a relation exceeds the signed 32-bit row range, doubling index stor-age and index-read traffic on TPUs. NTA instead preserves par-titioning metadata and row alignment across physical operators. Large relations are partitioned across devices, whereas small re-lations are replicated when they fit in device memory. Relations connected by high-volume PK–FK joins are co-partitioned when their existing layouts are compatible. The corresponding indexes use partition-local signed 32-bit tuple identifiers, allowing each de-vice to evaluate the indexed join using only its local partitions. Partition-local identifiers can also serve as group identifiers when the grouping attributes are aligned with the partitioning scheme. In this case, each device computes a local aggregation without ex-changing input tuples. Each partition carries a stable partition iden-tifier, and a tuple identifier that appears in the query result is rep-resented as (partition _id , local _id ) and decoded during result ma-terialization. Lookups into replicated relations are also local. Joins whose inputs are neither replicated nor compatibly partitioned re-quire a repartitioning exchange. Each device executes the compiled query over its local relation partitions. Scans, selections, co-partitioned indexed joins, and local aggregations proceed without communication. Data exchange is required only for repartitioning and for combining partial results into the final result relation. 

Concurrency and Multi-Tenant Scheduling. While the TPU excels at raw throughput, managing concurrent queries in a uni-fied compilation model exposes static execution constraints. In our current JAX/TPU deployment, the host submits query executables to a serialized, First-In-First-Out (FIFO) instruction queue. Con-sequently, unlike CPU databases that time-slice concurrent ana-lytical queries, NTA’s average query latency scales linearly with the number of concurrent tenants, even though aggregate cluster throughput remains constant. 

## 7 EVALUATION 

We evaluate NTA to validate three core claims: (1) our hardware-conscious algorithms effectively reduce TPU memory-bound stalls, (2) our hardware-conscious local physical planner selects perfor-mant JAX and Pallas implementations, and (3) our JAX distributed orchestration scales effectively to extreme bounds.

## 7.2 Macrobenchmarks (SF1 & SF100) 

Figure 5(a) reports per-query speedup over DuckDB at SF1. Di-rect JAX achieves a geometric-mean speedup of 0 .058 × and outper-forms DuckDB only on Q6, whereas NTA accelerates every query by 3 .5–61 .0×, achieving 10 .3× geometric-mean and 8 .5× total-runtime speedup. At SF100 (Figure 5(b)), Direct JAX achieves 0 .073 × geometric-mean and 0 .026 × total-runtime speedup, outperforming DuckDB only on Q1, Q6, and Q13. NTA accelerates every query by 1 .9– 30 .5× and achieves 7 .0× geometric-mean and 5 .7× total-runtime speedup. 

Sources of improvement. Q6 is the only Direct JAX query faster than DuckDB at both scales because its selective scan and scalar re-duction already map to a compact fused tensor program. At SF100, Q1 and Q13 also cross the baseline, but most Direct JAX join and grouped-reduction queries remain far slower. NTA retains the com-pact Q6 path and additionally regularizes the joins and grouped re-ductions that dominate the remaining queries. Selective dimension predicates become masks before fact-table access, indexed payloads use masked SparseCore gathers, and bounded or small-domain groups use reshape, histogram, or dense reduction rather than global scat-ter. These choices are especially effective for Q9 (25 .3× at SF1), whose multi-hop joins reuse compact lookup payloads, and for Q12 (16 .9×), whose selective order lookup feeds a two-group reduc-tion. Q13 and Q22 obtain the largest SF1 gains (61 .0× and 36 .7×): Q13 scans dictionary tokens and reduces directly into a 61-bin customer-count distribution, while Q22 extracts phone-code bytes and aggregates the surviving customers into a small dense domain. 

Residual bottlenecks. The benefit depends on how early the se-lected implementation collapses the working set. At SF100, Q15 (30 .5×), Q13 (25 .4×), and Q6 (23 .5×) retain compact aggregate state while their input scans grow. In contrast, Q1, Q5, Q7, and Q8 still stream much of lineitem and several payload columns, leaving them bounded by HBM bandwidth at 3 .1–3 .7×. Q16 has the smallest gain (1 .9×) because substring predicates, distinct supplier count-ing, and a full ordering over tens of thousands of output groups leave substantial per-row and high-cardinality work after filtering; Q11 similarly scans partsupp , forms per-part state, and sorts its sur-viving groups. The takeaway is that TPU-native operators remove irregular-access overhead, but they cannot eliminate bytes that the query must scan or large result state that it must materialize. 

## 7.3 Extreme Scale (SF1000) 

Figure 6 reports SF1000 performance using 16 TPU v5p chips against DuckDB. NTA accelerates every query by 5 .5–250 .7×, achieving 68 .6× geometric-mean speedup. The complete query set finishes in 1.613 seconds, down from 80.86 seconds, yielding 50 .1× total-runtime speedup. 

Scale-out behavior. Row-wise co-sharding keeps scans, masks, indexed gathers, and local reductions partition-local; devices ex-change only bounded aggregate state or Top-K candidates. Q6 there-fore reaches 250 .7×: each chip performs a contiguous scan and con-tributes one scalar partial sum. Q2, Q12, and Q13 achieve 164 .8– 172 .0× because selective predicates sharply reduce the fact-side work and the final Top-K or group state is small. Q3 and Q18, which are less dominant on one chip, reach 103 .2× and 185 .3× because clustered per-order reductions execute independently within each shard and require only a small final Top-K merge. 

Scale-out limits. Queries with large per-shard state or work that does not shrink with row partitioning remain the tail. Q16 im-proves by only 5 .5× because string matching, high-cardinality dis-tinct counting, and final ordering are still performed within ev-ery shard; Q17 reaches 15 .4× because its correlated per-part av-erage requires variable-fanout child reads and multiple reductions. Q11, Q15, and Q20 also retain per-key state or dependent filter-ing passes, limiting them to 29 .8–40 .0×. Consequently, the 50 .1×

total-runtime gain is lower than the 68 .6× geometric mean: the re-maining long-running, state-heavy queries receive less benefit and dominate elapsed time. Even so, the slowest query remains 5 .5×

faster, showing that NTA’s static programs scale without shifting the bottleneck to inter-device exchange.

Variable string lengths and highly selective string matching (e.g., textttLIKE, regex ). This is challenging because the underlying static tensor shapes would require shorter strings to be right-padded to the worst-case bounds. This padding and worst-case bound static tensor representation incur severe memory and bandwidth waste. When average string lengths are much shorter than the maximum, the majority of materialized tensors consist of zero-padding bytes that saturate scarce HBM bandwidth and on-chip scratchpad mem-ory (VMEM). Furthermore, TensorCore VPU vector lanes waste significant compute throughput comparing these padded positions. We see this variable string lengths challenge as a future co-design opportunity for us. Overall, NTA explicitly binds to JAX/XLA and Pallas kernels to bring about maximum performance from TPU and its various computing units. JAX/XLA also provides backend portability to different HW backends. Although writing performant Pallas ker-nels traditionally requires manual tuning, emerging agentic data-base coding systems [20, 32] offer a compelling solution path. By leveraging specialized database coding agents, systems can auto-matically synthesize, optimize, and specialize JAX/XLA and Pallas query kernels directly for TPU microarchitectures. 

## 8.2 HW & SW Co-Design Opportunities 

Re-engineering database operations for TPUs highlights residual performance gaps stemming from data-dependent dynamism, from 

redundant work from shape dynamism (padded rows and masked SIMD lanes) and memory stalls from address dynamism (fusion breaks at HBM roundtrips). To bridge these gaps without sacrific-ing the TPU’s highly optimized static (compiler-based) execution model, we propose four critical hardware co-design directions: 

Dynamic Tile-Skipping. Static shape bounding forces VPUs to schedule and evaluate fully invalid or padded tiles. Lightweight hardware mask-evaluation units that inspect tile validity metadata prior to dispatch could dynamically bypass dead tiles, conserving memory bandwidth and freeing execution cycles for active data. 

Compaction of Sparse Vectors. Another source of sparsity is originated in the processing of the data, at the tuple level. Prior operators eliminate some of the tuples, which may not be consec-utive in memory, leading to a finer-granular sparsity. For this case, 

> 11

compacting the data, locally near the VPU units, to have dense vec-tors would be a very useful hardware feature. 

Smart Caching. Unlike the hardware-managed caches seen in CPUs and GPUs, TPUs provide kernel-managed scratchpad mem-ories (SPMEM/VMEM). Prior work [3] has noted that cache evic-tions of hot data leads to significant performance drops. For hardware-managed caches, this is unavoidable, as accessing transient data (e.g., tuples) pollutes the cache, evicting hot data (e.g., hash table entries) and requiring extra HBM accesses. With TPUs, managing the scratchpad becomes a critical optimization point, allowing the database designer to ensure that frequently accessed data is ac-cessed at a high bandwidth and low latency, reducing stalls. 

Hardware-Level Virtual Partitioning: Currently, there is a lack of hardware partitioning and isolation on TPUs, enforcing strict se-quential execution of query kernels and preventing efficient multi-tenancy. Future TPUs could benefit from virtual partitioning and hardware supported isolation [3], to improve aggregate through-put and hardware utilization under concurrent workloads (Section 6). 

## 8.3 End-to-End Semantic Queries 

Emerging semantic AI query engines [7, 8, 12, 22, 27] extend rela-tional queries with semantic operators (e.g., filters and aggregations evaluated implicitly via LLM inference). Today, these pipelines suf-fer from severe data transfer penalties as they constantly move across the host-to-accelerator boundary, alternating between CPU-based relational logic and LLM model inference on accelerator hard-ware. By deploying NTA, the entire semantic AI query (relational operators and LLM invocations) can be compiled into a unified JAX program that runs natively on the TPU end-to-end. We view this unification and elimination of the execution boundary as a promis-ing application of our work, enabling the next generation of AI-native database engines [6]. 

## 9 RELATED WORK 

Hardware-Accelerated Query Processing. Relational query ac-celeration on massively parallel hardware has historically centered on GPUs. Early engines leveraged GPU SIMT architectures and hardware-managed caches to mask memory latency [13, 29], while subsequent systems integrated JIT compilation into heterogeneous CPU-GPU runtimes [5, 10, 28]. Concurrently, Tensor Query Pro-cessing (TQP) [14] proved that relational algebra can execute atop tensor computation runtimes—a paradigm now commercially de-ployed in Microsoft Fabric [17] with substantial speedups over CPU engines. Recently, modular GPU-native accelerators have emerged: Sirius [36] accelerates existing engines (e.g., DuckDB, Apache Doris) via drop-in CUDA-X libraries ( libcudf , RMM) for up to 10 × speedups, while Theseus [1] optimizes distributed GPU query execution across high-speed interconnects. However, these frameworks remain GPU-centric. While initial studies evaluated TPUs [14, 16], they largely treated the TPU as a black-box GPU drop-in, ignoring the severe HBM stalls and fu-sion breaks caused by the hardware’s statically scheduled execu-tion model. In contrast, NTA re-engineers relational query execu-tion specifically for TPU hardware, directly co-designing physical operators around SparseCore and TensorCore via custom Pallas kernels at terabyte scale. 

Join Algorithms on Accelerators. Efficiently executing joins— the most computationally expensive relational operator—has driven decades of research into hardware-conscious algorithm design. Tra-ditional optimizations focus heavily on Hash Joins [15, 30], opti-mizing hash table bucket layouts and probing strategies to max-imize cache hit rates on multi-core CPUs and GPUs. Advanced iterations have explored leveraging fast GPU interconnects (e.g., NVLink) to scale radix partitioning for joins beyond device mem-ory [23, 24]. However, these techniques rely implicitly on dynamic memory allocation and fine-grained scatter/gather operations. On a TPU, formulating a sparse hash table with empty padding buck-ets induces severe sparsity, while erratic hash-probing causes DMA queue contention at the memory banks. To circumvent these hard-ware limitations, Sorted-Hash Lookup Join abandons sparse hash materialization. Inspired by sort-merge architectures for highly par-allel vector engines, it transforms sparse, memory-bound hash prob-ing into packed-key hashing, parallel sorting, and vectorized search. 

Other TPU Applications. While TPUs were designed to accel-erate deep learning (e.g., matrix multiplications and embedding lookups [19]), recent work has also used them for scalable nearest-neighbor search [4]. This workload still maps to predictable, it-erative tensor computations. Analytical database queries present a uniquely challenging environment for TPUs due to their data-dependent dynamism, where output sizes and memory access pat-terns are dictated by the underlying data distribution/values at runtime. To the best of our knowledge, our engine is the first to successfully challenge these static dynamic restrictions, enabling TPUs to execute strict relational algebra effectively across multi-terabyte datasets up to SF 1000. 

## 10 CONCLUSION 

Google’s TPUs bring about massive computing at scale, yet they have not been sufficiently explored for analytical database work-loads. Our Native TPU Accelerator (NTA) demonstrates immense potential for analytical query processing through HW-conscious algorithm design and JAX/XLA optimizations that leverage Spar-seCore to efficiently offload dynamic memory accesses, multi-chip TPU slices, and fast ICI links. We show that TPUs have powerful programmable software stacks that enable per-query engineering and unlock effective TPU performance optimizations. Our NTA achieves very competitive TPU-accelerated analytical query pro-cessing results (e.g., state-of-the-art performance on TPC-H bench-marks). With AI/ML workloads consuming all the latest and great-est accelerators, older generation TPUs, like TPU v5p, are natu-rally becoming more available. It is becoming sensible to migrate database workloads to the earlier-generation accelerators, as they provide massive speedups for analytical query processing. As LLMs and semantic AI queries are increasingly integrated into data analytics engines to enable richer structured and unstruc-tured data analytics, migrating SQL workloads to the accelerator opens an unprecedented opportunity. By executing both relational queries and AI semantic operations on a shared computing sub-strate, our study shows that it is possible to unify enterprise data management with ML/AI accelerator HW/SW stacks, unlocking fundamentally greater performance and efficiency.
