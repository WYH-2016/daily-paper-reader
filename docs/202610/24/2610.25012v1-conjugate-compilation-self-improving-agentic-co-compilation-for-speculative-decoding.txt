## ABSTRACT 

As LLM adoption surges, scaling model serving requires not only adding more GPUs but also unlocking the substantial capacity stranded in those already de-ployed. Speculative decoding brings two models into the serving process: a small draft model proposes tokens that a larger target model verifies. Yet compiling these models individually leaves their shared execution outside the compiler’s optimization boundary. We therefore ask whether co-locating the draft and tar-get models on the same GPU and co-compiling their execution can reclaim this stranded capacity. We introduce C ONJUGATE COMPILATION , which reframes speculative decoding as a cross-model compilation problem and jointly optimizes the draft and target models within their shared execution rather than treating each in isolation. One of our key insights is that cross-model compilation should be informed by the measured performance of the co-located shared execution it pro-duces: an optimization that improves a kernel in isolation need not improve the models when they execute together. To expand cross-model opportunities, we devise operand layouts that interleave blocks from both models within common tiles, co-locating GEMM and non-GEMM work while preserving their mathe-matics. We realize C ONJUGATE COMPILATION through a self-improving agentic search system in which an LLM edits cross-model optimization plans using the compiler and GPU execution as its environment. Each proposed plan is compiled and evaluated through its co-located shared execution, whose measured score, to-gether with kernel-level verdicts and compiler feedback, informs subsequent pro-posals, while Monte Carlo tree search accumulates rewards to guide exploration. Across six single-GPU speculative-decoding configurations on NVIDIA B300 and RTX 5090 GPUs, C ONJUGATE COMPILATION achieves a geometric-mean per-round speedup of 1.37 × over conventional execution. Interleaved kernels raise this speedup to 1.45 ×, reaching 1.59 × in the best case. CONJUGATE COMPI -

## 1 INTRODUCTION 

As demand for LLM serving grows, expanding GPU infrastructure is only one way to increase serv-ing capacity (International Energy Agency, 2025). Another is to recover the substantial capacity that remains unused within existing deployments. Figure 1 shows one week of hourly GPU compute utilization measurements across enterprise users, illustrating how low average utilization persists de-spite variation across users and time. Across 6,000 measurements from 350 users collected between May and August 2026, average GPU compute utilization is 17.6%, with 94% of users averaging below 50% (Systalyze, 2026). These observations motivate us to examine how execution-informed compilation can turn more of the GPUs already deployed into useful capacity for model serving. 1arXiv:2610.25012v1 [cs.LG] 18 Oct 2026 Turning this capacity into useful work depends in part on compilation, which determines how a model’s operations and data are organized for GPU execution (Li et al., 2020). The common practice is to compile and optimize each model individually (Lu et al., 2025). Yet a single model’s operations may provide too little parallel work to fill the GPU or leave compute resources underused while waiting for data (Ding et al., 2021; Pope et al., 2023). This limitation motivates us to expand the compiler’s optimization boundary: rather than optimize each model in isolation, we bring multiple models into concurrent execution on the same GPU and jointly optimize them informed by their co-located shared execution.

Speculative decoding provides a setting for exploring this opportunity because two mod-els already cooperate to generate each re-sponse. A small draft model proposes several tokens, and a larger target model verifies them in a single forward pass, reducing the num-ber of target-model passes needed for gener-ation (Leviathan et al., 2023). This cooper-ation, however, does not by itself coordinate how their operations share GPU resources, nor does it bring their co-located shared execution within the scope of compiler optimization (Liu et al., 2025; Zhang et al., 2026). We there-fore pose a central research question: without changing either model’s underlying computa-tions, can we coordinate and co-compile the draft and target models to reclaim the capacity left unused when they are optimized individually? Speculative decoding provides a concrete setting for exploring this opportunity because two mod-els already cooperate to generate each response. A small draft model proposes several tokens, and a larger target model verifies them in a single forward pass, reducing the number of target-model passes needed for generation (Leviathan et al., 2023). Prior approaches primarily exploit this struc-ture as a scheduling, placement, or resource-allocation opportunity, either distributing draft and target execution across multiple GPUs or within a single GPU, while leaving their shared execu-tion outside the compiler’s optimization boundary (Liu et al., 2025; Zhang et al., 2026; Chen et al., 2026). We instead pose a central research question: what becomes possible when we co-locate them on the same GPU and let their shared execution directly inform cross-model compilation. We introduce C ONJUGATE COMPILATION , which reframes speculative decoding as a cross-model compilation problem by bringing the draft and target models into a common optimization boundary on the same GPU. Their co-located shared execution uses capacity left idle by either model, but also changes the conditions under which their operations execute. An optimization that improves a kernel in isolation may increase contention, disrupt beneficial overlap, or otherwise fail to improve the models when they execute together (Elvinger et al., 2025). One of our key insights is therefore that cross-model compilation should be informed by the measured performance of the co-located shared execution it produces. CONJUGATE COMPILATION uses this joint execution feedback to jointly optimize the draft and target models rather than optimizing each model independently. Optimizing within this co-located shared execution requires a search that can respond to how the draft and target models actually behave together. We therefore contribute a self-improving agentic system that couples an LLM with Monte Carlo tree search (MCTS) (Tang et al., 2025), using the compiler and GPU execution as its environment. The LLM proposes edits to cross-model compi-lation plans, which the compiler checks, builds, and tunes before we measure the performance of the resulting co-located shared execution. We use MCTS as the agent’s search medium, organizing explored plans and propagating their measured rewards to guide further exploration, while returning the complete execution score, kernel-level verdicts, and compiler feedback to the LLM to inform subsequent proposals. This coupling allows the agent to improve its proposals from accumulated execution evidence and directs exploration toward plans that improve the models together. To give the agentic system choices beyond coordinating separate kernels, we contribute an operand memory layout transformation that brings work from both models into a common kernel. 2.1 BRINGING DRAFTING AND VERIFICATION INTO SHARED EXECUTION 

Figure 2(a) shows conventional execution of speculative decoding on a single GPU. The green blocks denote draft-model segments and the purple blocks denote target-model segments, with hor-izontal position representing execution time. The γ draft steps complete before target verification begins, so the green and purple work does not overlap. If one draft step takes TD and target verifi-cation takes TV , their execution takes 

Tconventional = γT D + TV . (1) This ordering reflects a true dependency within each batch: target verification cannot begin until that batch’s draft tokens are available. The dependency, however, does not extend across batches. While the target verifies the proposals for batch b, the draft model can generate proposals for batch b + 1 .We use a dependency-preserving multi-stream co-scheduler to expose this concurrency on the same GPU. Figure 2(b) shows the resulting co-scheduled execution. Where purple target and green draft blocks overlap along the time axis, segments from the two models execute concurrently; gaps indi-cate intervals in which only one stream is executing. We divide both models into ordered segments, ranging from layers and attention/MLP halves down to individual projection stages, and submit the target and draft segments to separate CUDA streams. Segments within each stream execute in order, 3while segments on different streams may execute concurrently unless a cross-stream dependency orders them. Our co-scheduler inserts CUDA events (NVIDIA, a) only where such coordination is required, preserving the dependencies within each model while exposing legal overlap. Formally, let Gσ = ( V, E σ ) denote the co-scheduled round, where V contains the draft and target segments and Eσ contains their intra-model dependencies together with any cross-stream edges σ.Execution preserves every edge: 

tstart (v) ≥ tfinish (u), ∀(u, v ) ∈ Eσ . (2) For co-scheduling alone, σ = ∅; cross-model compilation decisions may later introduce cross-stream edges when their placement requires them. We capture both streams and their dependencies in a single CUDA graph and replay the complete co-scheduled round as one unit, removing host launch overhead while preserving the dependency structure. This co-scheduled round realizes the co-located shared execution that C ONJUGATE COMPILATION optimizes. Its measured behavior provides the execution feedback for the cross-model compilation decisions introduced next. 2.2 CROSS -M ODEL CONJUGATE COMPILATION 

Once the draft and target models are co-located, compiler decisions interact through their shared execution. C ONJUGATE COMPILATION therefore jointly optimizes cross-model compilation plans and judges them in the execution they change. This optimization applies even when the two models retain separate kernels on separate CUDA streams. Their kernel configurations can still be selected according to their effect on the complete shared execution rather than their isolated latency. We represent these choices through a joint optimization plan θ, which captures the cross-model compiler decisions realized within the shared execution. Realizing a joint optimization plan involves four components: the conjugated operation groups 

selected for joint execution, the interleaving proportions that determine how much work each oper-ation contributes to this joint execution, the kernel configurations used to execute the resulting work, and the scheduling arrangement that places it into the co-scheduled execution.

Given the plan θt selected by MCTS, the LLM agent proposes new joint optimization plans by refining its conjugated operation groups. The LLM does not generate GPU kernels directly; instead, it operates on the joint optimization plan abstraction defined in §2.2. The agent has four actions: 

add creates a new conjugated operation group, merge combines existing groups, split separates members of a group, and remove dissolves a group. Each action identifies operations and ranges of target layers and draft steps, allowing one proposal to apply the same transformation across multiple locations in the shared execution. The agent returns m distinct proposals. Edit types, operation identifiers, ranges, and legal place-ments are drawn from enumerated choices supplied by the compiler, making each proposal either directly interpretable or rejectable with a specific feedback code. The LLM proposes these re-finements from accumulated optimization experience rather than from the selected plan alone. Its prompt includes the selected plan and its recent ancestors, their measured round performance, ac-cumulated kernel-level verdicts, compiler feedback, legal placements, and measurements of rep-resentative draft–target segment pairs executed separately, concurrently, and conventionally. By comparing a plan with its ancestors and the feedback they received, the agent can associate changes in measured shared execution with the decisions that produced them and use that evidence to guide subsequent proposals. We compute the candidate’s full-round speedup over the anchor as the median of the paired anchor-to-candidate latency ratios. To express the search reward relative to baseline, we multiply this speedup by the anchor’s speedup over the faster of two conventional baselines: the compiled mod-els executed back-to-back, or sequentially within one captured CUDA graph. This scaling factor is fixed within a configuration, so it does not change how MCTS ranks candidate plans. The measured full-round reward updates the MCTS search tree, while kernel-level verdicts and com-piler feedback enter the LLM’s accumulated optimization experience to guide subsequent proposals. Tuned kernels, kernel verdicts, compiled joint nodes, rejection outcomes, and search checkpoints persist across escalation phases and resumed runs. The system therefore improves through accumu-lated compiler and GPU experience, without modifying the weights of the LLM agent. Appendix A details search-space expansion and final plan acceptance.

## 5 RELATED WORK 

Parallel speculative decoding systems coordinate drafting and verification through runtime schedul-ing and placement (Liu et al., 2025; Chen et al., 2026). GPU-sharing and context-aware compilation approaches schedule concurrent computations or optimize kernels for resource constraints (Strati et al., 2024; Liu et al., 2022). LLM-guided optimization typically targets individual kernels or pro-grams (Ouyang et al., 2025; Dong et al., 2026). Conjugate Compilation searches joint draft–target compilation plans using an LLM agent and MCTS, with measurements of the complete co-located shared execution guiding subsequent proposals. Additional related work is in Appendix B. 

## 6 CONCLUSION 

We introduced Conjugate Compilation, a framework for jointly optimizing co-located models using the measured performance of their shared execution to guide compilation. Our approach combines a self-improving LLM–MCTS search over cross-model compilation plans with transformations that bring work from multiple models into common kernels, spanning GEMM and non-GEMM opera-tions. A.1 EXPANDING THE SEARCH SPACE 

A fixed search space and tuning budget can cause exploration to stall before profitable co-optimizations are found. When measured progress plateaus, it first retunes near-miss kernels with progressively larger budgets, then widens the candidate groups and legal placements, refines the co-schedule down to individual projection stages so joint nodes can contain more precisely selected work, and finally exposes additional kernel-template choices. The agent is informed whenever the available search space expands. We impose an effort floor before concluding that a kernel family offers no profitable co-optimization. Each kernel family from both models is explored through multiple groupings, and every cross-model GEMM kernel appearing in a final candidate receives at least the combined tuning budget of the kernels it replaces. This prevents differences in compiler effort from determining the comparison. A.2 FINAL PLAN ACCEPTANCE 

Search-time measurements guide exploration, but the reported plan is subjected to a stricter final evaluation. After search, we re-time the strongest candidates and the best agent-proposed plans in paired ABBA blocks against the co-scheduling anchor, while re-measuring the conventional and plain two-stream baselines in the same measurement window. A plan is accepted only if its outputs pass the numerical checks in §3.3, the paired 95% confidence interval of its gain excludes zero, and its improvement exceeds a noise threshold. Finally, we remove every range of joint nodes whose leave-one-out gain does not exceed the noise threshold, unless the full plan is itself significantly faster than the reduced plan. This final pruning requires each retained range to contribute measurable value, either independently or through its interaction with the rest of the plan. 12 B ADDITIONAL RELATED WORK 

B.1 PARALLEL SPECULATIVE DECODING 

Prior work on parallel speculative decoding primarily treats draft–target parallelism as a runtime scheduling, placement, or resource-allocation problem rather than a compile-time optimization problem. Most of these systems place the draft and target models on separate GPUs, which im-prove performance but leave both devices underutilized: PEARL overlaps drafting and verification through adaptive parallel speculative decoding (Liu et al., 2025), MineDraft exploits batch-level parallelism across speculative-decoding rounds (Tang et al., 2026c), and SwiftSpec disaggregates draft and target execution across GPU resources (Zhang et al., 2026). FASER instead is a profile-driven runtime system for parallel draft–target execution on a single GPU, using offline profiling to guide how the two models share the device (Chen et al., 2026). These approaches operate after compilation: they schedule, place, or partition already-compiled model computations rather than changing how the draft and target are compiled together. Conjugate Compilation instead treats co-located execution as a compilation problem, searching cross-model transformations and evaluating each candidate using the complete score produced by the co-located shared execution. B.2 GPU S HARING AND CONTEXT -A WARE COMPILATION 

GPU sharing and inter-operator scheduling systems improve utilization by concurrently executing independent operators or models on the same device (Kwon et al., 2020; Ding et al., 2021; Chen et al., 2025; Strati et al., 2024; Zhang et al., 2025; Coppock et al., 2025). These systems do not target speculative decoding; rather, they address general multi-tenant or inter-operator GPU shar-ing, primarily deciding which already-compiled computations should execute concurrently, while context-aware compilation approaches optimize individual kernels for a predefined resource budget or interference condition (Liu et al., 2022; Ma et al., 2024; Lu et al., 2025). More fundamentally, these approaches rely on profiling, analytical models, or conventional optimization policies to make their scheduling and compilation decisions; they do not use an execution-driven agentic compiler that learns how to improve co-located execution from the outcomes of its own optimization attempts. Conjugate Compilation instead targets speculative decoding directly and couples an LLM agent with Monte Carlo tree search to iteratively propose cross-model compilation plans, compile and execute them, and use the complete score from the co-located shared execution together with kernel-level verdicts and compiler feedback to guide subsequent proposals. This self-improving loop makes the measured behavior of the co-located execution the feedback signal for compilation, allowing the search to adapt its transformations as it discovers which optimizations help—or hurt—the models when they execute together. B.3 LLM S FOR COMPILER OPTIMIZATION 

Recent work uses LLMs and agents to optimize individual kernels or programs (Ouyang et al., 2025; Dong et al., 2026; Cummins et al., 2025; 2023; Tang et al., 2025; 2026a;b). Conjugate Compilation extends agentic optimization across multiple models, using an LLM with MCTS to search joint draft–target compilation plans guided by measurements from their co-located shared execution. 13
