# ABSTRACT 

Reducing memory use in large language model (LLM) training is an ongoing challenge. Activa-tion checkpointing saves memory by recomputation, while lossy compression changes the stored activations. The reemergence of sparse ReLU and ReLU 2 activations creates a third opportunity: losslessly compressing the activation cache itself. We present BitSparse, a GPU-resident lossless compression format for sparse activations. Compression and reconstruction run in custom Triton kernels fused into an autograd function, shrinking the activation cache while recovering it exactly for the backward pass. Bfloat16 (BF16) and FP8 activations are supported. Optional sign-bit packing further increases compression up to close to the theoretical limit. We analyze its compression ratio and compare it to the theoretical optimum. BitSparse lowers per-token VRAM by 31% and 30% Modded-NanoGPT and Nemotron-H respectively, with overheads of no more than 1% at practical sequence lengths. Additionally, a new preallocated buffer system avoids host synchronization during training when variable size tensors are allocated. 

# 1 Introduction 

The memory required to train large language models limits the batch sizes and sequence lengths that fit on an accelerator. Alongside weights, gradients, and optimizer states, backpropagation requires activations retained from the forward pass. Parameter-related storage is largely independent of input size, whereas saved activations and some temporary buffers grow with the number of tokens processed simultaneously. Reducing this input-dependent memory cost is therefore important even when the model weights already fit on the device. Feed-forward layers are a natural target. They expand each token’s hidden representation, typically by a factor of 

3–5, and retain intermediate values for computing weight gradients. While the original Transformer Vaswani et al. (2017) used quadratic memory, more recent memory-efficient attention (Rabe and Staats, 2022; Dao et al., 2022) and state-space architectures such as Mamba (Gu and Dao, 2024) are both linear in the number of tokens, so the feedforward layers make up a significant portion of the memory cost. Certain activations produce sparse outputs that can be exploited to reduce memory usage. The ReLU activation ( ReLU )maps nonpositive inputs to exact zeros (Nair and Hinton, 2010). Large language models (LLMs) have used alternative activations such as GELU Hendrycks and Gimpel (2016) and gated activations such as SwiGLU. However, recently squared ReLU ( ReLU 2) activations have demonstrated competitive efficiency in LLMs (So et al., 2021) and are used in the Nemotron family and Modded-NanoGPT (Blakeman et al., 2025; Basant et al., 2025; Adler et al., 2024; Jordan et al., 2024a). Sparsity naturally emerges in training without any sparsity-inducing objective (Li et al., 2023; Mirzadeh et al., 2024). In our measurements, the pretrained Nemotron-H model has approximately 92% feed-forward activation sparsity. Exploiting this redundancy requires an inexpensive enough representation to use during backpropagation with minimal latency. Alternatives such as activation checkpointing reduce storage by recomputing forward intermediates (Chen et al., 2016), while lossy activation compression trades accuracy for memory (Chen et al., 2021; Shamshoum et al., 2025). This raises a simple question: can the exact zeros already produced by ReLU-family LLMs be converted into activation-memory savings without recomputation or approximation ?

# 3 Methodology 

3.1 Overview 

We propose BitSparse , an activation compression method for ReLU -like activations (e.g. ReLU 2) that adopts the notation and storage conventions of Section 2.2. BitSparse stores only the nonzero values, together with small index buffers for reconstruction, so the activation cache shrinks while the feed-forward projection is still computed densely. Activations are compressed before caching and reconstructed during the backward pass, preserving values in the selected storage format.

3.3 Sign-bit packing 

Because the output of ReLU activations is always nonnegative, our method can optionally remove the redundant sign bit. BF16 can be reduced to 15 bits and FP8 values to 7 bits. Zero entries are reconstructed as positive zero. We refer to BitSparse with sign-bit packing enabled as BitSparse-sb .GPU memory is byte-aligned, so a custom Triton kernel is written for packing individual bits. Let ui be the unsigned bit pattern of the ith compact value vi with its sign bit removed, and let wj be the jth output byte. The corresponding input index is i = ⌊8j/ (d − 1) ⌋, with bit offset k = 8 j mod ( d − 1) within ui. The output byte is 

wj = [( ui ≫ k)|(ui+1 ≪ (d − k − 1))] & (11111111) 2. (10) Here i indexes compact values, j indexes packed bytes, and k is a bit offset; out-of-range input words are treated as zero. The sign-bit packing reads two words and writes one byte at a time without atomics for high speed. Decoding works in an analogous way, also without atomics. 

3.4 GPU compression and reconstruction 

Compression is performed entirely on the GPU in three stages. First, a Triton tile kernel loads one tile, evaluates 

Ht > 0, constructs m and the count st. Second, a scan over the per-tile counts constructs the starting offsets p in Equation (9). Third, a second Triton kernel expands each tile mask and scatters positive values into v according to Equation (8). Optionally, a final Triton kernel strips the sign bits and packs values into bytes according to Equation (10). Reconstruction is performed by a single Triton kernel. Each tile identifies the location of its values using pt and loads the relevant values along with the bitmask. Next, a prefix sum is used to compute the location of each value in the final array. Finally, a masked gather is used to produce the decompressed tensor H, with sign-bit unpacking if necessary. Optionally, the values may be squared during decoding for the ReLU 2 activation. Two further kernels fuse the backward-pass operations. The ReLU backward pass requires only the support mask, so a single kernel multiplies the incoming gradient by that mask in place, without reconstructing the activation. The ReLU 2

pass performs the same operation with an additional dependence on Z, again in a single fused kernel. Furthermore, our blockwise structure allows for computing the backward matmul (Equations 19, 2) in blocks to avoid materializing the full activation to reduce peak memory further. 

3.5 Shared value buffers and implementation details 

The size of the value buffer v depends on the data, so allocating it on the host requires reading the device-resident count 

s, which interrupts asynchronous kernel submission. To avoid this, BitSparse optionally appends the values of different activations to a TensorBuffer , a large preallocated block with device memory offsets. Compressing a tensor appends its values and saves the starting offset on the device; decoding reads from the buffer using that offset, implemented in the kernels as val_idx = tl.load(prefix_ptr + tile_id) + tl.load(vals_offset_ptr) . This allows BitSparse to operate completely asynchronously. The buffer is reset at the end of every train step, and must be sized to not overflow. We recommend setting it as large as possible to use the unallocated memory. The buffer gives a latency improvement for small sizes which are CPU bound. Appendix E.6 shows a 5.2% runtime reduction at 32 tokens, diminishing as batch size increases and becoming negligible beyond 128 tokens. Furthermore, this allows BitSparse to work with torch.compile .

3.6 Sparse activation checkpointing for feed-forward layers 

Section 2.1 shows that the positive preactivation values and their positions contain the activation-dependent information required for backpropagation. We therefore cache a compressed representation of ReLU( Z) for both activation functions. For ReLU 2, the unsquared activation is stored to avoid a more unstable square root and keep numerical consistency with the forward pass. Our method is implemented in PyTorch as a custom torch.autograd.Function class that combines the ReLU 

or ReLU 2 activation along with a linear matrix multiplication; Algorithm 1 gives its forward and backward passes. Sign-bit packing and TensorBuffer are optional, with support for Bfloat16 and FP8 (both e5m2 and e4m3) with scaling Micikevicius et al. (2022). The overhead of compressing and decompressing is fairly minimal for typical LLM training. Besides using highly optimized Triton kernels, the overhead is asymptotically reduced as the LLM’s hidden dimension increases. # 5 Related work 

Lossy activation compression and low-precision training. Multiple methods have investigated lossy compression for activations. ActNN (Chen et al., 2021) uses randomized mixed-precision quantization and analyzes the resulting gradient variance. GACT (Liu et al., 2022) extends activation compression to generic network architectures, dynamically choosing tensor compression ratios. CompAct (Shamshoum et al., 2025) uses random projections to store low-rank activations. Low precision datatypes such as FP8 halves the storage per value compared to BF16 and offers speed-ups with hardware support (Micikevicius et al., 2022). COAT (Xi et al., 2025) targets both activation and optimizer-state memory through FP8 quantization. Hardware-accelerated 2:4 sparsity for ReLU 2 activations has been investigated by Haziza et al. (2025) for training and inference where activations are pruned so only 2 of every 4 activations are nonzero. 

Lossless memory reduction techniques. A few methods have explored lossless activation storage with ReLU 

activations. BitTrain (Hosny et al., 2021) stores the nonzero activation values for training convolutional neural networks (CNNs) on CPU-based edge devices. cDMA (Rhu et al., 2018) exploits activation sparsity to reduce transfers between GPU and host memory during training for host activation caching, also for CNNs. Gist (Jain et al., 2018) compresses sparse activations with a 8-bit CSR format. BitSparse extends these methods in several ways, including the standard GPU training setup without host synchronization, dedicated fused kernels for low overhead, low precision support and sign-bit packing for higher compression. We view these as essential for adoption in the modern LLM training era. In addition, nvCOMP (NVIDIA Corporation, 2026) provides optimized codecs for general and floating data, which can be applied to activations. # 6 Experiments 

6.1 Sparsity in LLMs 

We first examine activation sparsity in the feed-forward layers of two LLMs using ReLU 2: a 162M-parameter Modded-NanoGPT transformer (Jordan et al., 2024a) and the 8B-parameter Nemotron-H-8B-Base-8K model. These models differ in both size and architecture: Modded-NanoGPT uses transformer blocks, whereas Nemotron-H combines attention, Mamba, and MLP blocks. Full details are given in Appendix E.1. The Modded-NanoGPT model is trained following the Track 3 baseline procedure. Activation sparsity is measured on the validation set every 300 steps for every layer. Figure 5 shows an initial sparsity of approximately ρ = 0 .5, rapidly increasing to ρ = 0 .82 . This phenomenon has been observed in other works Haziza et al. (2025). Next, we evaluate the pretrained Nemotron-H model. The mean activation sparsity is 0.9273 , with minimum batch-wise mean sparsity over 256 evaluation batches of 0.9176 , corresponding to 92 .73% and 91 .76% sparsity, respectively. The sparsity is extremely consistent, with the minimum batch-wise mean sparsity only 0.97 percentage points below the mean, meaning activation compression can be used effectively.

6.4 Memory and runtime in LLMs 

As a larger training example, we evaluate peak VRAM usage and per-step latency when training Modded-NanoGPT and Nemotron-H across a range of sequence lengths (Appendix D.4), comparing dense activation storage, BitSparse(-sb), and activation checkpointing. Again, no optimizer buffer is used. A numerical equality check confirms that all methods reproduce the gradients up to floating-point rounding. Figures 3 and 4 report the memory and runtime results, respectively. Across the measured token counts, VRAM per token on Modded-NanoGPT decreases from 0.402 MiB to 0.277 MiB with BitSparse and 0.276 MiB with BitSparse-sb. On Nemotron-H, the corresponding values are 2.719, 1.894, and 1.890 MiB. This corresponds to an asymptotic VRAM reduction of 31% on Modded-NanoGPT and 30% on Nemotron-H. BitSparse incurs a negligible performance penalty. Checkpointing uses less memory but generally incurs a notable runtime cost. # 7 Conclusion 

We presented BitSparse , a GPU-resident tile-wise sparse representation for ReLU and ReLU 2 feed-forward activations that is lossless and can be used as a drop-in replacement to reduce memory usage. It is fast, using optimized fused Triton kernels, with overhead typically less than 1% for large sequence lengths while reducing memory by up to 30% . Because this sparsity arises naturally, BitSparse converts existing exact zeros into memory savings without approximation. BitSparse supports both BF16 and FP8 formats and can operate without host synchronization. BitSparse depends on the continued success of ReLU -family activations, since its gains rest on exact structural zeros. The scope is limited to feed-forward activations; attention and Mamba layers are not affected. Future work should extend the representation to gated activations and co-design it with checkpointing, offloading, and distributed training.

# A Memory usage during training 

Reference model and assumptions. Here, we describe in more detail the memory usage involved in training LLMs. We assume Bfloat16 storage is used everywhere for this analysis (2 bytes per element). Let P be the number of parameters in a model, W be its width, D be its depth and FFN expansion factor r. For LLM training, let the sequence length be n and total number of tokens be N , equal to sequence length times batch size. The model parameters require storage of 2P bytes. The optimizer states require either a buffer for every parameter, like Muon Jordan et al. (2024b) and SGDM, or 2 buffers for optimizers such as Adam Kingma and Ba (2014). Hence at least 2P bytes are needed. If gradients are all stored, an additional 2P bytes of storage are needed. However, gradient overhead can be removed by fusing the optimizer into the backward step, where the momentum buffers are updated as soon as gradients are computed, removing the need for gradient storage Lv et al. (2024). Hence, in this setup for LLM training or finetuning with Muon, a static memory overhead of 4P is required. The rest of the memory used is for the activations. These scale linearly with input size. While attention complexity is the square of sequence length, the peak memory required is only linear Rabe and Staats (2022). Furthermore, Flash attention Dao et al. (2022) provides a highly optimized attention implementation, where the intermediate computations are recomputed in the backward pass rather than stored. This reduces the cache size to O(N ). State-space methods such as Mamba Gu and Dao (2024) also use fused checkpointed kernels for the backward pass for good memory efficiency without saving the full intermediate computation graph. The storage used is O(DW N ).The feedforward layers make up the other major portion of the activation cache. # D Experimental setup 

D.1 System setup 

All experiments were implemented using PyTorch 2.14 with Triton 3.7.1 in Python 3.14. All experiments were run on an NVIDIA RTX 3090 24GB with the exception of the FP8 MLP and Nemotron-H experiments, which were run on an RTX 5090 32GB, for the FP8 support and extra VRAM. CompAct used the official implementation. The nvCOMP baseline uses version 5.3.0.16. Random seed 0 is used for all experiments. Timings are averaged over 5 runs, after warmup. 

D.2 Baselines Activation Checkpointing. Activation checkpointing Chen et al. (2016) reduces the amount of memory required by recomputing activations in the backward pass, rather than storing them in the forward pass. This trades off storage for computation, since certain layers will have computations repeated twice in a training step. PyTorch supports activation checkpointing natively. In our method, we checkpoint the full feedforward block, including the RMS norm layer. 

Lossless compression. Lossless compression can be used to reduce the size of the saved activations. The activations are compressed before being cached, and decompressed in the backward pass when needed. The nvCOMP NVIDIA Corporation (2026) library provides highly optimized GPU-native codecs for this task, including LZ4 Collet (2011), Zstd Collet and Kucherawy (2021), Bitcomp, and Cascaded. LZ4 uses dictionary matching to replace repeated byte 15 BitSparse: Compact Activation Storage sequences with short references. Zstd similarly exploits repeated patterns, while also using entropy coding to improve compression ratio. Bitcomp is a proprietary format designed for numerical data and can efficiently encode sparse values. Cascaded combines techniques such as run-length encoding, delta encoding, and bit-packing. While these are general lossless compression codecs, they benefit greatly from activation sparsity, since the many zeros are easy to compress. 

Compressed Sparse Row. A standard format for sparse matrices is the CSR format. This stores the nonzero values, their column indices and a cumulative counter of row indices, and is well optimized for GPU multiplication, with native support on our GPUs. This method is however suboptimal for this setting, where sparsity is around 0.5 to 0.85 , where the overhead from indices is significant. Currently, there is no FP8 support for CSR tensors. 

CompAct. Lossy compression has been considered. We compare against a recent method CompAct Shamshoum et al. (2025), which uses random Gaussian matrices to compress the hidden pre-nonlinearity activations into a lower dimension space. This method exploits the low-rank nature of activations. Training using CompAct demonstrates lower memory, with a small increase in training loss due to its lossy nature. The amount of compression can be tuned. We use CompAct-f to denote a compression factor of f , meaning its compression dimension is 1/f times the activation. A higher f gives lower memory and faster compression, at the cost of lower accuracy. 

D.3 MLP training benchmark setup Architecture and workload. The comparisons in Section 6.3 use a stack of eight residual MLP blocks. Each block applies RMS normalization, a bias-free linear expansion from 4096 to 21 ,504 features (the same as Nemotron-H), a 

ReLU or ReLU 2 activation, and a bias-free projection back to 4096 features before adding the residual connection. Inputs are synthetic standard-normal batches with 16 ,000 rows and 4096 features. Parameters and activations use BF16. In this test, parameters are not updated since we are interested in the performance and memory for computing the gradients, not the optimizer. Each lossless method is validated by checking that its gradients match the dense baseline up to floating-point rounding.

D.4 Language-model memory and runtime setup Models and data. We evaluate two models. The first is the 162M-parameter Modded-NanoGPT checkpoint from Section 6.1, trained by us according to the Track 3 baseline and evaluated at step 3300 (12 layers, 768 hidden dimensions, 

50 ,304 -token vocabulary). The second is NVIDIA’s official pretrained Nemotron-H-8B-Base-8K model. Both run in BF16 on a single GPU: an RTX 3090 with 24 GiB for Modded-NanoGPT and an RTX 5090 with 32 GiB for Nemotron-H. Models are evaluated on text from the FineWeb10B validation dataset Penedo et al. (2024), truncated to the target length. 

Batch size. Modded-NanoGPT is evaluated with a fixed batch of 4 sequences, sweeping the sequence length from 

256 to 16 ,000 tokens, so the number of tokens per step ranges from 1,024 to 64 ,000 . Nemotron-H is evaluated one sequence at a time at each length. 

Configurations. Each model is measured with dense activation storage, activation checkpointing on every feed-forward block, BitSparse, and BitSparse with sign-bit packing. Both models use ReLU 2 feed-forward activations. BitSparse compresses each activation at the sparsity the model exhibits naturally (Section 6.1). We modify both models to use the same fused RMS normalization, and chunk the Nemotron-H vocabulary projection head, to keep incidental memory overhead low (Appendix A.1). 

Workload. Each step performs a forward pass and the backward pass of the language-model loss over that step’s tokens. Model parameters are never updated and gradients are released as they are produced, so no full-model parameter-gradient buffer or optimizer state is retained. Transient parameter gradients still contribute to peak memory. 

Timing and memory. The timing and peak memory consumption in a training step are measured. Times are averaged per step over repeated iterations after warmup. Memory is tracked using torch.cuda.max_memory_ allocated("cuda") . As in Appendix D.3, peak memory covers model parameters, activations, and temporary tensors. Warmup steps are used to ensure accurate timing.
