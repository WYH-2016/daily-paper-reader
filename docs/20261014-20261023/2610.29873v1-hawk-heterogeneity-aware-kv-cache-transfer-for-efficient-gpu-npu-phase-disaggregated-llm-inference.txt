Abstract
Large language model (LLM) inference exhibits distinct compu-
tational characteristics across its two phases: prefill is compute-
intensive, whereas decode is more memory-bound. As a result, AI
accelerators achieve varying levels of efficiency across the two
phases. GPUs are well suited to prefill, but are often underuti-
lized during decode. By contrast, NPUs can utilize their compute
resources more effectively during decode. Motivated by this ob-
servation, we explore a heterogeneous architecture that integrates
GPUs and NPUs, mapping prefill to GPUs and decode to NPUs to
achieve high performance and efficiency. However, realizing such
heterogeneous integration is challenging because LLM phase disag-
gregation requires KV cache transfer from prefill to decode—that is,
from GPUs to NPUs—which is complicated by differences in inter-
device communication mechanisms and KV cache tensor layouts.
To address this, we propose HAWK, a transfer mechanism that en-
ables rapid KV cache transfer across heterogeneous devices. HAWK
establishes a remote direct memory access (RDMA) path for direct
cross-device transfers while handling inter-device tensor layout
discrepancies as part of the transfer process. In particular, HAWK
allocates tensor-layout-aware RDMA buffers on the NPU side to
match the target tensor layout. Leveraging these buffers, HAWK
orchestrates data transfer from a conventional contiguous GPU
RDMA buffer to the corresponding NPU buffers, allowing trans-
ferred tensors to be consumed directly without additional data re-
arrangement while maintaining transfer efficiency. We implement
and evaluate HAWK on a system built with commercially available
GPUs and NPUs, demonstrating performance within 7.88% of a
GPU-only system under the same SLO constraints while achieving
up to 1.26× higher power efficiency and 1.72× higher cost efficiency.

GPU Underutilization in LLM Inference: However, GPU effi-

resulting in general matrix-matrix multiplication (GEMM) oper-

enable high computing utilization. In contrast, during decode, the
model generates one token at a time and the computation is domi-
nated by general matrix-vector multiplication (GEMV). Since GEMV
provides limited tile-level parallelism and data reuse, it results in
lower compute utilization. [2, 3, 29, 59, 76, 79, 106].

Challenges: Despite its potential advantages, this heterogeneous
system faces several challenges to practical adoption. The first chal-
lenge is transferring KV caches generated during GPU prefill to
NPUs for decode. In homogeneous GPU systems, optimized commu-
nication software stacks such as NVIDIA NIXL [68, 72] enable direct
GPU-to-GPU data transfer via RDMA over InfiniBand or RoCE. In
contrast, heterogeneous data transfer remains relatively under-
explored. Moreover, NPUs often rely on diverse, vendor-specific
communication mechanisms [5, 32, 95, 100], further complicating
interoperability with other devices. The second challenge is handling
heterogeneous tensor memory layouts. In LLMs, many data struc-
tures, including weights, activations, and KV cache, are represented
as tensors [46]. Accelerators across device types and vendors often
employ device-specific tensor memory layouts to reduce memory
traffic and optimize computation [16, 22, 30, 82, 98]. Resolving such
tensor layout discrepancies requires additional data rearrangement,
complicating data transfer and increasing latency.
Enabling Heterogeneous LLM Inference: This paper presents
HAWK (Heterogeneity-AWare Key-Value Transfer), a mechanism
that enables high-performance LLM inference across heterogeneous
devices. HAWK establishes a direct data transfer path between GPU
and NPU memory by connecting both to a common RDMA stack. To
handle tensor layout discrepancies, HAWK applies a transfer-aware
transformation to the GPU KV cache to produce a tensor layout that
matches the target NPU layout while facilitating efficient RDMA
transfer. On the NPU side, HAWK allocates RDMA buffers to match
the tensor layout expected by the target NPU, with separate buffers
distributed across its DRAM channels. This organization allows
the transferred tensor to be consumed directly for decode without
post-transfer conversion.

• We characterize the phase-dependent execution behavior of GPUs
and NPUs for LLM inference. GPUs achieve high compute uti-

Background
2.1
LLM Inference
Figure 1 illustrates the inference process of a conventional decoder-
only Transformer, which consists of two phases: prefill and decode.
Both phases follow the same sequence of a token embedding layer,
multiple decoder layers, and a language modeling (LM) head, but
differ in the number of tokens processed. During the prefill phase,
all input tokens are first converted into embedding vectors by the
token embedding layer (❶). The resulting embeddings are then
processed by multiple decoder layers, each consisting of layer nor-
malization, multi-head attention, residual connections, and a feed-
forward network (FFN) (❷), to capture inter-token relationships,
incorporate contextual information, and refine token representa-
tions. The output of the decoder layers is then passed through the
LM head to produce token scores, from which the next token is
selected (❸). The selected token is subsequently fed back into the
token embedding layer as input, initiating the autoregressive de-
code phase (❹), which continues until an end-of-sequence (EOS)
token is generated or the maximum generation length is reached.
In particular, multi-head attention within each decoder layer
computes Query, Key, and Value (QKV) activations from the input,
which serve as the core intermediate representations for attention
computation and inter-token interaction [103]. The Key and Value
activations generated for each token remain unchanged during
subsequent decoding steps and can therefore be reused. To exploit
this property, LLM inference stores these activations in memory
as a key-value (KV) cache and retrieves them in later decoding

2.2
Characteristics of Prefill and Decode
The dominant computations in the decoder layer, including QKV
projections, attention computation, output projection, and FFN
projections, depend on the input shape [3, 76], as shown Table 2.
During prefill, all input tokens are processed in parallel (𝐿equals
the initial input length), producing a matrix of embedding vectors;
consequently, these computations are dominated by GEMM. During
decode, in contrast, the model processes one newly generated token
at a time (𝐿equals 1), producing a vector; accordingly, the dominant
computations are mapped to GEMV, which exhibits lower arith-
metic intensity and reduced data reuse relative to GEMM. Moreover,
decode requires fetching KV caches from previously processed to-
kens, which introduces more memory traffic than prefill.

3.2
Potential of NPUs for Efficient Decode
NPUs are specialized accelerators designed for AI workloads. While
their detailed designs vary, most broadly adopt dataflow-oriented
architectures that explicitly manage computation and data move-
ment to maximize data reuse and reduce the impact of off-chip
memory accesses [4, 18, 37, 41, 51, 90]. These characteristics can be
particularly beneficial for GEMV-like computation during decode.
Table 4 compares the compute utilization and power efficiency
of GPUs (A100) and NPUs (p150a) for representative kernels in a
decoder layer during decode. Compute utilization is calculated by
dividing the achieved throughput (TFLOPS) by the peak through-
put of the compute cores used by each kernel and multiplying by
100. During decode, the evaluated NPUs use fewer compute cores
than during prefill (e.g., 8 versus 64 for FFN operations [97]) and
select cores closer to DRAM to better accommodate the limited
parallelism and memory-intensive nature of GEMV-like computa-
tion. By concentrating computation on fewer cores, they maintain
high utilization of the assigned cores, exceeding GPU utilization
across all evaluated kernels. While using fewer cores may limit
kernel throughput, it can also improve power efficiency by reduc-
ing the number of active compute cores. In our evaluation, the
NPU achieves higher power efficiency for attention and FFN ker-
nels, which account for a substantial fraction of LLM decoding
time [106]. Although we evaluate one NPU platform, other NPU
architectures may achieve similar efficiency gains through differ-
ent mechanisms. When these efficiency gains are achieved while
maintaining comparable performance, as shown in Table 1, NPUs
can be considered an attractive option for efficient decode serving.

3.4
Challenges: Handling Heterogeneity
Despite the potential benefits of a heterogeneous GPU–NPU sys-
tem, several challenges hinder its practical deployment. The first
challenge is cross-device data transfer, particularly for KV caches.
In a GPU-only system, GPUs support RDMA-based transfers [69]
through optimized communication software [72, 81], allowing the
network interface card (NIC) to directly access GPU memory, as
shown in Figure 3 (④). However, in a heterogeneous system, GPUs
and NPUs rely on distinct software stacks and communication
mechanisms [5, 32, 95, 100], which may not directly interoperate.
A straightforward solution is to use the host as a staging point,
which avoids the need for direct interoperability (⑤). However, this
approach incurs substantial latency from additional copies between
the host and each device, as well as host intervention. We observed
that, even between GPUs, host-staged transfer incurs 1.83× to 5.25×
the latency of direct transfer as the transfer size increases from
10 MB to 1.2 GB, adding substantial overhead to LLM serving.
The second challenge is handling differences in KV cache tensor
layouts across devices. A tensor layout defines the ordering and
shape of tensor dimensions, as well as how tensor elements are
mapped to the virtual address space and distributed across physical
memory channels. Different accelerators employ device-specific
tensor layouts to optimize data movement and computation, and

Heterogeneity-Aware KV Cache Transfer
Our goal is to enable an efficient GPU–NPU heterogeneous LLM
inference system. To this end, we present HAWK, a heterogeneity-
aware KV cache transfer mechanism that enables direct, high-
performance tensor transfer between GPUs and NPUs.

HAWK. HAWK builds on the Linux RDMA stack and establishes
a common RDMA path for GPU and NPU memory by integrating
device-specific RDMA memory support (❶), enabling the NIC on

tion. Once the GPU prefill instance generates the KV cache, HAWK
transforms the GPU KV tensors into transfer-friendly aligned ten-
sors (❷). The transformation partially aligns tensor elements with
the target NPU layout while maximizing the size of each RDMA
transfer. HAWK then transfers the transformed tensors from a con-
ventional GPU RDMA buffer into multiple layout-aware RDMA

4.1
Building a Direct Data Path Across Devices
The essential step toward efficient data transfer is to establish a
high-performance transfer path between computing devices. To this
end, HAWK connects GPU and NPU device memory through a com-
mon Linux RDMA stack spanning kernel space (e.g., ib_core [42])
and user space (e.g., libibverbs [31]), as shown in Figure 6. On the
GPU side, HAWK leverages the GPU peer memory client [64, 69]
(①), whereas on the NPU side, it extends the NPU driver with a
corresponding peer memory client (②). Table 5 summarizes the
implementation of the NPU-side RDMA stack. These clients ex-
pose device memory to the RDMA subsystem by providing the
memory-mapping information required for memory registration,
enabling the NIC to directly access the registered memory. Building
on this kernel-level support and a common RDMA stack, various
transfer engines [55, 81, 111] abstract low-level RDMA primitives
and orchestrate runtime data movement (③). Together, these com-
ponents establish a high-performance, flexible data transfer path
across heterogeneous devices.

For GPUs, tensors are distributed across multiple DRAM channels

mapping, improving memory locality and reducing traffic between
off-chip memory and on-chip SRAM. Therefore, an NPU tensor has
a distinct memory layout and address mapping compared with a
conventional virtually contiguous buffer.

These discrepancies in address mapping and memory organization
between GPUs and NPUs introduce two major issues. The first issue
is that, even if a GPU tensor is transformed to match the target NPU
tensor layout in dimensions and element ordering, transferring it
through a conventional RDMA buffer may still require additional
post-transfer adjustment before it can be used as an NPU tensor
object ( c○). The second issue is that using a conventional virtually
contiguous RDMA buffer on an NPU can cause severe memory
fragmentation. Because the buffer layout does not follow the NPU
tensor layout, memory usage can become imbalanced across DRAM
channels, leaving some channels exhausted while capacity remains
available in others. This imbalance can prevent subsequent tensor
allocations ( d○). Even if new tensors are allocated only from parti-
tions with sufficient remaining capacity, such selective allocation
can disrupt the intended data placement and reduce data-movement
efficiency, ultimately degrading performance.
To address this issue, HAWK allocates NPU RDMA buffers ac-
cording to the target NPU tensor layout, using one virtually con-
tiguous buffer per DRAM channel with corresponding software
support, as shown in Table 6. This layout-aware allocation allows
transferred data to be consumed directly from the RDMA buffers
or converted into the target tensor with only limited intra-channel
data movement, avoiding costly data rearrangement across multiple
DRAM channels. Although using multiple virtually non-contiguous
buffers can increase buffer-management overhead and the num-
ber of RDMA requests required to transfer a tensor, the number
of buffers is bounded by the number of DRAM channels in the
NPU. This count is typically around ten or fewer, and each per-
channel buffer remains contiguous. As a result, the additional buffer-
management and RDMA-request overhead remains modest relative
to a conventional single-buffer design.

4.5
Discussion
4.5.1
Extensibility Across NPU Architectures. Diverse NPUs employ
device-specific tensor layouts to optimize memory placement, data
movement, and compute efficiency, and these layouts often differ
from GPU tensor layouts [22, 30, 82, 98]. Such layout differences
can arise even when the same framework-level tensor is placed
on different devices. For example, TensorFlow tensors placed on
Google TPUs [1, 36, 37] use layouts that differ from those used on
GPUs [22, 23], including differences in tiling, padding, and element
ordering. These differences highlight the need for heterogeneity-
aware data transfer across devices. In this context, HAWK provides
a generalizable design for such transfers. Our prototype imple-
mentation is configured for an optimized tiled tensor layout [98],
many other NPUs similarly employ tiled or blocked tensor lay-
outs [22, 30], allowing HAWK’s core mechanisms to be adapted to
these architectures. Even when tensor-layout details differ, HAWK
can be adapted through device-specific changes to tensor-aware
RDMA buffer allocation to accommodate the target NPU layout.
4.5.2
Adaptability to Other Forms of Disaggregation. Most data
objects in LLM inference, including model weights, KV caches, and
intermediate activations, are represented as tensors. Since HAWK
fundamentally targets efficient tensor transfer across heterogeneous
devices, it can be adapted to other heterogeneous disaggregation
schemes that require transferring tensor objects between devices.
For example, in operator-level disaggregation [26, 112], attention
7


computation can be performed on GPUs while subsequent opera-
tors are executed on NPUs. In such a configuration, intermediate
activation tensors must be transferred between the two devices.
Compared with KV caches, intermediate activations are typically
smaller, making fixed transformation and layout-adjustment over-
heads more significant relative to the transfer time. Moreover, their
transfer lies between dependent operators, limiting opportunities
for latency hiding through overlap. In this context, HAWK can
provide substantial benefits for such tensor transfers.
4.5.3
Reverse Transfer. While HAWK targets data transfer from
GPUs to NPUs, the same approach can be extended to NPU-to-GPU
transfers, which can be useful when an NPU offers higher prefill
efficiency than a GPU. In such cases, the transfer-aware transfor-
mation can be performed on the NPU, partially aligning the tensor
with the target GPU layout while arranging portions destined for
contiguous regions of the GPU buffer contiguously within each per-
channel NPU buffer. Each contiguous portion in the per-channel
NPU RDMA buffers can then be mapped to the corresponding re-
gion of a virtually contiguous GPU RDMA buffer, completing the
remaining layout alignment during transfer. This preserves the ben-
efit of fewer, larger RDMA transfers while allowing the transferred
tensor to be used directly for GPU decoding without additional
post-transfer layout transformations.

5.1
Methodology
5.1.1
Hardware Configuration. The system consists of a single pre-
fill instance and a single decode instance: the prefill instance runs on
NVIDIA A100 PCIe GPUs [62], interconnected within each node via
NVLink Gen 3 and PCIe Gen 4, while the decode instance runs on
Tenstorrent p150a boards [92], interconnected via Ethernet-based
links. We use Tenstorrent NPUs because, to the best of our knowl-
edge, they are the only NPU platform that provides an open-source
software stack permitting the low-level modifications required by
HAWK. The prefill and decode instances run on separate nodes
connected via 200 Gbps HDR InfiniBand, with each node equipped
with a ConnectX-6 NIC [63].
5.1.2
Software Configuration. We use vLLM v0.10.0 [46] as the
serving framework to demonstrate that our system and HAWK
can operate within a widely used LLM serving environment. To
support NPU execution, we integrate the Tenstorrent LLM stack
with vLLM through a plugin. For GPU-side RDMA support, we
use nvidia-peermem [67, 73]. On the NPU side, we extend the
Tenstorrent software stack (user-mode driver v0.68.0 [94, 97] and
kernel-mode driver v2.5.0 [93]) to implement the RDMA-related
functionality required by HAWK, including a peer memory client
and tensor-layout-aware RDMA buffer allocation. Building on this
support, we implement a user-space transfer mechanism on top
of Mooncake Transfer Engine v0.3.6 [45, 81], a high-performance
data transfer engine for disaggregated LLM serving. Our mecha-
nism integrates transfer-aware tensor transformation with RDMA
buffer pairing. For the model, we use Llama 3.1 70B [24], whose
scale requires multiple accelerators and is therefore suitable for
evaluating phase-disaggregated serving. We distribute the model
across four devices per instance using tensor parallelism (TP). In

HAWK’s tensor-layout-aware RDMA buffer allocation. We there-

5.4
Serving Efficiency
The main benefit of GPU-NPU heterogeneous integration with
HAWK lies in power and cost efficiency. We compare these efficien-
cies at 90% SLO attainment using output token throughput, focusing
on GG-Direct and GN-HAWK as the best-performing homogeneous
and heterogeneous configurations, respectively.
5.4.1
Power Efficiency. We calculate power efficiency by dividing
output token throughput by the aggregate ASIC power of all prefill
and decode devices, averaged over the same measurement interval.
Specifically, we use device ASIC power, including compute cores
and on-chip SRAM, because the available Tenstorrent monitor-
ing interface reports only NPU core power [99]. To estimate GPU
ASIC power, we first collect board-level power measurements using
NVIDIA DCGM [71]. We then collect binary traces of GPU kernels
executed during prefill and decoding using NVBit [104] and feed
them into a detailed GPU power simulator to estimate the fraction
of total power attributable to the GPU ASIC for each phase [39].
Finally, we apply these phase-specific fractions to the correspond-
ing board-level power measurements. Regarding excluded power
components, both configurations use the same interconnect hard-
ware and exhibit similar transfer times, suggesting that differences
in interconnect energy consumption may be limited. We also con-
sider memory power. Although HBM2e in the evaluated GPU offers
higher bandwidth per watt than GDDR6 in the evaluated NPU, esti-
mates accounting for their respective memory bandwidths indicate
higher memory power consumption for the GPU [56].
As shown in Table 8, GN-HAWK achieves 1.26× and 1.15× higher
power efficiency than GG-Direct for Chatbot and Summarization,
respectively. These gains come from combining GPU prefill with
NPU decode to improve efficiency while maintaining comparable
serving performance. HAWK makes this combination effective by
reducing transfer overhead between the heterogeneous devices. Al-
though the magnitude of the gains may vary across NPU platforms,
the results demonstrate the potential of GPU-NPU heterogeneous
serving to improve power efficiency.

Cost Efficiency. Since device prices vary with market condi-
tions, we report cost efficiency as a reference rather than a definitive
comparison across configurations. Cost efficiency is calculated by
dividing output token throughput by the aggregate cost of all pre-
fill and decode devices. We use the official vendor price for the
NPU [92] and publicly listed market prices for the GPUs [20, 89].
As shown in Table 8, GN-HAWK achieves 1.72× and 1.61× higher
cost efficiency than GG-Direct for Chatbot and Summarization,
respectively. These results suggest that GPU-NPU heterogeneous
systems can be an economically attractive option for LLM serving
with proper system support.
5.4.3
Comparison with Another GPU Architecture. To examine
whether the efficiency benefits of our proposed system hold with a
different GPU architecture, we replace the decode-side A100 GPUs
in GG-Direct with NVIDIA H100 GPUs [65], refer to this configu-
ration as GGH-Direct, and compare it with GN-HAWK. As shown
in Table 9, GN-HAWK achieves only 6.53% and 6.50% lower output
token throughput than GGH-Direct at 90% SLO attainment for Chat-
bot and Summarization, respectively. In terms of power efficiency,
GN-HAWK achieves 1.03× higher efficiency for both workloads.
These gains are smaller than in the A100 comparison because the
H100 GPUs consume less power during decoding in our evaluation.
For cost efficiency, GN-HAWK achieves 2.73× and 2.76× higher
efficiency for Chatbot and Summarization, respectively, reflecting
the higher H100 prices used in our evaluation [21]. These results
further demonstrate the potential of GPU-NPU heterogeneous serv-
ing to improve efficiency, with the gains depending on the specific
GPU and NPU platforms used.
6
Related Work
6.1
Phase-Disaggregation
Prior work has proposed diverse optimizations for prefill-decode
disaggregated serving systems, including phase-aware resource pro-
visioning and placement [29, 78, 110], heterogeneous GPU deploy-
ment [16, 34], cluster-level scheduling and dynamic prefill-decode
ratio adaptation [35, 81, 83, 105, 108], and KV cache management
and transfer optimization [27, 28, 81]. These efforts primarily opti-
mize disaggregated serving within GPU-based systems. We extend
this scope to GPU-NPU phase disaggregation and demonstrate its
potential for LLM serving.
6.2
Other Forms of Heterogeneous Integration
Prior work has explored LLM inference systems that combine
GPUs with CPUs [25, 33, 38, 52], NPUs [15, 59, 107], or PIM/PNM
accelerators [43, 44, 47, 76], as well as integrated NPU-PIM sys-
tems [17, 26, 84]. These studies exploit hardware heterogeneity
through workload partitioning, offloading, scheduling, and disag-
gregation to improve inference performance and efficiency. Against
this backdrop, we investigate the practical challenges of coordinat-
ing GPUs and NPUs across multiple servers and develop system-
level solutions to address them.
7
Conclusion
We propose a GPU–NPU phase-disaggregated LLM inference sys-
tem that leverages GPUs for prefill and NPUs for decode to achieve
both high performance and efficiency. Realizing such a system,
however, requires an efficient data-transfer path that addresses
heterogeneity between GPUs and NPUs. To this end, we present
HAWK, which enables direct data transfer over a common RDMA
stack while addressing tensor-layout discrepancies through tensor-
layout-aware RDMA buffer allocation and transfer-aware tensor
transformation. Our evaluation shows that HAWK enables the het-
erogeneous system to maintain performance within 7.88% of a
GPU-only system under the same SLO constraints, while achieving
up to 1.26× higher power efficiency and 1.72× higher cost efficiency.
