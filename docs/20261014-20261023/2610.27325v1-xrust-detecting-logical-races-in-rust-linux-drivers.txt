JEFF HUANG, Texas A&M University, USA Rust is increasingly used in Linux to improve memory safety, but its guarantees do not prevent logical races: individually synchronized operations can still interleave in ways that violate higher-level invariants. Detecting such bugs typically requires manually written specifications and carefully controlled execution environments. We present XRust, a technique for detecting logical races in Linux Rust drivers without manually specified invariants. Using Logical Happens-Before (LHB) analysis, XRust identifies shared-state accesses relevant to logical ordering, automatically constructs operation-pair harnesses, and uses serial differential oracles to detect concurrent executions inconsistent with either serial order. XRust also uses lightweight userspace abstractions to execute driver code under reproducible schedules. Applied to Linux 7.3-rc2, XRust identifies 17 shared objects across 102 Rust files from ten drivers, constructs 1,654 executable harnesses, and discovers two previously unknown logical races. The rnull block-driver race has been confirmed by Linux maintainers, with a fix accepted into the Linux block subsystem tree. 1 Introduction 

Rust offers a path toward eliminating memory-safety vulnerabilities and data races through its own-ership and type systems [31]. These guarantees are particularly compelling for operating-system kernels, where a single defect can have system-wide consequences [13]. Linux, historically imple-mented primarily in C, has long faced memory-safety and concurrency bugs due to manual memory management, unrestricted pointer manipulation, and complex synchronization protocols [9]. Rust-for-Linux (RFL), launched in 2020, is an effort to bring Rust’s memory- and thread-safety guarantees into the Linux kernel and enable kernel components, particularly device drivers, to be written in Rust [4, 30]. The first functional Rust driver was merged into Linux 6.8 in early 2024. Since then, Rust adoption in Linux has accelerated, growing from 95 SLOC in 2024 to 19,726 SLOC by September 2026 [13]. The increasing complexity of this code is exemplified by Android Binder: Google’s Rust Binder driver entered mainline Linux in version 6.18, with ongoing work toward replacing the legacy C implementation [16, 25, 26]. This rapid evolution—from basic language support to complex, highly concurrent drivers—makes understanding the concurrency correctness of Rust kernel code increasingly important. However, Rust’s memory- and thread-safety guarantees do not imply that Linux drivers written in Rust are free of concurrency bugs. In 2025, a severe vulnerability (CVE-2025-68260) was reported in the Rust Binder driver [14], as illustrated in Figure 1. The vulnerability arose from an invalid assumption about list ownership and lock protection. Concurrent operations are allowed and corrupt the notification list. This example highlights an important limitation of Rust’s safety guarantees: they do not ensure the logical correctness of concurrent operations . A driver may be free

We call such a failure a logical race : an execution in which the ordering or interleaving of concurrent operations invalidates a logical assumption on which one or more operations depend. As increasingly complex Linux components are implemented in Rust, detecting such bugs becomes increasingly important because they fall outside the class of concurrency errors that Rust’s type system is designed to prevent. In this case, Binder maintains a list of death notifications associated with each node. During node destruction, Node::release moves these notifications to a temporary local list and releases the node lock before processing them. A concurrent operation may nevertheless attempt to remove a notification under the assumption that it is either linked to its owner’s list or not linked to any list. Moving the notification to the temporary list violates this assumption: the notification remains linked, but is no longer protected by the lock expected by the concurrent operation. The two operations may therefore manipulate the same notification under incompatible assumptions about its state, eventually corrupting the underlying list. This example illustrates a broader challenge: logical races arise from violations of program-specific invariants that are often implicit in the code rather than enforced by Rust’s type system. Detecting logical races of this kind is non-trivial for several reasons: 

• Challenge 1 Concurrency testing requires an oracle that distinguishes an incorrect in-terleaving from a valid concurrent execution. One approach is to manually specify the intended behavior. E.g., CONVEROS [29] verifies 12 concurrency modules in the Rust-based OS Asterinas [23] using PlusCal specifications derived from its implementation. Such speci-fications can express rich safety properties, but constructing and maintaining them requires substantial effort and expertise. Kernel concurrency fuzzers can expose failures through controlled schedule exploration. E.g., SECT [33] injects scheduling points through LLVM instrumentation and uses a sched_ext -based eBPF scheduler to explore kernel thread inter-leavings. Such testing, however, still requires an observable failure condition or other oracle to determine whether a particular execution is incorrect. For logical races, the challenge XRust: Detecting Logical Races in Rust Linux Drivers 3

is therefore not only to expose unusual interleavings, but also to determine automatically whether their behavior is semantically invalid. 

• Challenge 2 The number of possible executions grows rapidly with the number of threads and scheduling points. Controlled concurrency testing addresses this problem by repeatedly executing a harness under different controlled schedules. Loom [32] systematically explores valid execution permutations while applying state-reduction techniques, whereas Shuttle [1] emphasizes randomized schedule exploration together with deterministic replay of failures. Nevertheless, their effectiveness depends critically on which operations a harness exercises and where scheduling choices are introduced [3]. Exploring every possible scheduling point is prohibitively expensive for realistic driver code; effective testing must instead identify the interleavings most likely to expose violations of logical ordering constraints. 

• Challenge 3 Linux drivers depend heavily on kernel interfaces and execution contexts that are difficult to reproduce in a small, deterministic userspace test. A Rust driver does not execute in isolation: it invokes kernel interfaces implemented in both Rust and C and inter-acts with kernel objects, callbacks, synchronization primitives, and lifecycle management. Testing a small piece of driver logic inside a complete Linux kernel requires executing a large system in which unrelated kernel activity makes fine-grained schedule control difficult. RustMC [22] operates over LLVM IR to model-check concurrent Rust programs, including programs with C/C++ dependencies. However, controlled concurrency testing of Linux Rust drivers still requires a lightweight execution environment that faithfully reproduces the kernel dependencies and synchronization behavior relevant to the driver code under test. To address these challenges, we propose XRust, a technique for detecting logical races in Linux Rust drivers. At the core of XRust is a new relation, Logical Happens-Before (LHB) , which captures semantic ordering requirements between operations on shared state. Conventional happens-before characterizes ordering induced by program order and synchronization and is commonly used to reason about conflicting memory accesses. LHB preserves thread-local program order while omitting the mutex release-acquire ordering. Two operations may individually use synchronization correctly and contain no conventional data race, yet an interleaving of their constituent steps may still produce behavior that cannot be explained by any valid serial execution. XRust uses this distinction to identify and test precisely such interleavings. First, XRust automatically constructs an executable oracle for logical races. For a pair of operations on a shared state, XRust executes the operations sequentially in both possible orders from equivalent initial states and records their observable outcomes. These serial executions define the reference behaviors for the operation pair. XRust then executes the same operations concurrently under controlled schedules. If a concurrent execution produces an observable state or outcome that is inconsistent with both serial orders, XRust reports a potential logical race. This serial-equivalence oracle avoids requiring developers to manually encode a separate invariant for every operation pair while still capturing violations of their expected atomic behavior. Second, XRust uses LHB to focus exploration on promising interleavings. Exhaustively inserting scheduling decisions at every memory access would create an impractically large search space. XRust instead performs runtime analysis of shared-state accesses and synchronization events to identify points at which the relative ordering of the two operations may affect their logical behavior. These observations are used to prioritize scheduling points around accesses to shared state and around synchronization boundaries that may separate logically related steps. XRust then guides controlled concurrency testing toward these candidate interleavings rather than exploring the entire schedule space uniformly. 4 Xu et al. 

Third, XRust uses a lightweight userspace abstraction to execute Linux Rust driver code under controlled schedules. Rather than running the driver inside a full Linux kernel, XRust emulates only the kernel interfaces exercised by a target harness, replacing them with lightweight userspace imple-mentations that preserve the state, synchronization, and callback behavior relevant to concurrency testing. These implementations are constructed with assistance from Claude Code ( claude-opus-5 )and checked through compilation and manual compatibility review. The original Rust driver logic remains unchanged. Within this environment, XRust uses Shuttle to control thread scheduling and record executions that trigger oracle violations, enabling deterministic replay of reported logical races. XRust performs its shared-state and synchronization analysis dynamically on compiled harnesses. It extends ThreadSanitizer [28] to observe memory accesses and synchronization relationships at runtime, avoiding the need for a whole-program static model or source-level rewriting of synchronization primitives. Combined with the lightweight userspace abstractions described above, this design allows XRust to analyze executions of real Rust driver code while retaining precise control over thread scheduling. In summary, this paper makes the following contributions: (1) We introduce Logical Happens-Before (LHB), a formulation for reasoning about semantic ordering requirements between concurrent operations. Such exposed synchronized ac-cess conflicts may be individually data-race-free yet collectively violate higher-level state invariants. (2) We present XRust, an automated technique for detecting logical races in Linux Rust drivers. XRust constructs operation-pair harnesses and serial-equivalence oracles, guides schedule exploration toward interleavings likely to violate logical ordering constraints, and supports deterministic replay without requiring manually specified invariants. (3) We develop a lightweight userspace approach for executing Linux Rust driver code under controlled schedules. XRust extends ThreadSanitizer to observe shared-memory accesses and synchronization at runtime and provides lightweight abstractions for the kernel interfaces required by each harness. (4) We evaluate XRust on ten Rust drivers in Linux kernel 7.3-rc2, covering diverse synchro-nization mechanisms, including spinlocks, mutexes, and file locks. Across these drivers, XRust enumerates 1,735 pairs of operations that may access the same object and constructs executable harnesses for 1,654 of them. XRust discovers two previously unknown logical races in rnull and Binder . The fix for the rnull logical race has been accepted and applied by the Linux block subsystem maintainer. 

2 Background 2.1 Logical Races 

Concurrent executions induce a partial order over program events known as the happens-before 

(HB) relation. HB includes both program order within a thread and synchronization order across threads. For example, releasing a mutex and subsequently acquiring the same mutex creates an HB relation between the corresponding critical sections. 

Data race. A conventional data race occurs when two threads access the same memory location, at least one access is a write, and the accesses are not ordered by synchronization. ThreadSanitizer and related detectors identify such unordered memory conflicts [28]. Rust prevents most data races in safe code by restricting mutable aliasing and requiring shared mutable state to be accessed through synchronization abstractions. Logical race. Data-race freedom, however, does not imply concurrency correctness. Empirical studies have shown that many real-world concurrency failures arise from atomicity and ordering violations rather than individual unsynchronized memory accesses [17, 22]. We use the term 

logical race for an interleaving-dependent violation of a program-level invariant even though the underlying memory accesses are individually synchronized. Such a failure can arise when one operation observes protected state, releases the lock, and later continues based on that observation after another thread has legally changed the state.

2.2 Rust Support in the Linux Kernel 

The Linux kernel integrates Rust as an additional implementation language alongside its pre-dominantly C code base. A 2024 empirical study of RFL evaluated its early safety, performance, and development costs during an early stage of Rust driver development [13]. Since then, Rust driver code in Linux kernel has grown into a meaningful subject for study. In a Linux 6.8 snapshot preceding that study, ’drivers/’ contained just one Rust source file with 95 source lines of code (SLOC). As of September 2026, the Linux snapshot analyzed in this work contains 50,703 SLOC of non-vendored Rust code, including the 19,726 SLOC under ’drivers/’, including implementations in the Android and GPU subsystems. Rust is increasingly moving beyond experimental kernel modules and being adopted in production-quality drivers. In several subsystems, new Rust implementations are beginning to complement or replace existing C drivers, demonstrating a gradual transition of security-critical kernel functionality from C to memory-safe Rust [16]. As shown in Figure 3, in-kernel Rust code consists primarily of two parts: the Rust support infrastructure under rust/ and selected Rust drivers under drivers/ . 2.3 ThreadSanitizer Runtime Patch 

ThreadSanitizer. ThreadSanitizer (TSan) is a dynamic data-race detector based on happens-before analysis. During compilation, the compiler inserts callbacks around memory accesses and synchronization operations. At runtime, TSan maintains metadata for each monitored memory location, a logical clock for each thread, and synchronization clocks for objects such as mutexes. The clock transfers create a release-acquire happens-before edge [6, 11]. TSan reports two accesses 

𝑒 1 and 𝑒 2 when they originate from different threads, access the same memory location, with at least one write, and are not ordered by happens-before. 

Binary-wide applicability. Implementing the analysis in the TSan runtime avoids source-level rewriting of individual drivers and synchronization primitives. Any executable or library compiled with TSan instrumentation and linked against the patched runtime automatically receives transfor-mation before analysis. The analysis therefore operates across the complete instrumented binary rather than only the source files explicitly examined by a source-level transformation. This binary-level deployment is substantially easier to apply across a heterogeneous driver corpus: the runtime is patched once, while each target only needs to be rebuilt with standard TSan instrumentation and linked against that runtime.

Rust prevents conventional data races in safe code by disallowing unsynchronized concurrent access to mutable memory. This guarantee applies to individual accesses rather than to program-level operations spanning multiple critical sections. A thread may observe protected state, release the corresponding lock, and later continue based on that observation. During the interval, another thread may legally acquire the lock and invalidate the first thread’s decision.

4 XRust Design 

Figure 4 presents the overall workflow of XRust. XRust first identifies operations on shared driver state and automatically constructs concurrent harnesses together with serial-differential oracles. The oracle establishes the expected behavior of an operation pair by executing the two operations in both serial orders from equivalent initial states. XRust then performs Logical Happens-Before (LHB) analysis to identify interleavings that may violate these serial behaviors. It selectively relaxes lock-induced happens-before relationships during analysis to expose cross-thread accesses that are individually synchronized but may participate in a logical race. For each exposed access pair, XRust records the locks held at the access sites and uses their common lock to associate the accesses with the shared protected state and corresponding critical sections. Finally, XRust translates these candidate accesses into targeted scheduling points. A controlled scheduler prioritizes interleavings around these points while preserving the synchronization se-mantics of the original execution. Each concurrent outcome is checked against the serial-differential oracle; an outcome inconsistent with both serial orders is reported as a potential logical race and can be deterministically replayed.

4.2 LHB-Based Candidate Detection 

XRust uses logical happens-before (LHB) analysis to identify synchronized memory-access pairs that may participate in a logical race. Its candidate detector selectively relaxes happens-before edges in ThreadSanitizer’s vector-clock analysis, and preserves thread-local program order. By recording the locks held at each access, XRust exposes conflicting pairs that conventional ThreadSanitizer would suppress and retains their synchronization context for subsequent testing.

4.3 Candidate-Guided Schedule Exploration 

Candidate detection identifies synchronized memory accesses that may participate in a logical race, but it does not establish that a violating interleaving is feasible. XRust therefore uses the candidate access sites to guide controlled concurrency testing with Shuttle [1]. Shuttle executes the same XRust: Detecting Logical Races in Rust Linux Drivers 11 

harness repeatedly under a user-space scheduler by replacing standard threading, synchronization, and atomic primitives with instrumented equivalents. This exposes scheduling decisions to the runtime and allows failing executions to be replayed deterministically [8, 19, 27]. Shuttle supports probabilistic concurrency testing (PCT), which explores executions by assigning priorities to runnable threads and changing those priorities at a bounded number of scheduling points [3]. In unguided PCT, these priority changes may be selected from all eligible scheduling operations. A realistic driver harness can contain many such operations, most unrelated to the shared state interaction identified by XRust. Consequently, the probability of choosing the few decisions needed to expose a candidate interaction decreases as unrelated scheduling points accumulate. 

Scheduling probes. XRust inserts scheduling probes at all eligible scheduling sites throughout the harness and the driver source code. These sites are where PCT scheduler chooses to select other runnable threads. For each conflicting access, XRust walks up the recorded call stack to identify the corresponding call sites in the driver and harness code, then matches their source locations to the inserted probes. 

Targeted Preemption. XRust changes where PCT concentrates its scheduling decisions. For each candidate pair, XRust records the source locations of the two conflicting accesses. The instrumented harness contains dormant scheduling probes at eligible driver locations; only probes matching the candidate sites are activated for the corresponding test. Reaching an inactive probe has no scheduling effect, whereas an active probe allows Shuttle to suspend the current thread and schedule another runnable thread. For example, suppose Thread A reads protected state and later acts on that observation, while Thread B contains the conflicting update. After Thread A performs the candidate read, an active probe gives the scheduler an opportunity to run Thread B before Thread A continues. That is, The competing operation can enter its critical section after the reader releases the protecting lock. The resulting execution preserves the driver’s synchronization semantics but increases the chance of exposing an interleaving in which Thread A acts on stale state. XRust therefore narrows the scheduling locations at which PCT concentrates its priority changes.

5.2 Confirmed Logical Races 

The candidate analysis and controlled executions produced two logical races that we manually confirmed against the corresponding driver state transitions. Both are data-race-free: every individ-ual access to the affected state is protected by the intended synchronization primitive. The rnull 

finding has been confirmed by Linux maintainers. The corresponding patch was included in the Rust block-layer series submitted for Linux v7.4. 

5.2.1 R1: rnull Geometry Update During Power-On. The rnull driver stores configuration state in 

DeviceConfig.data , a Mutex<DeviceConfigInner> . A live disk copies the configured block size when the disk is created. The intended behavior is that geometry cannot change while the disk is powered. However, the block-size setter can perform its powered-state check and its update in two different critical sections. The following simplified excerpt preserves the relevant locking structure:     

> fn store_blocksize(& self , page: &[u8]) -> Result {
> if self .data.lock().powered {
> return Err(EBUSY); }
> let value = parse_u32(page)?;
> self .data.lock().block_size = value; XRust: Detecting Logical Races in Rust Linux Drivers 13
> Ok(()) }

In contrast, the power operation holds the same mutex while creating the disk and setting 

powered . The harness first configures an unpowered device with block_size=512 , and then exe-cutes power.store("1") concurrently with blocksize.store("4096") . The following execution is feasible: (1) blocksize.store acquires the mutex, observes powered=false , and releases the mutex; (2) power.store creates the live disk using the current block size 512 and sets powered=true ;(3) blocksize.store reacquires the mutex and changes the configuration to 4096. The final state contains a powered disk whose live block size is 512 while the stored con-figuration says 4096. All individual accesses are mutex protected, but the check and update in 

blocksize.store are not atomic with respect to power-on. In the serial order power; blocksize , the second operation observes a powered disk and returns 

EBUSY , leaving the configuration at 512. In the opposite order, blocksize; power , the disk is created with block size 4096. The concurrent state ⟨disk = 512 , config = 4096 ⟩ matches neither serial execution. 

Fix strategy. The check and update must execute within a single critical section. The setter acquires DeviceConfig.data , checks powered , and retains the same mutex guard until the con-figuration update is complete. This restores atomicity between geometry updates and power-on without introducing an additional lock. The fix was accepted and applied by the Linux block subsystem maintainer. 

5.2.2 B1: Binder Allocation Resurrection After Cancellation. The second race occurs in Binder’s 

Transaction state. Each transaction stores an optional allocation behind a spinlock: 

> allocation: SpinLock<Option<Allocation>>

prepare_file_list temporarily removes the allocation from the protected field while trans-lating file descriptors, and restores it on success. cancel , meanwhile, removes and destroys the allocation:    

> prepare_file_list(): alloc = self .allocation.lock().take() translate_fds(alloc) // lock not held *self .allocation.lock() = Some(alloc) cancel(): alloc = self .allocation.lock().take() drop(alloc)

Each individual access to allocation is synchronized. Nevertheless, removing the object, op-erating on it outside the lock, and later restoring it creates a window in which cancellation can occur. Starting from allocation=Some(a) , XRust exposes the following schedule: (1) prepare_file_list takes a, leaving the protected field as None ;(2) cancel acquires the lock, observes None , and therefore has no allocation to destroy; (3) the translation in prepare_file_list succeeds; (4) prepare_file_list reacquires the lock and stores Some(a) back into the transaction. The transaction therefore contains a live allocation after cancel has completed—an allocation resurrection. 14 Xu et al. 

This outcome cannot occur in either serial order. For prepare; cancel , preparation restores the allocation before cancellation removes it, so the final state is None . For cancel; prepare ,cancellation removes the allocation first and preparation immediately observes None , again leaving the final state as None . The concurrent execution instead terminates with allocation=Some(a) .

Fix strategy. A possible fix is to distinguish cancellation from the temporary absence of an allocation. A cancellation flag can be protected by the same spinlock as the allocation field. The 

cancel operation sets this flag even when the allocation is temporarily held by prepare_file_list .Before restoring the allocation, preparation checks the flag under the same lock and restores it only if cancellation has not occurred; otherwise, it releases the lock and drops the allocation.

5.4 Scaling to Realistic Transaction Workloads 

Our experiment used automatically generated two-function harnesses, which provide a controlled setting for comparing unguided PCT with XRust-guided scheduling. To evaluate whether the advan-tage persists in a more realistic workload, we constructed more complex harnesses from methods implemented by Binder’s Transaction object. These harnesses surround the same candidate pair with actual driver operations that read or modify the shared transaction state. For each harness, two threads operate on the same Transaction instance and execute an identical prefix of real transaction.rs methods. Only their final operations differ: Thread A invokes prepare_file_list , while Thread B invokes cancel . The split final operations preserve an observable difference between the two orderings while allowing the prefix to increase the surrounding workload. We progressively extended the shared prefix by adding methods from the same driver implemen-tation. Early variants contain state setters and observers such as set_outstanding , is_oneway ,and debug_print . These methods add realistic computation but few relevant scheduling de-cisions because the observers do not acquire the target locks. Later variants add submit and 

drop_outstanding_txn , which introduce additional synchronization and shared-state transitions. The largest harness also includes do_work , which may consume the transaction allocation before the final candidate pair executes. Thus, increasing 𝑁 expands not only the scheduling trace but also the state space that must be explored to reach the vulnerable allocation state. 6 Discussion 6.1 Executing Linux Rust Driver Logic in User Space 

Linux drivers cannot execute directly in a user-space concurrency-testing framework because they depend on kernel-only types, allocation routines, synchronization primitives. To make the driver logic executable under XRust and Shuttle, we construct a user-space environment containing compatibility shims and thin peer modules for the kernel dependencies imported by each target driver. We use Claude Code ( claude-opus-5 ) to assist in constructing this compatibility code. The generated code is checked through compilation and manually inspected for compatibility with the tested driver operations. The compatibility layer implements only the neighboring APIs imported by the selected driver files. For example, a shim provides the interface of a kernel mutex or reference-counted object. Similarly, thin peer modules retain only the definitions required to compile and execute the target code. This approach keeps the executable environment small while allowing the analyzed driver methods to remain source-identical to their in-kernel implementations. 16 Xu et al. 

Consequently, our results establish that a logical race exists in the preserved driver logic under the modeled environment. They do not prove that every generated execution is reachable through the complete kernel interface. We reduce this risk by keeping the shims thin, and preserving synchronization and shared-state operations. 

6.2 Cost Trade-offs and Scalability 

XRust-guided scheduling reduces the number of schedules required to expose a logical race, but it introduces a fixed preprocessing cost. Its end-to-end running time can be expressed as 

𝑇 XRust = 𝑇 detection + 𝑇 instrumentation + 𝑇 compilation 

+ 𝑇 guided testing . (10) By comparison, unguided PCT requires no XRust analysis and has an approximate cost of 

𝑇 PCT = 𝑁 iterations · 𝑇 iteration , (11) where 𝑁 iterations is the number of schedules executed before a failure is observed or the testing budget is exhausted. On a small harness, one Shuttle iteration is inexpensive. In our experiments, even 150 unguided PCT iterations require approximately 0.2 seconds, while XRust must additionally perform candidate detection, source instrumentation, and compilation. Pure Shuttle can therefore have lower wall-clock latency despite requiring substantially more iterations. The relevant crossover occurs when the accumulated cost of unguided schedule exploration exceeds XRust’s fixed preprocessing cost: 

𝑁 PCT 𝑇 iteration > 𝑇 detection + 𝑇 instrumentation + 𝑇 compilation + 𝑁 guided 𝑇 iteration . (12) Our experiments show that the iteration count of unguided PCT increases as real synchronization and state-changing operations are added to the harness, whereas guided testing continues to find the race with fewer iterations. We expect the crossover to become more favorable to XRust for large drivers containing hundreds or thousands of scheduling points, or when the same instrumented binary is reused to test multiple candidate pairs. Thus, the current evidence primarily demonstrates a reduction in schedule-search cost; establishing an end-to-end wall-clock advantage at kernel scale requires larger and longer-running workloads. 

6.3 XRust for Migrating C Drivers 

Most Linux drivers are still written in C, so we conducted a preliminary study to examine whether XRust could also be useful for future C-to-Rust driver migration. We examined all 707 C files in 

drivers/iio , where direct device accesses must be rejected while buffered streaming is active. We identified 12 sites that use iio_buffer_enabled() as an unlocked rejection guard rather than the atomic iio_device_claim_direct() interface. Since mainline Linux currently provides no Rust IIO abstraction, we recreated the relevant synchronization structure in our userspace environment and ported representative drivers from this pattern. The same check-then-act race remained after migration: XRust localized the conflicting accesses when the unlocked guard was preserved and stopped reporting the pair when the guard was replaced by the atomic interface. This preliminary result suggests that logical concurrency defects can survive migration to memory-safe Rust.

In this section, we walk through design choices encountered in an automatic workflow for discovering logical races in Linux Rust driver workspaces. We discuss systems described in prior work, how their designs lead to trade-offs across various quality attributes that XRust considers, and what XRust adopts or improves upon. 

Concurrent Test Generation. Ballerina [20] generates concurrent unit tests consisting of a se-quential prefix that constructs and initializes shared objects, followed by two threads that each invoke one method. This structure limits the cost of schedule exploration while allowing the prefix to establish states needed to expose concurrency bugs. ConTeGe [24] generates sequential initialization and concurrent method-call sequences on a shared object. It reports exceptions or deadlocks observed concurrently when the same failure cannot occur in any serial ordering. These approaches establish automatic concurrent test generation in small concurrent test scenarios. XRust adopts the shared-object, small-harness testing strategy of these approaches. Its contri-bution is to organize operations around shared lock-protected state and generate both self-pair and distinct-function-pair harnesses. These harnesses are then connected to LHB-based candidate analysis and serial-outcome checking in a lightweight userspace environment. 

Atomicity Checking Oracles. AVIO [18] infers access-interleaving invariants from correct execu-tions and reports subsequent violations of those inferred expectations. Velodrome [7] checks conflict serializability of designated atomic blocks by constructing a transactional dependency graph and detecting cycles. XRust, however, separates candidate identification from outcome validation. LHB analysis identifies accesses that may participate in a logical race, but an access conflict alone is not reported as a confirmed violation. Sequential-reference checking approaches like Line-Up [2] automatically check deterministic lin-earizability by enumerating sequential behaviors of the implementation and comparing concurrent behaviors against them, avoiding a manually written sequential specification. Violat [5] generates self-contained tests of observational refinement and precomputes combinations of return values admitted by the reference abstract data type. Likewise, for each instantiated function pair, XRust compares the concurrent snapshot, including selected protected state, with the snapshots from both serial orderings. XRust shares the sequential-reference principle of these approaches. For each instantiated driver-operation pair, it executes both serial orders from equivalent initial states and compares their snapshots with the concurrent outcome. The snapshots include selected lock-protected state as well as operation results. This provides an executable check for the tested pair and initial state. 18 Xu et al. 

Schedule exploration and targeted triggering. CTrigger [21] identifies potential unserializable interleavings involving two accesses from one thread and an interfering access from another. Although CTrigger ignores locks, its exploration targets access triples, whereas XRust utilizes lock-protected accesses to connect LHB candidates. Lock acquisition and release boundaries are used to provide scheduling locations. Other systems provide execution-control and exploration mechanisms that offer thorough explo-ration or are applicable to a specific setting or environment. Shuttle [1] and Loom [32] support controlled exploration of Rust programs through instrumented concurrency primitives. RustMC [22] extends the GenMC stateless model checker to Rust at the LLVM IR level. Fray [12] uses shadow lock-ing to control JVM thread interleavings without replacing the underlying concurrency primitives. SECT [33] provides fine-grained concurrency testing within the Linux kernel through eBPF-based scheduling control. SECT explores concurrency within the Linux kernel, whereas XRust executes selected Rust driver operations in a lightweight userspace environment. This enables controlled test-ing of preserved driver logic, but the resulting executions remain subject to the compatibility-layer assumptions discussed in Section 6.1. These systems provide mechanisms for controlling or exploring concurrent executions. XRust builds on Shuttle as its execution backend and adds LHB-guided scheduling. Our evaluation therefore compares XRust-guided scheduling with unguided PCT within the same Shuttle environment. 

8 Conclusion 

Rust eliminates broad classes of memory-safety violations and data races, but it does not guar-antee that individually synchronized operations preserve higher-level program invariants. As Rust increasingly replaces C in complex Linux drivers, detecting these logical races has become a practical systems problem. Conventional happens-before race detectors suppress the relevant accesses because they are protected by locks, while unguided concurrency testing must search a large space of scheduling decisions. This paper presented XRust, a directed concurrency-analysis pipeline for finding logical races in Linux Rust drivers. XRust extends ThreadSanitizer with a relaxed happens-before analysis that exposes conflicting accesses hidden by mutex synchronization while preserving program order. It records the locks held at each access, identifies candidate pairs protected by a common lock, and translates their source locations into targeted preemption points for Shuttle-based probabilistic concurrency testing. We further automate harness and oracle generation by grouping functions around shared lock-protected objects and comparing concurrent outcomes against serial execution orders. We evaluated XRust on the Rust driver code in Linux v7.3-rc2 and confirmed logical races in two substantially different drivers: a check-then-act violation in rnull , and an allocation-resurrection error in Android Binder. Experiments with increasingly complex Binder workloads show that unguided PCT becomes less likely to select the critical interleaving as real synchronization and state-changing operations are added. These results demonstrate that memory safety and data-race freedom do not eliminate concur-rency failures from safe Rust systems code. XRust recovers interactions hidden by synchronization and uses them to direct schedule exploration, providing a practical path from low-level execution evidence to reproducible, invariant-violating behaviors.
