## 摘要
当前使用经典公钥算法加密的数据，在大型量子计算机问世后可能被解密。云对象存储通常长期保存数据，因此用于保护这些数据的客户端加密方案必须迁移至ML-KEM等后量子算法；此类算法在每个存储对象上引入额外的密钥封装步骤，并产生更大的密文。迄今为止，ML-KEM的开销仅在算法自身层面及用于保障网络连接安全的场景下得到评估，尚未针对服务于大量并发客户端的对象存储系统中逐对象加密这一场景开展测量。因此，ML-KEM是否会拖慢此类系统、在何种条件下发生、以及根本原因为何，均尚不明确。我们通过在S3兼容型对象存储上，采用两种客户端实现、两种处理器类型及最高达500个并发工作线程，对每对象级ML-KEM与经典密钥交换进行实测，并结合预注册实验与统计等价性检验，来解决该问题。结果表明，仅当客户端处理器处于或接近满载状态时，ML-KEM才会导致吞吐量下降（存在一个尚未解释的例外情况），且在我们的主客户端中降幅为4.0%至4.9%。针对其中一种处理器类型的受控实验表明，大部分性能损失源于软件库的调用方式；而另一款原生客户端则进一步表明，性能损失幅度依赖于具体实现。其持久性开销在于存储：相比经典密钥交换，每个对象需额外占用1056字节。本研究结果覆盖两种客户端、一个单节点存储系统及一家云服务提供商。

## Abstract
Data encrypted today with classical public-key algorithms could be decrypted once large quantum computers exist. Cloud object stores keep data for years, so the client-side encryption that protects it must move to post-quantum algorithms such as ML-KEM, which adds a key-encapsulation step and a larger ciphertext to every stored object. So far, the cost of ML-KEM has been measured for the algorithm on its own and for securing network connections, but not for encrypting each object in a storage system that serves many clients at once. It has therefore been unclear whether ML-KEM slows such a system, under which conditions, and why. We address this problem by measuring per-object ML-KEM against classical key exchange on an S3-compatible object store, with two client implementations, two processor types and up to 500 concurrent workers, using pre-registered experiments and statistical equivalence tests. ML-KEM reduced throughput only when the client's processor was at or near full load, with one unexplained exception, and then by 4.0 to 4.9% in our main client. Controlled experiments on one processor type traced most of that loss to the way the software library was called, and a second, native client showed that the size of the loss depends on the implementation. The lasting cost is storage: 1,056 more bytes per object than with classical key exchange. The results cover two clients, one single-node store and one cloud provider.

## 1. 核心问题与整体含义（研究动机和背景）

- **量子威胁的现实紧迫性**：当前云对象存储中长期保存的加密数据（如使用RSA或ECC）面临“先窃取、后解密”（harvest-now-decrypt-later）风险——攻击者可预先截获密文，待大型量子计算机问世后利用Shor算法破解私钥。NIST于2024年8月正式标准化ML-KEM（FIPS 203），作为模块格基密钥封装机制（KEM）的首选后量子方案。
- **现有研究的空白**：已有工作集中于三类场景：（1）ML-KEM原语级性能（如密钥生成/封装/解封装耗时）；（2）后量子TLS连接建立开销；（3）无密码学的S3接口或经典客户端加密性能。**但均未评估ML-KEM在真实对象存储数据路径中的系统级影响**——即每个PUT/GET操作都需执行一次KEM（而非每连接一次），且该操作与网络、元数据处理、服务端I/O共同构成端到端瓶颈。
- **核心科学问题**：在高并发客户端负载下，ML-KEM是否成为性能瓶颈？若会，其触发条件（如CPU饱和阈值）、量化影响（吞吐量下降幅度）、根本原因（是算法计算开销、密文传输开销，还是软件实现缺陷？）分别是什么？

## 2. 方法论：核心思想与关键技术细节

- **核心思想**：采用**端到端系统级基准测试**（而非算法微基准），将ML-KEM嵌入真实的S3兼容客户端加密流水线（envelope encryption），在可控并发负载下测量其对吞吐量、延迟、CPU等关键指标的影响，并通过**受控消融实验**（controlled experiments）分离不同因素的贡献。
- **关键技术细节**：
  - **加密架构**：采用客户端信封加密（client-side envelope encryption）：每个对象用独立数据密钥（AES-256-GCM）加密；该数据密钥再由公钥KEM保护（如ML-KEM-768），并连同上下文（ctx）一起存入JSON格式manifest。
  - **性能归因模型**：提出并验证**CPU会计恒等式**（CPU accounting identity）：当客户端CPU饱和时，吞吐量比 $X_a/X_b$ 等于客户端CPU耗时比的倒数 $c_b/c_a$。这将性能迁移问题转化为一个可测量的CPU耗时问题与一个可验证的饱和度检查。
  - **统计严谨性**：采用**预注册实验设计**（pre-registered experiments）与**双单侧检验**（Two One-Sided Tests, TOST）进行等效性检验，设定±5%为最小感兴趣效应（smallest effect of interest），避免p-hacking。
  - **算法流程**（以PUT为例）：
    1. 生成UUIDv7版本号 `v`，构造上下文 `ctx`（含租户、桶、键、版本、算法名、明文大小、密钥ID、密文哈希等）；
    2. 执行 `ML-KEM.Encaps(ek)` 得到密文 `C` 和共享密钥 `S`；
    3. 用HKDF-SHA256派生数据密钥 `K = HKDF(S, salt, "pqc-s3-object-v2"∥0∥ctx)`；
    4. 将对象分块（4 MiB/chunk），每块用随机前缀 `p` + 序列号构造nonce，AES-GCM加密；
    5. 分片上传密文流（data.enc），最后原子写入manifest.json（含`ctx`, `C`, `salt`, `p`）。

## 6. 主要结论与发现

- **核心结论**：ML-KEM在绝大多数现实并发场景下**性能开销可忽略**，其可观测的性能影响仅出现在**客户端CPU近饱和的狭窄区间内**。
- **关键发现**：
  - **吞吐量影响**：在主Python客户端上，仅当64 KiB GET并发达500 workers（CPU使用率≈93%）时，ML-KEM吞吐量比X25519低**4.0%（x86）或4.9%（ARM）**；其他所有场景（包括大对象、低并发、服务器/网络瓶颈场景）均等效（equivalent）。
  - **根本原因归因**：该4%损失**并非源于ML-KEM算法本身**，而是：
    - **17%** 来自更大的manifest（1056字节密文导致JSON/base64解析开销）；
    - **83%** 来自`liboqs-python`绑定缺陷——每次解封装需4次跨语言调用（allocate/decaps/cleanse/free），释放GIL锁造成严重线程竞争。
    - **验证**：改用单次调用绑定后，ML-KEM与X25519吞吐量差异降至**<0.2%**（等效）。
  - **实现依赖性**：原生Go客户端在相同饱和条件下（1核@128 workers）损失达**9.5%**，证明性能影响高度依赖具体实现（如Go标准库中ML-KEM解封装比X25519慢）。
  - **持久性开销**：**存储成本是唯一不可规避的开销**——每个对象manifest需额外**1056字节**（ML-KEM密文）；在JSON/base64编码下为1412字节，已触及Amazon S3 2KB用户元数据上限。
  - **混合方案与会话**：X-Wing混合方案带来额外开销（最高~10%），而会话模式（N1）可节省2–4%客户端CPU，但仅在客户端瓶颈时转化为吞吐量提升。

## 7. 优点（亮点）

- **开创性基准**：首次在真实的、高并发的S3对象存储数据路径上，系统性地量化了后量子加密（ML-KEM）的端到端性能代价，填补了理论与工程实践间的关键鸿沟。
- **方法论严谨**：将预注册、等效性检验（TOST）、CPU会计恒等式、受控消融实验有机结合，实现了从现象观察（“变慢了”）到因果归因（“为什么慢、慢多少”）的完整闭环。
- **工程洞察深刻**：揭示了“算法性能”与“软件集成性能”的巨大差异，指出**库绑定方式（binding artifact）可能比算法本身更致命**，为PQ密码学的工程落地提供了极具价值的实践指南。
- **结果普适性强**：结论不仅适用于ML-KEM，其分析框架（CPU饱和度判断 + 恒等式归因）可直接迁移到其他后量子算法（如ML-DSA）或任何客户端加密方案的性能评估中。

## 8. 不足与局限

- **实验覆盖有限**：
  - **存储系统单一**：仅测试单节点MinIO，未覆盖分布式MinIO、Ceph、AWS S3、Azure Blob等主流生产环境，其写路径、元数据服务、复制/纠删码机制可能完全不同。
  - **客户端实现窄**：主结论基于一个特定Python栈（liboqs-python），原生客户端仅覆盖GET且限于1种对象大小和3种模式。
  - **算法基线窄**：未测试ML-KEM-1024、RSA-3072或远程密钥服务（如AWS KMS）封装等常见生产部署选项。
- **偏差与风险**：
  - **架构外推风险**：ARM结果虽复现了趋势，但控制实验（如Binding）仅在x86上运行，其归因结论在ARM上的适用性未经验证。
  - **“饱和”定义模糊**：对Python客户端的“近饱和”判定（如128 workers vs 500 workers）是后验的、非预注册的，存在主观性。
- **应用限制**：
  - **结论不适用于广域网**：所有实验在亚毫秒延迟的局域网内进行，广域网场景下网络延迟将成为绝对主导，掩盖所有客户端加密开销。
  - **未解决多接收方/密钥承诺**：论文明确声明不支持多接收方场景（因AES-GCM非密钥承诺），也未解决发送方认证、防重放等更高阶安全需求。
  - **长期效应缺失**：20秒的测量窗口无法捕捉内存泄漏、GC压力、后台compaction等长期运行效应。
