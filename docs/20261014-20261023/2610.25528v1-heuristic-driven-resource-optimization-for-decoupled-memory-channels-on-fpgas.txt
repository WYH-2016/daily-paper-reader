# Heuristic-Driven Resource Optimization for Decoupled Memory Channels on FPGAs 

Arnab A Purkayastha ∗, Shobhit Aggarwal †, Jay Tharwani ‡∗Western New England University, Member IEEE, Springfield, MA, USA Email: arnab.purkayastha@wne.edu

Abstract —Determining OpenCL channel depths for De-coupled Access-Execute (DAE) architectures in High-Level Synthesis (HLS) is critical for balancing performance and hardware efficiency. Conventional static analysis tools often over-provision these memory channels to ensure performance safety, leading to significant resource stranding. This paper presents an expansion of an LLVM-based static analysis framework-originally proposed for automated DAE generation, by introducing a hardware-aware refinement layer. We identify a counter-intuitive Performance Inversion Paradox linked to baseline memory stalls, where high-stall, grid-based kernels reach peak performance at minimal channel depths and suffer up to a 61% throughput degradation when depths are increased. We propose a Heuristic Refinement Layer that optimizes OpenCL channel depths based on this correlation between baseline stalls and performance saturation. Experimental results demonstrate that our expanded framework successfully identifies the 

Minimal Peak Performance point across various benchmarks. By avoiding the performance traps of standard over-provisioning, we achieve a 2.52 × improvement in Resource Efficiency ( η) for an illustrative HotSpot application. This approach maintains peak execution speedup while ensur-ing the leanest possible hardware profile, outperforming conservative tool-based static predictions. 

Keywords —Hardware Accelerators, Reconfigurable Com-puting, FPGA, OpenCL, LLVM, Automation tool. 

I. I NTRODUCTION 

The rapid evolution of High-Level Synthesis (HLS) has transformed the landscape of FPGA-based hardware design, enabling developers to abstract complex spatial architectures using high-level languages like C, C++, and OpenCL. By automating the transition from software algorithms to hardware description, HLS has significantly lowered the barrier to entry for accelerating data-intensive workloads in domains such as genomics, finance, and artificial intelligence. However, despite the massive par-allel processing capability provided by modern FPGA fabrics, achieving peak theoretical performance remains an elusive goal due to the memory wall. As highlighted in architectural studies, the memory wall represents a fun-damental performance gap where the data-consumption rate of the internal logic far outpaces the rate at which the memory subsystem can supply that data [1]. In the context of FPGAs, this gap is uniquely chal-lenging; unlike traditional CPUs that rely on deep, fixed cache hierarchies to mitigate latency, FPGAs require designers to manually or semi-automatically orchestrate data movement. When memory-bound applications are ported to FPGAs, the execution pipelines often spend a majority of their operational cycles in a stalled state, waiting for high-latency DRAM transactions to com-plete. This under-utilization of the FPGA’s computational resources negates the energy-efficiency and throughput benefits that hardware acceleration is intended to provide. Consequently, the primary challenge in modern HLS design is not just the implementation of the computational logic, but the engineering of sophisticated memory-interfacing structures that can effectively bridge this wall. To quantify the impact of the memory wall, we characterized three representative benchmarks on an Intel Arria 10 FPGA. As shown in Table I, the baseline (non-decoupled) versions of these kernels suffer from significant memory-related inactivity. These stall percent-ages represent a massive under-utilization of the FPGA’s computational resources. For instance, in the HotSpot kernel, the execution engine is idle for over three-quarters of its operational cycles, waiting for memory transactions to complete. This empirical evidence highlights that the primary bottleneck is not the compute logic itself, but the lack of an efficient data-supply mechanism. Table I: Baseline Memory Stall Characterization

As described in [1], [2], these channels facilitate high-bandwidth, point-to-point communication between concurrent kernels, allowing data to be streamed directly between logic blocks without the overhead of returning to global memory. This capability is foundational for implementing the DAE framework, a hardware architecture specifically designed to mitigate memory latency. In a DAE system, the computational kernel is par-titioned into two distinct units: the Access unit and the Execute unit. The Access unit is dedicated solely to calculating memory addresses and issuing read/write requests to DRAM, while the Execute unit focuses on the core algorithmic operations. By separating these concerns, the Access unit can run ahead of the computation, pre-fetching data into FIFO-based channels. This creates a producer-consumer relationship where the Execute unit pulls data from a ready buffer rather than waiting on high-latency memory transactions. When properly implemented, this decoupling allows the FPGA to overlap memory communication with computation, effectively 

hiding the latency that would otherwise stall the execution pipeline. While DAE is effective, manual partitioning is complex. Recent work introduced an LLVM-based toolchain to automate this process at the Intermediate Representation (IR) level [1]. By analyzing data-flow graphs, this tool automatically identifies predictable access patterns. However, a significant limitation remains: the tool does not give the optimal channel depth. The onus thus lies on the designer/ programmer who generally default to a one-size-fits-all channel depth (typically 64) for any complex indexing. This over-provisioning leads to Resource Stranding, where physical Block RAM (BRAM) is occupied but provides no additional performance gain, as many kernels reach performance saturation at much lower depths. This paper extends the foundational LLVM-based DAE work by introducing a Stride Classification logic and a Heuristic-Driven Optimization Layer. We propose that by analyzing the baseline stall characteristics identified in Table I, we can right-size channel depths to achieve a pareto-optimal trade-off. The proposed framework operates as a multi-stage optimization pipeline that transforms high-level OpenCL kernels into resource-optimized DAE architectures. The core of this system is the integration of a front-end LLVM static analysis engine with a back-end heuristic refinement layer. The primary goal is to bridge the gap between 

performance-safe static predictions and resource-efficient 

hardware implementations. 

A. LLVM Static Analysis Engine 

The first stage of our methodology involves an en-hanced LLVM-based parser which operates directly on the LLVM Intermediate Representation (IR) [3], [4]. Parsing at the IR level is critical because it allows the tool to observe the finalized data-flow and memory-addressing logic after initial compiler optimizations. 

1) Mechanism of the LLVM Parser: The parser func-tions by traversing the LLVM Module’s Call Graph and Control Flow Graph (CFG). The analysis follows a three-step instruction-walking process:  

> •

Iterative Context Identification: The tool first identi-fies the innermost loops within a kernel. It searches for the Induction Variable (IV), which serves as the primary iterator for memory indexing. By identifying the initial value and the increment step of this iterator, the tool establishes a baseline for calculating address offsets.  

> •

Instruction Walking (Use-Def Chains): Upon loc-ating a memory access instruction (e.g., a load or store), the parser walks backward through the Use-Def Chain. This recursive process analyzes the operands to determine how the effective memory address was calculated. It specifically looks for arithmetic operations—such as multiplications and additions—that link the memory address to the previously identified induction variable.  

> •

Address Offset Analysis: The address offset analysis focuses on the address calculation instructions. The parser extracts the Base Pointer (the start of the array or buffer) and the Computed Offset. If the offset is found to be a linear function of the induction variable, the tool identifies it as a Predictable Stride .

III. E XPERIMENTAL SETUP 

This section details the hardware and software envir-onments used to validate the proposed heuristic-driven optimization framework. The methodology relies on real-time hardware profiling to bridge the gap between static LLVM IR analysis and physical resource utilization. 

A. Hardware and Software Environment 

All experiments were conducted on an Intel Arria 10 GX FPGA. The development environment utilized the Intel FPGA SDK for OpenCL and the Quartus Prime Pro Edition toolchain [5], [6]. 

B. Profiling and Characterization 

To obtain the stall data ( Tstall ) required for Step 3 of the toolchain, we utilized the Intel FPGA Dynamic Profiler. Kernels were initially compiled without OpenCL Pipes to identify the raw memory bottleneck. We spe-cifically monitored Load/Store Stalls, which represent the percentage of cycles the execution pipeline is inactive due to memory back pressure. Post-synthesis reports were used to extract Memory Blocks (Block RAM, BRAM), Logic Utilization (Adaptive Logic Module, ALM), and Registers (Flip-Flop, FF) usage for each depth configuration. 

C. Benchmarks 

We selected three representative applications from the Rodinia Benchmark Suite [7], [8]. These benchmarks were chosen specifically because they represent distinct memory access behaviors that test the limits of automated HLS depth allocation:  

> •

HotSpot (Physics Simulation): Chosen for its regular, grid-based access pattern that paradoxically suffers from high baseline stalls (76.8%). It serves as the primary test case for Saturated Kernel optimization.  

> •

BFS (Graph Analytics): Selected to represent ir-regular, non-deterministic access patterns that are heavily bandwidth-limited (40.7% stalls). This tests the tool’s ability to categorize VARIABLE strides that hit performance saturation early.  

> •

RangeK (Database Search): Included as a control for Latency-Sensitive applications. With very low baseline stalls (3.01%), it requires deep buffering (D = 64 ) to handle bursty transactions without losing performance. IV. R ESULTS AND DISCUSSION 

A. Performance Analysis and Stall Correlation 

The efficacy of our heuristic is rooted in the rela-tionship between baseline memory stall rates ( Tstall )and the resulting speedup across varying OpenCL chan-nel depths. Initial characterization results revealed a significant disparity in memory behavior among the Rodinia benchmarks. For instance, HotSpot and BFS exhibited high baseline stall rates of 76.8% and 40.7%, respectively, classifying them as bandwidth-saturated. In contrast, RangeK maintained a much lower stall rate (approximately 3.01%), indicating a latency-sensitive profile. Figures 2 and 3 show the Speedup and Stall reduction vs various channel depths (4-256) for the three representative applications. A critical observation from the results is the Per-formance Inversion Paradox , where increasing hardware resources leads to a drastic reduction in computational throughput.To quantify this loss, we define Performance Degradation ( P∆) as the percentage of peak speedup lost when transitioning to a standard safe-max default (D = 64 ):

Applying Equation 2 to the HotSpot benchmark, we observe a peak speedup of 4.62 × at a minimal channel depth of D=4 . However, at D = 64 , the speedup drops to 1.83 ×, resulting in a 60.3% performance degradation. Similarly, BFS experiences a degradation of 16.9% when moving from its optimal depth ( D = 16 ) to the standard default. These diminishing returns occur because, in bandwidth-saturated kernels, the execution unit is capped by the DRAM’s peak delivery rate. Any additional buffering via deeper OpenCL channels only adds management over-head and interconnect pressure without providing further latency-hiding benefits. Conversely, RangeK validates the necessity of the heuristic’s second stage; with low baseline stalls, it is highly sensitive to channel depth and achieves its Speak of 1.38 × only at D = 64 .The non-linear and often contradictory performance trends observed across these benchmarks underscore why choosing a channel depth arbitrarily or manually is Figure 2: Speedup vs. Channel depth for all three applications

B. Resource Overhead Analysis 

The transition from a standard kernel to a DAE framework requires the instantiation of OpenCL channel, introducing a fixed hardware overhead primarily in memory and logic utilization. This base cost is visualized in Figure 4, which compares the baseline resource foot-print against the optimized decoupled implementations. As illustrated in the profiling data, adding the DAE hardware results in a measurable resource requirement. For HotSpot, memory block utilization increases from 0.16% to 0.26%, while logic utilization rises from 0.23% to 0.29%. Similarly, BFS shows a jump in logic utilization from 0.22% to 0.25%. However, the data reveals a distinct flatline behavior where the resource footprint remains virtually unchanged as the channel depth scales from 

D=4 to D=64 .The lack of dynamic resource scaling reported by the profiler is likely due to the underlying hardware mapping on the FPGA fabric. FPGAs utilize discrete, fixed-size memory structures, such as Intel’s M20K blocks. When an OpenCL channel is instantiated, the compiler typically allocates a minimum of one such block to handle the interface. For the relatively small data widths and depth ranges (4 to 64) used in these representative benchmarks, the buffer fits entirely within the initial block allocation. This results in no reported increase in total block count despite the change in channel depth. It is important to note that while these specific applications demonstrate a flat resource overhead, the complexity of more advanced kernels (incorporating larger data types or significantly more parallel channels) may eventually force the compiler to utilize additional physical blocks at higher depths. Furthermore, even when block counts remain static, deeper channels can increase routing complexity and pressure on the interconnect fabric. This reinforces the need for our heuristic; by selecting the minimal depth required for peak performance, we avoid unnecessary hardware commitment and minimize the risk of routing-induced frequency degradation.

V. C ONCLUSION 

This paper presented an expansion of our LLVM-based compiler toolchain to automate OpenCL channel depth 

selection. This work addresses a fundamental limitation in automated decoupled architectures: the lack of systematic channel optimization. By correlating static IR analysis with hardware-level memory stall characterization, the framework eliminates suboptimal hardware configurations and resource stranding . Our findings reveal a Performance Inversion Paradox in bandwidth-saturated kernels, where arbitrary over-provisioning leads to significant throughput loss. We identify these regimes using a 40% baseline stall threshold, a heuristic marker that classifies a kernel as bandwidth-saturated. By utilizing this threshold, the framework successfully isolates the optimal channel depth required to maintain peak throughput without incurring performance penalties.The impact of this optimization is quantified through the Resource Efficiency (η) metric, which evaluates the performance return on hardware investment. For the HotSpot benchmark, the toolchain identified that a minimal channel depth of D = 4 provides the optimal balance of throughput and area, yielding a 2.52 × efficiency improvement compared to the standard 

D = 64 default. Ultimately, this expansion transforms 

OpenCL channel depth from a manual, trial-and-error tuning parameter into a deterministic optimization vari-able. By ensuring peak efficiency, this framework enables the development of denser and more balanced FPGA accelerators, providing a scalable pathway for complex hardware designs in resource-constrained environments.
