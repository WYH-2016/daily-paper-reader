## 摘要
对内存服务进行检查点（checkpoint）与恢复（restore）操作通常需将其内存页写入检查点镜像，并在目标节点重新填充这些页。当应用状态已驻留在故障转移后仍可访问的共享内存中时，将这些页复制进出检查点镜像即属冗余。本文提出 CXLResume——一个原型系统，它在检查点过程中保留服务主堆对象于共享内存中，仅序列化其余执行状态及映射元数据。检查点操作确保共享堆与序列化的进程状态在同一冻结时刻保持一致。恢复期间，CXLResume 在恢复执行前，先将同一块共享内存重新映射至其原始虚拟地址，从而维持共享内存与私有内存内部及彼此之间的直接指针有效性。我们基于 QEMU 的 CXL 功能仿真环境，对 Redis 和 Memcached 进行了 CXLResume 评估。在 6 GiB 数据规模下，Redis 的检查点与恢复总耗时由 15.015 秒降至 0.242 秒，Memcached 则由 19.770 秒降至 0.276 秒（在所评估的部署配置下）。结果表明，保留共享的应用状态可将庞大的应用堆内存排除出检查点数据路径，从而显著降低检查点与恢复延迟。

## Abstract
Checkpointing and restoring an in-memory service typically require writing its memory pages to checkpoint images and refilling them at the destination. When application state already resides in shared memory that remains accessible after failover, copying those pages into and out of checkpoint images is unnecessary. We present CXLResume, a prototype that retains the service's main heap objects in shared memory while checkpointing the remaining execution state and mapping metadata. Checkpointing preserves the shared heap at the same freeze point as the serialized process state. During recovery, CXLResume remaps the same shared memory at its original virtual addresses before restoring execution, preserving direct pointers within and across shared and private memory. We evaluate CXLResume with Redis and Memcached using QEMU CXL functional emulation. At 6 GiB, CXLResume reduces combined checkpoint and restore time from 15.015 s to 0.242 s for Redis and from 19.770 s to 0.276 s for Memcached in the evaluated deployments. These results show that retaining shared application state removes large application heaps from the checkpoint data path and substantially reduces checkpoint and restore latency.
