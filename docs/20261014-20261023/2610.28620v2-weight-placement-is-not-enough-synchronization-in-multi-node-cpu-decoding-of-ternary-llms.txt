## ABSTRACT 

Ternary LLMs read only a few gigabytes per decoded token, yet on dual-socket servers with four NUMA nodes the fastest ternary runtime we found uses less than half of the memory bandwidth. Placing each weight on the node of the thread that reads it is necessary but not enough: in a decode engine with node-local weights that reuses ik llama.cpp’s kernels, threads on two generations of Xeon servers still spend 20–48 % of each token waiting at synchronization points. Per-thread barrier traces show that most of the wait is for the slowest threads of each node; the barriers’ own latency (microseconds each, but up to 12 % of the token for the smallest model) and serial per-node work are smaller parts. On identical kernels, a Megatron-style column split beats a row-owned split without cross-node reductions in every configuration we measured, and isolating the number of barriers shows that most of its gain comes from its threads waiting less for each other and for their node leaders, and only a minority from having fewer barriers. Where decoding is DRAM-bound, the resulting engine is 1.5–2.1 × faster than ik llama.cpp with all cores and 1.5–1.9 × faster than ik llama.cpp at its fastest thread count (3.2 × and 2.8 ×

for a small model that runs from the L3 cache), at the same accuracy and with less energy per token. 

## 1 INTRODUCTION 

Ternary language models restrict their weights to 

{− 1, 0, +1 } and store them in about two bits each (Ma et al., 2024). An eight-billion-parameter model then reads about 2 GB per generated token, which brings single-stream decoding within reach of CPU servers, whose memory band-width, spread over several sockets and sub-NUMA nodes, adds up to hundreds of GB/s. On one NUMA node, de-coding is close to bandwidth-bound: each token reads all weights once, and the best runtimes use 72–78 % of the node’s bandwidth. Using the whole machine is harder. Across the four NUMA nodes of a dual-socket Ice Lake server, the fastest ternary runtime we found, ik llama.cpp ( ik ), reads DRAM at only 48 % of the machine’s local read bandwidth (Llama3-8B); on an Emerald Rapids server it becomes 3–12 % slower 

when given 104 instead of 64 cores. The natural diagnosis is weight placement, and placing every weight row on the node of the thread that reads it is indeed necessary; recent systems such as ArcLight (Xu et al., 2026) build on node-local tensor parallelism. ## 2 BACKGROUND AND MOTIVATION 

Ternary LLMs on CPUs Ternary models such as BitNet b1.58 (Ma et al., 2024) restrict every weight of the linear layers to {− 1, 0, +1 } times a per-tensor or per-row scale and quantize activations to int8. CPU runtimes for them include llama.cpp (ggml-org, 2026) (TQ1 0, TQ2 0), bit-net.cpp (Wang et al., 2025), the table-lookup kernels of T-MAC (Wei et al., 2025) and Vec-LUT (Li et al., 2026b), and ik (ikawrakow, 2026), a fork of llama.cpp with its own ternary formats IQ1 BN and IQ2 BN. In our measurements, the 2-bit formats of these runtimes decode at about the same speed on one node, and ik is the fastest once several nodes are used; it is our baseline. Decoding multiplies the activa-tion vector with every weight matrix, so each token reads all weights once: on one Ice Lake node with 16 threads, the DRAM reads per token of Llama3-8B are 1.01–1.04 times the weight bytes in every format we measured, and the 2-bit formats reach 72–78 % of the node’s read bandwidth, so going faster requires more nodes. 

Multi-node servers A dual-socket server with sub-NUMA clustering exposes each socket as two NUMA nodes with their own memory controllers (Table 1). Reading an-other node’s memory costs little within a socket on Ice Lake but 38 % across sockets, and 22–23 % for any remote node on Emerald Rapids; interleaving memory over the four nodes yields only 48–55 % of the bandwidth available when every thread reads its own node. Using the whole machine therefore requires that each thread reads weights placed on its own node. 

Existing runtimes stop at half the bandwidth The llama.cpp family offers two ways to use several nodes: inter-leaving the weights, and --numa distribute , which binds threads to nodes and lets the first touch of the memory-mapped weights place each page near its first reader. On Ice Lake with Llama3-8B, interleaving reaches 2.08 × the single-node speed and distribute 2.44 × (174 GB/s), only 49 % of the machine’s local bandwidth (48 % by DRAM counters in our main batch, §6.2); with all weights on one node, 64 threads are no faster than 16. On Emer-ald Rapids, ik with 104 threads decodes 3–12 % slower than with 64 threads on all three models, and a user of llama.cpp has reported a tenfold drop in decode throughput between 16 and 17 threads on another Emerald Rapids machine (kimd-dong0069, 2026). Two properties of ggml, the tensor library under llama.cpp and ik , suggest why. It executes the model graph one operator at a time, each a parallel region that ends in a global barrier, about 17 times per layer; and operators on a single row (RMS norm, residual add, activation quanti-zation) run on one thread while all others wait, after which threads on all nodes read the result. Section 4 measures what these costs amount to once the weights are placed correctly.

## 4 WHERE DOES THE TIME GO AFTER 

## PLACEMENT ?

4.1 Fixing placement within ik 

We start from the placement ik already achieves and add the changes of ik-P one at a time (Table 2); the increments depend on this order, which adds placement first. After ik ’s first pass over its memory-mapped weights, 97 % of the weight pages already sit on the node of the thread that reads them, so migrating the rest gains only 0–3 % (6–14 % on the small Falcon3-1B). The largest step on both platforms is synchronization: replacing ggml’s global barrier by a two-level one (threads meet within their node, then one thread per node meets globally) gains 10–14 % on Ice Lake and 20– 44 % on Emerald Rapids. Splitting single-query attention over KV chunks helps models whose few KV heads leave most threads idle in ik ’s schedule: the Falcon3 models, and on Emerald Rapids also Llama3-8B ( 8 × 256 < 32 × 104 ,

ik ’s threshold for splitting). Removing one change at a time from ik-P on Emerald Rapids gives the same order: without the two-level barrier it loses 18–35 %, without split attention 9–17 %, without migration 1–9 % and without the AVX-512 quantizer 0–2 %. Beyond this, local changes inside ggml stop paying off: spreading the single-row operators over all threads slowed the Falcon3 models by 5–9 %, and three variants of node-local activation quantization stayed within 

±2 %, because the activation vector still has to be gathered Weight Placement Is Not Enough: Synchronization in Multi-Node CPU Decoding 

from all nodes before the next operator. What remains is ggml’s execution model, one parallel region and one global barrier per operator, about 17 per layer. Replacing it by our engine (§5), with the same kernels and only a few barriers per layer, gives 1.40–2.24 × (Row ) and 1.53–3.23 × (Col )over ik .

4.2 How much of a token is synchronization? 

The engine records, per token, how long each thread waits at global and node barriers and for its node leader, which normalizes and quantizes each stage’s input alone. With node-local weights and 2 instead of about 17 global barriers per layer, threads still wait for 22–35 % of each token on Ice Lake and 20–48 % on Emerald Rapids (Fig. 2). Record-ing each thread’s entry and exit at every barrier for 32 tokens, which changes the speed by about 1 %, splits this wait: a thread waits for the last thread from its own entry until the last entry, and for the barrier itself from then until its exit. Waiting for the last thread is 17–26 % of the token on Ice Lake and 14–31 % on Emerald Rapids (65–86 % of the wait), barrier latency 1–6 and 3–12 %, and waiting for the node leader 2–3 and 3–5 %. More than half of the late arrivals are threads of the waiting thread’s own node, which read equal shares of node-local weights yet finish at dif-ferent times; we have not identified the cause. The share grows with the number of threads per barrier: with IQ2 BN and 13, 20 and 26 cores per node of Emerald Rapids, Col ’s threads wait for 18–31, 23–42 and 29–48 % of the token, mostly through late threads, while other processes kept a median of only 0.4–0.5 CPUs busy at every core count and the share does not correlate with them (Spearman’s ρ of 

−0.05 ). On Ice Lake the share rises similarly (13–20, 18– 27 and 24–34 % with 8, 12 and 16 cores per node), but about two foreign CPUs were busy throughout, and once every core is in use they can only run on the sibling hy-perthreads of our threads or preempt them, so this trend is partly confounded with interference. The share is largest for Falcon3-1B, which reads only 0.5 GB per token; on Emer-ald Rapids, where it runs largely from L3 (§6.2), nearly half of each token is spent waiting, and with 18 thin layers barrier latency alone is 9–12 %. 

4.3 Fewer bytes, more synchronization 

If the waiting cost a roughly fixed time per token while the streaming time grew with the bytes read, fewer bytes per to-ken would mean a larger synchronization share and a larger gain from a better dataflow. We test this by running each model in up to four formats: the ternary IQ2 BN and the non-ternary Q2 K, Q4 0 and Q4 K M, which read 1.3–2.1 ×

as many bytes. On Emerald Rapids the relation holds for both models with four formats: from IQ2 BN to Q4 K M, the share of Col falls from 34 to 22 % for Llama3-8B and from 48 to 39 % for Falcon3-1B, and the speedup over ik 

from 2.05 to 1.53 × and from 3.12 to 2.57 × (Fig. 3). On Ice Lake it is weak: the shares of Falcon3-1B stay within 30–35 %, and Llama3-8B in Q2 K has the highest share and the lowest speedup (1.20 ×), an exception that coin-cides with ik already using more bandwidth with Q2 K than with IQ2 BN there (51 vs. 46 %). Across models the or-dering holds on both machines: the model with the fewest bytes per token has the largest share and the largest speedup in every format. Quantitatively, the absolute wait is not fixed: it grows with the work between barriers (for Col with Llama3-8B on Ice Lake from 1.9 ms per token with IQ2 BN to 3.2–3.4 ms with Q4), because so does the load imbalance a barrier absorbs. 

4.4 Ruling out frequency and placement 

Could the engine simply place data better than ik in ways the ladder misses? Decode-phase core frequencies agree within 8 % (Emerald Rapids: 2.89 GHz for all; Ice Lake: 2.98–3.25 GHz for ik , 2.93–3.02 for Col ), so the speedup is not from frequency. Cross-socket traffic (UPI data flits per token) is 4.1–7.3 × higher for ik than for Col on Emer-ald Rapids and 5.6–7.1 × on Ice Lake although both read the same weight bytes; it comes from each layer’s activa-tion exchange and synchronization. The share of demand loads served by remote DRAM (33–58 % for ik on Ice Lake, 1–2 % for Col ) misleads, as the streamed weights arrive almost entirely through the prefetcher (L3-miss stall cycles are 0.5–10 %).

## DATAFLOW 

To find which property of a dataflow matters, we built a decode engine that keeps ik ’s kernels and GGUF weights and runs two dataflows that differ in how often all threads meet and how much data crosses nodes. 

5.1 The engine 

The engine is one process with one thread pinned to each physical core. At load time each weight matrix is cut into one slice per node and one range of rows per thread, and each slice is copied into memory of its node. ik ’s arithmetic on the same weights. Before each matrix stage, one leader thread per node normalizes and quantizes the stage’s input into a node-local buffer. 5.2 Two dataflows Row-owned ( Row ) Every matrix is split by output rows across all threads of all nodes. Since the next stage’s node leaders need whole vectors, each thread writes its output rows into a copy of the vector on every node, a parallel scat-ter instead of a serial gather. A layer has five stages (QKV, attention, O with residual, gate/up with SiLU, down with residual), each ending in a global barrier, and no reductions (Fig. 4). Avoiding cross-node reductions is meant to keep the traffic between nodes small; the scatter writes instead generate more cross-socket traffic, although §5.4 shows that this traffic is not what slows Row .

Column-split ( Col ) This is the Megatron-LM decompo-sition (Shoeybi et al., 2019), which ArcLight (Xu et al., 2026) applies to the NUMA nodes of a CPU. Node n owns a quarter of the query heads with their KV heads and KV cache, and a quarter of the FFN’s intermediate dimension, and computes them with node-level barriers only. 5.4 Isolating the number of barriers 

The two dataflows differ both in the number of global bar-riers and in where they read and write, so we separate the two in the engine (Table 4). Promoting three of Col ’s node barriers to global ones gives it the five global barriers per layer of Row with its own data placement, and adding empty global barriers right after an existing one, when all threads have just met, measures barrier latency without imbalance; neither changes the computed values. The number of barriers explains only a minority of the gap: five global barriers per layer slow Col by 5–26 % of the 

Row –Col difference, and three complete extra barriers by 16–38 %. An empty global barrier among 104 threads costs 1.4–4.4 μs, so Col ’s two per layer take 1–10 % of its token time, a small part of its 20–48 % wait. On Ice Lake the round-to-round variation of the shared machine (4–11 %) exceeded these effects (Appendix E). 

Row also writes across nodes (each thread writes its output rows into every node’s copy and its K and V rows to the node holding the token’s KV block), with 4.1–5.0 × the cross-socket traffic of Col on Emerald Rapids and 1.8–2.4 ×

on Ice Lake; its leaders quantize more than twice as many elements; and it splits attention by position rather than by head. In the traced batches (not that of Table 4), the gap of 0.43–2.67 ms per token consists of Row ’s longer waits for late threads (up to 1.29 ms) and for the leaders (up to 0.54 ms) and its longer QKV, attention and gate/up stages (up to 0.62, 0.15 and 0.19 ms), less Col ’s reductions (up to 0.23 ms); barrier latency adds at most 0.08 ms, and the residual is below 0.14 ms (Appendix F). The cross-node writes of the stage outputs do not explain the extra waiting: a variant of Row that writes the outputs of O, gate/up and down only to its own node and copies the other nodes’ rows after the barrier (bit-identical results) is 1–7 % slower and waits as long for late threads ( −4 to +3 %). Row ’s extra late arrivals occur mainly at the barriers after QKV and attention, which also differ in the K and V writes and the attention split.

## 6 EVALUATION 

6.1 Decode throughput 

At depth 0, Col decodes 1.53, 1.65 and 2.00 × as fast as ik 

on Ice Lake and 2.03, 2.05 and 3.23 × on Emerald Rapids for Llama3-8B, Falcon3-10B and Falcon3-1B (Table 2), with 95 % bootstrap intervals within 4 % of the medians; on another Ice Lake machine and other days, the ratios of the engine changed by less than 5 %. ik is not always fastest with all cores: on Emerald Rapids it is 6–14 % faster with 64 or 80 of its 104 cores, and on Ice Lake Falcon3-10B is 6 % faster with 32 of 64. Against ik at its fastest thread count, 

Col is 1.53, 1.54 and 1.93 × faster on Ice Lake and 1.89, 1.92 and 2.78 × on Emerald Rapids. Among existing run-times ik is the fastest on both machines: on Emerald Rapids, llama.cpp (TQ2 0, Q4 0) and bitnet.cpp (I2 S) reach 0.59– 0.85 × of its speed, and the two weight-replication pull requests (matteoscalabrini, 2026; SamuelOliveirads, 2026) do not improve on it (Appendix D). 

6.2 Bandwidth utilization 

Decode speed times bytes per token gives a kernel-independent effective bandwidth (Fig. 6). Col reaches 63– 71 % of the machine’s local read bandwidth on Ice Lake and 70–78 % on Emerald Rapids, against 31–46 % and 24– 37 % for ik . Memory-controller counters confirm this on Ice Lake, whose 48 MiB L3 per socket holds little: DRAM reads per token are 92–103 % of the weight and KV bytes, and Col uses 59–71 % of the bandwidth against 32–48 % for ik . On Emerald Rapids, 9–20 % of the bytes of the two larger models come from the 260 MiB L3 per socket, so by measured DRAM reads Col uses 60–61 % and ik 28–31 %. Falcon3-1B (482 MiB of weights) runs on Emerald Rapids almost entirely from L3, with only 0.03–0.06 of its 0.53 GB per token from DRAM; its 3.2 × speedup there measures on-chip synchronization and computation, consistent with its 39–48 % barrier share (Fig. 2). On Ice Lake, this is close to what every implementation reaches on a single node (§6.3), so the remaining limit there is the kernel. 

6.3 Scaling over nodes 

On one node the implementations differ by at most 17 % and all reach 70–84 % of the node’s bandwidth (Fig. 7). From one node to four, ik speeds up only 1.77–2.36 × (Ice Lake) and 1.29–1.82 × (Emerald Rapids), while Col speeds up 3.0–3.3 × and 3.4–3.7 × (on Emerald Rapids partly helped by the larger L3 of more nodes). The engine’s advantage therefore arises across nodes. 

6.4 Context depth and KV-cache placement 

Long contexts exposed a placement issue in the baseline: 

ik allocates the whole KV cache on a single node. Inter-leaving it with numactl --interleave=all , which needs no code change, makes ik faster at depth 8192 by 19, 38 and 60 % on Ice Lake and by 36, −3 and 76 % on Emerald Rapids (Llama3-8B, Falcon3-10B, Falcon3-1B), but slower at depth 128 by 15–20 % on Ice Lake and 11– 13 % on Emerald Rapids for the larger models (Appendix I). On Emerald Rapids, automatic NUMA balancing moves a varying part of the cache during each run (the most loaded node held 27–55 % of it), so the default placement there is also unstable (Appendix G). Against the faster of the two ik 

configurations at each depth (Fig. 8), Col is 1.46, 1.59 and 1.86 × faster on Ice Lake at depth 128 and 1.66, 2.08 and 2.49 × at 8192, and on Emerald Rapids 2.00, 2.02 and 3.23 ×

Implications for CPU runtimes First, on multi-node ma-chines one global barrier per operator, with single-row op-erators on one thread, costs more than misplaced weights; grouping a layer into a few stages is the larger lever, and beyond that, how the work is divided among threads matters more than the barrier count. Second, most of the remaining wait is imbalance among a node’s threads, which fixed row ranges cannot absorb; assigning rows dynamically within a node is the direct remedy to test. Spreading the leader’s se-rial work (3–5 % of the token) over the node’s threads made 

Col 3–22 % slower, because the threads must then exchange statistics and meet once more per stage; letting every thread quantize the whole vector itself would avoid both. Third, the KV cache should be placed like the weights: an interleave makes ik up to 76 % faster at depth 8192 than its single-node default. Fourth, thresholds tuned for one machine break on another: ik ’s rule for splitting single-query attention leaves most threads idle at short context for models with four KV heads and, at 104 threads, also for Llama3-8B. 

Scope Col supports Llama-architecture models whose head, KV-head and FFN counts are divisible by the num-ber of nodes and whose head size is a multiple of 128, and decodes a single sequence without prefill or batching; it targets latency-bound single-user settings (§6.5). Of the public ternary models, Llama3-8B-1.58 is fine-tuned from a full-precision model, and BitNet b1.58 2B4T, trained ternary, uses squared ReLU and extra sub-layer normaliza-tion, which the engine does not implement. Hybrid-attention models, more than four NUMA nodes, AMD systems and Intel systems with SNC disabled are outside our measure-ments, and Emerald Rapids’s large L3 makes its Falcon3-1B results reflect on-chip rather than memory behavior. 

Threats to validity Sharing the machines matters little for the comparisons between implementations, whose variants alternate within every round and are hit alike by other users’ load (§3). Absolute wait shares may be affected: in the trace batches of Fig. 2 the share grows with interference (Spear-man’s ρ of 0.36 on Emerald Rapids and 0.52 on Ice Lake); on Emerald Rapids, medians over rounds with at most one busy foreign CPU differ by at most 3.3 points, but Ice Lake never had fewer than 1.8 busy foreign CPUs, so its shares may be a few points high, and its thread-count trend is partly confounded with interference (§4.2). 

## 8 RELATED WORK 

Numbers quoted here are those reported by the cited works on their platforms. 

Multi-node CPU inference ArcLight (Xu et al., 2026) is the closest prior work: it groups threads by NUMA node, partitions weights in the Megatron-LM style (Shoeybi et al., 2019), synchronizes globally only at the boundaries of its tensor-parallel subgraphs, and reports up to 46 % higher throughput than mainstream frameworks. Col uses the same decomposition; our contribution is the measurement of what limits decoding once it is in place and the comparison with a row-owned dataflow on identical kernels (on our machines 

Col is 1.39–3.23 × faster than ArcLight). SGLang’s CPU backend maps tensor parallelism to NUMA nodes with shared-memory collectives and reports that communication takes 3 % of the end-to-end time overall, in deployments centered on large MoE models such as DeepSeek-R1 (In-tel PyTorch Team, 2025), consistent with synchronization weighing less when more bytes are read. xFasterTrans-former distributes inference over sockets and machines (He et al., 2024), KTransformers splits MoE expert weights across sockets in a CPU/GPU hybrid (Chen et al., 2025), and two pull requests replicate weights on every node (mat-teoscalabrini, 2026; SamuelOliveirads, 2026). Weight Placement Is Not Enough: Synchronization in Multi-Node CPU Decoding 

Synchronization when data movement shrinks On CPUs whose 3D-stacked last-level caches hold the weights, Zhang et al. (2026) find that operator-boundary synchroniza-tion becomes a visible bottleneck and relax it to sub-operator dependencies; on GPUs, Chen (2026) finds that batch-1 de-coding reaches a smaller fraction of peak bandwidth the faster the memory, and attributes the gap to kernel-launch overhead. We show the same shift for DRAM-bound de-coding on standard multi-node servers, quantify it against the bytes per token and the threads per barrier, and compare dataflows on identical kernels; our Emerald Rapids results for Falcon3-1B fall into the cache-resident regime of Zhang et al. (2026). 

Reducing synchronization on GPUs GPU decoders fuse a forward pass into one persistent kernel with few syn-chronization points per layer, hand-written (Spector et al., 2025a;b), generated by agents or search (Li et al., 2026a; Dong et al., 2026; Jaber & Jaber, 2026), or for multi-die GPUs whose dies resemble NUMA nodes (Chowdhary et al., 2026). On CPU nodes, we find that reducing the number of synchronization points stops paying off once they are few (§5.4). 

Ternary and low-bit kernels; AMX Ternary CPU work mostly optimizes the kernel on one node or socket: table lookups in T-MAC (Wei et al., 2025) and Vec-LUT (Li et al., 2026b), lossless kernels in bitnet.cpp (Wang et al., 2025), Intel’s near-roofline 2-bit microkernels (Georganas et al., 2025), the sub-two-bit BITCOS format (Georganas et al., 2026), and FairyFuse’s fused AVX-512 loop on one Xeon (Zuo et al., 2026). They are complementary: a faster kernel or a smaller format shortens the work between bar-riers and makes the dataflow matter more. AMX is used for MoE experts in KTransformers (Chen et al., 2025), for sparse compressed models in SparAMX (AbouElhamayed et al., 2025), and for ternary prefill in Intel’s TPP-based framework. Appendix J reports an AMX ternary prefill inside ik as a side result. 

## 9 CONCLUSION 

Placing every weight on the node of its reader is necessary for decoding ternary LLMs on multi-node CPU servers, but threads then still wait for 20–48 % of each token, mostly for the slowest threads of their own node. On the same kernels, a column-split dataflow decodes 1.5–2.1 × faster than the fastest existing ternary runtime where decoding is DRAM-bound, mainly because its threads wait less for each other and for their node leaders. Balancing the work among a node’s threads is the next target, along with integrating such a dataflow into a runtime with batching and prefill and testing it on more nodes and on other vendors’ CPUs.

Both machines were shared with other users. A round of a batch started only after the machine had been idle for 20 s (at most two busy CPUs). ## F ACCOUNTING OF THE ROW –C OL GAP 

Within one batch, the measured parts account for the gap to within 0.14 ms (Table 10). Two approximations enter: the stage times are means over the whole run, and the wait is divided into its three parts in the proportions measured on the traced runs of the same batch, which cover 32 tokens. These batches are not the one of the barrier-isolation table in the main text, so their gaps differ from it (e.g., 0.83 instead of 1.01 ms for Llama3-8B with IQ2 BN on Emerald Rapids). The largest compute difference is the QKV stage, where 

Row writes K and V to the node that holds the token’s KV block and Q to a shared buffer; the attention stage, which 

Row splits by position and Col by head, differs by up to 0.15 ms. We did not isolate these two differences. Col ’s reductions make its O and down stages up to 0.23 ms longer, and barrier latency contributes at most 0.08 ms.

## J AMX PREFILL AND ONE REQUEST 

Before the first token, the prompt is processed in one compute-bound matrix–matrix pass. Emerald Rapids pro-vides AMX tile instructions with an int8 peak of 552 Tops, Weight Placement Is Not Enough: Synchronization in Multi-Node CPU Decoding 

7.6 times its VNNI peak, which llama.cpp, ik and bitnet.cpp do not use for ternary weights. We add an AMX path to ik ’s prefill ( AMX-prefill ). 

Ternary GEMM on AMX AMX-prefill replaces ik ’s IQ2 BN matrix multiplication whenever at least 32 acti-vation rows are multiplied. Each thread expands its 2-bit weight rows into the int8 layout of AMX tiles (a 32-bit gather per four input positions of 16 rows, then shift, mask and subtract), unpacks up to 1 MB of weight panels into L2, and runs all 32-token activation blocks over them; on a socket or more, work is split over both weight rows and tokens. Activations are quantized exactly as for ik ’s VNNI kernel (four scales per row by channel group), with both operands reordered by group so that each 64-wide AMX step stays in one group, so AMX-prefill computes ik ’s inte-ger sums. Its perplexity on Llama3-8B is 0.9994 ± 0.0014 

of ik ’s (KL divergence 0.0022), and its downstream accu-racy matches ik ’s (Appendix B). In a microbenchmark with Llama3-8B shapes, the kernel is 4.3–7.2 × faster than the same tiling with VNNI and reaches 50 Tops on one node and 89 on one socket.
