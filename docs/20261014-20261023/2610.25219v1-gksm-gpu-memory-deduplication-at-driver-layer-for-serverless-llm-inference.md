## 摘要
在无服务器大语言模型（LLM）推理场景中，云服务提供商通常将多个实例部署在同一块GPU上以提升资源利用率。然而，每个实例均独立维护其模型权重和运行时状态，导致GPU内存重复成为主要性能瓶颈。内存去重是一种在CPU系统中广泛应用的消除冗余数据的技术，但将其扩展至GPU内存面临根本性挑战：有效的GPU内存去重必须避免CPU与GPU之间冗余的数据搬移，同时在缺乏原生写时复制（Copy-on-Write, COW）支持的情况下，保障共享页的写隔离性。本文提出gKSM——一种面向无服务器LLM推理的透明式GPU内存去重框架。gKSM通过三项关键技术应对上述挑战：（1）CPU-GPU协同哈希管理，将哈希计算卸载至GPU内核；（2）零拷贝模型权重去重，在模型权重传输至GPU之前即完成去重；（3）跨特权级页错误处理机制，结合轻量级内核钩子与用户态CUDA虚拟内存管理（VMM）重映射。此外，gKSM还设计了稳定的页面扫描算法与集群规模下的复用感知放置策略。实验表明，相较于ServerlessLLM，gKSM在保持高吞吐量的同时，GPU内存使用量降低59.8%；在内存受限的工作负载下，整体吞吐量提升2.15倍，并支持五个实例并发执行；在集群级仿真中，gKSM的服务率达到99.97%，显著优于SLInfer（78.2%）和ServerlessLLM（26.9%）。

## Abstract
In serverless LLM inference, cloud providers commonly locate multiple instances on a single GPU to improve utilization. However, each instance independently maintains its model weights and runtime state, making duplicate GPU memory the primary bottleneck. Memory deduplication is a widely-used technique for eliminating duplicate data in CPU systems, but extending it to GPU memory faces fundamental challenges. Effective GPU memory deduplication must avoid redundant data movement between CPU and GPU while preserving write isolation for shared pages without native copy-on-write (COW) support.   This paper presents gKSM, a transparent GPU memory deduplication framework for serverless LLM inference. gKSM addresses these challenges through CPU-GPU collaborative hash management that offloads hash computation to GPU kernels, zero-copy model weight deduplication that eliminates duplication before model weight transfer, and a cross-privilege page fault handler that combines a lightweight kernel hook and CUDA Virtual Memory Management (VMM) remapping in the user space. gKSM also designs a stable page scanning algorithm and a reuse-aware placement policy in cluster scale. Experiments show that gKSM reduces GPU memory usage by 59.8% while maintaining high throughput compared to ServerlessLLM. Under memory constrained workloads, gKSM improves aggregate throughput by 2.15X and supports five instances concurrently. In cluster level simulation, gKSM achieves a service rate of 99.97%, compared to 78.2% for SLInfer and 26.9% for ServerlessLLM.

- **根本瓶颈**：在无服务器（serverless）LLM推理场景中，为提升GPU计算资源利用率，云厂商普遍采用“多实例共驻单卡”策略；但各实例独立加载完整模型权重（数GB–数十GB）及运行时状态（如KV缓存），导致**GPU显存重复占用严重**，成为扩展实例密度的主要障碍。
- **现实规模佐证**：基于阿里云真实推理轨迹的仿真显示，ServerlessLLM与传统负载均衡策略下GPU内存重复率高达70%（约2000 GB），SLInfer虽通过同模型聚类优化仍达50%以上。
- **技术迁移困境**：CPU侧成熟的内存去重技术（如Linux KSM）无法直接移植至GPU，面临三大本质挑战：
  - **异构内存协同难**：GPU页数据在设备端，而元数据管理、哈希索引需在CPU端，跨PCIe搬运页数据做哈希开销巨大；
  - **关键路径冗余搬移**：模型权重从CPU加载至GPU需经`cudaMemcpy`，若先全量拷贝再扫描去重，将浪费PCIe带宽并引发瞬时OOM风险；
  - **写隔离缺失**：GPU驱动（尤其闭源用户态组件）不提供原生COW语义，无法像CPU MMU那样在写故障时透明分配私有副本。

> ✅ 整体含义：gKSM是首个面向**Serverless LLM推理场景**、在**CUDA驱动层实现透明GPU内存去重**的系统性方案，目标是在不修改上层框架、不牺牲实例隔离性的前提下，从物理内存层面根治重复占用问题。

## 2. 方法论：核心思想与关键技术细节

- **核心思想**：以**驱动层拦截+软硬协同**替代纯调度层优化，在GPU内存生命周期各关键阶段（加载、运行、故障）嵌入去重逻辑，实现“零感知”共享。

- **关键技术**：
  - **CPU–GPU协同哈希管理**  
    - GPU端：用CUDA kernel批量执行`xxHash3`（非加密哈希），吞吐达167.7 GB/s（比CPU快16.9×）；仅用于候选页筛选，不直接授权合并。  
    - CPU端：维护每GPU元数据表（含VA、权限、hash）与全局共享哈希桶表；哈希匹配后触发**精确内容比对**（防碰撞），仅全等才执行重映射。
  
  - **零拷贝模型权重去重**  
    - 在`cudaMemcpyHtoD`调用路径中插入钩子；  
    - 模型权重尚在CPU内存时即完成哈希→查表→精确比对→**直接重映射GPU虚拟地址至已有共享物理页**；  
    - 原分配的GPU内存立即释放，**避免任何冗余PCIe传输与临时显存占用**。

  - **跨特权级页故障处理（COW）**  
    - 共享页设为只读 → 写访问触发GPU页故障；  
    - **内核侧**：轻量钩子捕获故障（含地址、PID、GPU UUID），写入字符设备队列（无拷贝/重映射）；  
    - **用户侧**：专用COW线程批量消费队列 → 调用CUDA VMM API（`cuMemCreate`/`cuMemMap`/`cuMemSetAccess`）创建私有副本并重映射；  
    - 支持所有权转移（当原owner写时，选新owner并为其分配私有页），保障多实例并发安全。

  - **稳定页扫描算法**  
    - 后台线程周期扫描动态页（KV缓存、激活值）；  
    - 页面需连续`N`次扫描哈希不变才标记为“稳定”，方可参与去重；  
    - 扫描间隔采用指数退避（1s→16s），平衡响应性与开销。

  - **复用感知放置策略（集群级）**  
    - 将实例内存需求分解为**可共享部分**（只读权重、稳定前缀页）与**私有部分**（KV缓存、易变缓冲区）；  
    - 对候选GPU `g`，估算增量成本：`ΔM(i,g) = S_i + P_i − EstimateReuse(i, I_g)`；  
    - 选择`ΔM`最小且满足算力余量的GPU部署，**主动促成同模型/同家族实例共驻**，最大化去重收益。

## 7. 优点

- **首创性架构**：首个在**CUDA驱动层**实现GPU内存去重的系统，绕过框架耦合，天然支持vLLM/SGLang/TensorRT-LLM等异构推理引擎；
- **全链路优化**：覆盖“加载前（零拷贝）→ 运行中（稳定扫描）→ 写发生时（跨特权COW）”全生命周期，消除各环节冗余；
- **工程务实设计**：
  - 哈希+精确比对防碰撞，兼顾速度与正确性；
  - COW拆分至用户态，最小化内核修改（仅加钩子），保障驱动稳定性；
  - 2MB粒度匹配CUDA VMM分配习惯，平衡元数据开销与覆盖率；
- **部署友好**：复用感知放置策略与现有调度器兼容，可渐进式集成。

## 8. 不足与局限

- **安全侧信道风险**：与CPU KSM类似，存在基于去重信号的侧信道攻击可能（如推断模型权重），虽文中指出LLM场景敏感性较低且可限定信任域，但未提供具体防护机制；
- **硬件依赖性强**：深度绑定NVIDIA CUDA VMM API（如`cuMemExportToShareableHandle`），难以直接迁移至AMD ROCm或Intel XeHPG平台；
- **动态页去重保守**：稳定页扫描要求连续N次哈希一致，对短生命周期但高重复率的中间激活可能漏检；未探索机器学习预测稳定性等更激进策略；
- **生产集成挑战**：需修改CUDA Driver API（符号劫持），在严格管控的云生产环境中可能面临合规与升级维护阻力；
- **评估广度限制**：未测试多租户强隔离场景（如金融/医疗）下的性能干扰，也未报告长时间运行（>24h）的内存碎片与元数据膨胀问题。
