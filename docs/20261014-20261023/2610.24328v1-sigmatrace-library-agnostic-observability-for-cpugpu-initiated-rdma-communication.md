## 摘要
RDMA 网络技术可在大规模系统中实现低延迟、高带宽的通信。尽管该技术已被广泛采用，其可观测性却严重不足。现有工具或仅针对特定通信库，或仅报告聚合统计数据，无法反映单个操作的行为细节；其中 GPU 发起的网络通信可观测性缺口尤为显著——其内核态 RDMA 操作对主机完全不可见。本文提出 SigmaTrace，一种与通信库无关的 RDMA 性能分析框架，可为 CPU 和 GPU 发起的 RDMA 通信提供细粒度、逐操作级别的可观测性。SigmaTrace 在 libibverbs/mlx5dv 层（InfiniBand 与 RoCE 上各类通信库的共同底层）实施跟踪，并采用一种低开销的内存插桩技术；据我们所知，这是首个无需修改源码或二进制插桩即可实现 GPU 发起 RDMA 可观测性的方法。主机端跟踪在 128 卡 NCCL AllReduce 场景下引入 1.3% 的性能开销，在 1024 卡 RCCL 场景下开销低于 2%；在持久化内核的广度优先搜索（BFS）与混合专家（MoE）推理任务中，SigmaTrace 揭示了现有分析器无法观测到的内核态屏障扩散现象及 2.13 倍的跨节点流量倾斜。

## Abstract
RDMA networking enables low-latency, high-bandwidth communication on large systems. Despite its adoption, however, observability is lacking. Existing tools target specific communication libraries or only report aggregated data, missing per-operation behavior. The gap is widest for GPU-initiated networking, whose in-kernel RDMA operations are invisible to the host.   We present SigmaTrace, a library-agnostic RDMA profiling framework providing fine-grained, per-operation visibility for CPU and GPU-initiated networking. It traces operations at the libibverbs/mlx5dv layers, the common denominator beneath communication libraries on InfiniBand and RoCE, and employs a low-overhead memory interposition technique that, to our knowledge, gives the first observability into GPU-initiated RDMA without source patching or binary instrumentation.   Host-side tracing adds 1.3% overhead on NCCL AllReduce at 128 GPUs and under 2% on RCCL at 1024 GPUs. On a persistent-kernel BFS and Mixture-of-Experts inference, SigmaTrace exposes an in-kernel barrier spread and 2.13x inter-node traffic skew invisible to existing profilers.

# SigmaTrace 论文中文总结

## 1. 核心问题与整体含义（研究动机和背景）

- **可观测性严重缺失**：RDMA 已成为 AI 训练、科学计算等大规模分布式系统的通信基石（如 NCCL、UCX、NVSHMEM），但现有性能分析工具普遍缺乏对 RDMA 操作级行为的细粒度可见性。
- **GPU 发起 RDMA（GIN）完全不可见**：传统工具（如 Nsight Systems、NCCL Inspector、Mycroft、NPKit）仅能观测 CPU 侧 API 调用或内核代理线程，而 GPU 直接构造 WQE 并写入 NIC 门铃寄存器（UAR）的操作，在主机视角下仅为普通内存写（STG.E.STRONG.GPU），无 API 边界、无软件事件钩子，导致其“黑盒化”。
- **后果严重**：通信负载不均、QPs/节点间流量倾斜、内核级屏障扩散（barrier spread）、带宽利用率低下等关键性能瓶颈无法定位，严重阻碍分布式训练与推理的深度调优。

## 2. 方法论：核心思想与关键技术细节

- **核心思想**：**绕过软件栈，直击硬件交互点**——利用 GPU 发起 RDMA 必须通过 PCIe 向 NIC UAR 寄存器发起 MMIO 写这一不可绕过的硬件事实，将门铃寄存器映射页“劫持”为 CPU 可监控的 pinned 内存页，实现无侵入式拦截。
  
- **关键技术流程（Memory Hijack-and-Repeat）**：
  - **UAR 内存劫持**：在 GPU 初始化阶段（`mlx5dv_devx_alloc_uar` → `cuMemHostRegister` → `cuMemHostGetDevicePointer`），拦截三步流程，将原 NIC UAR 映射页替换为 CPU 分配的 4KB pinned host page，并返回该页对应的 device pointer 给 GPU。
  - **门铃监听与转发**：为每个劫持页启动专用 polling 线程，使用 `umonitor/umwait`（Intel）或 `monitorx/mwaitx`（AMD）指令高效监听 cache line 失效（由 GPU 门铃写触发），捕获门铃值（含 QP 编号 + producer index）后，立即转发至真实 NIC UAR。
  - **WQE 异步恢复与解析**：门铃写入仅表示“提交”，对应 WQE 存于 GPU 内存。Polling 线程在捕获门铃后，异步发起 CUDA stream 上的 `cudaMemcpyAsync` 将相关 WQE slot 拷贝至 host；待积累一定数量（如 128 个）后批量同步解析，提取 opcode、raddr、rkey、size 等元数据，避免高频同步开销。
  - **跨层关联重建**：通过拦截 `mlx5dv` 初始化调用（UAR 分配、UMEM 注册、QP 创建），构建 UAR–QP–SQ–GPU 的完整映射关系；结合 PTP 时间戳校准，实现多节点 trace 的纳秒级时间对齐与端到端事件关联。

- **库无关设计**：聚焦 `libibverbs` 和 `mlx5dv` 这一所有 InfiniBand/RoCE 库（NCCL、UCX、libfabric）的共同底层，同时扩展支持 Slingshot（via libfabric）与 EFA（规划中），避免绑定上层抽象。

## 6. 主要结论与发现

- **首次实现 GPU-initiated RDMA 的无侵入可观测性**：无需修改源码、无需二进制插桩、无需 kernel module，即可捕获精确门铃时间、WQE 内容及端到端关联。
- **极低开销**：主机侧 tracing 在 128 GPU NCCL AllReduce 中仅增 **1.3%** 开销；1024 GPU RCCL 下 **<2%**；门铃拦截本身仅引入 **2–4%** 固定延迟（UAR forwarding），WQE 解析带来额外 **22–46%**（worst-case）。
- **揭示隐藏性能瓶颈**：
  - **BFS 案例**：发现因 1D 图划分导致 GPU0（hub vertex）早期产生巨大跨分区通信，引发 **30 秒 barrier spread**（GPU0 最先到达，其余空等），该现象在 Nsight 中完全不可见。
  - **MoE 案例**：暴露 **2.13× 跨节点流量倾斜**（node2→node1 流量达均值 2.15×），证明 DP scheduler 的 token count 均衡 ≠ NIC 流量均衡，直接测量网络侧结果更具指导意义。

## 7. 优点

- **首创性与根本性突破**：首个在硬件交互点（UAR）实施内存劫持的 RDMA profiler，从根本上解决 GPU-initiated RDMA 不可见难题。
- **极致轻量与库无关**：基于 `libibverbs/mlx5dv` 层，天然兼容所有上层库；LD_PRELOAD + driver hook 设计，部署零侵入。
- **工程精巧**：`umonitor/umwait` polling 零 CPU 占用；异步 WQE 拷贝 + 批量解析平衡精度与开销；PTP 时间校准保障分布式 trace 可靠性。
- **分析能力强大**：支持 Perfetto timeline 可视化 + PerfettoSQL 定量查询，可灵活进行 barrier 分析、通信矩阵生成、GPU/QP/Node 多粒度聚合。

## 8. 不足与局限

- **硬件支持范围有限**：当前仅完整支持 **NVIDIA GPU + Mellanox NIC**（CX-5/CX-7）。AMD rocSHMEM 理论可行但需 ROCm driver hook 替换；Broadcom Thor 2、AMD Pensando Pollara 400、AWS EFA 等需适配新 doorbell/WQE 格式（文中已明确列出）。
- **软件栈绑定**：CUDA-specific driver interception（`cuGetExportTable`）；ROCm/HIP 支持需工程移植，尚未验证。
- **静态链接与内联函数限制**：`LD_PRELOAD` 无法拦截 `libcxi` 等大量使用 static inline 的库，HPE Slingshot 上仅能提供 libfabric 层部分可观测性，门铃级覆盖需 Frida/eBPF 等动态插桩补充。
- **场景覆盖偏差**：实验集中于 AllReduce、BFS、MoE，未覆盖更复杂 collective（如 AllToAll、ReduceScatter）或故障诊断场景（如丢包、重传）；MoE 实验仅用 4 节点，未验证超大规模 MoE（如百节点）下的 trace scalability。
