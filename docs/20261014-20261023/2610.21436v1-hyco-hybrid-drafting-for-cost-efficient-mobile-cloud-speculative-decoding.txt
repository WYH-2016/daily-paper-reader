Mobile–Cloud Speculative Decoding

Abstract
Device–cloud speculative decoding reduces
server computation, but growing a deep draft
tree with a small language model (SLM) re-
quires repeated passes on a mobile neural pro-
cessing unit (NPU). We present HYCO, which
assigns depth to the server model’s native multi-
token prediction (MTP) head, executed on the
device, and alternative branches to one SLM
pass. The server returns the hidden state, in-
put embedding, and key–value entries needed
by the head instead of executing its sequen-
tial steps. Quantization, a restricted vocabu-
lary, and a 1K-token window fit both drafters
to the NPU. An ϵ-threshold rule additionally
relaxes exact preservation of the verifier’s sam-
pling distribution. In single-client runs with
a Galaxy S26 Ultra over LTE/5G, HYCO re-
duces server GPU time per output token relative
to server-side MTP self-speculation by 38.6%
on Spec-Bench and 29.2% on 32K-token sum-
marization. With the same acceptance rule,
three Spec-Bench runs per system show 9.0 per-
centage points more saving and 1.9× delivery
speed than an SLM-only drafter. HYCO differs
from Cloud+MTP by +0.2 judge-score points
(paired 95% CI: −0.9 to +1.3); exploratory
translation favors SpecEdge-ϵ. Without relax-
ation, HYCO exact saves 27.7% and 11.9% on
the two datasets.

Introduction
Speculative decoding accelerates large language
models (LLMs) by verifying several draft tokens in
one forward pass, with exact verification preserving
the LLM’s sampling distribution (Leviathan et al.,
2023; Chen et al., 2023). Serving engines support
it (Kwon et al., 2023; Zheng et al., 2024), and re-
cent LLMs include a native multi-token prediction
(MTP) head (DeepSeek-AI, 2024; Gemma Team,
2026), one of several approaches to drafting from
the LLM’s hidden states (Cai et al., 2024; Li et al.,
2024, 2025b). Device–cloud speculative decod-
ing instead places a small language model (SLM)
on the user’s device and leaves verification to the
server (Park et al., 2025; Li et al., 2025a). Commu-
nication can make an individual request slower than
server-only speculation (Lyu et al., 2026); the op-
portunity is therefore to reduce server computation
without making the mobile experience impracti-
cally slow.
We target two goals. The server should spend
less GPU time per output token than Cloud+MTP,
which already runs the LLM’s own MTP self-
speculation. The user should receive tokens at
least as fast as the SLM alone generates them on
the device. These are distinct reference points:
Cloud+MTP measures the server-side opportunity,
whereas the SLM alone represents a local alterna-
tive for the user.
Meeting both goals is difficult on a mobile neu-
ral processing unit (NPU). The drafters must fit
integer execution graphs, limited shared memory,
and compiled context lengths. Acceptance varies
across tasks (Liu et al., 2024a; Xia et al., 2024) and
determines how effectively each round amortizes
server work and communication. A tree offers al-
ternative tokens at each position and is verified in
one pass (Miao et al., 2024), but growing it with an
autoregressive SLM requires a sequential pass per
level. The four-level SpecEdge-style tree studied
here raises the mean number of tokens accepted per
round (MAT), yet its four mobile SLM passes leave
the user slower than the SLM alone. The challenge
is to obtain useful depth and alternatives without
repeatedly running the SLM.
We present HYCO, based on a division of draft-
ing work. The LLM’s native MTP head reads only
a small slice of the LLM’s state, so it can execute
on the mobile device. This MTP Drafter supplies
a chain that gives the tree its depth. The server’s
LLM, the verifier, returns the head’s inputs with
each verification rather than executing the head’s
sequential steps itself. One pass of the device’s
SLM Drafter adds alternatives under the root and

Related Work
Work on device–cloud speculative decoding either
strengthens the draft or skips verification where
the device is confident. The draft is strengthened
in three ways: drafting a tree instead of a se-
quence (Miao et al., 2024; Park et al., 2025), train-
ing the draft model toward the target (Zhou et al.,
2024), or drafting several tokens in parallel (An
et al., 2026). The latter two retrain the draft model
and are orthogonal to our approach: HYCO keeps
its drafters as released, apart from quantization and
a restricted output vocabulary, and strengthens the
draft through its tree.
In SLM-based device–cloud systems, the de-
vice’s draft model drafts every proposed to-
ken (Park et al., 2025; Li et al., 2025a, 2026c),
one sequential pass per tree level, and SpecEdge
overlaps these passes with the round trip by proac-
tive drafting (PD), preparing the next round’s tree
while the reply is in flight.
Among the device–cloud systems in Table 1,
none drafts with the LLM’s native draft head:
HAT (Xie et al., 2026) runs the LLM’s first layers
on the device, whereas Li et al. (2026a) draft from
hidden states returned by the server. Cloud+MTP
drafts with that head, but on the server. HYCO
instead runs that head on the mobile device, beside
one SLM pass.
Skipping verification by confidence saves rounds
but is lossy. Synera keeps on the device the tokens
2


whose confidence clears a threshold and offloads
only the rest for the cloud to verify (Wang et al.,
2025). The cloud’s LLM does not check the locally
retained tokens. HYCO instead checks every round
with the verifier and raises acceptance within that
check through ϵ-threshold acceptance; its relaxed
rule is also lossy.
Raising acceptance within verification is the aim
of lossy acceptance rules, which accept drafted
tokens that the target would not necessarily sam-
ple, and they differ in what they test. BiLD keeps
a small model’s tokens unless its distribution di-
verges from the large model’s beyond a thresh-
old (Kim et al., 2023), and fuzzy speculative de-
coding and the edge–cloud E2-SCI accept within
divergence thresholds of their own (Holsman et al.,
2025; Li et al., 2026b). Judge decoding lets a
learned judge keep tokens that exact verification
rejects (Bachmann et al., 2025), and Medusa’s
typical acceptance tests the target’s raw softmax
against an entropy-adaptive threshold taken from
η-sampling (Cai et al., 2024; Hewitt et al., 2022).
HYCO’s ϵ-threshold acceptance instead thresh-
olds the verifier’s own sampling distribution ˜p
(§3.5).
3
Method
In HYCO, the mobile device constructs a hybrid
draft tree and the server’s verifier checks it (Al-
gorithm 1). We measure and compare settings on
UC-val, 60 prompts from the test split of UltraChat
200k (UC; Ding et al., 2023; Tunstall et al., 2024),
and fix the chosen configuration for the reported
SB and ∞Bench Sum runs (Appendix D). Server
cost g is the total GPU time including prefill di-
vided by output tokens. For decoding, this is server
time per round divided by MAT.
The default selection criterion minimizes g
among settings whose LLM-judge score (§4.3)
falls within the observed lossless-run range, 58.7–
63.0. This is a screening heuristic, not a quality-
equivalence test: two runs of the same setting
scored 57.1 and 61.5. When g differs by less than
the approximately 2% variation observed in valida-
tion, we use the stated device-cost or comparison
rationale.

At its first two steps, the MTP Drafter also plants
its second-ranked token beside the chain token as
a runner-up sibling, in case the top-1 misses the
verifier’s choice. The SLM Drafter, Gemma 4
E2B from Google’s QAT checkpoint (Google Deep-
Mind, 2026), then proposes in one pass children
under the root and every planted node, giving the
tree its width. Trimming the tree to its node budget
needs scores that weigh the chain’s nodes, which
carry no probability, against the SLM’s candidates.
Each depth along a node’s path costs ln 0.66 ≈
−0.42, as the chain’s acceptance rate per depth,
the share of rounds whose first k chain tokens are
3


all accepted among those whose first k−1 are, is
0.65–0.68 at every depth, with a geometric mean of
0.66. A depth-d chain node thus scores d ln 0.66,
about the logarithm of its chance of being accepted.
A runner-up sibling pays this cost twice on its own
edge, which ranks it just below the chain token it
doubles, and an SLM candidate adds its token’s log-
probability to the cost. The tree is then trimmed
by score, closed under ancestors, and sent as token
IDs and parent indices, 2.2 KB per round. The
verifier checks it in one forward pass with a tree
attention mask (Miao et al., 2024). Under exact
verification, it samples at each node v from its
sampling distribution ˜p(· | v) and descends to the
matching child, so the committed text follows ˜p
and verification is lossless. The first sample that
matches no child ends the round as its bonus token,
which MAT counts and which becomes the root of
the next tree.
The chain supplies most accepted tokens, and the
siblings and the SLM’s alternatives take over where
it breaks. An SLM leaf extends a fully accepted
chain to a fifth token in 17% of rounds under exact
verification.
We choose K=4 and runner-up siblings at
depths 1–2 on UC-val. The cumulative chain ac-
ceptance reaches 18.9% at depth 4; later siblings
bring little additional server saving. The 32-node
budget matches SpecEdge-style, and the verifier
uses the same 33-row CUDA graphs, including
the root. A second SLM pass is retained as the
HYCO-2P operating option rather than the default
(Appendix D).
3.2
Quantization
Integer graphs let both drafters exploit the mobile
NPU (Tan et al., 2024). In a diagnostic compari-
son, 16-bit floating-point activations lengthened the
SLM Drafter’s 32-row pass from 15.7 to 38–41 ms
at unchanged acceptance. The SLM’s QAT check-
point has 2-, 4-, or 8-bit weights but computes
in floating point (Gemma Team, 2026; Google
DeepMind, 2026). We convert it through graph
surgery and activation calibration without retrain-
ing its weights. The verifier’s MTP head is re-
leased in bfloat16 (BF16); we apply 4-bit QAT to
its linear weights. Both drafters use 16-bit fixed-
point activations and static graphs compiled with
the Qualcomm AI Runtime (QAIRT; Qualcomm
Technologies, Inc., 2026).
For the reported collaborative configurations, ac-
tivation calibration and head QAT use 60 prompts
from UC-tr, the train_sft split of UltraChat 200k,
not SB prompts. The head is trained for 100 steps
by minimizing Kullback–Leibler (KL) divergence
from the BF16 head on the verifier’s greedy an-
swers. On UC-val, this raises top-1 agreement with
BF16 from 87.4% to 91.0%; 8-bit weights retain
98.8% without training but double weight storage
(Appendix A).
3.3
Restricted output vocabulary
The output layers of both drafters span 262,144
tokens, and these layers and their top-k search, re-
peated for every row of the SLM pass and every
MTP Drafter step, take a large share of each round
on the mobile device. The full vocabulary length-
ens the mobile device’s time per round from 52.9
to 77.9 ms. As in FR-Spec (Zhao et al., 2025),
both drafters therefore predict from one keep set
of 86,089 tokens, mostly the tokens most frequent
in the answers of UC-tr, plus the special and byte
tokens. The MTP Drafter embeds its own drafted
tokens from an 8-bit, 242 MB table of the veri-
fier’s input embeddings for the kept tokens. Nei-
ther drafter can propose the tokens outside the keep
set, which make up 3.0% of the verifier’s bonus
tokens on UC-val, although UC-val is drawn from
the keep set’s own dataset, and more on SB. The
verifier still samples them from its full vocabulary
as bonus tokens, which both drafters take as input,
so the restriction costs only acceptance and exact
verification stays lossless.
By the default criterion, we use the 86K keep set,
whose g of 6.23 ms is the lowest of the four sizes,
against 6.44–7.57 ms, as Table 6 in Appendix D
shows. The full vocabulary has the highest g of all,
as its MAT is the lowest, 2.85.
3.4
1K-token context window
Both drafters read only the last 1,024 tokens of the
context, as prior drafters do on long inputs (Sad-
hukhan et al., 2025; Valliappan, 2026). The SLM
Drafter keeps its KV cache as a ring of the last
1,024 committed tokens, or 512 in its sliding-
window layers, so the mobile device never prefills
more than 1,024 prompt tokens. The MTP Drafter
reads the verifier’s keys and values over the same
window and prefills nothing on the device, while
the verifier prefills the whole prompt.
The device’s memory and prefill time set both
drafters’ windows at 1,024 tokens, as UC-val’s
short prompts cannot tell window lengths apart.

3.5
ϵ-threshold acceptance
The quantized, restricted and windowed drafters
on the mobile device propose some of the verifier’s
likely tokens less often than full drafters would,
and tokens outside the keep set not at all. Exact ver-
ification thus ends rounds that a plausible drafted
child could have continued.
Under ϵ-threshold acceptance, a drafted child
c of node v is accepted if it matches the verifier’s
sample or if ˜p(c | v) ≥ϵ. Here ˜p is the verifier’s
sampling distribution after temperature scaling and
top-k/top-p truncation, rather than its raw softmax.
With a one-hot greedy distribution, the threshold
adds no token beyond exact verification. The fixed
threshold follows ϵ-sampling (Hewitt et al., 2022).
The verifier selects the deepest path of accepted
children and appends its sample at that path’s end-
point as the bonus token. Among equally deep
paths, it prefers the one with more verifier-sampled
edges, then the highest product of ˜p. This is a path-
level preference, not a requirement to retain every
sampled edge.
Every accepted token is in the support of ˜p, but
the rule can commit tokens that the verifier did not
sample and changes their selection probabilities.
It is therefore lossy: membership in the verifier’s
sampling support does not guarantee distribution
preservation or equivalent quality. We measure the
quality–efficiency trade-off in §4.5; ϵ=1 gives the
exact-verification ablation.
Figure 3 depicts MAT against the judge score for
each acceptance rule on HYCO’s tree. At ϵ=0.005,
applying the threshold at every node rather than
only at rejections lowers g from 5.62 to 5.10 ms at
the same judge score of 60.0, and Medusa’s typical
acceptance at its defaults falls below the lossless
range. We choose ϵ=0.005 at every node by the
default criterion: it has the highest MAT and low-
est g among the screened settings, whereas ϵ=0.02
matches that g but scored 57.1 without node log-
ging. On the fixed logged trees of one run, lower-
ing ϵ has little remaining headroom: ϵ=0.005 gives
MAT 4.364 versus 4.366 if every drafted token in
the verifier’s sampling support were accepted.
4
Experiments
4.1
Setup
The verifier is Gemma 4 26B-A4B (Gemma Team,
2026) with 4-bit activation-aware weight quantiza-
tion (AWQ; Lin et al., 2024), served on one RTX
PRO 6000 cloud GPU. A Galaxy S26 Ultra with an
SM8850 chipset runs the drafters on its Hexagon
Tensor Processor v81 over a commercial LTE/5G
connection; the operator assigned LTE-CA or 5G
NSA during measurement. The verifier samples
with temperature 1, top-k 64 and top-p 0.95. Thus,
exact verification preserves this sampling distri-
bution, not a fixed greedy output. All configu-
rations use SpecEdge’s verification server (Park
et al., 2025), extended with our verifier and its
MTP head, the same kernels, and one client at a
time (Appendix B).
4.2
Baselines and variants
Cloud+MTP uses the released BF16 MTP head
over the full prefix and vocabulary, with exact veri-
fication and the same chain depth K=4 as HYCO.
SpecEdge-style drafts a 32-node tree in four se-
quential SLM passes, with the same 1K mobile
prefill bound. SpecEdge-style + PD additionally
uses proactive drafting while the verification reply
is in flight; both variants verify exactly. SpecEdge-ϵ
keeps this SLM-only construction but applies ex-
actly the same threshold and path-selection rule
as HYCO. This controls the acceptance rule, not
output quality; we therefore compare their quality
directly.
HYCO uses one SLM pass; HYCO-2P uses two.
Both apply ϵ=0.005. HYCO exact sets ϵ=1, which
adds no token that the verifier would not sample.
The server-head variant also verifies exactly but
5


leaves the head on the server, in BF16 with the
86K keep set and 1K window, and omits runner-
up siblings. It is an alternative configuration, not a
placement-only ablation (Table 5). On-device 8K is
the SLM alone with an 8K context, full vocabulary,
and greedy decoding, evaluated on SB only; it rep-
resents standalone local generation, not a matched
drafter ablation.
4.3
Evaluation and uncertainty
We use all 480 Spec-Bench questions (SB-480; Xia
et al., 2024) to measure decoding efficiency, in-
cluding both MT-bench turns, with a 1,024-token
output cap. To assess the effect of ϵ-threshold ac-
ceptance on the generated answers, we add the
following quality evaluations. GPT-5.4 scores first-
turn answers from 0 to 100 using the question, not a
reference answer. The aggregate judge score covers
non-QA tasks; QA diagnostics are reported sepa-
rately in Appendix E. Two summarization items
consistently refused by the judge’s filter are also
omitted. Thus, HYCO–Cloud+MTP quality com-
parisons cover 398 questions. Complete-case three-
run comparisons involving SpecEdge-ϵ cover 396,
owing to two additional missing scores across its
runs (Appendix E). Reference metrics supplement
this question-only judge.
For ∞Bench Sum, we evaluate the first 50 En-
glish novels in HELMET’s seed-42 order, truncated
to 32K tokens with its preprocessing (Zhang et al.,
2024; Yen et al., 2025), with a 1,200-token out-
put cap. We report ROUGE-L-Sum (Lin, 2004)
and HELMET’s model-based fluency-weighted F1,
key-point recall, and precision using GPT-5.4. Pre-
cision tests support in the expert summary, not
direct factual verification against the entire novel.
We measure GPU time per output token g, in-
cluding prompt prefill; MAT; and delivery speed,
pooled output tokens divided by mobile wall time
from request start to last token. Mobile draft time
excludes verification waits and prefill. HYCO and
SpecEdge-ϵ each have three SB generations, with
one judge evaluation per output; other configura-
tions, the 32K set, and Cloud+MTP have one. Re-
ported ± values are the sample SD of run-level
measurements, not confidence intervals.
Paired 95% CIs use 2,000 question-level boot-
strap samples, clustering MT-bench turns. For re-
peated quality, we first average each question’s
three scores and then resample common questions.
These intervals condition on the recorded genera-
tions and the single Cloud+MTP run; they do not
separate generation variation from judge variation
(Appendix E).
4.4
Efficiency under matched acceptance
rules
Under the same ϵ rule, HYCO reduces GPU time
by 38.6 ± 0.2% on SB versus 29.6 ± 0.2% for
SpecEdge-ϵ, an additional 9.0 percentage points.
Delivery speeds are 35.0 ± 0.7 and 18.9 ± 0.1 to-
kens/s, respectively. The hybrid tree achieves MAT
4.71 with one SLM pass, whereas the SLM-only
tree reaches 4.13 with four. On 32K summarization,
their reductions are 29.2% (95% CI: 27.8–30.6%)
and 15.7% (14.1–17.1%), at 21.0 and 12.4 tokens/s.
The benefit also appears without relaxation. On
SB, HYCO exact reduces g by 27.7%, compared
with 20.6% for SpecEdge-style exact. On 32K, the
corresponding savings are 11.9% and 2.9%. The
exact and same-ϵ comparisons therefore provide
complementary evidence: the design saves server
work without altering the sampling distribution,
and an additional advantage remains when both
device drafters share the relaxed rule.
HYCO-2P saves more server time, 44.7%/31.9%
on SB/32K, but delivers fewer tokens per second
than default HYCO. The server-head configuration
is faster on SB, at 36.1 tokens/s, but saves only
14.6% of server GPU time. PD raises SpecEdge-
style’s SB saving from 20.6% to 23.9%, but low-
ers delivery from 16.1 to 12.1 tokens/s. On 32K,
both save 2.9% (rounded), while PD lowers deliv-
ery from 10.0 to 8.2 tokens/s. Thus, neither more
passes nor overlapping draft work is uniformly ben-
eficial in this deployment.
Per-question analysis finds 2, 1, and 0 non-
saving cases among the 480 questions in HYCO’s
three runs. They are short RAG answers of about
40 tokens. Pooled g weights questions by each
configuration’s output length and is not the mean
per-question reduction (Appendix F).
4.5
Quality and failure cases

4.6
Mobile costs and head transfer
On SB, HYCO delivers 35.0 tokens/s versus 26.4
for the SLM alone. Its 12.1 ms of mobile draft
time per output token is about a third of the SLM
alone’s 36.8 ms. SpecEdge-style exact delivers
16.1 tokens/s and consumes 42.8 ms of mobile
draft time per token. The two efficiency goals
therefore use distinct references: less server work
than Cloud+MTP, and faster delivery than the local
SLM. Since Cloud+MTP was not streamed to the
phone, we do not compare its user delivery speed
with HYCO.
In a separate paired 150-question experiment,
the device-head configuration (W4, 86K keep set,
1K window) has 4.0% lower MAT than the original
BF16 server head (95% CI: 3.0–4.9%). In the full
SB experiment, relaxing HYCO exact raises MAT
from 3.84 to 4.71. These are separate comparisons,
not additive estimates of independent component
effects.
The first hand-off introduces a startup cost.
Single-run HYCO traces have mean time to first
token of 846 ms on SB and 4.60 s on 32K inputs.
Thus, higher average delivery speed does not im-
ply a lower first-token delay. We report GPU-busy
efficiency, not loaded-service capacity or energy
savings (Appendix G).
5
Discussion
5.1
From server accelerator to client drafter
Device–cloud systems commonly offload an inde-
pendent draft model (Park et al., 2025; Li et al.,
2025a, 2026c). When the server already has a na-
tive draft head, the remaining server-side opportu-
nity can be small (Lyu et al., 2026). HYCO changes
7


the work split itself: it moves the native head’s se-
quential steps to the mobile device and returns the
slice of verifier state that the head reads. MTP
self-speculation becomes a device–cloud protocol
rather than only a server-internal accelerator.
This split is useful when server GPU time is a
priority and the head’s inputs fit the link. The UC-
val comparison in §3.1 exchanges about 5 ms of
server time per round for about 20 ms of additional
mobile work, while the independent SLM supplies
alternative branches without taking over the chain’s
depth. Our single-client measurements establish
the execution-time trade-off, not the capacity gain
of a loaded service.
5.2
Choosing the mobile–cloud work split
The configurations expose different operating
points. Prior systems adapt draft length to the
channel (Li et al., 2026c), an acceptance thresh-
old (Li et al., 2026b), or which tokens reach the
server (Wang et al., 2025). Here, the choices also
include where the native head executes and how
many SLM passes accompany it. Figure 1 illus-
trates the associated deployment priorities, rather
than an evaluated online switching policy.
More drafting is not uniformly beneficial. The
second SLM pass in HYCO-2P exchanges more
mobile work for a larger server saving, at 29.0 to-
kens/s on SB-480 against 35.0 for default HYCO.
On ∞Bench Sum, however, that pass adds only 2.7
percentage points of server saving and reduces de-
livery speed by 10%: its MAT gain is smaller, and
prefill, which drafting does not shorten, accounts
for about a fifth of g.
Cloud+MTP removes mobile drafting altogether.
Among the exact configurations, server head uses
9.2 ms of mobile draft time per output token ver-
sus 14.7 ms for HYCO exact, with 13.1 percentage
points less server saving on SB. The preferred split
depends on which resource is constrained; time
measurements alone do not determine an energy-
optimal choice.
5.3
Lossy acceptance revisited
Wang et al. (2026) identify risks of truncation-
based verification: an allowed set constrains which
tokens can be accepted, but does not preserve the
verifier’s relative preferences within that set. Our ϵ-
threshold acceptance belongs to this category. The
repeated and long-summary results in §4.5 charac-
terize its trade-off on the evaluated tasks; they do
not remove the underlying distributional risk.
The exact comparisons favor HYCO over the
SLM-only baseline on both SB and 32K inputs,
while the same-ϵ comparisons retain an efficiency
advantage after matching the relaxed rule. The lat-
ter controls the acceptance rule but not the proposal
distribution. Its overall score interval and transla-
tion difference support a task-dependent trade-off.
The fixed-tree UC-val replay of §3.5 helps ex-
plain which proposals benefit. About two thirds of
threshold-only accepted tokens come from the ver-
ifier’s MTP chain, a tenth from runner-up siblings,
and a quarter from the SLM. Thus, most such to-
kens follow the native head’s proposals rather than
an independent drafter’s. This composition, the use
of ˜p rather than raw softmax, and the path-level
preference for sampled edges are plausible expla-
nations for the observed scores, not guarantees of
quality. The replay follows fixed logged trajec-
tories and does not measure the quality of newly
generated answers.
6
Conclusion
HYCO combines two complementary drafters on a
mobile NPU: the verifier’s native MTP head sup-
plies depth, and one SLM pass supplies alternative
branches. Returning the head’s inputs instead of
executing its sequential steps reduces server work,
while the hybrid tree avoids repeated SLM passes
for depth. Quantization, a restricted vocabulary,
and a bounded context make this split practical on
the device.
In single-client measurements, HYCO with ϵ-
threshold acceptance reduces server GPU time per
output token against Cloud+MTP by 38.6% on SB
and 29.2% on 32K-token summarization; with ex-
act verification, it still saves 27.7% and 11.9%,
respectively. On SB, it delivers tokens 32.5% faster
than the SLM alone at a third of its mobile draft
time per output token. Exact-verification and same-
ϵ comparisons support the design, while repeated
generation and summary assessment quantify a
task-dependent quality–efficiency trade-off. Hy-
brid drafting therefore offers a practical mobile–
cloud operating point without requiring the SLM
alone to provide both depth and alternatives. Ap-
plying the same split to other model families is
a natural next step; it requires a native head that
the mobile device can run, and Appendix H shows
the SLM Drafter working for Muse-Glimmer-30B
through a token bridge without retraining.
8


Limitations
Deployment scope and cost.
Each round waits
for one network round trip, which bounds mobile
delivery speed. Retaining unverified device tokens,
as in Synera (Wang et al., 2025), would introduce
a different lossy mechanism. The full hybrid de-
ployment uses one mobile device, one commercial
cellular network, one cloud GPU type, and one
verifier family. All configurations serve one client
at a time in our engine. We measure GPU execu-
tion time and mobile draft time, not loaded-service
capacity, monetary cost, or device and radio energy.
Distribution and quality.
Default HYCO does
not preserve the verifier’s sampling distribution.
The reported judge-score interval permits a mod-
est quality decrease. The aggregate covers scored
non-QA first-turn answers, not QA or second-turn
quality. Translation favors SpecEdge-ϵ in an ex-
ploratory comparison. The question-only judge
and reference-summary-based HELMET metrics
do not comprehensively assess factual consistency,
and we do not establish how relaxed acceptance
changes output diversity.
Only the two main
relaxed systems have three SB generations; the
other configurations and Cloud+MTP have one.
Question-bootstrap intervals condition on these out-
puts, and one judge evaluation per output does not
separate judging from generation variability. The
UC-val screening range is not an equivalence mar-
gin. Appendices A and D distinguish calibration
and development data from the reported benchmark
runs.
Requirements and device costs.
HYCO requires
access to the verifier’s native head, intermediate
hidden states, and KV entries, which may not be
available from closed model services; its head must
also run on the mobile device, and the SLM needs
a shared tokenizer or token bridge. Heads that read
more verifier layers (Chen et al., 2026) can require
a larger hand-off. The MTP Drafter adds about
20 ms per mobile round and up to 6.3 MB to the
first reply of a long prompt. The device stores
365 MB for it alongside the SLM’s 754 MB graph.
Vocabulary, context, and input scope.
The UC-
derived keep set and 1K window need not suit ev-
ery language or domain (Abramovich et al., 2026).
Tokens outside the keep set comprise 3.0% of veri-
fier bonus tokens on UC-val and 6.8% on the 150-
question SB subset of the head-configuration com-
parison (§4.6). Exact verification preserves the out-
put distribution despite these proposal restrictions;
relaxed acceptance does not. The SLM accesses
earlier context only indirectly through the MTP
chain. We evaluate text only, not Gemma’s image
or audio inputs.
Information exposure.
Each client holds the
MTP head and part of the verifier’s input embed-
dings. Transmitted activations and reply-size pat-
terns may expose information beyond the text (Cun-
ningham, 2026). We evaluate no safeguard.

Final calibration and training.
The collabo-
rative configurations in Table 2 use the UC-
tr-calibrated SLM and, where applicable, MTP
head. Both calibration procedures use 60 first-turn
prompts from the training split of UltraChat 200k
and the verifier’s greedy answers; no SB prompt

The graph surgery of the SLM Drafter keeps
the checkpoint’s bit allocation and the weights’ in-
tegers and scales bit-exact, rewrites each low-bit
weight matrix multiplication as an integer one with
an explicit encoding of its bit width, decomposes
root-mean-square (RMS) normalization into stan-
dard operators, computes the rotary tables on the
host, and keeps the embedding tables on the CPU
as lookup tables. For the final calibration, activa-
tion ranges come from the 60 UC-tr prompts with
the verifier’s greedy answers used for the MTP
head’s QAT, and KV caches use 8 bits with a range
of 1.2 times their 99.9th percentile. Keys enter the
KV ring with their rotary embedding applied, so an
entry keeps its absolute position wherever it sits in
the ring.
Table 4 shows the UC-tr training settings for
the MTP head, whose KL loss follows Gemma’s

QAT for LLMs (Liu et al., 2024b). After a per-

the quantization error, every linear layer is fake-
quantized with a straight-through estimator (Ben-
gio et al., 2013). The training inputs, captured
by teacher forcing the verifier in BF16, are the
input embedding, the last hidden state, and the
keys and values of the two source layers. The 60
UC-tr prompts are first turns sampled at random
from conversations that the keep set’s counts never
read. The top-1 agreement of §3.2 compares the
quantized integer head with the BF16 head on the
25,625 response tokens of the 60 UC-val sequences.

B
Verifier Engine
We ported the verifier’s text model with static
shapes into SpecEdge’s server (Park et al., 2025),
replacing its model side, and checked it against the
Hugging Face model. Attention projections run
as 4-bit integer Marlin matrix products (Frantar
et al., 2025) and the experts, 8 of 128 per token,
through vLLM’s fused Marlin mixture-of-experts
kernel (Kwon et al., 2023), while the dense MLP
and the router stay in 16 bits. RMS normalization
runs in FlashInfer (Ye et al., 2025), and attention
in PyTorch (Paszke et al., 2019) with the tree mask.
Tree verification uses the routed MoE kernel de-
scribed above rather than a dense all-expert path.
Each decode round is padded to the narrowest of
ten attention windows that covers its context, 256,
512 and 768 positions and then powers of two up
to the maximum context of 65,536, and replays
that window’s CUDA graphs, while prefill runs ea-
gerly in chunks. The verifier’s MTP head, which
Cloud+MTP and the server head variant run on
the server, replays its own graphs over the same
windows, and its chains agree with eager execution
on 99.2–99.6% of tokens, as often as two stock
attention kernels agree.

Additional Cross-Family
Measurements
The SLM half of the Hybrid Drafter is not tied to
Gemma 4. In additional runs, our SLM Drafter
drafted without retraining on a Galaxy Z Fold8
smartphone, which shares the S26 Ultra’s SM8850
chipset, for Muse-Glimmer-30B in NVFP4 (Meta
Superintelligence Lab, 2026; NVIDIA, 2026), a
verifier of another family whose tokenizer it is
mapped to through a token bridge. Glimmer’s own
DFlash2 head (Chen et al., 2026; Inco AI, 2026),
which reads five of its layers and was not deployed
on the device, drafted eight-token chains on the
server, as in our server head variant. Over all 480
SB questions, a SpecEdge-style tree of four SLM
passes and 127 nodes (128 verifier rows, against 33
in Table 5) reached an MAT of 3.16, and a 32-node
tree of the chain and a single SLM pass reached
4.07.
These runs used another verifier, server GPU,
and engine, and answers of up to 2,048 tokens,
so they are not comparable with Table 2, but they
show that the SLM Drafter carries over to another
model family through a token bridge. A head that
the mobile device can run for such families would
move the whole Hybrid Drafter, not only its SLM
half, to the device, which we leave to future work.
