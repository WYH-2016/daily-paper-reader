# PAGE404: Breaking GPU Isolation Through Hardware-assisted Page Migration 

Ravan Nazaraliyev ∗, Yicheng Zhang †, and Nael Abu-Ghazaleh ∗∗Department of Computer Science and Engineering, University of California, Riverside Email: rnaza005@ucr.edu, naelag@ucr.edu

Department of Electrical and Computer Engineering, George Mason University Email: yzhang95@gmu.edu Accepted to the 48th IEEE Symposium on Security and Privacy (S&P 2027) 

Abstract —NVIDIA’s Grace Hopper (GH200) superchip repre-sents a new generation of heterogeneous computing, tightly integrating a 72-core Arm-based CPU with a Hopper GPU on a single module via a high-bandwidth, cache-coherent interconnect. By eliminating the conventional PCIe bottleneck that has long constrained CPU–GPU data movement, this design establishes a unified memory domain that scales to the capacities demanded by generative AI and high-performance computing (HPC) workloads. The architecture also introduces hardware-assisted page migration support: driven by access counters, the system dynamically promotes frequently accessed pages from host CPU memory to the GPU DRAM to improve memory locality. In this paper, we study the security of this emerging architecture against new types of side- and covert-channel attacks targeting its page migration support. We analyze counter-driven migration across both the hardware mechanisms and the UVM driver’s interrupt-handling pipeline, and identify two side-channel vulnerabilities: one rooted in the shared structure of access counters, and the other in the driver’s response to migration interrupts. We further show that both channels are exploitable across Multi-Instance GPU (MIG) partitions, a feature intended to provide strong, hardware-enforced isolation between co-located tenants. Using proof-of-concept attacks, we build covert channels that reach roughly 8,500 bits per second through eviction-based signaling and 8,100 bits per second through migration-delay-based signaling across MIG instances. The interrupt-based channel also fingerprints inference workloads across distinct large language models (LLMs) and CPU SPEC2017 benchmarks, and estimates the prompt length processed during LLM inference with high accuracy. Taken together, these results expose a security gap in hardware-managed heterogeneous memory systems and call into question the isolation guarantees of current MIG-enabled multi-tenant GPU deployments. The artifact of PAGE404 is available at PAGE404 GitHub. 

## 1. Introduction 

The growing demands of machine learning models and high-performance computing (HPC) workloads challenge the capabilities of modern CPUs, GPUs, and their memory systems. Successive GPU generations have been developed with increasing computational and memory capabilities in an effort to meet these needs. A significant source of overhead arises from memory management across the GPU and CPU: existing memory management approaches such as 

Unified Virtual Memory (UVM) require expensive software-managed fault handling via the UVM driver to transfer pages from/to the CPU and GPU memories. With the large memory demands of large models (e.g., to hold the KV cache), efficient integration between the GPU and CPU is needed to allow the GPU to use the host CPU memory. To address these demands, newer designs, such as NVIDIA’s Grace Hopper (GH200) superchip, support tighter CPU–GPU integration and hardware-managed memory sys-tems to enable low-overhead uniform memory access be-tween the GPU and CPU. The GH200 integrates an ARM-based Grace CPU with a Hopper GPU via NVLink-C2C, a cache-coherent, high-bandwidth interconnect supporting the Address Translation Service (ATS) [1]. ATS enables GPU threads to access system-allocated memory directly through hardware-assisted virtual-to-physical address trans-lation, eliminating most of the software managed page-fault overhead of conventional UVM. The GH200 further introduces a hardware-assisted page migration policy that tracks page usage and automatically migrates hot pages to the GPU. This policy is implemented through access counters : per-region hardware counters that track GPU accesses to system memory pages and notify the UVM driver once a configurable threshold is reached. The driver then migrates the corresponding pages from host DRAM to GPU-local memory, optimizing memory locality without requiring programmer intervention. While this mechanism is designed for performance, shared access counters and the driver’s interrupt-handling pipeline for servicing these notifications are subject to contention from co-located GPU workloads, causing observable migration delays related to other system activity. In this work, we investigate whether these new mech-anisms for hardware-assisted page-migration expose side channel and covert channel vulnerabilities. Because these platforms are expensive, they are frequently shared among potentially mistrusting users (e.g., in a cloud deployment). We reverse-engineer the access-counter subsystem and the UVM driver’s interrupt-handling mechanism, characterizing the structure and behavior of the page migration counters and how migration notifications are processed by the driver. arXiv:2610.20962v3 [cs.CR] 21 Oct 2026 From this analysis, we identify two previously unexplored side-channel vulnerabilities. The first channel stems from the shared structure of the access-counter hardware across tenants. We discover that the counter hardware is organized into a set-associative structure similar to caches, and notifications are triggered deterministically once a migration threshold is reached. Since this structure is shared, it can be exploited using contention (e.g., evicting other processes’ counters) for covert communication across tenants. Similarly, the leakage through these shared counters can be measured (observed through the presence or absence of migration) to identify victim accesses to the same counter set. The second channel exploits migration contention on the shared driver: calls to the driver (e.g., to launch a new kernel) can be detected since they affect the response latency to migration events. Crucially, both channels target a GPU-wide shared resource, which makes them exploitable across Multi-Instance GPU (MIG) partitions , breaking the isolation guarantees of MIG. On GH200, MIG partitions are shared across two containers, which is currently the only mechanism by which MIG instances are exposed to users. Building on these findings, we demonstrate several covert-and side-channel attacks. The eviction-based covert channel achieves 8500 bps at a 1.5% error rate, rising to 15500 bps at roughly 5% error with two eviction sets, while the eviction-based side channel distinguishes among 10 different CUDA workloads with 94% accuracy when they use system-allocated memory. The migration-delay leakage enables a covert channel of 8100 bps at a 4% error rate and, across several side-channel attacks, distinguishes CUDA and LLM workloads with around or above 90% accuracy, estimating an LLM’s processed token length with a mean absolute error of 4.6 tokens on average. Moreover, we show that even when a tenant runs no GPU workload at all, a spy can still infer side-channel information about that tenant’s CPU workloads. This is because page migration requires the writer-prioritized mmap_lock to read the process’s memory map. As a result, concurrent CPU memory operations (for example, munmap calls) can delay the migration’s read request. PAGE404 makes the following contributions:

## 2. Background and Threat Model 

This section overviews the NVIDIA memory manage-ment and outlines the threat model and attack assumptions. 

2.1. Background 

Memory management across heterogeneous processors such as CPUs and GPUs provides a unified abstraction over what are physically distributed memory resources (separate GPU and CPU memories), allowing automated management of memory without expensive run-times or burdensome programmer management. NVIDIA’s Unified Virtual Memory (UVM) [2] was an early step in this direction, allowing CPU and GPU to share a single virtual address space. Heterogeneous Memory Management (HMM) [3], a later model, enables GPU threads to access system-allocated memory directly via shared virtual addressing. The overheads of memory management continue to be high, leading to more recent architectures, such as the Grace Hopper GH200 super-chip, that incorporate hardware-assisted address translation and dynamic page migration [1], [4] to improve performance and to provide coherence across an address space that spans the CPU and GPU memories. Workloads whose memory footprint exceeds GPU ca-pacity can benefit from this tight integration. Consider the key-value (KV) cache in large language model inference: as sequence lengths and batch sizes grow, the KV cache can quickly outgrow the available GPU memory [5], forcing developers to either cap context length or manually stage data between host and device. Large-scale graph processing poses a similar challenge, where the graph’s vertex and edge data may be far larger than GPU memory [6], [7], yet access patterns are irregular and data-dependent, making static partitioning ineffective. In both cases, the programmer is traditionally burdened with explicit memory management, allocating device buffers, orchestrating host-to-device trans-fers, and tracking which data resides where. This motivates the critical primitives these systems aim to provide: a unified address space so CPU and GPU can reference the same data through a single pointer, on-demand paging so data migrates automatically only when accessed, and transparent oversubscription so the working set can exceed physical GPU memory without manual intervention. The systems described below address these needs to varying degrees.

On the CPU side, the CUDA Runtime exposes a programmer-facing API for memory allocation and it communicates with the Kernel Module via ioctl system calls, which manage the virtual-address (VA) space mapping and migration policies. On the GPU side, Streaming Multiprocessors (SMs) each support their address translations through a micro-TLB (uTLB), which are managed by the GPU Memory Management Unit (GMMU) responsible for maintaining the GPU page tables. When a GPU thread accesses a page not currently mapped in its uTLB, a TLB miss is raised 1⃝ and forwarded to the GMMU. The GMMU writes a structured fault entry into the Fault Buffer: a GPU-visible ring buffer shared with the CPU 2⃝A. Subsequently, it raises an interrupt to the host 3⃝A. The UVM Kernel Module services this interrupt in its bottom half, draining the Fault Buffer. The module then updates the CPU-side page tables to reflect the new page placement 4⃝A, and instructs the Copy Engines (CE) to perform a direct memory transfer of the faulting page over NVLink or PCIe from Host Memory to Device Memory (HBM) 5⃝. Once the copy completes, the GMMU updates its own page table entries and invalidates the relevant uTLB entries so that the faulting instruction can be replayed transparently 6⃝.

Heterogeneous Memory Management (HMM). HMM extends UVM’s shared virtual addressing to any system-allocated memory (ordinary malloc , mmap , etc.) by integrating with the OS page-fault subsystem, whereas UVM only works for memory explicitly allocated through 

cudaMallocManaged . While this may improve the pro-grammer productivity, it leads to substantial overheads, which motivated the hardware-assisted memory management support present in the Grace Hopper superchip. 

Hardware-assisted memory sharing. GPU memory accesses may trigger page faults that require the UVM/HMM kernel module to intervene, introducing interrupt-handling overheads and additional OS interactions that can substan-tially impact performance. UVM/HMM also lacks hardware cache coherence between the CPU and GPU, requiring developers to manage memory coherence manually or limit updates from both the CPU and the GPU. As shown in Figure 2, the host side comprises the CPU and its Memory Management Unit (MMU), which owns the page tables, and an Input/Output MMU (IOMMU) that enforces address translation for device-initiated memory accesses. On the device side, the DMA Engine issues memory requests using virtual addresses and is backed by an on-chip Address Translation Cache (ATC) that stores recently resolved VA →PA mappings. When the DMA Engine needs to access a host memory location, it first checks its local ATC. On a miss, it sends an ATS translation request [8], [9] carrying the virtual address across the PCIe link to the host Root Complex, which forwards it to the IOMMU 1⃝. The IOMMU walks the page tables, resolves the physical address, and returns an ATS translation response 2⃝; the device caches this VA →PA mapping in its ATC for subsequent accesses. With a valid translation cached, the DMA Engine proceeds to issue physical-address DMA read/write operations directly to host memory over the PCIe link 3⃝, bypassing the need for further translation requests. On the GH200, NVLink-C2C [10] extends this mechanism with cache coherence, enabling the GPU to access host memory without explicit page migration. Within UVM, this serves as the hardware-assisted alternative to the fault-and-copy path in Figure 1 ( 3⃝B– 6⃝).

2.2. Threat Model 

PAGE404 assumes the highest level of isolation between tenants that use different Multi-Instance GPU slices. MIGs are allocated to users in containers [11], and Kubernetes Engines can be utilized to handle the sharing mechanism [12]. NVIDIA also provides vGPU technology [13], where each user has its own guest driver, but it is not supported on ARM platforms. Hence, the highest isolation level is that each user gets its own MIG slice within their container. Containers share the same GPU driver (nvidia.ko in Fig. 3). Previous works assumed sharing of a GPU with other tenants [14], [15], [16], [17], [18], where a spy CUDA application and a victim 

GPU context, i.e., a CUDA or graphics application, share a GPU. Other works assumed GPU sharing in cloud settings, where multiple tenants can share the same physical GPU through virtualization [19], [20], [21], [22]. Additionally, prior research has demonstrated practical techniques for achieving co-location in cloud systems [23], [24], [25]. MIG attack papers [18], [26] assumed that different users get their own MIG instance. The attacker does not require superuser privileges. Instead, they perform experiments to reverse-engineer the page migration details and the behaviour of hardware access counters, as a preliminary step for the attacks.

3.1. Page Migration Access Counters 

Overview of the page migration. To understand the behavior of page migration, we design an experiment that performs strided memory accesses over a system-allocated (i.e., CPU allocated) memory region using a single GPU thread. The resulting access latencies reveal a repeatable migration pattern that recurs over every 2 MB region. Fig-ure 4 depicts a representative 2 MB virtual address space, exposing the underlying migration mechanism. The migration behavior is explained by two complementary mechanisms: page migration driven by access counters, and prefetching performed by the UVM driver module. Prefetching is gov-erned by a tree-based promotion policy implemented within the UVM driver. Migration operates at the granularity of a single 64 KB page: once the access counter for a given 

64 KB page reaches a specific threshold, that page is migrated to GPU memory. With a sequential access pattern, upon each migration, potentially additional regions are prefetched corresponding to one node higher in the promotion tree, so that the number of prefetched 64 KB pages doubles at every migration event, following the sequence 1–1–2–4–8–

16 pages until the full 2 MB region has been promoted to HBM. Under a random access page migration pattern, a subtree is prefetched if more than half its leaf 64KB pages have already been migrated. 

Observation 1 

Hardware-assisted page migration operates at a 64 KB page granularity. The prefetching scheme is the traditional tree-based UVM prefetcher, and prefetching occurs within a single 2 MB virtual page. 

Determining the cacheline size. In this experiment, we vary the stride size to determine the cache line size of GPU memory accesses. Figure 5 shows access latencies for four different stride sizes. For stride sizes of 128, 64, and 32 bytes, the number of accesses required to trigger page migration remains constant at 256. However, when the stride size is reduced to 16 bytes, the number of accesses required to trigger page migration doubles. Furthermore, at a stride size of 16 bytes, the access latency alternates between that of CPU main memory (DDR) and GPU L1 cache, indicating that two consecutive 16-byte accesses fall within the same 32-byte cache line—with the first access fetching the line from DDR and the second being served from the L1 cache. Hardware Access Counter Circuit and Sharing Mecha-nism. As described in [4], [31], hardware counters in GH200 are implemented as a finite pool, where each counter is assigned to a specific address range, either virtual or physical, according to a replacement policy such as Least Recently Used (LRU) [31]. In this experiment, we probe the size of this counter pool. The experiment proceeds as follows: a process first accesses N − δ addresses to bring a target page’s counter close to the migration threshold. Using the default threshold of N = 256 and setting δ = 2 , only two additional accesses are needed to trigger hardware-assisted page migration for the target page. We then introduce M

distractor pages, each accessed X < N times, forcing the pool to assign counters to these new pages. After making 

X accesses to each of the M distractor pages, we perform the remaining δ accesses to the original target page and observe whether migration is triggered 2. Figure 6 shows (Single process) the probability of hardware-assisted page migration as a function of M , the number of distractor pages. The results indicate that the counter pool is exhausted at approximately 360–380 distractor pages. The lack of a sharp cutoff in the figure is attributable to a behavior we characterize and explain later: distinct 64KB pages residing within the same 2MB page are assigned the same counter, producing an apparent eviction effect that is, in reality, a consequence of using the same counter.

Deep dive into Hardware Counters. Virtual or Physi-cal addresses? While we have shown that hardware counters are shared across processes and MIG instances, this does not reveal how counters are assigned. Although Figure 6 shows that the counter pool saturates at approximately 380 entries, migrations still occasionally fail even beyond 400 distractor pages, suggesting a probabilistic assignment mechanism. This probabilistic behavior arises because counters may be assigned based on either virtual addresses (VA) or physical addresses (PA) [31], both of which are randomized across process invocations due to ASLR and OS memory allocation. To determine whether counter assignment is VA-based, we disable ASLR , ensuring that the process receives the same VA on every run. The experimental setup follows the previous experiment (single-process configuration) with this modification. If counters are assigned based on VA and the pool employs an LRU eviction policy, repeatedly running the process with fixed VAs should produce a deterministic eviction set of size E beyond which migration consistently fails. However, we observe entirely probabilistic behavior even with ASLR disabled, indicating that VA plays no role in hardware counter assignment. 

Observation 4 

Hardware access counters assignments are based on the physical addresses of pages.

Understanding mapping of pages to counters. Prior work has reverse-engineered the hash functions that map PAs to DRAM banks [32], [33], or to LLC cache sets [34], [35] under the assumption that these functions are linear (i.e., XOR-based). Adopting the same assumption, we search candidate XOR functions against the addresses we previ-ously identified as belonging to the same set. We use the functions to validate that our conflict sets are consistent. We then compute the null space of the resulting system, and as a final validation step, we verify that the recovered functions produce distinct set IDs across the 8 groups of PAs. Using the modified driver, we collect 8 groups comprising approximately 4,700 addresses in total and run the brute-force search. The procedure recovers exactly 3 independent functions in the null space, matching the expected number of selector bits ( 8 = 2 3). The recovered masks are shown in Figure 9. All three functions operate exclusively on bits 21 through 38, which implies that every 2 MB physically contiguous range is mapped to a single counter. 

Counter assignment vs. page migration. Because coun-ters are assigned at a 2 MB granularity, a discrepancy arises with the system page size, which also defines the default migration granularity of 64 KB. We design an experiment to determine how access to different 64 KB sub-regions within the same 2 MB range contributes to migration decisions. Across multiple trials, we observe that accesses to any 64 KB sub-region within a 2 MB range increment the same counter, and that migration is performed on the specific 64 KB region targeted by the most recent access. Observation 6 

Each access counter is owned by a 2 MB physical range, while migration is performed at the granularity of the most recently accessed 64 KB region within that range. 

Effect of Counter Values on the Eviction Policy. 

Throughout our experimentation, we assumed a Least Re-cently Used (LRU) eviction policy and held the counter values constant across all page accesses, ensuring that our measurements were not confounded by variations in the counter state. In this experiment, we relax that assumption to determine whether the counter values themselves influence the eviction decision. We first construct an eviction set of 

40 addresses, each residing in a distinct 2 MB region but mapping to the same counter set, following the methodology established in our earlier findings. We then execute a pair of nested loops: for a fixed number of accesses n to the target page, we sweep the number of accesses m to each page in the eviction set. To obtain noise-free measurements, we employ a second, independent eviction set to reset the counter values in the counter set between trials. Each trial first issues n accesses to the target page and subsequently issues m accesses to the eviction pages. Figure 10 reports the resulting behavior, where each line corresponds to a distinct counter value of the target (first) page. As we jointly vary n

and m, we observe that the counter values do in fact govern the eviction decision. When a counter must be evicted, the victim is the counter holding the smallest value, provided that value is below 7. Once all counter values reach or exceed 7, the counter value ceases to influence the decision and eviction reverts to LRU. The transition points visible in Figure 10, where each curve drops from an eviction set size of 41 back to 32 , shift rightward as the target page’s counter value increases, confirming that a higher counter value confers stronger residency until the saturation threshold of 7 is reached. In summary, the access counters prioritize eviction by counter value when that value is below 7, and otherwise fall back to LRU. 

Observation 7 

The eviction policy evicts the counter with the smallest value when that value is below 7, and reverts to LRU otherwise. 

Counter Persistence Across Process Launches. Having characterized the eviction policy within a single execution, we investigate whether hardware access counter state persists across process boundaries. Every one of these stages can add delay, and because they run strictly one after another, those delays simply pile up into the total time between an access and the data actually moving. We define migration delay ∆ as the latency from the Nth remote access to a target page, which triggers the hardware notification, to the start of data transfer over NVLink. Although NVLink contention is possible and potentially measurable [29], in practice, we find that the software pipeline stages described above dominate the transfer delay, particularly the shared work queue and lock contention. To isolate this software overhead, we measure migration delay in units of accesses rather than time, counting how many accesses to CPU memory are possible before the migration completes. The normal migration delay (with idle background) in units of system memory accesses is typically 20 to 30 .

## 4. Proof-of-Concept Attacks 

Throughout this section, we demonstrate how the findings from Section 3 can be leveraged to mount proof-of-concept attacks on the GH200 platform. Unless otherwise stated, all experiments are performed on a GH200 node from CloudLab [27] running NVIDIA driver version 590.48.01 and CUDA Toolkit 12.2. 

4.1. Attack Overview 

We implement two types of attacks for both covert and side channel: (1) a channel based on counter eviction sets (Fig. 12 A), and (2) a channel based on variation in the migration delay ∆ induced by a co-located process (Fig. 12 B). As demonstrated in §3, both leakage vectors are exploitable across two processes running on separate MIG instances. 

4.2. Attack Challenges 

Attacks share two core components: a probe phase and a 

migration detection phase . The critical parameter governing attack effectiveness is the sampling rate: a higher sampling rate increases the bit rate of the covert channel and enables the side channel to capture finer-grained patterns, ultimately leading to more accurate workload characterization and higher attack success rates. During the probe phase, the attacker performs N accesses to the target page, incrementing the hardware counter toward the migration threshold. In the detection phase, the attacker observes if the migration happens. 

Speeding up Probing Phase. To speed up migration triggering, we experiment with 2 methods: N parallel ac-cesses, or non-blocking loads. For parallel accesses, we can use N = 256 parallel threads and only a single thread checks the migration delay. With non-blocking loads, we refer to loading data and not waiting for the result, so the code continues issuing load instructions. We measure the sampling rate of each method over 90GB of memory: around 17000 samples per second with N-parallel accesses and around 15000 samples per second with the non-blocking load method. Hence, parallel accesses are more suitable for capturing more details. 

Bypassing UVM Prefetching. UVM operates on prefetch regions of 2 MB in the virtual address space. Within each region, page residency is tracked using a binary tree: the root represents the full 2 MB, and each level splits its parent in half, down to a leaf granularity of 64 KB. The driver uses this tree to detect locality; when one half of a node has been migrated, UVM treats the sibling half as likely to be accessed soon and prefetches it to GPU memory. This way, a few migrations in one part of a region trigger prefetching of the subsequent pages, reducing the number of migrations an attacker can exploit. To bypass this, we make the attacker operate at a 128 KB stride: it touches one 64 KB page, then skips the adjacent 64 KB page before touching the next. By leaving each touched page’s sibling leaf unoccupied, no node in the tree ever has one half fully resident, so prefetching is never triggered. This yields 16 migratable pages within a single 2 MB region, while keeping each migration limited to a 64 KB transfer with no prefetching triggered. 

Destructive Nature of Page Migration. Page migration is inherently destructive: once a page has been migrated to GPU memory, later accesses to it no longer fault, so the same page cannot trigger a migration again. PAGE404 handles this by moving to a fresh page after each migration. This step-forward approach also fits the UVM prefetching bypass discussed earlier: rather than advancing to the adjacent 64 KB page, the attacker moves to a new 128 KB-aligned region, so the next page is not covered by the prefetcher. 

4.3. Covert Channel Attacks 

Both covert channels exploit contention, but through distinct mechanisms, one in hardware counting, the other in interrupt servicing. The first channel is entirely embedded in hardware, leveraging an access-counter set shared across MIG partitions. The second resides in software, exploiting the kernel module shared between tenants: its interrupt-handling path becomes contended when concurrent processes raise migration interrupts. The following sections detail the challenges, implementation, and evaluation of each channel. 

4.3.1. Access Counter Set-based Covert Channel. Our reverse engineering results (§3) reveal that the access counter hardware comprises 256 access counters organized into 8 sets of 32 counters each, as shown in Fig. 8, governed by a Least Recently Used (LRU) eviction policy. In our set-based covert channel, the sender and receiver communicate through these access counter sets. Both parties construct eviction sets: the sender accesses a set to evict any counter allocated to the receiver’s process, while the receiver probes its target region to drive the counter value toward the migration threshold (N ) and observe whether the page is subsequently migrated. 

Challenges. As shown in Fig. 9, counter assignment is de-termined by three XOR hash functions operating on physical address bits 21–38, with each 2 MB physical memory region mapped to a single counter. This gives rise to two principal challenges. 

Address opacity. Neither the sender nor the receiver has knowledge of physical addresses [36], [37], [38]. Lacking this information, both parties are effectively blind, and assembling a known set of counters becomes a blind search. This diffi-culty is compounded by the migration mechanism itself: once a page is migrated from the CPU to the GPU, it is removed, preventing reliable collection of the corresponding addresses. While we employ a modified driver to reverse-engineer the counter structure, this is a controlled experimental setup and is not available to a real attacker. 

Synchronization. The sender and receiver must coordinate along two dimensions: (1) set agreement , ensuring both parties operate on the same counter set, and (2) timing alignment , ensuring transmitted and sampled bits are aligned across the two processes. 

Implementation. We now detail our approach to enabling reliable, counter-set-based covert channel communication by overcoming the aforementioned challenges. The pri-mary obstacle, the inability to discover exact physical addresses, cannot be resolved directly, as no architectural mechanism exposes this information to unprivileged par-ties. Our key observation is that the GH200 Linux kernel (linux-nvidia-64k ) enforces a default page size of 64 KB. This aligns perfectly with the hardware’s 64 KB migration granularity, guaranteeing coherence across all processing units in the system. Leveraging this, we look to huge pages: rather than standard 2 MB huge pages, the GH200 platform supports 512 MB huge pages. While a 512 MB huge page exposes physical address bits only up to bit 29 ( 512 MB = 2 29 ) rather than the necessary bits up to 38, we can exploit the behavior of the underlying hash functions. Specifically, these functions map each contiguous 512 MB region onto an identical collection of 2 MB-aligned addresses. As a result, all 256 × 2 MB addresses within this region predictably map to the complete set of 256 counters. Consequently, the sender and receiver can construct their eviction sets entirely within a single 512 MB huge page. Although this yields a functional eviction set, its absolute set ID remains opaque. Thus, the remaining challenge is to identify and synchronize corresponding sets across distinct 512 MB huge pages. The algorithms for the receiver and sender of the set-based covert channel are presented in Algorithms 1 and 2, respectively. The sender accesses its own eviction sets to transmit a ‘1’ and stays idle to transmit a ‘0’. A key constraint is that the sender cannot repeatedly access a single set across iterations: hammering one set, i.e., 32 counters, builds up access values and eventually migrates the sender’s own pages. While LRU should in principle prevent this, PAGE404 issues accesses to each distractor page in parallel, and because GPU threads execute non-deterministically, build-up can still occur. To avoid this, the PAGE404 sender accesses different eviction sets in an alternating fashion. The receiver attempts to trigger a migration by completing N accesses to its own pages in two steps. It first issues N − δ accesses, then waits for a duration D to allow the sender to signal, and finally completes the remaining δ accesses. After all accesses finish, the receiver waits for a migration: if a migration occurs, the transmitted bit is ‘0’; otherwise, it is ‘1’.

4.3.2. Migration Delay Variation. This covert-channel primitive leverages the fact that the hardware-assisted page migration delay can be varied based on the concurrent GPU context. The delay arises when a concurrent process delays the NVIDIA driver from serving a migration request issued by a process that has made enough accesses to a page to trigger promotion. This heightened delay can originate from memory allocation APIs, from the UVM driver servicing faults, or from OS-related stalls, as explained in Section 3. 

Implementation. This covert channel follows the set-based covert channel (Algorithms 1 and 2); indeed, the receiver is identical to the set-based case. The sender is modified to also migrate pages: it raises its access count to N

and does not wait for the migration to complete. To observe the channel, the receiver simply measures the migration delay, the interval from when migration is requested until it actually occurs. The sender encodes bits by creating contention: it delays the receiver’s migration by performing contending concurrent accesses. 

Evaluation and Results. The evaluation follows the same methodology as the eviction-set-based covert channel. This channel achieves approximately 8,100 bps with a 4% error rate. Its main drawback is that it relies purely on software-level contention, which makes it unstable across runs, primarily because the contention level is difficult to control. We measure the sensitivity of this covert channel, defined as the fraction of runs in which the message is transmitted successfully. This channel succeeds in roughly half of all runs. Thus, while it is convenient to implement, it suffers from inherent instability.

4.4.6. Input-Output Prompt Length Estimation. LLM inference proceeds in two phases. In the prefill phase, the model processes the entire input prompt in a single forward pass, initializing the key-value (KV) cache. In the decoding phase, it generates output tokens one at a time, each reusing the cached context, until a stopping criterion is met. The phases have different bottlenecks: prefill is compute-bound, performing large parallel matrix multiplications, while decoding is memory-bandwidth-bound, repeatedly reading the weights and growing KV cache to emit one token per step. As a result, prefill runs as a few long kernels, whereas decoding issues many short ones and dominates total latency, since each additional output token adds another serial step. 4.4.8. Future Finer-Grained Attacks. While PAGE404 primarily demonstrates coarse-grained fingerprinting, the vulnerability can be extended to fine-grained access metering due to an architectural granularity mismatch and persistent tracking state. Because page migration counters are tracked per 2 MB region while physical pages are allocated at 64 KB boundaries, distinct pages within the same aligned 2 MB range aggregate accesses to a single shared counter that persists across execution boundaries. An adversary can exploit this behavior by accessing a co-located 64 KB page to prime the shared counter close to the migration threshold, allowing the victim to execute, and subsequently probing their own page in small increments until migration is observed. By measuring the access delta required to trigger migration, the attacker transforms a binary access-detection channel into a quantitative side channel that can infer the victim’s precise access count within a 5% margin of error. 5. Potential Mitigations 

The root of the vulnerability is the shared counter hardware structure, and the shared access to the driver code. This sharing enables contention and causes leakage through observable delays. One approach for mitigation is to carry the MIG philosophy to ensure isolation even through these shared components in software and hardware. With respect to hardware isolation, this requires partitioning the counters into groups of counters dedicated to each MIG partition rather than sharing the counters across them. To close the contention through the driver, performance isolation of the driver, again perhaps by MIG partition, can mitigate the observable delays. The vGPU abstraction [58] provides driver isolation on MIG-backed versions, but NVIDIA does not yet support ARM platforms. Moreover, since the guest drivers in each instance are multiplexed by the host vGPU manager, the leakage may shift to observable delays through the vGPU manager; whether such delays are observable requires further confirmation through experimentation. 

## 6. Related Work 

Intra-GPU leakage. A large body of research targets 

intra-GPU leakage, exploiting shared microarchitectural resources such as caches [14], [59], the memory bus [15], functional units and on-chip networks [60], [61], TLB state [16], and DRAM-level effects [62], [63] to leak infor-mation between co-located GPU processes. On the defense side, GPU performance counters have been used to detect and mitigate contention-based channels [64] and to validate kernel execution integrity [65]. However, both defenses rely on GPU performance counters, which MIG partitions per instance, making them unlikely to detect an attacker residing in a separate MIG instance. Extending such defenses to operate at the host level and monitor activity across MIG instances could enable detection. 

Cross-domain (CPU–GPU) leakage. A complementary line of work examines cross-domain leakage between the CPU and GPU, exploiting resources shared across the heterogeneous boundary such as the PCIe bus and shared memory subsystems [66], [67]. 

Multi-GPU interconnect leakage. Attacks have also been extended to multi-GPU settings, where distributed work-loads across multiple devices create observable contention on inter-GPU interconnects [68]. Zhang et al. [69] showed that NVLink interconnect contention can be used to infer inter-device communication patterns across GPUs. However, this approach targets aggregate communication behavior and relies on bandwidth saturation — a condition that is increasingly difficult to achieve on modern high-bandwidth links such as the GH200’s 900 GB/s NVLink-C2C [29]. 

Rowhammer attacks on GPUs. Recent work has shown that Rowhammer is a practical threat to GPU memories. GPUHammer [70] demonstrated the first Rowhammer attacks on GDDR memory in GPUs and showed that the resulting bit flips can degrade the accuracy of machine learning models. Follow-up work turned these bit flips into stronger exploits: GPUBreach [71] and GeForge [72] corrupt GPU page tables to escalate privileges, and GDDRHammer [73] mounts cross-component attacks originating from the GPU. Most recently, GPUThor [74] uses non-uniform hammering patterns to induce exploitable bit flips even on ECC-protected GPUs. 

MIG isolation. Prior work has examined the isolation boundary between MIG instances, which NVIDIA advertises as complete and strongly hardware-enforced [75], [76]. Zhang et al. [18] show that the last-level TLB is shared, while recent work by Gu et al. [26] shows that some leakage remains across cache partitions in the presence of memory-barrier operations. Our work demonstrates a novel form of leakage that also compromises MIG isolation for this emerging class of tightly integrated architectures. It is important to identify and characterize this mode of leakage to both inform interventions and guide the design of future tightly integrated systems. Miao et al. [77] extend MIG-bypassing channels into the GPU “uncore” (DRAM, host–GPU and inter-GPU links), without requiring root privileges. More recently, MIGraine [78] demonstrates page-fault–based leakage across isolated MIG instances, even when the instances are provisioned as separate vGPUs. 

## 7. Conclusion 

In this paper, we present PAGE404, an analysis of the emerging Grace Hopper heterogeneous computing platform and its hardware-backed page migration scheme. We reveal that the access-counter hardware structure is shared across MIG instances, violating MIG’s security guarantees, and we further identify a migration-delay leakage arising from the driver’s interrupt-handling pipeline. Building on these findings, PAGE404 demonstrates a range of proof-of-concept covert- and side-channel attacks. The eviction-based covert channel achieves 8500 bps at a 1.5% error rate, rising to 15500 bps at roughly 5% error with two eviction sets, while the eviction-based side channel distinguishes among 10 CUDA kernels with 94% accuracy when they use system-allocated memory. The migration-delay leakage enables a covert channel of 8100 bps at a 4% error rate and, across several side-channel attacks, distinguishes CPU, CUDA, and LLM workloads with around or above 90% accuracy, estimating an LLM’s processed token length with a mean absolute error of 4.6 tokens on average. These results show that PAGE404 attains a high attack success rate and underscore the need for more secure architectures in multi-tenant environments.

## Appendix D. Meta-Review 

The following meta-review was prepared by the program committee for the 2027 IEEE Symposium on Security and Privacy (S&P) as part of the review process as detailed in the call for papers. 

D.1. Summary 

This paper details a newly discovered side channel in NVIDIA Grace Hopper (GH200), targeting its hardware-assisted page migration mechanism. Through reverse en-gineering, the authors demonstrate that the access-counter hardware structure, which tracks memory accesses to trigger page migrations from CPU to GPU memory, is inherently shared across Multi-Instance GPU (MIG) boundaries, which the paper exploits to build a covert channel, perform LLM fingerprinting, and measure the lengths of LLM inputs and outputs. 

D.2. Scientific Contributions 

1) Identifies an Impactful Vulnerability 2) Provides a Valuable Step Forward in an Established Field 

D.3. Reasons for Acceptance 

This seems to be the first security analysis of Nvidia’s Grace Hopper GPU and its MIG isolation primitive. The reviewers particularly appreciated the comprehensive and in-depth study of the hardware-assisted page migration in GH200 and exposing the security implications of sharing the underlying microarchitectural structure across isolated instances. 

D.4. Noteworthy Concerns 

1) Impact of the produced attacks: While there is value in the reverse engineering aspects of this work, showing stronger attacks, such as recovery of input or output of LLMs, or using the recovered information as part of prompt injection attacks, would have made the paper stronger. 2) Evaluation of the produced attacks: While the paper shows generalization across different runtime environments, it remains unclear if the attacks generalize to different system architectures.
