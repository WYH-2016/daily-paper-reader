# HardEval: An Execution-Verified Benchmark for AI-Driven Security Hardening and Compliance Remediation 

Manohar Vellala ∗† , Soumya Banerjee ∗‡ , Sandip Roy ‡, Ross Gore ‡, Sachin Shetty ∗∗Center for Secure & Intelligent Critical Systems, †Department of Computer Science, ‡School of Cybersecurity Old Dominion University, Virginia, USA 

{mvell001, s1banerj, sroy, rgore, sshetty }@odu.edu 

Abstract —Implementing Security Technical Implementation Guide (STIG) controls remains a demanding operating-system administration task. Each natural-language security requirement must be translated into a precise and persistent configuration change. These changes span Secure Shell (SSH) configuration, authentication policy, audit rules, and kernel parameters. Exist-ing benchmarks do not measure whether a model can perform this task on a live system. Code benchmarks evaluate isolated pro-grams without persistent system state, while agent benchmarks largely focus on applications rather than operating-system con-figuration. In this paper, we introduce HardEval, an execution-verified benchmark for evaluating language-model-assisted secu-rity hardening. HardEval is built from Red Hat Enterprise Linux 8 STIG controls that fail on an unhardened baseline system. Expert-written reference remediations and Open Vulnerability and Assessment Language (OVAL) checks serve as hidden ground truth for grading; they are never shown to the model, and each task states only the required security outcome while withholding the implementation. The model produces a Bash script, which is executed on a live virtual machine and graded from fail to pass using the corresponding OpenSCAP/OVAL compliance check. Evaluation of fourteen frontier and open-weight configurations reveals large and uneven capability differences across security domains. A recurring failure mode is plausible security code that does not satisfy the exact compliance condition. For four open-weight configurations, multi-run Wilson confidence intervals preserve the observed ordering. HardEval is publicly available. 

Index Terms —STIG compliance, OS hardening, LLM evalua-tion, Security benchmarking, Automated compliance, Gen-AI for cybersecurity. 

I. I NTRODUCTION 

Operating-system misconfigurations remain a persistent source of cyber risk. In Department of Defense (DoD) and regulated enterprise environments, this risk is managed through hardening frameworks such as the Defense Informa-tion Systems Agency (DISA) Security Technical Implementa-tion Guides (STIGs). In practice, STIG compliance requires administrators to translate hundreds of natural-language secu-rity requirements into precise, durable configuration changes spanning kernel parameters, authentication policy, audit rules, SSH, services, package state, and reboot-persistent system state. Tools such as OpenSCAP, ComplianceAsCode, Ansi-ble Lockdown, and commercial products can automate scan-

ning and apply pre-authored remediations, but they remain constrained by static rule content and manually maintained corrective actions. When no suitable fix exists, when con-figurations deviate from expected templates, or when policy guidance evolves, the burden falls back to human analysts and administrators. Large language models (LLMs) suggest a more adaptive alternative to static remediation playbooks: instead of selecting from prewritten remediations, a model may generate remedi-ation code directly from a natural-language security require-ment. However, end-to-end remediation systems can conflate model capability with retrieval context, post-processing, and orchestration. HardEval instead isolates the underlying code-generation capability: whether a model can produce security-hardening code that makes a live operating system compliant in the exact way an external scanner verifies. An isolated measurement also serves model selection: before investing in fine-tuning or retrieval pipelines, practitioners, especially those who must self-host, need a way to identify which base model can already bring a system to scanner-verified compliance. Existing evaluation suites are poorly matched to this ques-tion: execution-based code benchmarks score isolated snippets with no persistent system state, repository- and agent-grounded benchmarks target application code rather than OS configura-tion, and security-oriented evaluations leave OS hardening un-measured; even the most closely related system, SHIELDS [1], evaluates an end-to-end remediation loop rather than isolating the code-generation capability it requires (Section II). This paper addresses that gap with HardEval , a function-ally verified benchmark for LLM-generated Linux security-hardening code on the RHEL 8 family. HardEval is built from failed, automatable DISA STIG controls and expert-maintained ComplianceAsCode security content, including authoritative OVAL checks and reference remediation logic. Each task is presented to the model as an implementation-withheld natural-language security requirement that states the hardening objective and rationale while withholding the exact mechanism. The model must generate a Bash remediation script, which is then executed on a fresh RHEL-compatible virtual machine and scored by re-running the corresponding OpenSCAP/OVAL rule. The contributions of this paper are as follows:  

> •

We formalize a new evaluation problem, whether LLMs can generate remediation code that brings live op-erating systems into compliance under authoritative OpenSCAP/OVAL checks, and introduce HardEval , a reusable execution-based benchmark built from DISA STIG failures and ComplianceAsCode content, with implementation-withheld prompts and fail-to-pass grad-ing on throwaway virtual machines.  

> •

We provide a baseline study spanning fourteen model configurations, from frontier closed models to 4-bit quan-tized open weights, showing that frontier models solve many hardening tasks but fail on scanner-sensitive details invisible to text-based evaluation.  

> •

We validate the benchmark’s robustness with a cross-author study (GPT-4o re-authoring the prompts) and a zero-code port to Ubuntu 24.04, showing that the model ordering is stable across prompt authors and that the construction pipeline is not tied to a single operating system. II. R ELATED WORK 

Classical code-generation benchmarks such as HumanEval [2] and MBPP [3] evaluate Python function synthesis from docstrings via unit-test execution, and APPS [4] extends this to 10,000 coding-interview problems. MultiPL-E [5] adapts these suites to 18 programming languages, BigCodeBench [6] targets complex tasks requiring diverse library calls, and LiveCodeBench [7] draws on recent contest problems for contamination-resistant evaluation. All of these are execution-based, but they evaluate isolated snippets with no persistent system state and no security or OS-configuration concerns. A second line of work grounds evaluation in realis-tic environments. SWE-bench [8] requires models to edit real repositories so that failing tests pass, a protocol it calls fail-to-pass. WebArena [9], OSWorld [10], and Agent-Bench [11] evaluate agents on end-to-end web, desktop, and simulated-environment tasks. None of these benchmarks test the generation of OS-hardening shell scripts against domain-specific compliance checks, and many permit agent-tool loops that could trivially reveal the fix. HardEval instead uses implementation-withheld prompts, so the exact remediation is never exposed to the model. Security-focused evaluations emphasize either insecure-code avoidance or offensive capability. CyberSecEval 3 [12] measures cyber risks and capabilities such as exploit gener-ation and phishing. LLMSecEval [13] provides 150 prompts describing CWE-vulnerable code. HardSecBench [14] evalu-ates security-aware hardware and firmware code against exe-cutable oracles. Closest to our work, SHIELDS [1] remediates STIG findings through an iterative multi-agent loop driven by scanner feedback, resolving up to 73% of findings. SHIELDS evaluates an end-to-end agentic system, whereas HardEval is a reusable benchmark of single-shot remediation-code gen-eration (no agent orchestration, no scanner feedback) under fail-to-pass OpenSCAP scoring. Table I situates HardEval against representative benchmarks along the dimensions that matter for OS hardening. To our knowledge, HardEval is the first benchmark whose target artifact is OS-hardening Bash graded by execution and compliance-scanner verification on live virtual machines. III. T HE HARD EVAL BENCHMARK 

In this section, we describe the source material and dataset construction, the implementation-withheld prompt authoring process, the execution-based evaluation protocol, and the mod-els and experimental setup. Together, they form the pipeline that isolates hardening capability from retrieval, orchestration, and leakage confounds. 

A. Source Material and Dataset Construction 

HardEval is bootstrapped from a single source of truth. This source is an OpenSCAP scan of an unhardened RHEL 8 host executed under the DISA STIG profile using SCAP Security Guide 0.1.81 from the ComplianceAsCode/content project. This scan produces a fully rendered XCCDF TestResult 

document that provides, for each failing rule, three things: (i) the rule title, description, and rationale authored by Red Hat security engineers; (ii) the reference Bash remediation script, which constitutes the hidden answer key; and (iii) the OVAL check identifier, which is the grading oracle. Rule identifiers are cross-mapped to official DISA STIG IDs, with NIST 800-53, SRG, CCE, and CCI references retained as metadata. Dataset construction proceeds in two decoupled stages. An 

extraction stage parses the scan XML offline into reference data and grading metadata, and a generation stage authors the implementation-withheld task prompts (Section III-B). From the 233 rules that fail the initial scan, we select the 215 that carry a reference Bash remediation. The 200 of these that are automatable constitute the graded tasks (Sec-tion IV-A). A fixed cross-model manifest of 151 verified-applicable rules (137 excluding SSH) is graded identically for every model (Section IV-A). This manifest omits reboot-persistent kernel rules, hazardous access-severing rules, and GUI/hardware-dependent controls that cannot be evaluated to completion on a single live VM. Each item is a tuple 

(pi, r i, o i, stig id , sev , reboot ), consisting of the prompt, the hidden reference remediation, the OVAL check identifier, and the STIG ID, severity, and reboot-persistence flags. The prompt pi is the only element exposed to the model. ri and oi

are withheld at inference time and used only during grading. 

B. Implementation-Withheld Prompt Authoring 

Each prompt pi is authored by a generative model (Claude Opus 4.8, queried through the Batch API) conditioned on the rule’s title, severity, rationale, and description text, but never on the reference remediation script. ComplianceAs-Code descriptions frequently embed implementation specifics, for example “Set ClientAliveInterval to 600 in 

/etc/ssh/sshd_config .” Because of this, the authoring model operates under a structured system prompt, calibrated with few-shot exemplars and constrained to a JSON output schema, that enforces four requirements: 1) State the objective and rationale in plain English. The required end state must be precise enough that the OVAL check can grade it against one oracle-accepted outcome, and the threat or rationale must ground the objective. 2) Omit the implementation mechanism. Exact paths, directive and parameter names, sysctl keys, shell commands, and literal configuration lines are abstracted away; naming the affected component conceptually (“the SSH server”) is permitted, naming the knob, path, or command is not. Required target values or thresholds 

(“a minimum length of 15 characters”) are preserved. 3) Preserve correctness constraints that are mechanism-independent, including idempotency, persistence across reboots, and scope, and append a fixed output-format instruction requiring a single self-contained Bash script in one fenced code block. 4) Run a programmatic lexical-leakage check. A whole-word, case-insensitive scan compares each prompt against mechanism tokens extracted from the hidden reference script (paths, sysctl -style keys, directive names); of 215 prompts, 2 were flagged and both confirmed benign. The generator system prompt, exemplars, and output-format instruction are in the repository. Fig. 2 shows the prompt for 

accounts_password_pam_minlen (RHEL-08-020230): the required length is disclosed while the target file, directive, and enforcement mechanism are withheld. A model that knows Linux hardening can solve this; one that merely transcribes reference scripts cannot, because the script is never shown. 

C. Evaluation Protocol 

HardEval employs a strict single-shot, execution-based grading protocol: 1) The model receives only the implementation-withheld prompt and emits one Bash script (no retries, no tool access, no live system inspection). 2) Each configuration is graded on its own throwaway RHEL-8-compatible virtual machine (AlmaLinux 8), restored to the identical known-failing baseline, with no other model’s code ever touching it. Because of this, there is no reward for plausible-looking but non-compliant code and no string-similarity confound. The graded quantity is the end-state compliance of the machine hardened by a configuration’s scripts: scripts persist on the VM across a run, so HardEval measures cumulative batch hardening; the aggregate is exact, while credit for an individual rule is not always attributable to the script written for its task. The harness assumes non-adversarial models (the scoring logic and hidden references reside outside the evaluated machine, and a scan of all 6,494 generated scripts found no reference to the scanner, the SCAP datastream, or any grading artifact); a script that instead disables an entire scoring subsystem surfaces as an aggregate anomaly and its run is excluded as invalid (Section IV-D). 

a) Scope: compliance-oracle satisfaction, not security in the broad sense: HardEval’s unit of measurement is deliber-ately narrow: it measures whether LLM-generated remediation 

satisfies the DISA STIG compliance oracle , not whether the system is “more secure” in an unrestricted sense. A script may improve security through an alternative mechanism yet still fail the probe (Section IV-E), and a target-rule pass by itself does not certify the absence of collateral effects elsewhere on the host. We adopt this framing because it keeps grading objective and reproducible: there is exactly one adjudicator, and it is external to both the model and the authors, and because it is operationally faithful: in accredited DoD and enterprise environments, compliance is adjudicated by precisely these scanner checks, so oracle satisfaction is the deployable quantity. 

D. Models and Experimental Setup 

We evaluate fourteen model configurations. Seven are frontier closed models, queried through their official APIs: 

Claude Opus 4.8 , Claude Opus 4.7 , Claude Opus 4.5 ,

Claude Sonnet 5 , Claude Sonnet 4.5 , Claude Haiku 4.5 ,and GPT-4o . Seven are open-weight, code-specialized config-urations: DeepSeek-Coder-33B-Instruct , CodeLlama-34B-Instruct , CodeLlama-7B-Instruct , Qwen2.5-Coder-14B-Instruct , Qwen2.5-Coder-7B-Instruct , and GLM-4-9B in both FP16 and 4-bit form, the pair included to measure the cost of aggressive quantization. The Qwen models were served via vLLM on a single NVIDIA A100 GPU; the remaining open-weight models via Ollama at FP16, with the 4-bit GLM-4-9B using Ollama’s default Q4_K_M quan-tization. Every configuration received the same prompts and decoded greedily at temperature 0, and every script was scored, separately from inference, by the same model-agnostic grader on an identical AlmaLinux 8 host (OpenSCAP 1.3.14, SCAP Security Guide 0.1.81, stig profile): it ingests a predictions_<model>.jsonl file and extracts the script from a ‘‘‘bash fence, any fenced block, or raw text as fallback, so no model is penalized for output formatting. The complete construction pipeline described in this section is implemented in benchmark/build_dataset.py in the “code and data supplimentary” folder. IV. E VALUATION AND RESULTS 

We report cross-model HardEval results (Section IV-A), run-to-run variance (Section IV-B), cross-author prompt val-idation and cross-OS generalizability (Sections IV-C–IV-D), and failure analysis (Section IV-E). 

A. Cross-Model HardEval Results 

Table II reports HardEval results across all fourteen model configurations, broken down by the principal evaluation buck-ets: server configuration plus kernel hardening, audit rules, the combined server-safe aggregate (the headline metric), SSH configuration, and all verified-applicable rules. Invalid, empty, or unscored outputs are counted as failures, and every configuration shares identical fixed denominators (137 server-safe, 151 verified-applicable). The results reveal four findings. 

a) Frontier-scale models dominate, but scale is only a coarse predictor: On the fixed cross-model manifest, Claude Opus 4.7 leads with 81.0% verified success on the combined server-safe bucket, with Claude Opus 4.8 at 77.4%, a single-run gap we do not read as an ordering between the two (Section IV-B). The seven frontier models, whose undisclosed parameter counts are generally understood to be far larger than the 7B–34B open-weight models evaluated here, occupy the top seven positions (81.0% down to 51.1% for Haiku 4.5, with GPT-4o at 65.7% among them). The strongest open-weight configuration, DeepSeek-Coder-33B at 35.8%, trails the weakest frontier model by more than fifteen points, and code specialization alone does not close the gap. Scale sepa-rates the tiers but does not order models within them, as the next finding shows. 

b) Within the evaluated set, parameter count is a weak predictor of hardening ability: CodeLlama-34B (21.2%) trails the far smaller Qwen2.5-Coder-14B (33.6%), and DeepSeek-Coder-33B (35.8%) exceeds it only narrowly, de-spite both carrying more than twice the parameters. The Qwen-14B/CodeLlama-34B gap survives repeated sampling, since their pooled multi-run confidence intervals (Section IV-B) do not overlap. Training recency and data composition appear to dominate raw scale here, though model family, instruction tuning, and decoding remain uncontrolled confounders across families. Release recency within a family is likewise not a reliable predictor: Claude Opus 4.8 does not outscore Opus 4.7 on a single run, and Sonnet 5 trails the older Sonnet 4.5 by more than sixteen points. 

c) Capability is domain-structured: audit rules discrim-inate most sharply: Performance on auditd rule construc-tion separates models more sharply than any other bucket: Qwen 7B achieves 1.7% on audit rules versus 24.1% on server configuration, GLM-4-9B manages 3.4% in FP16 and 0% at 4-bit, and even GPT-4o lags (62.1% vs. 70.7% for Claude Opus 4.8 and 81.0% for Claude Sonnet 4.5). Nor does capability transfer uniformly across domains: GPT-4o’s SSH score (71.4%) matches Claude Opus 4.8 (though SSH carries a measurement-channel confound; Sections IV-E and V), Qwen-14B’s SSH success (50.0%) doubles its own audit-rule rate, and Sonnet 4.5 posts the highest audit-rule score of any model (81.0%) while ranking only third on the combined metric. These domain-level inversions would be invisible to an aggregate compliance score. 

d) No detectable quantization cost for GLM-4-9B at this sample size: Under Ollama’s Q4_K_M 4-bit quantization, GLM-4-9B’s aggregate accuracy barely moves, from 13.1% to 12.4% single-run, and the multi-run study confirms it. Pooled estimates of 14.1% (FP16) and 12.2% (4-bit) carry overlapping confidence intervals (Section IV-B). The single-run audit-rule score is very low in both cases, 3.4% for FP16 and 0.0% for 4-bit quantization. The pooled multi-run audit estimates, 1.3% and 0.4%, overlap, indicating a family-level weakness on 

auditd grammar rather than a quantization-specific collapse. 

B. Run-to-Run Variance 

A single greedy generation is one sample. For four open-weight configurations we therefore pooled the temperature-0 run with three independent seeded runs (temperature 0.2) and computed 95% Wilson score intervals over the combined server-safe metric, treating each (rule, run) pair as a Bernoulli trial ( 4×137 = 548 trials per model; Fig. 3). We read the inter-vals descriptively, as a sensitivity analysis rather than formal inference: the pool mixes two decoding settings, and trials on the same rule are correlated across runs, so the intervals are, if anything, slightly narrow. Every pooled estimate preserves the single-run ranking, and greedy runs read mildly optimistic: Qwen-14B’s greedy run (33.6%) lies just outside its pooled interval (29.6%, 95% CI 25.9–33.5%), while the other three greedy runs fall inside theirs. The Qwen-14B and CodeLlama-34B intervals remain separated, consistent with the parameter-count finding, whereas the two GLM-4-9B precisions overlap on both the combined metric and audit rules (1.3% vs. 0.4% pooled), indicating no detectable quantization penalty at this sample size.

E. Failure Analysis 

HardEval’s rule-level verdicts make failures directly in-spectable: a rule that ends the run failing was fixed by no script in the batch. On the Fig. 2 task, for ex-ample, Claude Opus 4.8, GPT-4o, and Qwen2.5-Coder-14B all locate /etc/security/pwquality.conf and pass, while Qwen2.5-Coder-7B writes PASS_MIN_LEN to 

/etc/login.defs , a valid-looking legacy control the OVAL probe does not inspect, and fails. Across all models, we observed three recurring failure patterns. Fig. 4 summarizes these. Their shared structure is precisely the gap — between plausible hardening code and 

verifiably compliant configuration — that HardEval is de-signed to measure (see the scope discussion in Section III-C), and that no text-similarity or LLM-judge evaluation can detect. Per-domain failure rates, derivable from Table II (per-rule results for all fourteen configurations are in the repos-itory), show three patterns. First, audit-rule construction is the sharpest discriminator (Section IV-A): auditd rule syntax is a scarce skill concentrated in frontier models. Second, SSH results require separate interpretation because aggressive SSH hardening can sever the grading channel itself (Section V); the inversion suggested by the earlier extended run did not reproduce in the manifest re-run, where GPT-4o and Claude Opus 4.8 both score 10/14. Third, package and service rules show the shallowest gradient, likely because common dnf 

and systemctl idioms are well represented in pretraining corpora. V. C ONCLUSION AND LIMITATIONS 

We introduced HardEval, a reusable benchmark of failed, automatable RHEL-8 DISA STIG controls, graded on a fixed 151-rule cross-model manifest (137 excluding SSH), with implementation-withheld natural-language prompts and Open-SCAP/OVAL fail-to-pass grading on real virtual machines. Across fourteen configurations, combined server-safe scores span 81.0% (Claude Opus 4.7) down to 12.4% (4-bit GLM-4-9B), with every frontier model above every open-weight one (Table II). Per-domain reporting reveals what the aggregates hide: audit-rule construction is the sharpest discriminator between models; parameter count and release recency are weak predic-tors within tiers (Section IV-B); four-bit quantization shows no detectable penalty for GLM-4-9B; and the recurring failures are value, mechanism, and audit-key mismatches rather than broken shell syntax. Two robustness checks support these findings: a GPT-4o-authored prompt set lowers scores for both solvers rather than favoring its author, and a zero-code port to Ubuntu 24.04 reproduces the pipeline on the 88 shared rules. These results carry scope constraints: all graded tasks derive from RHEL 8 under the DISA STIG profile and cover a cu-rated, automatable subset of controls; the Ubuntu port demon-strates methodological portability, but broader generalization to RHEL 9, Windows, or other profiles is unshown. Ten of the fourteen configurations were scored with a single greedy run, and the variance study excludes the closed models. SSH scores are conservative lower bounds because the harness grades over the same SSH channel the scripts harden, which is why that bucket is excluded from the headline metric (Section IV-E). Prompts were authored by a single model (addressed by the cross-author study, Section IV-C), and training-data contami-nation from public STIG content cannot be ruled out. Finally, grading measures compliance-oracle satisfaction rather than security in the broad sense (Section III-C). Taken together, these results establish scanner-verified com-pliance remediation as a first-class evaluation axis for language models.
