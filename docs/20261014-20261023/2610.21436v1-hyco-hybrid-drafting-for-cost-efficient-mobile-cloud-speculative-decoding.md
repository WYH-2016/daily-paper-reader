## 摘要
设备-云协同推测解码可降低服务器计算开销，但利用小型语言模型（SLM）在移动神经处理单元（NPU）上反复运行以构建深层草稿树，会带来显著的设备端开销。本文提出HyCo，其将服务器模型原生的多令牌预测（MTP）头分配至设备端执行，并赋予其固定深度；而其余替代分支则仅需一次SLM前向传递。服务器不再执行MTP头的串行计算步骤，而是直接返回该头所需的状态隐表示、输入嵌入以及键值（key-value）缓存项。通过量化、受限词表及1K词元窗口等技术，使两类草稿生成器均适配于移动NPU。此外，引入ε阈值规则，在不严格保持验证器采样分布的前提下进一步放宽约束。在搭载Galaxy S26 Ultra手机、经LTE/5G网络进行单客户端测试时，HyCo相较于纯服务端MTP自推测方法，在Spec-Bench基准上将每输出词元所需的服务器GPU时间降低了38.6%，在32K词元摘要任务上降低了29.2%。在采用相同接受规则的情况下，三轮Spec-Bench测试表明，HyCo相较纯SLM草稿器可额外提升9.0个百分点的节省率，并实现1.9倍的输出交付速度。HyCo与Cloud+MTP方案相比，人工评测得分高0.2分（成对95%置信区间：-0.9至+1.3）；探索性翻译任务更倾向采用SpecEdge-ε变体。若不启用上述松弛机制，HyCo在两个数据集上的精确版本分别节省27.7%和11.9%的服务器GPU时间。

## Abstract
Device-cloud speculative decoding reduces server computation, but growing a deep draft tree with a small language model (SLM) requires repeated passes on a mobile neural processing unit (NPU). We present HyCo, which assigns depth to the server model's native multi-token prediction (MTP) head, executed on the device, and alternative branches to one SLM pass. The server returns the hidden state, input embedding, and key-value entries needed by the head instead of executing its sequential steps. Quantization, a restricted vocabulary, and a 1K-token window fit both drafters to the NPU. An ε-threshold rule additionally relaxes exact preservation of the verifier's sampling distribution. In single-client runs with a Galaxy S26 Ultra over LTE/5G, HyCo reduces server GPU time per output token relative to server-side MTP self-speculation by 38.6% on Spec-Bench and 29.2% on 32K-token summarization. With the same acceptance rule, three Spec-Bench runs per system show 9.0 percentage points more saving and 1.9x delivery speed than an SLM-only drafter. HyCo differs from Cloud+MTP by +0.2 judge-score points (paired 95% CI: -0.9 to +1.3); exploratory translation favors SpecEdge-ε. Without relaxation, HyCo exact saves 27.7% and 11.9% on the two datasets.

# HyCo 论文中文详细总结

## 1. 核心问题与整体含义（研究动机和背景）

- **核心问题**：在移动–云协同推测解码（device–cloud speculative decoding）范式中，传统方案（如 SpecEdge）依赖手机端小型语言模型（SLM）**多次前向传播**构建深层 draft 树（如 4 层需 4 次 SLM 推理），导致 NPU 端延迟高、能耗大、用户体验差；而纯服务端 MTP 自推测（Cloud+MTP）虽高效，却未利用端侧算力潜力，且无法缓解网络往返瓶颈。
- **根本矛盾**：深度（depth）与分支（alternatives）难以兼顾——SLM 单次推理只能生成线性链或浅树，深树需串行展开；MTP 头天然支持多步预测，但原生部署在服务器，其计算被重复执行（每轮验证后重跑 K 步）。
- **研究目标**：在**严格受限的移动 NPU 资源**（整型计算图、有限共享内存、编译上下文长度）下，设计一种混合草稿机制，在不显著牺牲输出质量前提下，**最大化降低服务器 GPU 时间**，同时**保障用户端交付速度不低于纯 SLM 本地生成**。

## 2. 方法论：核心思想与关键技术细节

- **核心思想**：**分工协同的 Hybrid Drafting**——将 draft 树的“深度”交给服务器模型原生 MTP 头（卸载至设备执行），将“宽度”（替代分支）交给轻量 SLM（单次前向生成），二者共同构成 hybrid draft tree。
  
- **关键技术细节**：
  - **MTP Drafter（设备端）**：  
    - 将服务器 LLM 的原生 MTP 头（如 Gemma-4 的 4-token 预测头）通过量化-aware 训练（QAT）部署到 Galaxy S26 Ultra 的 Hexagon NPU 上；  
    - 每轮接收服务器返回的 *输入嵌入 e(xₜ₊₁)*、*上一隐藏态 hₜ*、*两层 KV 缓存*（共约 5.6 KB/轮 + 6.1 KB/token），执行 K=4 步 top-1 预测，生成主链 y₁:y₄；  
    - 在深度 1–2 处额外保留 runner-up sibling（次优 token），增强鲁棒性。
  - **SLM Drafter（设备端）**：  
    - 使用 Gemma-4 E2B（2.3B）QAT 检查点，**仅执行一次前向传播**，为 root 和所有 planted node（主链 + siblings）并行生成最多 32 个候选子 token；  
    - 不再逐层展开，彻底规避多轮 SLM 推理开销。
  - **Hybrid Draft Tree 构建**：  
    - 基于路径概率加权打分：主链节点得分 = *d × ln(0.66)*（d 为深度，0.66 为实测链接受率几何均值）；sibling 得分 = *2 × ln(0.66)*；SLM 候选得分 = *ln q(c|v) + ln(0.66)*；  
    - 按分截断至 B=32 节点，发送 token ID + parent index（2.2 KB/轮）。
  - **服务器验证与 ε-threshold 接受**：  
    - 服务器用 tree attention mask 一次性验证整棵树；  
    - **ε-threshold 规则**：对节点 v 的候选 c，若 `˜p(c|v) ≥ ε`（˜p 为经 temperature/top-k/top-p 后的采样分布），即接受（不限于 verifier 实际采样结果）；默认 ε=0.005；  
    - 此规则提升 MAT（平均接受 token 数），但属**有损接受（lossy）**，改变输出分布。
  - **NPU 友好适配**：  
    - **量化**：MTP 头 4-bit QAT 权重 + 16-bit fixed-point 激活；SLM 使用 graph surgery + 2/4-bit embedding lookup table；  
    - **受限词表**：从 UltraChat 训练集统计高频 token，构建 86,089 词元 keep set（覆盖 97%+ bonus token），大幅降低输出层计算开销；  
    - **1K 上下文窗口**：SLM 与 MTP Drafter 均只读取最后 1024 tokens，KV cache 采用 ring buffer 实现。

## 3. 实验设计

- **数据集与场景**：  
  - **Spec-Bench (SB-480)**：480 道综合问答题（含 MT-bench、RAG、Math、Translation 等），输出上限 1024 tokens；用于主效率与质量评估。  
  - **∞Bench Sum（32K）**：HELMET 数据集中 50 部英文小说（seed-42 order），截断至 32K 输入 tokens，输出上限 1200 tokens；用于长上下文摘要任务评估。  
  - **UC-val / UC-tr**：UltraChat 200k 的 validation/test_sft（60 prompts）与 train_sft（用于 keep set 构建、QAT 校准），非最终 benchmark，仅用于配置筛选。

- **Benchmark 指标**：  
  - **核心效率**：服务器 GPU 时间 per output token (`g`, ms/tok)，含 prefill；平均接受 token 数（MAT）；用户端交付速度（tokens/s，从 request start 到 last token）。  
  - **核心质量**：GPT-5.4 人工判分（0–100，question-only，non-QA first-turn）；ROUGE-L、BLEU、GSM8K 准确率等 reference-based 指标（辅助验证）。  

- **对比方法**：  
  - **Cloud+MTP**：服务端 BF16 MTP 头自推测（baseline，server-side opportunity）。  
  - **SpecEdge-style**：纯 SLM 四次前向构建 32-node 树（exact）。  
  - **SpecEdge-style + PD**：SpecEdge + proactive drafting（重叠 draft 与网络等待）。  
  - **SpecEdge-ε**：同 SpecEdge 构建，但应用与 HYCO 完全相同的 ε-threshold 规则（控制变量）。  
  - **HYCO variants**：HYCO（默认）、HYCO-2P（两次 SLM pass）、HYCO exact（ε=1，无松弛）、HYCO server head（MTP 头仍在 server）、On-device 8K（纯 SLM greedy baseline）。

## 6. 主要结论与发现

- **效率显著提升**：  
  - 相比 Cloud+MTP，HYCO 在 SB 上 `g` 降低 **38.6%**（4.80 vs 7.81 ms/tok），在 32K Sum 上降低 **29.2%**（16.92 vs 23.91 ms/tok）；  
  - 相比纯 SLM drafter（SpecEdge-style），在相同 ε 规则下，**额外多省 9.0 个百分点**，且交付速度达 **35.0 tokens/s（1.9× SLM alone）**；  
  - 即使禁用 ε-threshold（HYCO exact），仍分别节省 **27.7%** 与 **11.9%**，证明混合架构本身有效。  
- **质量可控**：  
  - HYCO vs Cloud+MTP 判分差异为 **+0.2 分**（95% CI: [−0.9, +1.3]），区间含零，**无统计显著差异**；  
  - Translation 任务是例外：HYCO 比 SpecEdge-ε 低 **2.6 分**（CI: [−5.2, −0.2]），表明任务依赖性；  
  - Reference metrics（ROUGE/BLUE/GSM8K）显示与 Cloud+MTP 基本一致（±0.1–0.5 点）。  
- **关键归因**：ε-threshold 接受大幅提升 MAT（HYCO: 4.71 vs exact: 3.84），且约 **2/3 的 threshold-only 接受 token 来自 MTP 链**，说明 native head 提供高质量主干。

## 7. 优点

- **架构创新性**：首次将 LLM 原生 MTP 头**作为端侧 draft 组件**，变“服务端加速器”为“端–云协议”，突破传统 device–cloud 仅 offload SLM 的范式。  
- **工程务实性强**：所有技术（量化、受限词表、1K window、ε-threshold）均针对**真实 NPU 约束**（内存、带宽、整型计算）设计，并通过详尽的 ablation（Appendix D）验证其必要性。  
- **评估全面深入**：不仅报告 aggregate judge score，还进行 task-wise breakdown、failure inspection、reference metrics、long-context summary analysis，多维度刻画 quality–efficiency trade-off。  
- **开源友好**：明确列出全部模型、数据、软件许可证（Apache 2.0 / MIT / CC BY），并验证 cross-family 迁移能力（Muse-Glimmer-30B + token bridge），具备强可复现性与扩展性。

## 8. 不足与局限

- **质量保证局限**：  
  - ε-threshold 是**有损机制**，不保真 verifier 采样分布；论文坦承其“does not preserve the sampling distribution”且“does not comprehensively assess factual consistency”；  
  - Judge score 仅覆盖 non-QA first-turn，未评估 multi-turn coherence、QA accuracy（仅 diagnostic）、second-turn quality；  
  - Translation 任务表现下降，提示该方法可能不适用于高 precision 要求场景。  
- **部署限制**：  
  - 依赖服务器开放 **MTP 头权重、中间隐藏态、KV 缓存**——闭源商业 API（如 OpenAI）无法支持；  
  - 需要 **shared tokenizer 或 token bridge**，跨模型 family 迁移（如 Glimmer）需额外映射成本；  
  - 当前仅验证单客户端、单 GPU、单 NPU、单网络类型（LTE/5G），未测试高并发、弱网、多设备等现实负载。  
- **资源与能耗未量化**：报告了 GPU time 与 delivery speed，但**未测量端侧 NPU 能耗、内存占用、发热、电池消耗**，也未评估 loaded-service capacity（吞吐量）或 monetary cost。  
- **实验覆盖偏差**：  
  - 所有 benchmark 为英文；keep set 基于 UltraChat（中英混合？），但未验证其他语言（如 Table 8 中 German WMT14 仅用于 BLEU，非主任务）；  
  - Long-context 仅测试 32K，未覆盖 ∞Bench 的 100K+ tokens 场景；  
  - “SLM alone” baseline 为 greedy decoding，未与更先进端侧方法（如 Medusa、EAGLE）对比。
