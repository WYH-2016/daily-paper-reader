In mature software systems, reviewers must recognize design trade-offs introduced by a proposed change, compare alternative solutions, and reason about their compatibility with project-specific constraints. We refer to this problem as design-aware code review .However, existing automated review approaches primarily focus on defects and correctness, while the design knowledge accumulated in historical review discussions remains difficult to reuse. To address these challenges, we present DesignLore, a knowledge-augmented approach that extracts design decisions from historical review discussions, organizes them into an adaptive design taxonomy, and reuses relevant historical knowledge to guide code review. 1 Introduction 

Code review is a central quality-assurance activity in software development, particularly in long-lived systems such as the Linux kernel, where reviewers examine proposed changes before inte-gration to identify and resolve potential problems [3]. With recent advances in large language models (LLMs) and LLM-based agents [13, 22, 41], a growing number of automated code-review approaches and benchmarks have been proposed [18–21, 40, 42]. These efforts, including the recent agent-based Sashiko [29], primarily focus on functional correctness or defects of the code changes. In practice, effective review often extends beyond detecting local defects or checking functional correctness to evaluating design trade-offs . A proposed change reflects one design choice, but alternative solutions may also satisfy the same functional requirements with different advantages. Reviewers therefore need to understand the trade-offs among viable alternatives and determine which choice better fits the project’s design principles and long-term needs. This consideration is particularly important in Linux kernel development, where development guidance explicitly asks contributors to consider how code will be maintained years after it is merged [35]. For example, when clearing huge pages in the memfd patch shown in Figure 1, reviewers suggested replacing 

folio_zero_range() with folio_zero_user() . Both are functionally correct but make different

We refer to this problem as design-aware code review , which goes beyond local correctness checking to identify and reason about the design trade-offs underlying code changes. Such reasoning may draw on information recorded in historical review discussions [5, 39, 47]. In the Linux kernel, these discussions take place on public mailing lists and capture design considerations at multiple levels of granularity, including the alternatives considered, their advantages and disadvantages, and the reasoning behind the final decisions. They may therefore offer useful context when similar design problems arise in future patches. For example, as shown in Figure 1, an April 2025 discussion of a different patch series considered the trade-off between bulk clearing and scheduling responsiveness, with a reviewer proposing bounded clearing batches with periodic rescheduling. The discussion thus provides relevant context for the later choice in the memfd patch. However, whether this opportunity matters in practice remains unclear: how frequently code review entails design trade-offs and how often similar design problems recur in ways that make historical decisions relevant. To answer these questions, we conduct a formative study on the memory-management ( mm ) subsystem of the Linux kernel, whose public review process provides rich historical discussions and traceable patch revisions. Analyzing design decisions across many review threads through manual inspection alone is impractical. Relevant reasoning is often fragmented across multiple replies, interleaved with implementation details and procedural discussions, and expressed at different levels of abstraction. We therefore propose an automated pipeline that reconstructs each design decision discussed in a thread, together with the alternatives considered and their trade-offs, into a structured decision case . Applying it to 600 threads sampled between 2021 and 2026 yields 1,774 decision cases, whose quality we validate through human evaluation. Based on the mined cases, the study confirms that design trade-offs are common in practice: 

60.29% of the sampled threads involve at least one design trade-off, and 33.91% contain a problem with a relevant historical precedent. It also shows that exploiting such precedents is non-trivial: the reasoning behind a decision must first be recovered from fragmented discussions, a relevant precedent often concerns different code and terminology than the new patch, and a historical resolution applies only if its conditions still hold in the current code. The challenge is therefore not the absence of historical design knowledge, but how to recover, organize, and reuse it effectively. Guided by the findings, we present DesignLore, a knowledge-augmented approach for design-aware code review. DesignLore first applies the extraction pipeline to review history to build a knowledge base of decision cases, then organizes them into an adaptive, project-specific design taxonomy based on the code patterns that trigger each case, enabling precedents to be retrieved from a new patch’s code rather than surface text. At review time, DesignLore uses the taxonomy and relevant historical decisions to guide the analysis of a target patch, helping the agent identify and validate design trade-offs against the current code and project context. We construct DesignReviewBench from real patch-review histories of the Linux kernel, com-prising 72 patch series and 79 reference design trade-offs. Each benchmark instance pairs a proposed patch series with the codebase snapshot available at review time and captures the design trade-offs revealed by subsequent human review. We compare DesignLore with state-of-the-art general-purpose coding agents, specialized code-review systems, and retrieval-augmented agents that access raw historical review emails. The results show that design-aware code review remains challenging for current agents: the strongest baseline, Sashiko [29], achieves an F1 of 0.213. In contrast, DesignLore achieves the best trade-off detection performance, with an F1 of 0.259, a 21.6% relative improvement at roughly half of Sashiko’s review cost. The improvement persists across three agent systems and four backbone models. The cumulative ablation shows incremental F1 improvements, with the largest increase observed when adding the planning and validation workflow. In summary, this paper makes the following contributions: 

• An empirical characterization of design-aware code review. We analyze historical Linux kernel reviews to characterize the prevalence and recurrence of design trade-offs and the challenges of reusing historical design knowledge. 

• A knowledge-augmented agentic code review approach. We present DesignLore, which extracts design knowledge from historical reviews, organizes it into an adaptive design taxonomy, and reuses relevant decisions to guide new patch reviews. 

• A benchmark for design-aware code review. We construct DesignReviewBench from real historical patch-review discussions to evaluate whether coding agents can identify design trade-offs exposed by proposed changes. 

• A comprehensive empirical evaluation. We evaluate DesignLore against general-purpose, review-specialized, and retrieval-augmented coding agents, demonstrating its effectiveness across diverse agents and backbone models. 

2 Formative Study 

We conduct a formative study to understand what design-aware code review entails in practice and whether historical review discussions can support it. We aim to investigate three questions: 

• FQ1 (Prevalence): How frequently do review decisions in Linux kernel patch review involve design trade-offs? 

• FQ2 (Recurrence): How often have similar underlying design decisions already appeared in earlier, independent patch series? 

• FQ3 (Implications): What challenges arise in reusing historical review discussions for code review, and what do they imply for automated support? FQ1 reflects the practical need for reasoning beyond local correctness, whereas FQ2 indicates whether historical review discussions can provide reusable precedents for future reviews. 2.1 Motivation and Definition of Decision Cases 

Raw review threads do not provide a consistent unit of analysis: one thread may contain several independent design questions, while reasoning about one question may span multiple reviewers and replies and patch revisions. We therefore reconstruct discussions into decision cases , analyze trade-offs and recurrence at the case level, and aggregate the results to the thread level. We define a decision case as a historical record of a design decision and the deliberation leading to it, including the alternatives considered and their trade-offs. Each case comprises: 

• Problem: The technical question or design tension motivating the decision. 

• Code-pattern trigger: The code context or recurring pattern giving rise to the problem. 

• Options: The alternatives considered, each with a Description of the proposed action or position, Conditions under which it applies, Pros describing its expected benefits, and Cons 

describing its limitations, risks, or trade-offs. 

• Decision: The option ultimately agreed upon by the participants. 

• Rationale: The justification for the decision. 

2.2 Decision Case Mining 

We propose a four-step mining pipeline that progressively transforms fine-grained atomic sugges-tions into coherent decision cases, as illustrated in Figure 2. 

2.2.1 Atomic Suggestion Extraction. We first use an LLM to extract source-grounded atomic sug-gestions from review threads, where each suggestion addresses a single independently decidable technical concern. A suggestion may defend or refine the current design, object to an existing pro-posal, introduce an alternative, or raise a substantive design question. Each suggestion records the 

Problem and Code-pattern trigger fields of a decision case, together with the Suggestion , Arguments 

for or against it, and applicable Conditions .Review discussions are tree structured through email replies, which does not directly align with the sequential context expected by autoregressive LLMs. We therefore organize each thread into bounded local contexts before extraction. (𝑝 (𝑣 ), 𝑣 ) ∈ 𝐸 denotes that 𝑣 directly replies to its parent 𝑝 (𝑣 ). For each target email 𝑣 , a local window of size 𝑠 is constructed from the target email and its nearest ancestors along the reply path:

In practice, 𝑠 = 2 is used to preserve local conversational context while keeping the extraction scope compact. Given a window 𝑊 (𝑣 ), zero or more atomic suggestions are extracted from the target email using the LLM. Only text newly written by the target author is treated as extractable evidence; the parent email and quoted text within the target email are provided as read-only context for resolving references and interpreting the discussion. The LLM is instructed to focus on substantive technical content and ignore purely procedural remarks, such as acknowledgements and requests to resend a patch. Each extracted suggestion retains provenance to its source email and supporting text, enabling subsequent relation construction and independent verification. 2.2.3 Decision Case Synthesis. As shown in Algorithm 1, suggestions concerning the same technical question are deterministically grouped by a depth-first traversal of the typed tree. A child linked by refined-from 

or alternative-to continues the same de-cision problem and joins its parent’s cluster, whereas a caused-by child opens a new clus-ter and records a causal edge between the two clusters. The suggestions in each cluster are then synthesized into a single decision case. For each cluster, an LLM is given the con-stituent atomic suggestions together with their provenance and inferred relations, and is instructed to reconstruct the decision case following a fixed schema. The problem and code-pattern trigger are consolidated, and the suggestions are processed chronologically to recover the alternatives considered. Suggestions that duplicate, refine, or complement the same solution are consolidated into one option, whereas suggestions advocating different solution directions are retained as separate options. To preserve the completeness of the decision space, the initial proposal embodied by the reviewed patch is also recovered as an option. Arguments supporting an option are consolidated into its Pros , while objections and reported drawbacks are consolidated into its 

Cons . Applicability conditions associated with the constituent suggestions are likewise propagated to the corresponding options. The final decision is identified as the adopted option based on explicit agreement or, when such agreement is absent, a subsequent revision that clearly implements the option. If neither provides sufficient evidence, the outcome remains unresolved. The rationale is reconstructed from the arguments supporting the adopted option. Finally, cluster-level caused-by 

relations are transferred to the corresponding decision cases to construct the decision-case tree. All reconstructed fields retain links to their supporting suggestions and source messages. 

2.2.4 Thread-Level Case Integrity Relection. An LLM is then given the reconstructed decision-case tree and is instructed to inspect the tree top-down for thread-level structural inconsistencies. The 6 Zhenhao Zhou, Kai Yu, Ying Wang, Zhiqiang Yuan, Junhao Zeng, Yijian Wu, Chong Wang, and Xin Peng 

decision-case tree is traversed to check whether each case forms a coherent and independently resolvable decision problem, and whether the relations between cases are consistent with the overall discussion. When an inconsistency is detected, one of three structural repairs is applied. First, merge combines cases that were separated locally but in fact describe different parts of the same decision problem. Second, reparent introduces or corrects a caused-by relation when two cases were placed as siblings although one technical question was actually triggered by the other. Third, split partitions an overly broad case when it conflates multiple independently resolvable questions. Each repair preserves the provenance of the affected fields and relations, resulting in a decision-case tree that provides a thread-level consistent representation.

2.5 Recurrence of Design Decisions (FQ2) 

We consider a decision case recurrent when an earlier case from a different review thread addresses the same underlying problem and can inform the later review. For each sampled decision case, we retrieve the eight most semantically similar eligible historical cases and ask the same annotators whether any candidate constitutes such a precedent. A decision case is labeled recurrent if at least one such historical precedent is identified. We then consider a review thread recurrent if at least one of its extracted decision cases is recurrent. 

Results. Overall, 33.91% of the sampled threads contain at least one recurrent decision case, with substantial inter-annotator agreement (Fleiss’ 𝜅 = 0.605). The yearly recurrence rate rises from 23% in 2021 and remains between 32% and 38% in subsequent years. Based on our manual inspection of some sampled threads, this LLM-based estimation is likely conservative. Annotators only examine the eight most semantically similar candidates, so precedents that concern different code or use different terminology, like the clearing discussion relative to the 

memfd patch, may fall outside the candidate set and remain uncounted.

2.6 Implications (FQ3) 

FQ1 motivates explicit support for reasoning about design trade-offs during review, as well as a benchmark for this capability, and FQ2 shows that historical discussions contain reusable precedents. These precedents, however, are not directly reusable. Our study surfaces three challenges, each motivating one stage of DesignLore. 

C1: Recovering Coherent Design Decisions. A decision rarely appears in one place: in the clearing discussion, the proposal, the problematic preemption condition, and the bounded alternative appear in different replies, while the merged code records only the adopted solution. Historical review knowledge therefore needs to be reconstructed into decision-level units that connect the design problem, alternatives, trade-offs, and final decision, rather than treated as raw emails. 

C2: Locating Relevant Precedents. Precedents may involve different files, features, and terminol-ogy, as in the clearing discussion and the memfd patch. Our recurrence analysis identifies similar problems from reviewer discussions, but at review time only the new patch is available. Relevant precedents therefore need to be indexed by the code situations that trigger them, rather than by surface-level similarity in the discussion. 

C3: Applying Precedents to the Current Code. A historical resolution holds only if its con-ditions still hold: applying the clearing precedent requires checking page sizes and preemption configuration in the current code. Historical precedents therefore need to be treated as hypotheses to be checked against the current code rather than answers to be copied directly. 

Finding 3: Historical review discussions cannot be reused as is. Effective reuse requires (C1) recovering decision-level knowledge from fragmented discussions, (C2) locating precedents from the code situation of a new patch rather than from surface text, and (C3) validating whether a precedent still applies to the current code. 

3 DesignLore: Knowledge-Augmented Code Review 

We propose DesignLore, a knowledge-augmented code review approach that recovers reusable design knowledge from historical review discussions and leverages it to support design-aware review of new patches. As illustrated in Figure 5, DesignLore consists of two stages, each addressing one of the chal-lenges identified in the formative study. First, it recovers structured decision cases from historical review threads through the mining pipeline introduced earlier in our formative study, which pro-gressively transforms fine-grained atomic suggestions into coherent design decisions (C1). Second, it organizes the recovered cases into a design taxonomy according to their code-pattern triggers, forming a reusable project-level knowledge base that can be navigated from the code of a new patch (C2). At review time, DesignLore uses the target patch to navigate the knowledge base, retrieves relevant historical precedents, synthesizes them into a decision-oriented review plan, and validates the plan against the code under review (C3). 

3.1 Decision Knowledge Extraction 

The first stage of DesignLore addresses challenge C1 by applying the mining pipeline of Section 2.2 to the entire historical review corpus rather than to a sample of threads. Each thread is thereby transformed into a decision-case tree, whose nodes are source-linked decision cases and whose Benchmarking and Enhancing Design-Aware Code Review in the Linux Kernel 9

3.2 Design Taxonomy Construction 

The decision cases recovered in the previous stage preserve the reasoning behind individual review discussions. A flat collection of such cases, however, provides no stable routing structure for a new patch. DesignLore therefore organizes historical decision cases into a hierarchical design taxonomy according to their Code-pattern trigger . The taxonomy provides a structured entry point for locating historical decisions that arise under similar code circumstances. Inspired by established taxonomy development methods [14, 24], DesignLore constructs the taxonomy using a round-based, top-down procedure that combines a pre-established seed schema with data-driven adaptation. Algorithm 2 summarizes the process.

An LLM-based annotation agent induces, for each level, a candidate routing dimension and its associated categories from a sampled subset of decision cases. The resulting schema is then validated and refined on disjoint batches until its dimensions and categories stabilize. Finally, the stabilized upper-level schema is manually reviewed and confirmed before being fixed as the seed taxonomy schema. Each routing node additionally maintains an unslotted bucket for cases that cannot be assigned to any existing category.

3.2.3 Iterative Structural Refinement. After batch settlement, the resulting taxonomy may still be too coarse to organize the accumulated cases effectively. DesignLore therefore examines overloaded nodes and applies three refinement operations. (1) Vertical growth handles overloaded leaf nodes by introducing a more specific routing dimension and its categories beneath the leaf. (2) Horizontal expansion handles routing nodes with large unslotted buckets by introducing additional categories under the existing dimension. (3) Dimension revision is triggered when repeated horizontal expansion fails to produce a meaningful partition; DesignLore then redefines the routing dimension of the affected adaptive subtree and repartitions its cases. Expert-seeded dimensions are never revised. A refinement agent performs these operations using two complementary forms of context. Path context contains the definitions and routing dimensions along the path from the root to the current node, ensuring that a newly introduced dimension is more specific than its ancestors. Peer context 

contains the definitions and routing dimensions of nodes at comparable depth, helping maintain a consistent level of abstraction across the taxonomy. The agent is additionally provided with decision cases from the node being refined. After each structural change, all affected cases are re-annotated against the updated local subtree. Refinement continues until no overloaded node admits a valid structural improvement or a predefined refinement limit is reached, i.e., the maximum depth or retry count. 

3.3 Design Knowledge-Augmented Code Review 

The previous offline stages construct a reusable knowledge base of historical design decisions organized by the design taxonomy. In the online stage, DesignLore integrates this knowledge base into a coding agent through a set of knowledge-access skills. Specifically, DesignLore organizes Benchmarking and Enhancing Design-Aware Code Review in the Linux Kernel 11 

the review process into two stages: knowledge-guided review planning and code-grounded review validation .

3.3.1 Knowledge-Guided Review Planning. Given a target patch and the repository snapshot under review, DesignLore first instructs the agent to inspect the changed code and its surrounding context, identify salient code patterns, and formulate an initial characterization of the affected functionality and implementation mechanism. The agent then uses this characterization to explore the historical design knowledge base. To support this exploration, DesignLore provides three complementary knowledge-access skills: 

• annotate : maps code patterns identified in the target patch to candidate taxonomy nodes using the same classification procedure employed during taxonomy construction. This provides an initial entry point into the historical knowledge space; 

• navigate : explores structurally and semantically related taxonomy nodes. The agent can navi-gate parent, child, and sibling nodes, and follow the caused-by relation to reach historically related situations, while inspecting the associated case statistics and representative decisions; 

• retrieve : retrieves historical decision cases using BM25-based ranking. Retrieval can be per-formed globally over the complete knowledge base or locally within taxonomy nodes selected during navigation, allowing the agent to progressively narrow or expand the search scope. Knowledge access proceeds iteratively through taxonomy navigation and case retrieval. The agent first maps the target code to relevant taxonomy nodes, then explores neighboring or causally related nodes and retrieves candidate decision cases. Based on the retrieved evidence, it can refine the search scope and continue exploring additional nodes as new relevant concerns emerge. This iterative process progressively focuses the search on historical design knowledge relevant to the current patch. From the retrieved cases, the agent identifies recurring design concerns, alternative solutions considered in prior reviews, their advantages and disadvantages, and the conditions under which different solutions were preferred. It synthesizes this information into a review plan , which contains a set of candidate design concerns for further examination. Each plan item records the relevant code region, the potential design issue, supporting historical precedents, possible alternative solutions, and the conditions to be validated in the current repository. At this stage, each plan item serves as a hypothesis for subsequent code-grounded validation. 

3.3.2 Code-Grounded Review Validation. The second stage validates each planned concern against the current codebase. For every review-plan item, the agent traces the affected code, relevant control and data dependencies, and surrounding implementation context to determine whether the historically observed design situation actually applies to the target patch. The agent further checks whether the assumptions and applicability conditions associated with the historical cases hold in the current implementation, such as lifecycle assumptions and interface constraints. Plan items that are not supported by the current code are discarded. For the remaining items, the agent combines code evidence with the relevant historical precedents to produce concrete review findings . Each finding identifies the underlying design concern, explains why it applies to the current patch, and, when supported by both the historical evidence and the current context, recommends a corresponding resolution with its rationale. This validation stage prevents historically similar but contextually inapplicable cases from being directly propagated into review comments.

4.1 DesignReviewBench: A Design-Aware Code Review Benchmark 

We introduce DesignReviewBench, a benchmark for evaluating design-aware code review. Whereas existing code-review tasks primarily assess whether a proposed patch contains correctness defects, DesignReviewBench focuses on the project-specific design trade-offs exposed by the patch. 

4.1.1 Task Definition. We define design-aware code review as the task of identifying underlying design tensions or trade-offs exposed by a proposed code change. Formally, given a patch series 𝑃 ,that is, a set of related patches that collectively implement a change, and the codebase snapshot 

𝐶 available at review time, a reviewer outputs a set of findings {𝑓 𝑖 }𝑚 𝑖 =1, each describing a design trade-off that may require further consideration during review. 

4.1.2 Benchmark Construction. We construct DesignReviewBench through four phases: data collection, rule-based filtering, LLM-based verification, and manual inspection. 

Step 1: Data Collection. We collect patch-review threads posted to the Linux kernel mm mailing list from January 2025 to August 2026. We retain only threads associated with patch submissions and containing substantive discussions among human reviewers, resulting in 6,542 threads. For each retained thread, we apply the Decision Case Extraction pipeline (Section 2.2), with GPT-5.6 Luna as the underlying LLM, to reconstruct the corresponding decision cases. These cases provide structured evidence for constructing realistic design-aware code-review instances grounded in historical review outcomes. Specifically, we use the recovered Problem field as a candidate design trade-off point. 

Step 2: Rule-Based Filtering. We next apply deterministic filters to remove cases that cannot support a reliable code-review instance. Specifically, we require that (i) the recovered case contains at least two substantive alternatives, indicating that an actual design choice was considered; (ii) the reviewed patch can be linked to the corresponding kernel snapshot available at review time and can be applied to that snapshot, ensuring that the benchmark instance has a reproducible code context; and (iii) the patch series can be linked to its eventual mainline integration, providing downstream evidence for validating the recorded resolution. 

Step 3: LLM-Based Verification. We then perform semantic verification of the remaining candi-dates. Each verifier is given the recovered case together with the original reviewed patch and the corresponding final patch integrated into mainline. It independently checks whether (i) the case captures a design trade-off rather than a purely mechanical or straightforward correctness issue, with multiple plausible alternatives under the available constraints; (ii) the recorded final decision and rationale are sufficiently explicit and supported by the review evidence; (iii) the eventual reso-lution differs meaningfully from the design embodied in the original patch; and (iv) the recorded resolution is reflected in the version ultimately integrated into mainline. We use GPT-6 Sol and DeepSeek-V4.1 Flash as independent verifier models and retain only candidates accepted by both. 

Step 4: Manual Inspection. Finally, two human annotators independently inspect the surviving candidates and assess whether each case constitutes a valid design-aware code-review instance. A Benchmarking and Enhancing Design-Aware Code Review in the Linux Kernel 13

4.2 Experimental Setup 

4.2.1 Baselines. We implement DesignLore on top of OpenCode [1] and compare it against six baselines. The first four represent general-purpose or review-specialized coding agents. The remaining two are retrieval-enhanced variants of OpenCode that directly access the raw historical review-email corpus. 

• Sashiko [29] is an agentic reviewer developed by the Linux Foundation specifically for the Linux kernel, with kernel-specific prompts and a dedicated review protocol. 

• OpenCodeReview [19] is a review-specialized agent combining rule-guided dispatch, tool-grounded file inspection, and independent reflection. 

• Codex [26] is a general-purpose coding agent; we use its native review workflow. 

• OpenCode [1] is an open-source coding agent; we use its native review workflow. 

• OpenCode-RAG applies retrieval-augmented generation [17] over the raw historical review emails, providing semantically similar emails as additional context. 

• OpenCode-Search lets OpenCode search the same raw-email corpus through keyword-based 

grep queries and inspect the retrieved emails as needed. 

4.2.2 Implementation Details. Temporal Data Cut-off. To prevent temporal data leakage, the histor-ical email corpus used by DesignLore and the retrieval-enhanced baselines contains only emails from 2021–2024, which strictly precede all benchmark patches (2025–2026). 

Code Review. All baselines use GPT-5.6 Luna, controlling for the underlying model when com-paring review workflows. We also provide all agents with the same design-aware code-review instruction, asking them to identify design tensions or trade-offs exposed by the target patch. For OpenCode-RAG, we encode historical emails using sentence-transformers/all-MiniLM-L6-v2 

and retrieve the top-8 most similar emails for each target patch. 

LLM Judges. We use three SOTA LLMs from distinct model families, namely GPT-6 Sol, DeepSeek-V4.1 Flash, and Claude Opus 5.5, as independent judges. Each judge evaluates agent findings using 14 Zhenhao Zhou, Kai Yu, Ying Wang, Zhiqiang Yuan, Junhao Zeng, Yijian Wu, Chong Wang, and Xin Peng 

the criteria defined in Section 4.1. We average the resulting graded scores across judges to obtain the final scores, reducing dependence on any single evaluator.

5 Discussion 

Toward Design-Aware Code Review. Our results suggest that recognizing design trade-offs and reasoning about appropriate alternatives remain challenging for current review agents. Unlike defect detection, a design concern may involve multiple viable solutions whose suitability depends on project-specific constraints and rationale. This calls for review systems that go beyond identifying problematic code to explicitly reason about design decision points, competing alternatives, and their trade-offs. Historical design knowledge provides a promising source of such context, enabling review agents to relate a new patch to how similar design choices were previously discussed. 

Toward an Evolving Project Memory. DesignLore currently reconstructs decision cases offline from historical review discussions. A natural extension is to incrementally incorporate newly completed reviews, allowing these cases to form a continuously evolving project-specific design memory. Such reuse, however, should remain context-sensitive: a historical decision reflects the constraints and assumptions under which it was made and should not be treated as a prescriptive Benchmarking and Enhancing Design-Aware Code Review in the Linux Kernel 17 

rule. Future systems should therefore retrieve relevant precedents while also reasoning about whether their applicability conditions still hold in the current code and project context. 

Offline Construction Cost. Building the project-specific design knowledge base incurs an upfront cost because DesignLore processes historical review discussions through multiple LLM-based stages. In our study, extracting decision cases from 8,382 review threads costs $307.9, while constructing the design taxonomy incurs an additional $16.7. This yields a total offline construction cost of $324.6. This cost is paid only during knowledge-base construction and can be amortized across subsequent reviews. Once the historical archive has been processed, newly arriving review discussions would only require incremental extraction and taxonomy updates. The practical trade-off is therefore between the one-time cost of constructing and maintaining project-specific design knowledge and its repeated reuse during future code reviews. 

6 Related Work 6.1 Design Knowledge Extraction 

Software development continuously involves design trade-offs and decisions, whose underlying knowledge is important for the long-term evolution of software systems. Prior work has therefore explored explicitly representing and preserving such knowledge to mitigate its loss over time. Jansen and Bosch modeled software architecture as a composition of explicit design decisions [12], while subsequent studies extended this view to capture alternatives, rationale, assumptions, context, and decision history, and further regarded architectural decisions as reusable knowledge assets [15, 48]. These studies establish the value and key elements of design knowledge, but largely assume that such knowledge is explicitly documented and maintained during development. Another line of research focuses on recovering design knowledge from development artifacts, motivated by the observation that important design decisions are often discussed and refined through informal communication rather than explicitly documented [4–7, 28, 30, 31, 39]. More recently, researchers have leveraged LLMs to recover increasingly structured forms of design knowledge from such artifacts. Dhaouadi et al. [8, 9] constructed rationale and decision graphs from development histories, while DRMiner [44, 45] combines LLMs with heuristic signals to recover proposed solutions together with supporting and opposing arguments from issue discussions. Yu et al. [38] extracted project-specific design constraints from code review discussions arising during issue resolution. Other recent studies further explore LLMs for generating or recovering architectural rationale from textual artifacts [46]. Collectively, these studies show that development artifacts provide a rich source for recovering otherwise implicit design knowledge. 

6.2 Automated Code Review 

Early learning-based approaches formulate code review as prediction over code changes and review comments. Tufano et al. [36] studied pre-review transformation and comment-guided refinement, while CodeReviewer [18] introduced review-specific pretraining for change-quality estimation, com-ment generation, and code refinement. Retrieval-based approaches such as CommentFinder [10] and LAURA [43] further exploit historical reviews to improve comment generation. More recent systems increasingly combine repository context, tool use, and multi-stage verification. CodeAgent [32], RovoDev [34], OpenCodeReview [19], and Sashiko [29] organize review around repository explo-ration, specialized guidance, and validation of generated findings. Historical discussions can also provide reusable review knowledge: FLINT [20] distills Linux review discussions into validation rules and retrieves relevant rules and source context for new patches. Existing benchmarks evaluate complementary aspects of automated code review. CodeRe-viewer [18] and CodeReviewQA [21] assess review generation, refinement, and comprehension, 18 Zhenhao Zhou, Kai Yu, Ying Wang, Zhiqiang Yuan, Junhao Zeng, Yijian Wu, Chong Wang, and Xin Peng 

while DeepCRCEval [23], CRScore [25], and HalluJudge [33] focus on review quality and grounding. More recent benchmarks move toward realistic agent-level evaluation with broader repository con-text: SWR-Bench [40] evaluates issue coverage over complete pull requests, ContextCRBench [11] incorporates issue and program context, CR-Bench [27] evaluates defect detection together with review usefulness and noise, and c-CRAB [42] evaluates code-review agents on real pull requests by converting human-identified review concerns into executable tests. Our work focuses on implicit design trade-offs, requiring the reviewer to recognize the design trade-off exposed by a patch and reason about it under project-specific constraints. While FLINT distills historical Linux review knowledge into validation rules, DesignLore reconstructs decision cases that preserve the problem, competing alternatives, and their underlying trade-offs. Accord-ingly, DesignReviewBench focuses on whether an agent can identify such design trade-offs from a proposed patch. 

7 Threats to Validity 

Internal Validity. A key threat is the reliance on LLMs in multiple stages. We mitigate it by using multiple independent LLMs for verification and evaluation, and validate both the extracted decision cases (Section 2.3) and the LLM-based evaluation (RQ4) through human assessment. Second, the candidate trade-offs in DesignReviewBench are recovered by the same extraction pipeline that builds the knowledge base of DesignLore, which may favor its representation. To reduce this risk, every reference is verified against the original and mainline patches by two LLM verifiers and two human annotators, and the knowledge base contains only discussions that precede all benchmark patches. Third, the backbone LLMs may have been exposed to the benchmark discussions during pre-training; since all methods share the same backbone, this exposure affects them equally. 

External Validity. Our study focuses on the Linux kernel memory-management subsystem (mm ), a representative and mature software system with long-running patch-review discussions and traceable patch evolution. The prevalence of design trade-offs and the effectiveness of DesignLore may differ across other repositories. However, we believe that the underlying principle of recovering and reusing historical design knowledge can generalize to other projects with rich developer discussions, including pull-request-based development platforms. Further validation on additional repositories is left for future work. In addition, although the main experiments use GPT-5.6 Luna as the backbone model, we evaluate DesignLore with additional LLMs, such as DeepSeek-V4.1 Flash, and observe consistent improvements, suggesting that the approach is not tied to a single model. 

Construct Validity. The reference design trade-offs in DesignReviewBench are derived from documented developer discussions and subsequent patch evolution. Therefore, they may not cap-ture implicit design considerations that were never explicitly discussed or recorded. Consequently, our benchmark measures observable design reasoning rather than the complete set of design con-siderations involved in software maintenance. Nevertheless, it provides a practical and reproducible approximation of design-aware code review beyond conventional correctness checking. 

8 Conclusion 

A formative study of Linux kernel mm review discussions shows that design trade-offs are prevalent and that similar problems frequently recur across independent patch series. Building on these findings, we develop DesignLore, which recovers, organizes, and reuses historical decision cases, and construct DesignReviewBench for systematic evaluation. Existing coding agents show limited capability in design-aware review, whereas DesignLore achieves the strongest performance and generalizes across agent systems and backbone models. These results underscore the importance of design-aware review and demonstrate that explicitly reco vering and structuring historical design knowledge can improve automated code review beyond local correctness checking.
