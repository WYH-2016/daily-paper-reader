Abstract—Data encrypted today with classical public-key al-
gorithms could be decrypted once large quantum computers
exist. Cloud object stores keep data for years, so the client-
side encryption that protects it must move to post-quantum
algorithms such as ML-KEM, which adds a key-encapsulation
step and a larger ciphertext to every stored object. So far, the
cost of ML-KEM has been measured for the algorithm on its own
and for securing network connections, but not for encrypting each
object in a storage system that serves many clients at once. It has
therefore been unclear whether ML-KEM slows such a system,
under which conditions, and why. We address this problem by
measuring per-object ML-KEM against classical key exchange on
an S3-compatible object store, with two client implementations,
two processor types and up to 500 concurrent workers, using
pre-registered experiments and statistical equivalence tests. ML-
KEM reduced throughput only when the client’s processor was
at or near full load, with one unexplained exception, and then by
4.0 to 4.9 % in our main client. Controlled experiments on one
processor type traced most of that loss to the way the software
library was called, and a second, native client showed that the
size of the loss depends on the implementation. The lasting cost
is storage: 1,056 more bytes per object than with classical key
exchange. The results cover two clients, one single-node store and
one cloud provider.
Index Terms—ML-KEM, hybrid KEM, envelope encryption,
client-side encryption, cloud storage security, HPKE, equivalence
testing, performance evaluation
I. INTRODUCTION
Cloud object stores keep data for years, and much of
that data is encrypted under keys established with RSA or
elliptic-curve Diffie–Hellman. Shor’s algorithm would allow a
sufficiently large quantum computer to recover those keys, so
an adversary who records ciphertext today can decrypt it once
such a machine exists, a threat usually called “harvest now,
decrypt later”. For data at rest the exposure lasts as long as the
data is retained. In August 2024 NIST published FIPS 203,
standardizing the module-lattice key-encapsulation mechanism
ML-KEM [1].
With client-side envelope encryption, as implemented by
the Amazon S3 Encryption Client and by Azure Blob Storage
client libraries [2], [3], every object is encrypted under its own
data key, and that key is protected for the recipient and stored
with the object.
A public-key KEM per object is needed only in some
deployments. If writer and reader share a symmetric key-
encryption key, wrapping the data key with AES is already
quantum-safe and no KEM is needed; that is our baseline B1.
A public-key mechanism is required when the writer must not
be able to decrypt, or does not share a secret with the reader:
write-only producers such as log shippers, backup agents
and sensors that hold only a public key; objects encrypted
to several recipients or to an escrow key; and data handed
across organizational boundaries. These deployments use RSA
or elliptic-curve key establishment today, and they are the
ones that must migrate. For them, ML-KEM places a key
establishment and its 1,088-byte ciphertext on every PUT and
every GET rather than once per connection.
What is known falls into three groups of measurements.
Primitive-level studies report the cost of key generation,
encapsulation and decapsulation and the sizes of keys and
ciphertexts on several processor families [4], [5], [6], [7].
Studies of post-quantum TLS and KEMTLS measure connec-
tion establishment under latency, loss and bandwidth limits
[8], [9], [10], [11]. Storage studies measure the S3 interface
without cryptography [12] and client-side encryption without
post-quantum key establishment [13], [14].
What is not known is the cost on the data path of an object
store. None of these measures ML-KEM where an object store
would use it: once per object, on a data path whose throughput
is set jointly by client CPU, network, metadata handling and
the storage server, with many clients at once. A back-of-
envelope estimate already says that tens of microseconds of
KEM against milliseconds of storage round trip should be
invisible. What that estimate cannot say is whether it holds

under concurrency, in which regime it fails, by how much,
and whether the cause is the KEM computation or the larger
ciphertext it carries through the data path (Section II, Table I).
The thesis of this paper is the following. In the configu-
rations we measured, replacing X25519 by per-object ML-
KEM lowered throughput only where the client was at or
near CPU saturation, with one unexplained exception in the
native reader. The size of the loss there depended on the client
implementation: it ranged from no measurable loss (0.999 of
X25519’s throughput, the Python client calling liboqs through
one foreign call) through 4.0–4.9 % (the same client through
the standard binding) to 9.5 % (a native Go reader on one
core). The cost that every implementation pays is storage: a
larger ciphertext with every object. The observations that do
not fit this picture are collected in Section V-G.
The contributions are the following.
C1 The saturation-regime result, with a method to apply
it: measurements of ML-KEM-768 against X25519 over
object size, 1–500 concurrent workers, two client archi-
tectures and two client implementations, with the inde-
pendently restarted run as the experimental unit and pre-
registered equivalence tests. We use a CPU accounting
identity (Section IV-C) as a method: under client satura-
tion the throughput ratio of two modes is the inverse ratio
of their client CPU per request, which turns a migration
question into a CPU measurement and a saturation check
(Sections V-B–V-C).
C2 A binding artifact, and what it implies for library authors:
two pre-registered controls on the x86 Python client show
that its client-bound deficit is produced by a library
binding that makes four foreign calls per decapsulation,
and for 17 % by the larger manifest (Section V-C).
C3 The storage cost: the per-object metadata cost of ML-
KEM and of two hybrids, separated into ciphertext and
encoding, scaled to fleet sizes, and set against the 2 KB
limit that Amazon S3 places on user-defined object meta-
data (Section V-E).
Secondary results are the measured trade-off of bounded
session amortization, which saves a few percent of client
CPU and changes throughput only on a client-bound workload
(Section V-F); the attribution of the store’s small-object write
ceiling to its metadata path and not to its disk (Section V-B);
and the observation that RSA-4096 is the one mode that moves
the bottleneck in the Python client. The instrumented client,
the harness, the native reader and the analysis pipeline are
an artifact that supports these results and are not claimed as
a contribution; neither is the architecture or commit protocol,
which is not a new cryptographic construction (Table III). The
open-loop capacity observations in the supplementary material
describe the store, not post-quantum cryptography, and their
main lesson is known [15].
The scope of the study is limited as follows. We do not
evaluate the security of ML-KEM, side channels, or transport
security, which is held constant. All performance statements
concern one Python client stack and one small native reader,
one single-node MinIO deployment and one cloud provider
(Section VI). The native reader covers the GET path of three
modes only. Section VI lists the experiments that remain.
This paper measures what per-object ML-KEM-768 costs
against RSA-4096, X25519 and symmetric-only baselines on
the same data path; how that cost depends on object size,
concurrency and a hybrid construction, and what causes it;
and what bounded sessions trade for the key-establishment
work they save.
II. BACKGROUND AND RELATED WORK
A. Post-Quantum KEMs, Hybrids and HPKE
A key-encapsulation mechanism (KEM) consists of key
generation, encapsulation, which takes the recipient’s public
key and outputs a ciphertext and a shared secret, and de-
capsulation, which recovers the secret with the private key.
ML-KEM, derived from CRYSTALS-Kyber, relies on the
hardness of module learning with errors. ML-KEM-768 targets
NIST security category 3 with a 1,184-byte encapsulation
key, a 1,088-byte ciphertext and a 32-byte shared secret [1].
Decapsulation uses implicit rejection: a modified ciphertext
yields a pseudorandom secret instead of an error, so tampering
is detected by the authenticated encryption that follows.

vate keys from one 32-byte seed; its security proof depends on

Hybrid Public Key Encryption (HPKE, RFC 9180) [18] is
the standard construction for encrypting to a public key: a
KEM produces a shared secret, a key schedule derives an
AEAD key and base nonce from it and from application-
supplied context, and messages are sealed under sequence-
numbered nonces. An IETF draft adds ML-KEM-768 and
an X25519+ML-KEM-768 hybrid as HPKE KEMs [19]. Per-
object envelope encryption has the structure of HPKE’s single-
recipient base mode. HPKE [18] and its post-quantum exten-
sion [19] specify how to encrypt to an ML-KEM or hybrid
public key but contain no measurements; the file-encryption
tool age adopted such recipients [20]. Our envelope predates
our reading of that draft and is not HPKE-conformant; Sec-
tion III maps one onto the other and states what transfers. For
hybrids, the security of the result depends on the combiner. X-
Wing [16], [17] comes with a proof for its concrete combiner,
and the general theory of KEM combiners states the conditions
under which a combination stays secure if one component fails
[21], [22]. Our mode P2 concatenates two shared secrets into
HKDF and has not been checked against those conditions,
which is why it carries no security claim and serves only as
a performance reference (Table III).
In envelope encryption a per-object data key encrypts the
object, and key establishment protects that key. We derive
data keys with HKDF-SHA256 [23] and encrypt with AES-
256-GCM, whose security requires that a nonce is never


reused under one key [24]. The classical alternatives are key
transport with RSA-OAEP [25] and ephemeral-static X25519
[26]. Object stores expose buckets and keys through HTTP
operations, chiefly PUT and GET of whole objects; the S3
interface is the de facto standard [12]. We use MinIO [27],
compiled from its final community release (RELEASE.2025-
10-15T17-29-55Z). Because that community edition is no
longer developed, our store-specific results (ceilings, knee)
should be read as those of one representative single-node S3
server, not as current product behaviour.
The closest analogue of a per-object KEM with bounded
reuse is secure messaging. Signal’s PQXDH adds a post-
quantum KEM to initial key agreement [28], and Apple’s
PQ3 applies one to initial key establishment and to a periodic
rekeying step as well [29]. There the unit of amortization is
a session or a rekeying interval, and the question of how
many messages one KEM output may protect is the same
one our session mode poses for objects (Section V-F). We
are not aware of throughput measurements of these protocols
that would transfer to an object store.
B. Related Measurements
Table I positions this study. The entries describe the scope of
each work, not a shortcoming: a TLS study is not incomplete

Existing measurements stop at two boundaries. At the
primitive level, the Kyber design paper [32], the standard [1],
library benchmarks [4] and recent comparative preprints [5],
[6], [7] give the cost and sizes of the three KEM operations
on several processor families; they establish that platform and
implementation matter, which is why we repeat our primary
comparison on a second architecture and test a second imple-
mentation, but they contain no storage, concurrency or end-
to-end request latency. At the transport level, studies of post-
quantum TLS and KEMTLS [8], [9], [10], [11], [33] measure
connection establishment under latency, loss and bandwidth
limits and decompose the handshake. They are the closest
systems precedents, but their amortization boundary differs: a
handshake protects a connection, whereas in client-side object
encryption key establishment and its ciphertext recur for each
object.
Storage studies measure the S3 interface without cryptog-
raphy, and client-side encryption without post-quantum key
establishment. Gadban and Kunkel [12] attribute losses on the
S3 path to layers of the client stack, a separation our harness
applies to cryptographic stages; Henziger and Carlsson [13]
and Ozeri et al. [14] concern where client-side encryption
sits and what it costs synchronization. Two 2026 preprints
approach post-quantum cloud storage from the design side:
Prikutse et al. [30] combine AES-256-GCM, X25519+ML-
KEM-768 and ML-DSA-65 and amortize signatures over a
batch of files, and Junaid [31] proposes a client-side hybrid
architecture with self-hosted key management. According to
their abstracts, neither evaluates concurrent S3 PUT/GET or
compares with classical per-object key establishment; we have
read only the abstracts. Bounded key reuse is established
practice in this setting: Amazon S3 Bucket Keys derive per-
object data keys from a time-limited bucket-level key and
reduce key-service requests by up to 99 % [34], and the AWS
Encryption SDK caches data keys under age, message and
byte limits [35]. Our session mode applies that principle to
ML-KEM roots and quantifies the trade-off.
In October 2026 we ran keyword searches, restricted to
arXiv, dblp and Semantic Scholar and on the open web,
combining ML-KEM, Kyber or X-Wing with object storage,
S3, MinIO, client-side encryption, envelope encryption and
concurrency; the queries and their outcome are logged in the
artifact. This is a keyword search, not a systematic review.
It returned primitive benchmarks, transport studies, vendor
tutorials and the two storage designs above, but, to our
knowledge, no measurement of per-object ML-KEM under
concurrent S3 load. The search did not cover IEEE Xplore,
the ACM Digital Library, the IACR ePrint archive or Google
Scholar, which is a limitation of that statement.
C. Benchmarking Method
Three strands of method inform our design. Cloud instances
show run-to-run and time-dependent performance variation
large enough to change conclusions drawn from single runs
[36], [37], [38], which is why our experimental unit is the
independently restarted run, compared in randomized blocks
and never across sessions. Reporting rules for performance
measurements [39], [40] ask for intervals over independent
repetitions and a full description of the setup. Schroeder et
al. [15] show that closed- and open-loop load generators
produce systematically different behaviour; our open-loop
observations are an instance of that result. For equivalence
we follow the two one-sided tests procedure [41], [42].
III. DESIGN AND THREAT MODEL
The network and the object store are honest-but-curious
for confidentiality and potentially malicious for integrity: an
adversary may read, replace, delete, reorder or replay stored
ciphertexts and manifests. The adversary does not hold the
recipient’s decapsulation key and may in the future operate
a quantum computer. Availability, traffic analysis, deletion of
whole objects, compromised endpoints and side channels in
the client are out of scope.
Writers are not authenticated. The envelope encrypts to a
public key and carries no signature, and neither does HPKE
base mode. Integrity therefore means that an object written
by an honest writer cannot be modified, reordered, truncated,
extended or spliced without detection. It does not mean that
an object is authentic: anyone who knows the recipient’s
public key, including the store, can create a new object
under any identity, and it will decrypt without error. Sender
authentication is out of scope.
Rollback is not prevented. Replay is detected only where it
crosses an identity: a manifest or chunk moved to another
object or another version fails authentication, because the
object identity and version are bound into the key and into

A third limit concerns key commitment. AES-GCM is not
key-committing: a ciphertext can be constructed that decrypts
validly under more than one key [43], [44]. We accept this
for the single-recipient setting studied here, on the following
argument. Since writers are not authenticated, a malicious
writer can already store any plaintext it likes under a key the
recipient will derive; a ciphertext that also decrypts under a
second key gives it no further capability against one recipient.
That argument is not a proof and we make no formal claim
(Table III). It does not extend to several recipients, where one
ciphertext could decrypt to different plaintexts for different re-
cipients, or to password-derived keys: a multi-recipient design
must use a key-committing construction [45].

Our envelope has the structure of HPKE base mode [18]:
one KEM encapsulation, a key derivation bound to application
context, and AEAD encryption of a sequence of records. It
differs in three ways. (1) The data key is derived with a single
HKDF-SHA256 call whose info is the object context, where
HPKE uses a labelled extract-and-expand key schedule that
also outputs a base nonce. (2) Chunk nonces are a random
prefix followed by a counter, where HPKE computes base
nonce XOR sequence number. (3) The chunk index, length
and final-chunk flag are authenticated in the associated data;
HPKE leaves truncation protection to the application. Mode
P1 uses a KEM that [19] defines for HPKE (ML-KEM-
768). That draft also defines an X25519+ML-KEM-768 hybrid
under the KEM identifier that the X-Wing draft [17] requests,
so P3 corresponds to it; we did not test interoperability. A
deployed example of this approach is the file-encryption tool
age, whose version 1.3.0 added HPKE-based hybrid ML-
KEM-768 recipients [20]. It shows that a per-file post-quantum
KEM is already practice; we found no performance study of
it under concurrent load. We did not implement or benchmark
HPKE. Since an HPKE-based envelope would perform the
same KEM operation once per object, a key schedule of a
few hash calls and the same AEAD, we expect the per-object
costs reported here to transfer, but that expectation is untested,
and a new design should use HPKE and not this format.

IV. IMPLEMENTATION AND METHODOLOGY
A. Implementation
Figure 1 shows the system and Table IV its components.
The client, harness and analysis are written in Python 3.12.3;
the project comprises 8,006 non-blank lines of code, including
290 automated tests.
ML-KEM-768 comes from liboqs 0.16.0 through liboqs-
python 0.16.0.1 [4], [47]. We build liboqs from a pinned
release with only the ML-KEM parameter sets enabled and
load it from an explicit installation path, so the benchmark
cannot silently pick up a different library; a start-up check
verifies the library version and that ML-KEM-768 is enabled,
and every call checks key and ciphertext sizes. RSA-OAEP-
4096 (SHA-256), X25519, HKDF and AES-256-GCM come
from pyca/cryptography 50.0.1 [48]. A registry maps each
mode to its key-establishment and recovery functions, and

The storage layer implements the commit protocol of Algo-
rithm 1 on the MinIO Python SDK 7.2.20. Ciphertext records
are passed to the SDK through a file-like adapter over the
encryptor’s output, so an object is uploaded in 8 MiB parts
while it is being encrypted; on GET the stream is decrypted
chunk by chunk into a sink. For benchmarking, the HTTP
client uses a connection pool sized to the worker threads
and performs no automatic retries, so failures are counted
rather than hidden inside latency. Auxiliary functions list
committed versions, verify a commit by reading it back,
delete versions and collect uncommitted data left behind by
interrupted uploads.
A run executes one configuration (mode, operation, object
size, concurrency and loop type) with freshly started worker
processes; it is the unit of replication. Concurrency N is
realized as exactly N worker threads spread over min(N, 16)
processes, one per vCPU. Each process warms up, reports
readiness, and all of them start at a common wall-clock instant,
so that no worker measures while others are still starting.


Each run has a 5 s warm-up phase and a 20 s measured phase;
Python’s garbage collector is run before and disabled during
the timed window, so its pauses cannot land inside a stage
timer. In closed-loop runs each thread issues requests back to
back. In open-loop runs each process draws Poisson arrivals
at its share of the target rate, a request waits in a queue for
a free thread, and the wait is recorded separately; a request
that cannot start before the end of the run is recorded as a
failure, never dropped. GET runs read a set of pre-written
fixture objects that are created before and deleted after the run,
and every object written by a PUT run is deleted afterwards,
outside the timed window.
Every request, including warm-up requests and failures,
produces one record with perf_counter timers for the five
stages of Algorithm 1 (key establishment, key derivation, AES-
GCM, manifest handling and storage), its total latency, the
thread CPU time it consumed, bytes on the wire and metadata
size, plus identifiers that tie it to its run, repetition, code
commit and configuration. A client sampler records the CPU
time and resident memory of the worker processes and the
host’s CPU and network counters once per second; a server
sampler reads the same information from MinIO’s Prometheus
metrics endpoint and, in the confirmatory campaign, dirty and
write-back memory, disk write rate and latency, and I/O wait
from a node-exporter endpoint on the server host.
A validator checks every data set before analysis and refuses
it if any check fails: checksums of all files; a complete schema
with correct types for every record; that no request’s stage
times exceed its total; that per run the 99th percentile of
unaccounted time stays below 2 % of the request time and
below 1 % in aggregate; and that no N1 session exceeds its
bound. The 290 automated tests cover the cryptographic core,
the commit protocol, tampering (bit flips; deleted, reordered,
duplicated, truncated or extended chunks; swapped, replayed
or relabelled manifests; mode downgrade), that manifests
contain no secret material and private-key files are protected,
session bounds under concurrent stress, and end-to-end runs
against a live MinIO.
A single script provisions and operates the cloud testbed:
it creates both instances in one cluster placement group with
a firewall that admits SSH only from the operator’s address,
copies the committed code, builds MinIO from source into
a Docker image, formats the server’s local NVMe disk at
boot, runs network (iperf3, ping) and disk (fio) baselines, starts
experiments in a detached session, fetches results and stops or
deletes all resources. Before launch, a planner estimates the
run time and cost of each experiment configuration. To bound
cost, both instances stop themselves when idle, and the client
stops itself shortly after an experiment completes.
As a second client (Section V-C) we wrote a deliberately
small reader in Go (1.26.2): the GET path of modes B2,
P1 and P3, with ML-KEM-768, X25519, HKDF, SHA-3 and
AES-GCM from Go’s standard library and the MinIO Go
SDK. A test opens objects written by the Python client in all
three modes and several sizes and rejects modified ciphertexts
and a wrong expected mode, so the two clients agree on the
object format. Because Go’s ML-KEM takes keys as seeds,
the recipient keys for this client are generated from seeds on
the Python side. Its benchmark runs goroutines in one process
and reports throughput, process CPU and latency; it has no
stage timers.
A summarizer streams the compressed request records of
each experiment once and writes one row per run. A statistics
stage computes intervals, paired equivalence tests, bottleneck
labels and the queueing models. A final stage generates every
figure, table and number in this paper as LATEX macros, so no
result is typed by hand.

The study has an exploratory campaign, a confirmatory

C. Statistical Analysis
For a cell and two modes a and b, repetition i gives the
paired log ratio di = log(xa,i/xb,i) of throughput. We test


equivalence with two one-sided tests (TOST) [41], [49] against
the bounds [log 0.95, log 1.05]:
H−
0 : E[d] ≤log 0.95,
H+
0 : E[d] ≥log 1.05,
each with a one-sided paired t-test at α = 0.05. The modes
are declared equivalent only if both are rejected, which is
the same as the 90 % confidence interval of the ratio lying
inside [0.95, 1.05]; the TOST p-value is the larger of the two.
We also show the 95 % interval for estimation. A cell whose
90 % interval lies wholly outside the bounds is non-equivalent;
anything else is inconclusive, which is not evidence of “no
difference”.
The margin of five percent is our smallest effect of interest
and was fixed in advance, as the margin the exploratory cam-
paign had already used. Its practical meaning is a provisioning
one: a 5 % loss of capacity raises utilization by the same
factor, so a deployment planned at or below 0.71 of peak
throughput stays under the stability boundary we measure for
this store (supplementary material) and needs no additional
capacity. That argument uses a result of this study and was
made after the fact; an operator with a tighter target needs a
tighter margin, which is why we report sensitivity at ±2 %
and ±10 % [42].
The pre-registered hypothesis is the ratio P1/B2 in eight
closed-loop cells chosen before the campaign: 64 KiB GET at
128 and 500 workers; 64 KiB PUT at 32 workers (the knee of
the throughput curve) and 128; 1 MiB PUT and GET at 32; and
16 MiB PUT and GET at 32. The eight p-values are adjusted
with Holm’s procedure [50], which controls the family-wise
error rate. A limitation of this family, recognized after the
campaign: only one cell, 64 KiB GET at 500 workers, has
a saturated client. The 64 KiB PUT cells are limited by the
server and the four cells at 1 MiB and above by the network
or the server; at 64 KiB GET with 128 workers the client is
the busiest resource but still has spare CPU, which a costlier
mode simply uses (see the CPU accounting below). In seven of
eight cells, therefore, no key-establishment mode could have
changed throughput, and equivalence there confirms where the
bottleneck is and little about ML-KEM. Throughput is also an
insensitive endpoint in those cells; we therefore add client CPU
per request as an exploratory second endpoint (Table XIII).
The same family measured on the ARM client is a replication
and is adjusted in the same way. All other comparisons (P3 and
P2 against P1 and B2, R1 against P1, and every cell outside the
family) are exploratory and reported with unadjusted intervals.
The number of repetitions follows from a power calcu-
lation. From the paired log-ratio standard deviations of the
exploratory campaign, a normal-approximation calculation at
α = 0.05/8 and power 0.8 required at most 7 repetitions in
every primary cell except the knee, which required about 19.
We therefore ran 10 repetitions per cell and 20 at the knee,
with no optional stopping.
The tests rest on a distributional assumption. The t-tests
assume approximately normal mean log ratios from 10 or 20
pairs. As a check we recompute each primary verdict from
a percentile-bootstrap 90 % interval of the mean log ratio
(20,000 resamples).
The stall rule was fixed in advance and is blind to the mode:
a closed-loop run is a stall if its server CPU is below 0.8
times and its throughput below 0.9 times the median of its
own cell. The primary analysis uses all runs; excluding stalls
is a sensitivity analysis.

Throughput is cores in use divided by CPU per request. If the
client CPU is exhausted, two modes use the same number of
cores, and the throughput ratio of mode a to mode b is the
inverse ratio of their client CPU per request,

This is an accounting identity, not an empirical finding and
not a model with free parameters: evaluated on the runs it
describes, its error measures only how equal the core counts
of the two modes are. We use it as a method, in two ways.
It localizes a throughput difference: if the identity holds, the
difference has no source other than client CPU. And it gives an
operator a procedure: measure CPU per request for the current
and the candidate mode on the real client, check whether the
client is saturated, and read off the expected change.
The saturation criterion differs between the two clients.
For the native reader the criterion was fixed in advance: a
cell is client-saturated if process CPU is at least 0.95 of the
cores made available, in every mode. For the Python client
no criterion was pre-registered, and we do not claim a sharp
one. In the 64 KiB GET cells the post-quantum modes use
nearly the same number of cores as X25519 at 500 workers
and visibly more at 128 workers (Table XV); RSA-4096 uses
more cores than X25519 in both. We therefore write “at or
near saturation” and describe the regime by what was observed
(next paragraph), not by a threshold.
A throughput deficit is defined by one rule. To say where
ML-KEM lowered throughput we apply one rule to every
closed-loop cell in which the Python client ran both ML-
KEM and X25519: a deficit if the 90 % interval of the paired
throughput ratio lies below 0.98, an advantage if it lies above
1.02. This is the rule pre-registered for the native reader;
applying it to the other experiments was decided afterwards
and is exploratory (see the end of this subsection).
The identity becomes a prediction only when applied to data
it was not computed from. We did that once, with a ratio fixed
before two follow-up experiments; it missed (Section V-C).

C. Why the Saturated Client Is Slower
The deficit in the saturated cell needs an explanation,
because on GET ML-KEM’s decapsulation is cheaper than
X25519’s exchange (Table VIII).
Table XV applies the identity of Section IV-C to 64 KiB
GET. At 500 workers, where the post-quantum modes and
X25519 use the same number of cores to within 0.1, the
inverse CPU ratio matches the observed throughput ratio of
ML-KEM and of both hybrids to within 0.9 percentage points
on both architectures, and that of RSA-4096, which needs
more than twice the CPU, to within 1.7. At 128 workers
the costlier mode uses more cores, throughput holds, and the
identity, which assumes equal cores, overstates the loss by 1.8–
3.0 points for the post-quantum modes and 3.5 for RSA-4096.
In the saturated cell the deficit of Section V-B is therefore
a difference in client CPU: ML-KEM needs 79 µs more per
request than X25519 on x86 (of 1.71 ms) and 109 µs more on
ARM.

The stage timers therefore rule out decapsulation and leave
two candidates: the handling of a manifest 1,412 bytes larger,
and the way the client reaches ML-KEM. We tested each
with a pre-registered control on 64 KiB GET at 500 workers
(Table XVII; decision rules fixed before the runs).
The first control, Control-Manifest, tests manifest size.
Mode C2 is X25519 whose stored ciphertext is zero-padded
to 1,088 bytes, so its manifest is byte-for-byte as long as ML-
KEM’s. Padding alone costs 0.7 % of throughput (ratio 0.993,
90 % CI 0.991–0.995). ML-KEM remains 3.3 % slower than
the padded control (0.967, 0.965–0.969). By the pre-registered
rule, manifest size does not explain the deficit: it accounts
for 17 % of it (90 % CI 14–21 %). At one worker the padded
control shows the same slower manifest stage as ML-KEM
(+6.0 µs against +5.6 µs), so that stage difference is purely one
of size, and it is small.
The second control, Control-Binding, tests the library bind-
ing. Our client reaches liboqs through liboqs-python, which
creates a key-encapsulation object for every operation and
makes four foreign calls per decapsulation (allocate, decapsu-
late, cleanse, free), each releasing the interpreter lock; X25519,
through pyca/cryptography, is a single call. Modes H1 and
G1 run the same liboqs ML-KEM-768 and write the same
manifest as P1, but make one foreign call per operation on a
handle created once per process; H1 releases the interpreter
lock around it and G1 holds it. With one call, throughput
is equivalent to X25519’s within ±2 %: H1 reaches 0.999
(0.997–1.002) and G1 1.002 (0.997–1.006), while P1 in the
same experiment is at 0.963 (0.960–0.967). By the pre-
registered rule the binding explains the deficit; it removes 99 %
of it (90 % CI 92–105 %). Whether the single call releases the
lock makes no measurable difference (G1/H1 1.002, 0.999–
1.006), so the cost lies in the per-operation object handling
and the number of foreign calls, not in the locking policy
as such. The one-worker timers agree: a decapsulation takes
0.047 ms through the binding and 0.028 ms as a single call,
against 0.050 ms for X25519.
The controls establish the following. On the x86 Python
client, where both controls ran, the deficit in the saturated cell
is produced by how the binding invokes the library: 17 % of it
comes from the larger manifest, and with one foreign call per
operation ML-KEM is equivalent to X25519 within ±2 %. The
two controls are independent and their effects need not add up:
the one-call modes carry the larger manifest and still match
X25519. The deficit itself was observed in three independent
experiments on two server instances (0.960, 0.960 and 0.963).
The controls were not run on ARM (Section VI).
The one advance prediction missed. Before Control-
Manifest and Control-Binding we fixed a predicted ratio of
0.956 from the CPU ratio measured in Primary-x86. The
observed ratios differed from it by 0.4 and 0.7 points, and
the prediction lay outside both intervals. The identity holds
within an experiment; it did not carry a ratio exactly from one
experiment to the next.
Finding 3. On the x86 Python client, the 4.0 % deficit in the
saturated cell is produced by the binding, which makes four foreign
calls per decapsulation: with one call ML-KEM is equivalent to
X25519 within ±2 % (0.999 of its throughput). The larger manifest
accounts for 17 % of the deficit.
If the Python client’s deficit is a binding artifact, does a
compiled client show none? We wrote a reader in Go that
implements the GET path of modes B2, P1 and P3 and
opens objects written by the Python client; it does the same
per-object work (two S3 reads, manifest parsing, ciphertext-
hash check, key recovery, HKDF, AES-GCM per chunk,
a hash of the plaintext), with ML-KEM-768 and X25519
from Go’s standard library. A compiled client needs so little
CPU that 16 cores cannot be saturated by this store, so the
pre-registered primary cell restricts it to one core with 128
workers, which saturates it by construction (Native-GET, 90
runs, Table XVIII).
The result for the native reader is as follows. In the saturated
cell ML-KEM reaches 0.905 of X25519’s throughput (90 %
CI 0.900–0.910) and X-Wing 0.826 (0.821–0.831): by the
pre-registered rule, a deficit for both. Their CPU per request
is higher by the inverse factors (1.105 and 1.211); here the
identity of Section IV-C holds by construction, since every
mode ran on exactly one core, and this is not a validation of
it. On one core the native reader spends 343 µs of process CPU
per request with X25519.

E. Storage Overhead
The lasting cost of post-quantum key establishment is
storage. Table XXI converts the per-object manifest into fleet
totals. An ML-KEM manifest is 2,034 bytes, 1,412 more than
X25519; X-Wing adds another 40. Two parts of that difference
must be kept apart. The intrinsic cost of ML-KEM is its
ciphertext, 1,056 bytes more than an X25519 public key.
The remaining 356 bytes are our encoding: the manifest is
JSON and carries the ciphertext in base64 (1,452 characters),
plus 4 bytes for a longer algorithm name. For one billion
objects the difference is 1.41 TB (1.28 TiB) in this encoding
and 1.06 TB with a binary one. Relative to the payload it is
negligible from 1 MiB upward and larger than the payload
itself at 1 KiB. These are logical bytes: replication or erasure
coding multiplies them, and because the manifest is a separate
S3 object in our design, it also doubles the number of stored
objects and write requests, which matters under per-request
billing and for inventory scans. Carrying the manifest in the
object’s own metadata, as the Amazon S3 Encryption Client
does by default [2], would avoid the second object. Amazon S3
limits user-defined metadata to 2 KB per object [51]: our JSON
manifests for ML-KEM and both hybrids (2,034–2,085 bytes)
are at or above that limit, whereas a binary manifest (a 1,088-
byte ciphertext and a few hundred bytes of context) would
fit, provided the store accepts binary metadata values or the
client pays the base64 expansion once more in the header. Our
storage results therefore describe a two-object, JSON-manifest
design, which we chose so that an interrupted upload is never
visible and a manifest can be read without the data; they
overstate both the bytes and the request count of a metadata-
based design.
Finding 5. Against X25519, ML-KEM-768 adds 1,056 bytes of
ciphertext per object, and 1,412 in our JSON encoding: irrelevant
for large objects, dominant for kilobyte-sized ones, and 1.06–
1.41 TB per billion objects before redundancy.
F. Bounded Sessions
A session changes what a compromise exposes. In P1 every
object has its own shared secret, and an attacker who obtains
one learns one object. In N1 the unit of compromise is the
session root: whoever reads a root from process memory, a
crash dump, a swap file or a log can derive the data keys of
every object it protected, at most Bmax objects written within
Tmax seconds. A cache shared between tenants would extend
that exposure across tenants, so roots must be scoped to one
recipient key, as ours are. This exposure is distinct from, and
much smaller than, compromise of the recipient’s long-term
decapsulation key, which exposes all objects in every mode.
The theoretical 1/Bmax operations per object holds only when
sessions fill before the time limit, so we report what was
observed.
Table XXII gives the result for 1 KiB PUT, the workload
where key establishment is the largest share of a request.
Operations per object follow 1/Bmax when sessions fill
(0.0011 at Bmax = 1000, Tmax ≥10 s). When the time limit
binds first they do not: at Tmax = 1 s a root protected a median
of 248 objects under closed-loop load (0.0038 operations
per object) and 94 under light open-loop load, where even
Bmax = 100 was not reached (median 94). The time limit, not
the object limit, therefore bounds exposure for lightly loaded
clients.
Client CPU per request falls by 2.1–3.7 % for Bmax ≥10,
and nearly all of that is reached at Bmax = 10. A session of
one object costs 1.7 % more CPU than P1, the bookkeeping
overhead of the mechanism.
Throughput and tail latency do not change: in none of the
9 configurations with Bmax ≥10 does the throughput interval
exclude 1 (0.966–1.062), because this workload is limited by
the server. On a client-bound workload, 64 KiB GET at 32
workers, a receiver that caches roots gains 3.3 % throughput
(95 % CI 3.1–3.5 %) at Bmax = 100. This is an upper bound:
the run reads 32 objects repeatedly, so every root stays in
the receiver’s cache and almost no decapsulation remains;
a workload with a large working set would gain less. The
exploratory campaign agrees: N1 saved 30–66 µs of CPU per
request at one worker and raised throughput only for small
GETs at 32–128 workers (1.4–5.1 %). Its queue-aware variant
lowered the bound under light load as designed, re-keying
5.5× as often as a fixed bound of 100 at 1,500 requests/s
with no measurable change in tail latency; we did not show
that it is better than a smaller fixed bound.
The measurements support a conservative rule. Per-object
ML-KEM is the default. Amortization is enabled only for a
workload in which profiling shows the client CPU to be the
bottleneck, and then with the smallest bound that achieves the
gain: in our data Bmax = 10 already removes most of the
CPU cost, so a larger bound buys exposure without benefit.
Tmax should be set from the tolerated exposure of an idle
client, since it is the limit that binds under light load. The
same reasoning applies to the choice between ML-KEM and
a hybrid: where the client is not the bottleneck the hybrid
costs only 40 bytes per object, and where it is, the cost is the
throughput difference reported in Section V-D.
Finding 6. Sessions trade compromise scope for a 2.1–3.7 % saving
in client CPU. That saving becomes throughput only on client-
bound workloads; a bound of 10 objects captures most of it.

and the diagnostic was exploratory.

Order and time effects were checked as follows. Modes are
shuffled within each repetition. As a check, for each primary
cell we regress log throughput on the mode, repetition fixed
effects, elapsed time in the experiment, position in the block
and whether the previous run was a PUT. The adjusted P1/B2
ratio differs from the paired ratio by at most 1.1 % in any cell
on either architecture.
The ARM replication reproduces the pattern: equivalence at
1 MiB and above, a deficit of 4.0 % (x86) and 4.9 % (ARM)
in the client-bound cell, and noise in small PUT. Because that
testbed also has another server instance, it tests the robustness
of the ratios and not ARM against x86 in absolute terms.
Threats to internal validity are the following. Stage timers
above one worker include interpreter-lock waiting, so key-
establishment time is reported at one worker only. During the
x86 chain of the confirmatory campaign, completed experi-
ments were downloaded from the client while parts of Hybrid-
Matrix, Sessions and Open-Loop were running; the transfer
used client CPU and network and may have added noise
to those runs. Mode order is randomized within repetitions,
so it cannot favour a mode, and no transfer overlapped
Primary-x86 or Primary-ARM. Modes differ in manifest size
as well as in key establishment; Control-Manifest separates
the two for the Python client only (Section V-C). Seven of
the eight primary cells could not have shown an effect of
the mode on throughput. The exploratory campaign’s pause
failure (Section IV) added noise to small PUT cells; its results
for those cells come from Expl-SmallPUT. The 1 MiB one-
worker slowdown of the hybrids is attributed to the allocator
by an exploratory diagnostic and keeps an unexplained residual
(Section V-G). The profiling attribution names a subsystem,
not a function. The two inconclusive primary cells were under-
powered; Power-PUT repeated them on x86 only, so on
ARM 64 KiB PUT at 128 workers and 64 KiB GET at 500
workers remain inconclusive. Both controls, Control-Manifest
and Control-Binding, ran on the x86 client only: the ARM
client uses the same binding and shows a similar deficit, but
the attribution to the binding is not tested there. The line we
draw between a saturated and an unsaturated Python cell rests
on a difference of a few tenths of a core, was drawn after
the data and was not pre-registered; anomaly A3 may be a
consequence of drawing it too high.
Threats to external validity are the limits of what the data
supports. Most of the study uses one Python client with liboqs
through a binding, and Control-Binding shows how much
that instrument can shape a result: its one client-bound deficit
was produced by the binding. The native reader removes the
interpreter but covers only the GET path of three modes at one
object size, uses different cryptographic implementations, and
reaches saturation only when confined to one core, which is an
artificial condition; a production client saturating many cores
may behave differently. The baseline set is narrow: no ML-
KEM-1024, no RSA-3072, and no remote key-service wrap,
which is a common deployment path. MinIO ran as a single
node without erasure coding or replication, in a community
edition that is no longer developed; a distributed deployment


has a different write path and may have a different ceiling
and knee. Both hosts sat in one placement group with a sub-
millisecond round trip; a wide-area client would be dominated
by the network. All runs used AWS, in two regions, with one
server instance type. liboqs is intended for prototyping, not
production.
Threats to construct validity concern what the measures
mean. Throughput equivalence within ±5 % is an engineering
criterion, not a statement that two modes are identical; a ratio
of 0.960 with a narrow interval is formally equivalent and still
a real difference. The CPU accounting is an identity on the
runs it describes; in the native reader it holds by construction;
its one advance prediction missed by up to 0.7 points and lay
outside both intervals. The statement that a throughput cost
appears only at or near client saturation is contradicted by
anomaly A2 if “saturation” is read strictly, and the Python
client’s process CPU and the native reader’s are not measured
the same way (thread CPU at 500 workers against process
CPU on one core), so their per-request figures should not be
compared as like for like. The exploratory verdict counts are
not corrected for multiplicity. Runs last 20 s; slower effects
such as compaction or long-term memory growth are not
observed.
The following have not been run, and the paper’s claims
are limited accordingly. (1) A full native client: PUT, the
remaining modes and several object sizes, saturating many
cores, with a second ML-KEM implementation so that library
and language can be separated. (2) A manifest control in the
native reader, to split its ML-KEM cost into key recovery
and manifest handling by measurement and not by a separate
timing. (3) An HPKE-conformant envelope, to confirm that the
per-object costs transfer. (4) Wider baselines: ML-KEM-1024,
RSA-3072 and a remote key-service wrap. (5) A distributed
or second S3 implementation, and runs of 10 to 30 minutes,
for the store-side results. (6) The two controls on the ARM
client. (7) Multi-recipient objects, which would need a key-
committing construction.
VII. DISCUSSION AND CONCLUSION
A practitioner learns more from these measurements than
the back-of-envelope estimate gives. That tens of microsec-
onds of KEM are small against milliseconds of storage is true
but incomplete. Three things could not have been read off that
estimate. First, the regime in which a cost appeared is narrow
and identifiable: a client at or near CPU saturation, with the
size of the cost given by client CPU per request. Second, the
first cause we suspected was wrong. The 1,088-byte ciphertext
and its handling explain 17 % of the x86 Python client’s deficit;
the rest came from a binding that crosses into native code four
times per decapsulation. Third, the size of the effect depends
on the library: the ML-KEM operation was cheaper than an
X25519 exchange with liboqs called directly and dearer in
Go’s standard library, and the throughput cost under saturation
ranged accordingly from equivalence within ±2 % to 9.5 %. In
no saturated cell was ML-KEM faster than X25519.
For migration planning, the CPU accounting of Section IV-C
gives a short procedure. Measure client CPU per request for
the current and the candidate mode on the real workload
and client. If clients are well below CPU saturation, our
data gives no reason to expect a change in throughput, with
the reservation of anomaly A2. If they are saturated, expect
throughput to change by about the inverse ratio of the two
CPU figures: 4.0–4.9 % in our Python client, 9.5 % in our
native reader on one core, and equivalence within ±2 % with
a one-call binding on x86. A measurement on one client stack
does not transfer to another.
For library authors the lesson concerns bindings. A binding
that allocates an object and makes several foreign calls per
operation can cost more under thread contention than the
cryptography it wraps. In our x86 client, holding a handle
per process and making one call per operation removed 99 %
of the deficit (90 % CI 92–105 %); whether that call released
the interpreter lock made no measurable difference.
The cost that does not depend on the implementation is ML-
KEM’s 1,088-byte ciphertext: 1,056 bytes more per object than
an X25519 key, or 1,412 more in a JSON/base64 manifest,
which puts such a manifest at or above the 2 KB that Amazon
S3 allows for user-defined metadata (Section V-E). For hybrids
there is in addition a client-CPU increment under saturation.
RSA-4096 is the poor choice: its private-key operation makes
small-object reads CPU-bound at 0.42–0.46 of ML-KEM’s
throughput in the Python client.
On the capacity of the store, the open-loop measurements
are reported in the supplementary material because they de-
scribe the store and not post-quantum cryptography. Their
result is that mean response time doubles at 0.68–0.81 of
peak closed-loop throughput, in line with the known gap
between closed- and open-loop behaviour [15]; the exploratory
campaign found that knee in the same place for the symmetric-
only mode and for ML-KEM.
In conclusion, we evaluated per-object post-quantum key
establishment on an S3-compatible store with a Python client
on x86 and ARM and with a native Go reader, against a single-
node MinIO server on AWS. In these configurations ML-KEM
lowered throughput against X25519 only where the client was
at or near CPU saturation, with one unexplained exception in
the native reader (Section V-G). In the one saturated cell of
the pre-registered family the Python client was 4.0 % (x86)
and 4.9 % (ARM) slower; two pre-registered controls on x86
attribute that deficit to the library binding and 17 % of it to
the larger manifest, and with one foreign call per operation
ML-KEM was equivalent to X25519 within ±2 %. A native
reader saturated on one core was 9.5 % slower with ML-
KEM and 17.4 % with X-Wing; a slower key recovery in
its library accounts for about half of the extra CPU for ML-
KEM and about three quarters for X-Wing. In the saturated
cells the throughput loss matched the extra client CPU per
request, which makes CPU per request the quantity to measure
before a migration. The size of the cost depends on the client
implementation. The cost that every implementation pays is
storage: 1,056 bytes more per object than X25519.


These results describe two clients, one single-node store
and one cloud provider, and the native reader covers the GET
path only. They should not be extended to distributed object
stores, other S3 implementations, other libraries or wide-area
deployments without new measurements (Section VI).
