Abstract
Vector search engines built on cloud object storage have drawn
growing attention from both academia and industry. These systems
typically adopt a disaggregated storage-compute architecture, per-
sisting the primary vector payload in object stores (e.g., Amazon
S3) while retaining compact index metadata on compute nodes.
However, conventional vector indexing structures are not natively
tailored to the pronounced network latency and per-request access
costs of cloud object stores, resulting in network I/O amplification,
degraded query throughput, and higher API expenses.
To resolve these challenges, we present RemoteANN, a vector
search engine explicitly co-designed for cloud object storage across
indexing and querying. To mitigate the dominant network I/O bot-
tleneck, RemoteANN couples an Inverted File (IVF) index with
RaBitQ quantization, further optimized by inter-cluster and intra-
cluster data reordering for improved data locality. Building on this
tailored data layout, RemoteANN’s query engine combines cluster
pruning, fine-grained Range-GET requests, request merging, and
local NVMe SSD caching, dramatically reducing discrete storage
requests and network transfer volume without sacrificing accuracy.
To address the index construction bottleneck, we further develop
QGKMeans, which substantially reduces construction latency with-
out compromising clustering quality. Extensive evaluations on real-
world datasets demonstrate that, compared with representative
baselines, RemoteANN achieves up to a 5.9× throughput speedup
while issuing up to 16.1× fewer object storage requests at 97% target
recall.

Introduction
Cloud object storage platforms (e.g., Amazon S3 [3], Azure Blob
Storage [50], and Torch Object Storage [12]) have become an attrac-
tive storage backend for modern database systems, owing to their
horizontal scalability, high data durability, and cost efficiency. By
decoupling compute from storage, this architecture allows stateless
compute instances (e.g., AWS EC2 [2]) to handle query execution
while offloading primary data to elastic, remote object stores. Moti-
vated by these infrastructure benefits, both academia and industry
have sought to extend this paradigm to vector database systems
and approximate nearest neighbor (ANN) search engines (e.g., Ama-
zon S3 Vectors [4], Turbopuffer [61], Lance [46], Databricks [53]).
In these systems, compact index metadata and routing structures
reside in the compute nodes’ local storage, while the bulk of high-
dimensional vector payloads is persisted in cloud object storage.
However, conventional vector index structures are not natively
suited to cloud object storage, and deploying them directly leads
to suboptimal query performance and elevated operational cost.
First, compared to local storage media (e.g., DRAM and local SSDs),
data retrieval from cloud object stores incurs substantial time-to-
first-byte (TTFB) network latency, which dominates total download
latency for small payload requests [19]. As a result, graph-based
index structures [22, 40, 49] suffer severe performance degradation
due to their iterative, multi-hop routing patterns, and existing vector
search systems on cloud object storage predominantly adopt cluster-
based indices instead (e.g., IVF in Lance [46] and SPFresh [65] in
turbopuffer [61]). Second, cloud providers charge substantially for
the number of discrete storage requests issued, which is a cost
dimension that traditional, locally-oriented index designs do not
account for. A naive implementation can therefore trigger excessive
request volumes, leading to prohibitive API costs. Despite this, no
existing system jointly optimizes index layout, index construction,
and query execution for the latency and cost characteristics of cloud
object storage.
To close this gap, we present RemoteANN, a vector search engine
explicitly designed for cloud object storage. Through an algorithm-
system co-design spanning indexing, querying, and the storage
hierarchy, RemoteANN systematically mitigates the network I/O
bottlenecks that limit vector search on cloud object storage. Specif-
ically, RemoteANN makes the following contributions in both in-
dexing and querying:
• Query-Oriented Indexing and Data Layout.
RemoteANN combines an IVF index with RaBitQ quanti-
zation [25, 27]. Following existing frameworks, it keeps
index metadata and 1-bit RaBitQ codes in DRAM while
storing primary vector payloads in cloud object storage.
The memory-resident codes support pruning before remote
data retrieval, while inter-cluster and intra-cluster data
reordering improve physical locality. These changes sub-
stantially improve the effectiveness of our I/O optimization
strategies during querying. To reduce the cost of index-
ing, we develop QGKMeans, which uses SymphonyQG [31]
to accelerate centroid assignment during 𝑘-means cluster-
ing. This substantially reduces index construction latency
without compromising clustering quality.

• Co-Designed Query Engine.
RemoteANN incorporates a multi-tier query optimization

We evaluate RemoteANN on diverse real-world datasets span-

representative baselines.

Preliminary
2.1
Cloud Object Storage
Cloud object storage refers to the online object storage service of-
fered by cloud vendors [3, 12, 30, 37, 50, 52, 60]. By orchestrating a
distributed environment across diverse storage nodes and servers,
cloud object storage delivers high data durability, seamless hori-
zontal scalability, and exceptional cost-efficiency, rendering it ideal
for hosting massive scales of unstructured data.
Cloud object storage differs fundamentally from local storage
across two primary aspects: the pricing model and underlying I/O
characteristics, both of which require careful design of the system
built on it. First, regarding data retrieval operations, cloud vendors
mainly charge the user by the number of requests 1. Second, the
retrieval operations incur high latency due to the time-to-first-byte
(TTFB) overhead (typically tens of milliseconds) introduced by
network communication. As established in a previous study [19],
this TTFB penalty dominates total latency for small payload sizes.
2.2
Vector Search on Cloud Object Storage
The inherent advantages of cloud object storage have driven in-
terest from both academia and industry in building ANN search
engines on it (e.g., Amazon S3 Vectors [4], Turbopuffer [61]). As
illustrated in Figure 1, these systems typically contain two core
layers: (i) a compute instance utilizing local storage (memory and

disk) to cache index metadata, and (ii) a cloud object store respon-
sible for persisting the primary index payload data. To mitigate
the pronounced TTFB latency overhead intrinsic to cloud object
stores, these engines predominantly adopt cluster-based ANN in-
dices (such as IVF variants and SPFresh [4, 18, 61, 65]) rather than
popular graph-based indices [22, 40, 49] for in-memory or disk-
based scenarios. This is because cluster-based indices can fetch
all target vector data within a single network round-trip from the
cloud object storage. Conversely, the iterative routing pattern of
graph-based indices necessitates multi-round-trip network traver-
sals, leading to cumulative TTFB overhead and inflated end-to-end
query latency.
2.3
RaBitQ Quantization
For vector search, quantization constitutes a class of techniques de-
signed to compress high-dimensional vectors into compact, low-bit
quantization codes [6, 9, 10, 25, 27, 29, 33, 41, 62, 63, 66, 67]. During
query processing, the system uses these compressed codes for dis-
tance estimation. Recently, a novel quantization framework named
RaBitQ [24, 25, 27] was proposed to address the limitation (i.e., the
lack of theoretical support) of classical quantization methods.
During indexing for 𝐷-dimensional vectors, RaBitQ constructs a
codebook with 2𝐵·𝐷unit vectors using a uniform grid, where 𝐵de-
notes the number of bits allocated per dimension. Subsequently, the
codebook is randomly rotated via Johnson-Lindenstrauss Transfor-
mation [42], and each data vector is normalized and then quantized
to its nearest codeword within the codebook. For querying, RaBitQ
estimates the distances between a query vector and data vectors
based on their codewords. Based on rigorous theoretical analysis,
the RaBitQ estimator provides an unbiased estimation with a theo-
retical error bound, enabling superior empirical retrieval accuracy
across real-world workloads [25].
3
Methodology
In this section, we present the comprehensive system design of our
cloud vector search framework called RemoteANN, discussing both
index construction and query processing optimizations tailored for
the specific environment. Due to the high I/O latency of the cloud
object storage discussed in Section 2.1, we choose the IVF index
since it enables single-round-trip target cluster retrieval for a given
query. To mitigate the remaining cloud I/O overheads, we introduce
coordinated architectural optimizations spanning both indexing
and querying.
We present details of our indexing pipeline in Section 3.1, in-
cluding the heterogeneous storage layout configured with RaBitQ
quantization (Section 3.1.1), our efficient IVF clustering acceler-
ation (Section 3.1.2) and data reordering strategies to boost data
locality and support query optimization strategies (Section 3.1.3).
Section 3.2 then details our proposed query processing framework.
Specifically, for an IVF index deployed on cloud object storage,
the query engine initially identifies the 𝑛probe target clusters for
a given query vector via the metadata resident on the compute
node, subsequently fetching the corresponding data payloads from
cloud object storage. To reduce cloud I/O overhead, our engine
incorporates four optimization strategies: namely RaBitQ-based
2


cluster-level pruning (Section 3.2.1), fine-grained range optimiza-
tion (Section 3.2.2), request merging (Section 3.2.3), and caching
(Section 3.2.4). These multi-tier components are structurally co-
designed; the layout properties established during index generation
directly dictate and unlock the high-efficiency I/O primitives lever-
aged throughout query processing. Section 3.3 provides a summary
of the indexing and querying components of RemoteANN.
3.1
The Index Phase
3.1.1
Storage Layout of IVF index with RaBitQ Quantization. As
established in Section 2, vector search on cloud object storage con-
tains two components – the compute node and the cloud object
storage, thereby establishing a distinct three-layer storage hierarchy
consisting of local DRAM, local disk, and remote storage. To opti-
mize operational costs, the system may persist all data exclusively
within cloud object storage during periods of inactivity. When a
query is initiated, the system needs to spin up a compute instance
and pull required data from the cloud object storage through the
network, which results in a severe cold-start penalty with prohibi-
tive initial query latency. We note that this latency can be mitigated
via strategic system-level co-design. For instance, when integrating
vector search engines with interactive downstream applications
(e.g., conversational AI agents), the user’s interaction (e.g., typ-
ing) can serve as early pre-fetching signals. The backend system
captures these initial signals to asynchronously initiate the down-
load of index metadata, effectively hiding the cold-start latency.
Therefore, in this study, we restrict our focus to the warm query
processing paradigm, where the high-precision vector data resides
permanently within the cloud object storage, whereas frequently
accessed index metadata (e.g., the IVF cluster centroids) are pinned
within the compute node’s main memory during query processing.
We detail our data layout framework as follows.
The compute node’s DRAM caches the high-dimensional cen-
troid vectors and the low-precision quantized data vectors as a rout-
ing index. Specifically, we leverage the RaBitQ quantization [25, 27]
to compress high-dimensional raw vectors into a 9-bit representa-
tion2. Furthermore, we partition this 9-bit code into a 1-bit prefix
and an 8-bit suffix. The 1-bit prefixes are resident in local DRAM,
whereas the corresponding 8-bit suffixes are persisted in cloud ob-
ject storage. If the compute instance is configured with local NVMe
SSD, the system can utilize it as an intermediate cache for the 8-bit
suffixes of frequently accessed clusters. The primary objective of
this decoupled quantization scheme is to optimize cloud object
storage I/O – the dominant performance bottleneck of the whole
system. The RaBitQ framework delivers high-accuracy distance
estimation with rigorous theoretical guarantees. Consequently, the
query engine can exploit the in-memory 1-bit prefixes to prune
vectors and clusters, thereby reducing both the total number of
distinct Range-GET requests issued to cloud object storage and the
data volume downloaded (detailed in Section 3.2).

3.1.3
Data Reordering for Facilitating Query Processing. In con-
ventional in-memory or disk-based IVF storage layouts, multiple
clusters share a large binary file, and the query engine retrieves the
selected clusters from this file. Both the order of clusters within
the file and the order of vectors within each cluster are typically
arbitrary, as efficient random access in RAM and SSDs makes these
layouts less sensitive to physical ordering. However, directly adopt-
ing this layout and access pattern in cloud object storage introduces
two issues.
First, because the vendors charge users of cloud object storage
by the number of requests, issuing discrete Range-GET requests
for every target cluster becomes financially non-viable, particularly
for high-recall queries that necessitate traversing many clusters. A
straightforward solution is to consolidate multiple target clusters
into a unified request, thereby substantially reducing the query
cost. However, if the target clusters for a given query exhibit poor
spatial locality (i.e., they are sparsely distributed across the index
object), request consolidation becomes highly inefficient, as the
growing request size amplifies the overall download latency. Second,
monolithic downloading for every target cluster introduces severe
I/O inefficiencies. An individual IVF cluster may contain hundreds
or even thousands of vectors, yet a given query typically finds only
a small fraction of them as promising nearest neighbor candidates.
Consequently, always downloading the whole cluster results in a
waste of network bandwidth and degraded throughput, especially
for the workload with many concurrent queries.
To address these two problems, we introduce two query-side
optimization strategies: request merging and range optimization. The
former consolidates disparate cluster requests into a unified one,
while the latter reduces the data volume transferred per cluster.
We detail these query processing mechanisms in Sections 3.2.3
and 3.2.2, respectively; this section focuses on the indexing part

Inter-cluster reordering. To enable effective request merging,
we need to reorder clusters within the IVF object so that clusters
likely to be accessed together are placed close to one another. Recall
that IVF selects target clusters based on the distances between the
query vector and the cluster centroids. Intuitively, clusters with
nearby centroids are more likely to be selected together by a query,
motivating us to place them close to one another in the IVF object.
Assuming no prior knowledge of the query workload, we deter-
mine the cluster order solely from the centroids. Specifically, we
seek an ordering that minimizes the sum of distances between the
centroids of consecutive clusters. We formulate this objective as a
minimum-weight Hamiltonian path problem, where each vertex
represents a cluster and each edge is weighted by the Euclidean
distance between the corresponding centroids. We then seek an
approximate minimum Hamiltonian path under the Euclidean dis-
tance metric. Because the minimum Hamiltonian path problem is
NP-hard, exact solutions are impractical for large cluster counts
(the best-known classical exact algorithm based on dynamic pro-
gramming runs in 𝑂(𝑛22𝑛) time [28], where 𝑛is the number of
vertices/clusters). Given that the edge weights satisfy the trian-
gle inequality, we can leverage polynomial-time approximation
frameworks to achieve high-quality results. Specifically, we adopt
two foundational algorithms: the nearest-neighbor heuristic, which
provides an 𝑂(log𝑛) worst-case approximation [54], and the MST-
doubling algorithm, which provides a 2-approximation [35]. Both
algorithms require an initial distance matrix computation, lead-
ing to a total time complexity of 𝑂(𝑛2𝑑) for 𝑑-dimensional vectors.
While more advanced algorithms achieve tighter theoretical bounds
(e.g., [5, 68]), they introduce substantial computational overhead,
which degrades the efficiency for index construction. Additionally,
we evaluate space-filling curves, specifically the Hilbert and Z-order
curves [34, 51, 55], as alternative baselines because of their estab-
lished utility for data ordering and nearest-neighbor search [13, 48].
As space-filling curves suffer from the curse of dimensionality, we
introduce a dimensionality reduction by Principal Component Anal-
ysis (PCA) to project the high-dimensional cluster centroids into a
3-dimensional subspace before using them for reordering.
We evaluate the four aforementioned cluster reordering strate-
gies on six million-scale datasets. We utilize QGKMeans to construct
4


the initial IVF index with 4, 096 clusters, where the resulting cen-
troid sequence naturally exhibits an arbitrary, randomized baseline
order. We subsequently execute our four reordering strategies over
these centroids. To quantify the quality of inter-cluster reordering,
we compute the total Hamiltonian path length (i.e., the cumulative
Euclidean distance across all adjacent pairs in the global cluster
sequence) for both the baseline and optimized configurations. The
results are presented in Table 2. As illustrated, the nearest-neighbor
heuristic achieves the minimum Hamiltonian path length across all
evaluated datasets, despite the fact that the MST-doubling algorithm
offers a superior theoretical worst-case approximation. Conversely,
the space-filling curves exhibit significantly longer Hamiltonian
paths. Therefore, our framework implements the nearest-neighbor
heuristic as the default cluster reordering method. Section 3.2.3
evaluates how different inter-cluster reordering methods influence
request merging during ANN search, which presents the effective-
ness of reordering by reducing the Hamiltonian path length.
To mitigate the 𝑂(𝑛2𝑑) computational overhead encountered
on large-scale datasets with many centroids, we introduce a pre-
liminary centroid partitioning process 3. Specifically, we employ
a recursive bisection 𝑘-means strategy to progressively subdivide
the centroids until the cardinality of each leaf node is less than a
predefined constraint. Subsequently, the localized nearest-neighbor
heuristic is applied independently within each partition, and the
resulting sub-sequences are coalesced according to the hierarchical
tree traversal order to finalize the global cluster sequence. When
evaluated on 262, 144 centroids, the whole reordering process com-
pletes in less than 1 minute, demonstrating operational viability for
large datasets.
Intra-cluster reordering. Range optimization aims to selectively
download only the specific byte range within an IVF cluster that
contains promising nearest-neighbor candidates for a given query.
To boost the range optimization, we sort vectors within each cluster
by their Euclidean distance to the centroid. Intuitively, when a clus-
ter’s centroid is far from the query, vectors near the centroid are less
likely to contribute to the final top-𝑘results, while peripheral vec-
tors may remain relevant. This ordering groups peripheral vectors
into a contiguous region, potentially reducing the byte range that
needs to be downloaded. Moreover, our RaBitQ-based range opti-
mization also benefits from distance-based intra-cluster reordering,
which will be further explained and evaluated in Section 3.2.2.

Our pruning strategy shares similar high-level goals with the
query-aware dynamic pruning adopted in SPANN and SPFresh [14,
65]. However, our approach diverges fundamentally in its pruning
criterion and mathematical foundations. SPANN and SPFresh rely
on a ratio-based heuristic (i.e., discarding clusters whose distances
to the query exceed that of the nearest cluster by a predefined
multiplier), and provide no theoretical guarantees. Furthermore,
this ratio introduces an additional hyperparameter that complicates
user configuration and system setting. In contrast, our mechanism
leverages the error bounds of the RaBitQ estimator to establish
high-probability analytical error bounds, providing a theoretically
grounded pruning criterion while eliminating the overhead of pa-
rameter tuning.
3.2.2
Range Optimization for Request Size Reduction. Range opti-
mization aims to selectively download only the precise byte range
containing valid nearest-neighbor candidates within each target
cluster for a given query. Specifically, as detailed in Section 3.2.1,
the system leverages the distance estimator of RaBitQ to generate
pruning thresholds. With this pruning framework, the remaining
un-pruned vectors typically occupy only a fractional slice of the
cluster’s total physical address space. As illustrated in Figure 2, for
a cluster, our method dynamically issues a bounded range request
covering the minimum contiguous byte sequence that encompasses
all un-pruned candidates, which reduces overall download latency
and conserves valuable network bandwidth.
As discussed in Section 3.1.3, we reorder the vectors within a
cluster by their distances to the cluster centroid. Next, we provide
more analysis on how this distance-based reordering facilitates the
effectiveness of the aforementioned range optimization strategy.

bound (𝑑𝑖𝑠𝑡𝑙𝑜), rendering it more difficult to be safely pruned. Con-

centroid effectively assembles these hard-to-prune vectors in the
data layout. This spatial localization enables range optimization to
further reduce byte volume retrieved from the cloud object storage.

influences the effectiveness of request merging. If clusters are or-

sparsely distributed across the index layout, leading to poor merg-

inter-cluster reordering strategies, discovering that the nearest-
neighbor heuristic achieves the smallest Hamiltonian path length
across tested datasets. To validate this approach, we evaluate the

request count across most datasets. This empirically validates the
use of Hamiltonian path length as a useful proxy for quantifying
cluster spatial locality for downstream IVF-based ANN search.

The cache operates at cluster-level granularity mirroring the spa-
tial access patterns executed during querying. To reduce physical
fragmentation within the cache, each cluster is padded to align with
standard 4 KB pages. A single, pre-allocated backing file opened
using the O_DIRECT flag (to bypass the OS’s page cache) is used
to cache all data. Storage allocations within the backing file are
managed at 4 KB granularity via a best-fit free-extent map that dy-
namically coalesces contiguous freed extents upon cluster eviction.
Following an empirical evaluation of various cache strategies, we
use a caching engine combines TinyLFU-inspired admission [20]
with aging LFU replacement, using per-cluster frequency coun-
ters with periodic halving. To improve I/O concurrency, we launch
cache reads and writes asynchronously by leveraging the high-
performance io_uring interface. Specifically, read operations are
pooled, batched, and subsequently dispatched asynchronously; con-
currently, cache insertion operations are completely decoupled from
the critical query execution path and delegated to a background
worker thread.
Note that there is an inherent architectural conflict between
the cluster-level caching and our range optimization strategy of
downloading. Specifically, the cache manages data at cluster-level
granularity, whereas range optimization aims to selectively retrieve
minimal byte ranges of a cluster to conserve bandwidth. We resolve
this tension by introducing an adaptive fallback threshold. When
local NVMe caching is enabled, the range optimization is evaluated
by a predefined threshold ratio𝛾(e.g.,𝛾= 0.8). The system executes
a range-optimized download request if and only if the optimized
range spans less than 𝛾of the total cluster volume. For any request
exceeding this ratio, the system downloads the complete cluster,
thereby trading marginal network overhead to populate the local
SSD cache and benefit subsequent queries.

5
Related Work
Indices for Approximate Nearest Neighbor Search. Existing
index structures for Approximate Nearest Neighbor (ANN) search
predominantly encompass graph-based [22, 40, 49], quantization-
based [6, 9, 25, 27, 29, 33, 41], hashing-based [16, 23, 36, 38, 58,
59], cluster-based [14, 65], and tree-based [7, 11, 15, 32] methods.
While prior research has predominantly focused on in-memory or
disk-based scenarios, RemoteANN is specifically designed for both
indexing and querying over the cloud object storage.
Cloud Object Storage and Vector Search. Driven by the elastic-
ity, durability, and cost-effectiveness of cloud object storage, both
academia and industry have proposed different data management
systems with an object store backend. AnyBlob [19] explored the
potential of utilizing the cloud object storage for OLAP workloads
and developed a high-performance download manager. A recent
empirical study [47] benchmarked the performance of two repre-
sentative disk-based ANN indices (SPANN [14] and DiskANN [40])
deployed over cloud object storage backends. In industry, a series
of vector search engines on cloud object storage has emerged, in-
cluding Turbopuffer [61], Amazon S3 Vectors [4], Lance [46], and
Databricks [53]. Both Turbopuffer and Amazon S3 Vectors adopt
SPFresh [65] as their underlying index structure, whereas Lance
and Databricks utilize Inverted File (IVF) index variants. We do
not directly compare RemoteANN with the closed-source services
turbopuffer and Amazon S3 Vectors, or with the full Databricks
platform. Instead, we evaluate Lance’s IVF-RQ index as Lance-RQ,
alongside RemoteSPANN, to compare representative indexing ap-
proaches under controlled storage and data-placement settings,
focusing on the algorithmic co-design of index structures and the
cloud environment.
Accelerating IVF Construction. Recent work accelerates the
𝑘-means clustering in IVF construction by adopting techniques
from ANN search. SuperKMeans [44] combines dimension prun-
ing [26] with the PDX data layout [45] to reduce the cost of dis-
tance computation. Graph-based approaches also accelerate this
step [17, 57, 64]. For example, SeededANN [57] uses an HNSW-
based index over centroids and exploits assignments from previous
iterations to seed subsequent searches. Another direction performs
clustering on compressed vectors to reduce computation and mem-
ory overhead [43]. Input compression represents an orthogonal
design dimension to the choice of centroid-assignment method and
could potentially be combined with our QGKMeans. Our evalua-
tion focuses on acceleration using the original input vectors; we
therefore leave combinations with input compression outside the
scope of this comparison.
6
Conclusion and Discussion
In this paper, we presented RemoteANN, a vector search engine
explicitly co-designed for cloud object storage. Motivated by the
pronounced network latency and per-request pricing of the storage
tier, RemoteANN couples an IVF index with RaBitQ quantization
and a locality-aware data layout, accelerates index construction
via QGKMeans, and introduces a query engine combining cluster
pruning, range optimization, request merging, and caching. When
evaluated on real-world datasets, RemoteANN consistently outper-
forms all representative baselines in query throughput and incurs
lower storage API expenses. Our ablation study further confirms
the contribution of query-side optimizations, and our scalability
evaluation demonstrates that these gains persist at billion-scale.
Several limitations point to directions for future work. Currently,
RemoteANN targets a static IVF index. Supporting efficient incre-
mental updates and deletions remains an open challenge for vector
search on cloud object storage. Moreover, our evaluation focuses on
12


the warm-query setting, where index metadata is already resident
in the compute node’s memory. A deeper investigation of cold-start
mitigation strategies, such as workload-driven prefetching, would
further broaden RemoteANN’s applicability to bursty or intermit-
tent workloads. We believe the co-design principles introduced
in this work offer a general foundation for future systems in this
space.
